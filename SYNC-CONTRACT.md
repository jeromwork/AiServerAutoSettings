## Safety boundary

The original selected folder is a seed source, never a Syncthing receiver or execution workspace. Create a NEW Ubuntu project and a NEW Windows replica. Ubuntu is the sole writer; Windows is receive-only. Receive-only does not protect local edits from incoming replacement: do not edit the replica. Incoming version history is not a VPS backup. No automatic revert, override, reset, delete, or cleanup of existing project directories.

Only explicit relative AllowedRoots enter inventory/seed. The implementation excludes secrets, generated dependencies, caches, private keys, Android SDK/build state, local databases and uploads before traversal/read; reparse/symlink paths fail closed. File-extension allowlisting is an additional conservative guard, not a guarantee that every arbitrary source file is free of embedded secrets. Owner approval of external source transfer remains required. Source must be quiescent during initial seed. Original project rules were read; no original source contents were read by the model.

## Explicit project selection

The Windows PowerShell 5.1 launcher selects projects in its console by default, including under STA. The window is retained only with explicit -Window. Add one or more exact folders by pasting paths on separate lines (quotes/spaces supported) or using a folder picker. Manual search runs inside an explicitly chosen folder; full disk search is a separate confirmed action. The explicit Quick repositories button (console Q) searches only named conventional project folders below the user profile, Documents, Desktop and ready fixed local drives; it never traverses entire profile/disk roots. Newly found candidates are unchecked. Saving checked rows is the only operation that creates new bindings; cancellation starts no transfer. Each selected project receives a separate project ID, server workspace, Windows receive-only replica and host binding. The shared parent is never treated as a project automatically.

Candidates show Git/worktree/folder type, maximum modification date of eligible source files, estimated metadata bytes/file counts and incomplete/exclusion status, newest first. Directory modification time is not used as project freshness. Large eligible files remain in the estimate and are marked. Bounded searches/estimates report incompleteness. Secret/service/dependency/build trees and reparse paths are skipped; personal/system roots cannot be selected. Legacy/manual discovery stops at candidate roots; quick discovery also lists independent nested repositories; overlapping checked projects are rejected. Worktrees are identified with Git plumbing without directly reading the `.git` pointer file. NonGit discovery is optional and uses project marker names; any ordinary safe folder can be added explicitly.

Selection APIs: `ConvertFrom-RemoteSyncProjectPaths`, `Get-RemoteSyncProjectCandidates`, `Find-RemoteSyncProjectCandidates`, `Get-RemoteSyncSelection`, `Save-RemoteSyncSelection`, and `Show-RemoteSyncProjectSelection`. Selection is stored per host outside source folders and reused on repeat launches. Legacy bindings initially remain enabled; their binding files are preserved. Unchecking disables future connection and stops the current installer-owned session without deleting source, replica or server data. Console selection shows names, source dates and exact paths in ten-row pages: empty initial lists automatically run quick discovery before the first selection prompt; Q runs discovery again; Enter confirms the current selection when any row is checked and runs discovery otherwise, N/P page, numbers separated by comma/dot/whitespace toggle, F scoped folder discovery, A exact paths, S explicitly saves, 0 cancels. Enter and S share the explicit save/connect path when rows are checked. Explicit Q never saves a selection. Legacy root/discovery APIs remain available for compatibility but the installer never calls automatic root registration.

## Per-project Git mode

Explicitly checked Git/worktree projects use `ScopeMode git` at their exact root. Existing allowlist registrations retain their previous scope. Seed inventory uses `git ls-files --cached --others --exclude-standard -z`, then mandatory secret/dependency/build exclusions and the conservative source/asset extension policy. Deleted files are omitted; nested repositories/submodules and reparse paths are excluded or rejected. Original `.git` is never copied. Original project folders remain read-only to this workflow.

Initial seed allows 60000 ms per local Git invocation, independently of the shorter discovery budgets. Timeout/exit/output-limit errors identify the operation using fixed labels without logging arbitrary arguments or stderr (which may contain private configuration); unsuccessful child processes are killed and reaped. Local inventory/seed never performs clone/fetch/push or hosting authentication and is independent of GitHub/GitLab/other remotes. Original history/remotes and account credentials are not transferred; hosting setup for later remote Git operations remains an explicit owner task.

Git plumbing redirects and closes its own stdin rather than inheriting the managed launcher's open control pipe. A real hidden PS5.1 child with a background Console.ReadLine reproduces the previous rev-parse hang without this isolation. The native Process.Handle is retained as with the other PS5.1 components.

Windows.Paths.ps1 provides a shared extended-path adapter for PS5.1 file IO. Archive staging/publication/cleanup, hashes/JSON, transport streams, receiver inventory/snapshot checks and runtime config IO use explicit device-prefixed paths without changing registry/policies. Stored identities, source/replica paths, manifest relative names and remote paths stay logical/unprefixed. Dot segments are normalized before applying the prefix; transport strips the prefix and canonicalizes before its existing DataDir fence. PS5.1 fixtures reproduce a 221-character state directory with a 272-character staging archive, longer snapshot/transfer paths, nested source/replica files over MAX_PATH, cancellation cleanup, UNC roundtrip and out-of-scope extended input rejection. No source/profile/workspace relocation is performed.

SSH script text is normalized from CRLF/CR to LF after heartbeat wrapping and before shell/native quoting, without changing binary upload bytes. The transmitted nested Bash probe is executed by native regressions (empty/complete/partial), not just marker-emulated. Literal bracket route paths are admitted and escaped as backslash+bracket on Linux or pipe+bracket on Windows; previous exact includes are decoded strictly, without admitting arbitrary glob rules. A one-time upload retry on SSH exit 255 is allowed for installer-owned transfer artifacts; exec requests are never automatically replayed.

Interactive progress uses ConsoleStatusLine to overwrite a single row, erase a shorter prior value and finish before a new stage/prompt. Redirected output remains line-based. Native private-console tests verify actual row/cell contents. Get-RemoteSyncPreparedSeed stores an atomic seed-index.json bound to project/host, current manifest SHA256 and archive metadata. Its cached archive SHA256 skips only redundant local reads of an immutable prepared seed; full server archive verification and live-file readiness hashing remain mandatory. A damaged index is rebuilt. Native file traversal preserves the deny/reparse/nested-repository/extension fences. Small-file hashes use ComputeHash without allocating a chunk-progress buffer per file. FS watcher remains enabled; periodic full rescans are 3600 seconds (also migrated on resume), and explicit initial/per-command server scans remain in place.

Connect-RemoteSyncProject and Export-RemoteSyncSeed accept an optional Progress callback. Structured stage/byte/file frames reach the real managed console and private log, with 64-bit counters; display is throttled to about 5 seconds, transfer speed/ETA are estimates. Inventory/hash stages can report indeterminate totals. Percentages are per stage, not overall readiness. The initial managed project connection has a 43200-second ceiling and a 300-second missing-status watchdog. Long upload/extract/install/snapshot/initial-scan requests also allow 43200 seconds with a 300-second activity check. Remote heartbeat prevents silent hashing/scanning from looking like a dead SSH connection; transfer byte movement is separately monitored while uploading. The existing short per-command barrier defaults remain unchanged. Initial receive polling tracks needed bytes/items, sequence/state and connection received bytes, and hashes only a complete idle replica. A final fresh hash barrier is still mandatory.

Seed archive builds use unique staging files; failed builds are discarded only inside their own state directory, and old uncommitted final archives are preserved under a new name. Resumable SSH upload seeks the local archive to the server partial length, uses an archive-SHA256-specific `.part` path and exclusive flock, verifies expected length/full SHA256 before atomically replacing its own transfer artifact, and never writes into the source/server workspace. A full corrupt partial is quarantined; a short interrupted one is retained. Existing matching complete archives are reused without retransmission. Python extraction checks hashes while streaming and atomically publishes a new directory with Linux RENAME_NOREPLACE (Windows os.rename in fixtures). A seed-receipt.json outside the workspace binds project/host and manifest hash; seed-status permits continuing an unconfigured completed seed, not reseeding it. A crash between publication and receipt still fails closed for inspection. Test-project-transfer.ps1 covers orchestration interruption/retry, native transfer faults and real console rendering; server publication/receipt tests run on Windows and Linux.

Explicit nonGit folders use `ScopeMode folder`, `allowedRoots=['.']`, with the same hard deny and source/asset extension rules. They require no Git binary or recreated Git metadata. New safe server-created source files and deletions are synchronized. Git ignore semantics apply only to Git projects; nonGit folders use the fixed safe source policy. This conservative policy can omit unsupported file types; the estimate and contract describe the transferred source scope rather than a complete disk backup.

The server creates a new private Git metadata directory beside the seed manifest, outside the synchronized workspace. Its baseline index comes only from the validated manifest paths. New server-created source files become eligible before commit when repository `.gitignore` rules permit them, including nested rules and negation; generated output and secrets stay denied even when tracked. Deletions produce tombstones as before. Ubuntu requires Git. Windows resolves installed Git from PATH or standard locations, otherwise automatically downloads a checksum-pinned official portable MinGit into the user's RemoteAgents cache without admin access or PATH changes. No local AI agent is required for this prerequisite. Machine-specific global ignores and the original `.git/info/exclude` affect the initial Windows selection but are not copied; future server additions use the transferred repository `.gitignore` files. Put portable project exclusions into repository `.gitignore` before choosing the project. The current one-host seed and receive-only hash verification passed as recorded in Status.

`New-RemoteSyncProject -DataDir -ProjectId -HostId -SourcePath -ScopeMode git` registers this mode without an AllowedRoots prompt. It stores the single root as `allowedRoots=['.']` plus `scopeMode='git'`. The seed manifest also contains the filtered `gitPaths` baseline. Registering is local metadata only; it does not imply a live connection or bridge readiness.

`Get-SyncGitExecutable` returns the installed or automatically provisioned full executable path. Use its default per-user cache for installer integration and child processes. Optional `-DataDir`, `-DownloadedArchive`, and `-ForcePortable` support an explicit private/offline installation and synthetic checks. Portable archives for x64, ARM64 and x86 are pinned to [official MinGit 2.56.0.4 checksums](https://github.com/git-for-windows/git/releases/tag/v2.56.0.windows.4); archives are verified before extraction, existing installations are preserved, and cached portable executables are checksum-checked before reuse. Only x64 has been exercised locally.

## Public Windows API

Dot-source Sync.Workspace.ps1 followed by Sync.Runtime.ps1 and Sync.Orchestrator.ps1. All parameters are runtime values, no fixed computer/profile/server identity. DataDir is the caller's per-server, per-computer directory.

- `Get-RemoteSyncProjects -DataDir`: objects with projectId, hostId, sourcePath, replicaPath, allowedRoots, folderId, state, fileCount, bytes. Server path is operator-chosen; default `/home/remoteagents/work/projects/<projectId>`.
- `New-RemoteSyncProject -DataDir -ProjectId -HostId -SourcePath -AllowedRoots`: names/sizes only, saves binding. Explicit roots such as `backend`, `mobile`, `pos`, `sdk`, root package manifests can be selected after names/sizes review. Do not automatically allow the whole selected root. Missing roots are errors.
- `Export-RemoteSyncSeed -DataDir -ProjectId -HostId`: runtime hashes/copies only approved files; returns archivePath, manifestPath, sha256, fileCount. Does not connect/upload. Existing seed.zip is never overwritten.
- `Install-RemoteSyncBinary -DataDir [-DownloadedArchive]`: official Windows amd64 Syncthing 2.1.7 ZIP, pinned SHA256, extracts binary only.
- `Initialize-RemoteSyncWorker -DataDir -ProjectId -HostId -Executable -ListenPort -PeerTunnelPort -GuiPort [-PeerDeviceId]`: first call without peer generates public deviceId; repeat with peer configures paused receive-only worker. Refuses replacing a configured worker. Runtime-owned API key stays in private generated worker state and is consumed internally; never print configuration.
- `Start-RemoteSyncWorker`, `Resume-RemoteSyncFolder`, `Stop-RemoteSyncWorker`, `Get-RemoteSyncLiveHealth`: same DataDir/ProjectId/HostId identity. Start does not imply ready. Caller owns process/tunnel lifecycle; stop the specific worker using its API. Existing configured workers are reused, not initialized again.
- `Test-RemoteSyncBarrier -DataDir -ProjectId -HostId -SnapshotPath -HealthProbe { Get-RemoteSyncLiveHealth ... }`: returns ready, reason, projectId, hostId, replicaPath, snapshotId. Only ready=true permits bridge execution. SnapshotPath is `<state>/current-snapshot.json`, where state is `<DataDir>/sync/projects/<projectId>/<hostId>`.

The barrier requires authenticated live peer connection, idle database, zero pending/errors/receive-only changes, matching project/host and every allowed source-file size/hash, with stable local Syncthing sequence across hashing. Freeze agent writes between approved snapshot and runner action; this is an acceptance barrier, not an atomic distributed filesystem transaction. Runner must hold the same project task lock until action completes. Dependencies/generated output remain Windows-local and excluded from source hashes. An offline peer, changed file or stale mismatch blocks the run.

## Remote operator sequence

1. First use a tiny synthetic project, not the real source. Upload only the authored scripts and approved archive/manifest over existing explicit SSH identity/known-hosts profile. Run nonroot. `bash server-install-sync.sh <absolute-bin-dir>` downloads pinned official Linux amd64 archive and verifies its SHA256. No system packages, existing agent auth or SSH settings are altered.
2. `python3 server-sync.py seed --base <projects-base> --project <id> --host <host> --manifest <seed-manifest> --archive <seed.zip>` validates paths, IDs, sizes, hashes and archive links, creates only a new destination. Existing destination means stop, not merge.
3. `python3 server-sync-runtime.py identity --state <private-state> --binary <syncthing> --project <id> --host <host> --workspace <new-project> --listen <S> --tunnel <Sforward> --gui <Sapi>` yields public server device ID. Use the same arguments with `configure`, adding `--manifest <seed-manifest> --peer <Windows-device-id>`. Configure Windows with the server ID. Both folders initially paused; server send-only, Windows receive-only.
4. Windows initiates the existing SSH connection with two additional private TCP forwards: `-L 127.0.0.1:<Wforward>:127.0.0.1:<S>` and `-R 127.0.0.1:<Sforward>:127.0.0.1:<W>`. W/S are peer listeners; Wforward/Sforward are peer addresses. Reserve all ports per host/project, enable ExitOnForwardFailure and keepalive. No public Syncthing/API listeners; global/local discovery, relays, NAT traversal, automatic upgrades, usage reporting and browser launch disabled. APIs remain loopback and are never forwarded. Syncthing device pairing provides independent peer authentication.
5. Launch server `start` through the operator's managed nonroot service/session, launch Windows worker hidden in the logged-in user session, then `resume` on server and Windows. `health` returns only sanitized status. Connect-RemoteSyncProject in Sync.Orchestrator.ps1 now automates staged install/seed/pair/start through caller SSHTransport and TunnelHook. Main owns reconnect supervision/autostart; readiness still requires acceptance.
6. With agent writes paused, run `server-sync.py snapshot --base <projects-base> --project <id> --host <host> --manifest <seed-manifest> --output <outside-source/current-snapshot.json>`. Fetch only this metadata into the Windows state path, call barrier, then run only against replicaPath. Original remains untouched. Snapshot metadata stays outside replicated source. Explicit new seed roots require approval.

Server `.stignore` is an exact approved source-path allowlist. Fresh snapshot --refresh-ignores regenerates it for safe current files inside the fixed approved roots before scan; secrets, blocked extensions and generated directories stay excluded. Invoke-RemoteSyncBarrier uses this sequence and a new GUID snapshot for every request. It does not reuse the initial snapshot. Windows dependency installation/watch/devserver/browser/ADB execution belongs to the bridge, not this module.

## Acceptance before readiness

Two-peer synthetic acceptance must prove initial files, modification, deletion history, secret exclusion, out-of-scope link rejection, wrong device/auth denial, disconnected barrier denial, reconnect, source preservation and project/host isolation. Then approve metadata inventory for the real project, seed it to new destinations and repeat a harmless source-to-replica check. No real project transfer or readiness claim until those checks pass. No copy of `.git`, local `.env`, credentials, dependencies or uploads; runtime local configuration must be supplied separately by the owner.

## Automated entry points
Connect-RemoteSyncProject -DataDir -ProjectId -HostId -SSHTransport -TunnelHook [-DownloadedArchive] performs guarded connection/setup. Invoke-RemoteSyncBarrier -DataDir -ProjectId -HostId -SSHTransport [-TimeoutSec20] refreshes server snapshot and returns ready/fresh/reason/replicaPath/snapshotId. SSHTransport receives exec/upload/download objects and returns exitCode/stdout/stderr; TunnelHook receives projectId/hostId/localForwardPort/serverListenPort/remoteForwardPort/windowsListenPort and returns ok/processId/reason. No SSH keys/config are read by this module. Interrupted destinations without a valid completed-seed receipt fail closed; receipt-bound completed seeds can continue configuration. Additional-computer attachment uses the explicit subscription workflow below. Ordinary seed bindings still refuse an unbound existing destination.

## Shared projects and multiple computers (1 November 2026)

There is no global active-PC selection and no exclusive-device lease. A stable per-user Windows `computer.json` hostId identifies the computer independently of RDP or mouse activity. Each project/host has its own outgoing SSH broker, paired Syncthing identities, loopback ports, server worker state and receive-only Windows replica. Additional subscriptions point send-only server workers at the same canonical source workspace. Independent devices may stay connected simultaneously.

The installer project menu explicitly separates new local seed, attach by exact server projectId, and reconnect saved bindings. First successful configuration registers the project's canonical manifest under `work/.remote-agents-projects/<projectId>/project.json`. Existing projects migrate into this catalog when their original binding reconnects. Directory names/file similarities never establish identity. Interrupted seeds without a valid completed-seed receipt still fail closed for inspection.

`server-sync.py projects --base ...` lists only explicit registered projects. `register --project ... --host ... --manifest ...` requires matching configured subscription metadata and rejects a different policy. `attach` copies the registered policy with the new hostId into that host's private state; it never opens a local source, uploads an archive, merges or reseeds a workspace. Missing projects and incompatible existing manifests fail. `New-RemoteSyncSubscription -DataDir -ProjectId -HostId -ServerProject` creates a new local binding with subscription=true; sourcePath is a compatibility/display field pointing at its replica, not a seed source. Seed export is explicitly forbidden for subscriptions. Reattach reuses/re-enables the same binding. A configured server subscription's current .stignore is not reset to the old seed when another host attaches. Seed/register/attach/snapshot metadata mutations are serialized per server project using flock. Canonical/subscription manifests are published exclusively as complete files; snapshot .stignore updates stage outside the source and replace atomically, so a live worker never sees an empty partial policy.

`server_node_catalog.py` keeps public per-host/project records in `~/.local/share/remote-agents-nodes`. MCP registrations use `codex-windows-bridge.py --catalog ...`. `windows_devices` lists hostId, deviceName, projectId, paths, live availability and executable discovery. Every row is probed through its own broker and checked against the exact Windows device/workspace/sync_guard identity. A stale catalog row is unavailable, never a fallback. Availability is transport reachability, not sync freshness or working VPN/SDK/USB. All catalog Windows tools require projectId and hostId; command/process_start/poll/stop additionally require taskId. Each call selects its own explicit target, enabling remote reassignment without shared implicit state.

Managed brokers and Windows executors both reject absent/mismatched bindings. Old --socket callers and cached schemas cannot execute against updated managed bridges without an explicit binding. Every participating computer must reconnect once with the updated package; restart MCP and create a new model session after migration. Old, still-running versions on other PCs are not declared migrated or accepted. No regular target switch requires closing another computer's BAT.

Windows environment coordination is per Windows user across executor processes, using a named mutex for metadata updates and installer-owned process leases identified by PID plus creation time. Same-task background devserver/emulator and companion command starts are allowed. Another task gets busy while a live operation holds the environment. Ended processes are pruned before a new operation even without poll; stop/poll/command completion and executor shutdown clean their leases. A lease is local to that physical Windows environment, so independent computers do not lock one another. taskId is coordination metadata, not a security principal; owner permissions and normal shell trust still apply. Do not use another task's ID to bypass a conflict. Detached/untracked child services are outside this process coordination contract.

Source writes on VPS must remain sequential and paused during fresh snapshot/barrier/start, including while another host receives that project. The installer does not intercept an agent's arbitrary Linux shell writes or create a distributed filesystem transaction. Windows dependency/SDK/database state stays local and excluded; no bidirectional synchronization of original folders is promised.

`Start-RemotePreview.ps1` is a separate managed loopback SSH forward to an owner-chosen VPS 127.0.0.1 service port. It chooses another free local port when 3801 is occupied, reports the exact URL, preserves strict host checking and closes on BAT exit. It neither starts nor publishes the service, and reports serviceChecked=false.

Regression coverage: test-sync-subscription.ps1, test-sync-selection.ps1, test-multi-node.py, test-node-execution.py, test-preview.ps1, and Linux test-multi-sync-loopback.py. The last downloads the existing checksum-pinned Syncthing release into a fresh temporary directory and starts four private workers; it proves two subscriptions, attach/rerun, preserved newer server content, additions/deletions and exclusions with Linux receive-only peers. It does not prove Windows/SSH/model acceptance. See CONTINUE.md for the remaining physical two-computer acceptance.

## Multiple owners are not isolated tenants

Only the current host explicitly selected project IDs are connected; another host/project is not attached automatically. This is a synchronization subscription boundary. The shared remoteagents Linux user, desktop, agent application state and project/device catalogs are not a multi-owner access boundary. Shell permission is full Windows-user access and catalogs do not enforce owner ACLs. Two people require separate server identities/environments for access separation; this installer does not implement that tenancy yet. A project selector, projectId, hostId or taskId must not be presented as a security principal or private account.

Console mouse selection uses the shipped project-console-input.cs, ReadConsoleInputW and owner-visible current row matching. QuickEdit/line/echo mode changes apply only during a menu read and the exact original console mode is restored in finally. Redirected/unsupported console sessions use Read-Host. Left-button release, double-click continuation, mouse movement and stale/nonmatching rows do not toggle projects. Mouse selection is still only a checkbox operation; S is required to save/start connection. Console source dates are sorted within normal Git and worktree groups, with worktrees last. F searches only explicit owner-entered folder roots with a 30-second budget and depth 8, without broadening the default roots.

## Independent server actions and returning-user entry

After verified SSH and supported-OS probing, the installer opens the server action menu directly. Enter/1 opens a managed RDP session with AgentApplications=0; app installation/login is not a gate. Action 3 edits/adds project selections, action 13 reconnects saved selections without discovery UI, 11 explicitly installs/configures agents, 2 opens the chosen app in the same desktop, and 6 explicitly probes components. SSH connection maintenance is opt-in using M plus the server number; normal saved-server entry skips the old maintenance question. Human account authentication remains in the official UI.

Initialize-ServerWorkspace prepares the existing managed ordinary account and only missing python3/git/curl prerequisites from Ubuntu on the VPS; it installs no AI app. In Windows-control mode Connect-ProjectFolders with Agents=0 still starts the bridge and handoff, registering MCP only for installed apps. The chosen control mode authorizes Windows commands without another BAT question. Later explicit agent setup can attach/reconfigure a bridge on the existing running sync without stopping or reseeding it. Agent/bridge readiness remains separate from sync readiness. Live sessions and RDP stay owned by the same menu and are stopped only on explicit disconnect, switching to autonomous mode, or menu exit.

The selector action footer refreshes selected count and folder names after each toggle. V displays only selected rows with original global row numbers, and returns to all rows on repeat. Native console mouse accepts the current S/V footer text as well as checkboxes. Unchecked old discovery candidates without a binding are not rescanned when reopening selection; selected/registered rows get bounded metadata and explicit quick search finds additional candidates. Saved main-menu names are read without registering a new computer or creating local project state for an RDP-only user.
