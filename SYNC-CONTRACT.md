# Sync pilot: operator and installer contract

Status: Windows PS5.1 synthetic workspace tests and real pinned Windows Syncthing loopback-worker test pass. Linux scripts and real two-peer acceptance are pending. Registration is not readiness. No original project source has been transferred by this module yet.

## Safety boundary

The original selected folder is a seed source, never a Syncthing receiver or execution workspace. Create a NEW Ubuntu project and a NEW Windows replica. Ubuntu is the sole writer; Windows is receive-only. Receive-only does not protect local edits from incoming replacement: do not edit the replica. Incoming version history is not a VPS backup. No automatic revert, override, reset, delete, or cleanup of existing project directories.

Only explicit relative AllowedRoots enter inventory/seed. The implementation excludes secrets, generated dependencies, caches, private keys, Android SDK/build state, local databases and uploads before traversal/read; reparse/symlink paths fail closed. File-extension allowlisting is an additional conservative guard, not a guarantee that every arbitrary source file is free of embedded secrets. Owner approval of external source transfer remains required. Source must be quiescent during initial seed. Original project rules were read; no original source contents were read by the model.

## Explicit project selection

The STA Windows PowerShell 5.1 launcher opens a project selection window. Add one or more exact folders by pasting paths on separate lines (quotes/spaces supported) or using a folder picker. Optional search runs only inside an explicitly chosen folder; disk search is a separate confirmed action. Newly found candidates are unchecked. Saving checked rows is the only operation that creates new bindings; cancellation starts no transfer. Each selected project receives a separate project ID, server workspace, Windows receive-only replica and host binding. The shared parent is never treated as a project automatically.

Candidates show Git/worktree/folder type, maximum modification date of eligible source files, estimated metadata bytes/file counts and incomplete/exclusion status, newest first. Directory modification time is not used as project freshness. Large eligible files remain in the estimate and are marked. Bounded searches/estimates report incompleteness. Secret/service/dependency/build trees and reparse paths are skipped; personal/system roots cannot be selected. Discovery stops at candidate roots; overlapping checked projects are rejected. Worktrees are identified with Git plumbing without directly reading the `.git` pointer file. NonGit discovery is optional and uses project marker names; any ordinary safe folder can be added explicitly.

Selection APIs: `ConvertFrom-RemoteSyncProjectPaths`, `Get-RemoteSyncProjectCandidates`, `Find-RemoteSyncProjectCandidates`, `Get-RemoteSyncSelection`, `Save-RemoteSyncSelection`, and `Show-RemoteSyncProjectSelection`. Selection is stored per host outside source folders and reused on repeat launches. Legacy bindings initially remain enabled; their binding files are preserved. Unchecking disables future connection and stops the current installer-owned session without deleting source, replica or server data. Console fallback requires explicit toggles and save; Enter cancels. Legacy root/discovery APIs remain available for compatibility but the installer never calls automatic root registration.

## Per-project Git mode

Explicitly checked Git/worktree projects use `ScopeMode git` at their exact root. Existing allowlist registrations retain their previous scope. Seed inventory uses `git ls-files --cached --others --exclude-standard -z`, then mandatory secret/dependency/build exclusions and the conservative source/asset extension policy. Deleted files are omitted; nested repositories/submodules and reparse paths are excluded or rejected. Original `.git` is never copied. Original project folders remain read-only to this workflow.

Explicit nonGit folders use `ScopeMode folder`, `allowedRoots=['.']`, with the same hard deny and source/asset extension rules. They require no Git binary or recreated Git metadata. New safe server-created source files and deletions are synchronized. Git ignore semantics apply only to Git projects; nonGit folders use the fixed safe source policy. This conservative policy can omit unsupported file types; the estimate and contract describe the transferred source scope rather than a complete disk backup.

The server creates a new private Git metadata directory beside the seed manifest, outside the synchronized workspace. Its baseline index comes only from the validated manifest paths. New server-created source files become eligible before commit when repository `.gitignore` rules permit them, including nested rules and negation; generated output and secrets stay denied even when tracked. Deletions produce tombstones as before. Ubuntu requires Git. Windows resolves installed Git from PATH or standard locations, otherwise automatically downloads a checksum-pinned official portable MinGit into the user's RemoteAgents cache without admin access or PATH changes. No local AI agent is required for this prerequisite. Machine-specific global ignores and the original `.git/info/exclude` affect the initial Windows selection but are not copied; future server additions use the transferred repository `.gitignore` files. Put portable project exclusions into repository `.gitignore` before choosing the project. The pilot source has not been transferred and the current SSH reachability check timed out.

`New-RemoteSyncProject -DataDir -ProjectId -HostId -SourcePath -ScopeMode git` registers this mode without an AllowedRoots prompt. It stores the single root as `allowedRoots=['.']` plus `scopeMode='git'`. The seed manifest also contains the filtered `gitPaths` baseline. Registering is local metadata only; it does not imply a live connection or bridge readiness.

`Get-SyncGitExecutable` returns the installed or automatically provisioned full executable path. Use its default per-user cache for installer integration and child processes. Optional `-DataDir`, `-DownloadedArchive`, and `-ForcePortable` support an explicit private/offline installation and synthetic checks. Portable archives for x64, ARM64 and x86 are pinned to [official MinGit 2.56.0.4 checksums](https://github.com/git-for-windows/git/releases/tag/v2.56.0.windows.4); archives are verified before extraction, existing installations are preserved, and cached portable executables are checksum-checked before reuse. Only x64 has been exercised locally.

## Public Windows API

Dot-source Sync.Workspace.ps1 followed by Sync.Runtime.ps1 and Sync.Orchestrator.ps1. All parameters are runtime values, no fixed computer/profile/server identity. DataDir is the caller's per-server, per-computer directory.

- `Get-RemoteSyncProjects -DataDir`: objects with projectId, hostId, sourcePath, replicaPath, allowedRoots, folderId, state, fileCount, bytes. Server path is operator-chosen; default `/home/remoteagents/work/projects/<projectId>`.
- `New-RemoteSyncProject -DataDir -ProjectId -HostId -SourcePath -AllowedRoots`: names/sizes only, saves binding. Explicit roots such as `backend`, `mobile`, `pos`, `sdk`, root package manifests can be selected after names/sizes review. Do not automatically allow the whole selected root. Missing roots are errors.
- `Export-RemoteSyncSeed -DataDir -ProjectId -HostId`: runtime hashes/copies only approved files; returns archivePath, manifestPath, sha256, fileCount. Does not connect/upload. Existing seed.zip is never overwritten.
- `Install-RemoteSyncBinary -DataDir [-DownloadedArchive]`: official Windows amd64 Syncthing 2.1.7 ZIP, pinned SHA256, extracts binary only.
- `Initialize-RemoteSyncWorker -DataDir -ProjectId -HostId -Executable -ListenPort -PeerTunnelPort -GuiPort [-PeerDeviceId]`: first call without peer generates public deviceId; repeat with peer configures paused receive-only worker. Refuses replacing a configured worker. Runtime-owned API key stays in private generated worker state and is consumed internally; never print configuration.
- `Start-RemoteSyncWorker`, `Resume-RemoteSyncFolder`, `Stop-RemoteSyncWorker`, `Get-RemoteSyncLiveHealth`: same DataDir/ProjectId/HostId identity. Start does not imply ready. Caller owns process/tunnel lifecycle; stop the specific worker using its API. Existing configured workers are reused, not initialized again.
- `Test-RemoteSyncBarrier -DataDir -ProjectId -HostId -SnapshotPath -HealthProbe { Get-RemoteSyncLiveHealth ... }`: returns ready, reason, projectId, hostId, replicaPath, snapshotId. Only ready=true permits bridge execution. SnapshotPath is `<state>/current-snapshot.json`, where state is `<DataDir>/sync/projects/<projectId>/<hostId>`.

The barrier requires authenticated live peer connection, idle database, zero pending/errors/receive-only changes, matching project/host and every allowed source-file size/hash, with stable local Syncthing sequence across hashing. Freeze agent writes between approved snapshot and runner action; this is an acceptance barrier, not an atomic distributed filesystem transaction. Runner must hold the same project task lock until action completes. Dependencies/generated output remain Windows-local and excluded from source hashes. An offline peer, changed file or stale mismatch blocks the run.

## Remote operator sequence

1. First use a tiny synthetic project, not the real source. Upload only the authored scripts and approved archive/manifest over existing explicit SSH identity/known-hosts profile. Run nonroot. `bash server-install-sync.sh <absolute-bin-dir>` downloads pinned official Linux amd64 archive and verifies its SHA256. No system packages, existing agent auth or SSH settings are altered.
2. `python3 server-sync.py seed --base <projects-base> --project <id> --host <host> --manifest <seed-manifest> --archive <seed.zip>` validates paths, IDs, sizes, hashes and archive links, creates only a new destination. Existing destination means stop, not merge.
3. `python3 server-sync-runtime.py identity --state <private-state> --binary <syncthing> --project <id> --host <host> --workspace <new-project> --listen <S> --tunnel <Sforward> --gui <Sapi>` yields public server device ID. Use the same arguments with `configure`, adding `--manifest <seed-manifest> --peer <Windows-device-id>`. Configure Windows with the server ID. Both folders initially paused; server send-only, Windows receive-only.
4. Windows initiates the existing SSH connection with two additional private TCP forwards: `-L 127.0.0.1:<Wforward>:127.0.0.1:<S>` and `-R 127.0.0.1:<Sforward>:127.0.0.1:<W>`. W/S are peer listeners; Wforward/Sforward are peer addresses. Reserve all ports per host/project, enable ExitOnForwardFailure and keepalive. No public Syncthing/API listeners; global/local discovery, relays, NAT traversal, automatic upgrades, usage reporting and browser launch disabled. APIs remain loopback and are never forwarded. Syncthing device pairing provides independent peer authentication.
5. Launch server `start` through the operator's managed nonroot service/session, launch Windows worker hidden in the logged-in user session, then `resume` on server and Windows. `health` returns only sanitized status. Connect-RemoteSyncProject in Sync.Orchestrator.ps1 now automates staged install/seed/pair/start through caller SSHTransport and TunnelHook. Main owns reconnect supervision/autostart; readiness still requires acceptance.
6. With agent writes paused, run `server-sync.py snapshot --base <projects-base> --project <id> --host <host> --manifest <seed-manifest> --output <outside-source/current-snapshot.json>`. Fetch only this metadata into the Windows state path, call barrier, then run only against replicaPath. Original remains untouched. Snapshot metadata stays outside replicated source. Explicit new seed roots require approval.

Server `.stignore` is an exact approved source-path allowlist. Fresh snapshot --refresh-ignores regenerates it for safe current files inside the fixed approved roots before scan; secrets, blocked extensions and generated directories stay excluded. Invoke-RemoteSyncBarrier uses this sequence and a new GUID snapshot for every request. It does not reuse the initial snapshot. Windows dependency installation/watch/devserver/browser/ADB execution belongs to the bridge, not this module.

## Acceptance before readiness

Two-peer synthetic acceptance must prove initial files, modification, deletion history, secret exclusion, out-of-scope link rejection, wrong device/auth denial, disconnected barrier denial, reconnect, source preservation and project/host isolation. Then approve metadata inventory for the real project, seed it to new destinations and repeat a harmless source-to-replica check. No real project transfer or readiness claim until those checks pass. No copy of `.git`, local `.env`, credentials, dependencies or uploads; runtime local configuration must be supplied separately by the owner.

## Automated entry points
Connect-RemoteSyncProject -DataDir -ProjectId -HostId -SSHTransport -TunnelHook [-DownloadedArchive] performs guarded connection/setup. Invoke-RemoteSyncBarrier -DataDir -ProjectId -HostId -SSHTransport [-TimeoutSec20] refreshes server snapshot and returns ready/fresh/reason/replicaPath/snapshotId. SSHTransport receives exec/upload/download objects and returns exitCode/stdout/stderr; TunnelHook receives projectId/hostId/localForwardPort/serverListenPort/remoteForwardPort/windowsListenPort and returns ok/processId/reason. No SSH keys/config are read by this module. Interrupted seeded-but-unconfigured destinations fail closed for inspection. Additional-computer attachment to an existing server project needs explicit workflow; current first pilot refuses an unbound existing destination.
