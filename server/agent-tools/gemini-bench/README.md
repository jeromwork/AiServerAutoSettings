# gemini-bench

Повторяемый прогон готовых задач на Gemini 3.8 Flash с отдельной механической приёмкой и ревью. Python 3.9+, Linux (`fcntl.flock`, `/proc`), git, bash, GNU timeout; для задачи Telegram нужен openssl. Используется установленный `gemini-task`, код обёртки набор не меняет.

Живой запуск расходует квоту Gemini: **только после явного «да» владельца**. Перед запуском посмотреть остаток и время снимка в `~/.cache/remoteagents/agy-usage.json`. Сам набор квоту не запрашивает и в сеть при `list`, `report`, `review`, `add-verdict` не ходит.

Установка ссылки (выполняет человек после размещения кода по постоянному пути):

```bash
ln -s ~/Disk/AiServerAutoSettings/server/agent-tools/gemini-bench/gemini-bench ~/.local/bin/gemini-bench
```

До слияния можно вызывать файл напрямую из worktree. Ссылку на временный worktree не устанавливать.

```bash
gemini-bench list
gemini-bench run --tasks all --modes low,medium,high --repeat 1
gemini-bench run --tasks 01-component-files-tests --parallel 2 --max-min 10 --keep-all --label trial
gemini-bench report --since 2026-11-21 --label trial
gemini-bench review <runid>
gemini-bench add-verdict <runid> 01-component-files-tests low ПРИНЯТО "проверено"
```

`run` синхронный: агент запускает его через поддерживаемый средой `run_in_background` и ждёт уведомления, без опроса. По умолчанию: все задачи, три режима, один повтор, до четырёх одновременных Gemini, 20 минут на каждый вызов. `--max-min` — целые минуты. Повторов при EOF/503 нет. Код выхода 0 — все вызовы ГОТОВО, механика принята и очистка успешна; 1 — есть неудачи; 2 — ошибка аргументов/подготовки. runid напечатан в начале и записан в каждой строке.

Создание и удаление worktree последовательно под общим git-flock. Каждый прогон фиксирует текущий commit локальной `main`; работа в `~/work/wt-gb-<runid>-<task>-<mode>-<repeat>`, ветки `gb/<…>`. Набор ничего не вливает и не пушит. Удаляет свои worktree с изменениями и свои ветки после сохранения результатов; `--keep-failed` сохраняет ошибки, непринятую механику и нарушения файлов, `--keep-all` сохраняет всё для ревью. Сохранённые worktree и ветки после ревью удаляет человек через `git worktree remove --force <путь>` и `git branch -D <ветка>` (путь/ветка есть в результате).

## Результаты и отчёт

`~/work/bench-gemini/results.jsonl` — одна строка на попытку; `verdicts.jsonl` — история ручных вердиктов; `runs/<runid>/<task>-<mode>-<repeat>/` — подставленный план, снимок check.sh, runner.log и check.log. Оригинальные `.progress`/`.jsonl` обёртки остаются в `~/work/briefs/gemini/`; путь в `progress_file`. Запись JSONL защищена flock, можно запускать независимые наборы одновременно.

`seconds` измеряет вызов `gemini-task` монотонным таймером; создание worktree и приёмка в него не входят. `ts`, `hour`, `weekday` — местное время старта попытки с часовым поясом, weekday: Пн=0…Вс=6. `turns` — число служебных строк с `→`, это вызовы инструментов, а не сообщения чата. `tokens` — последние числовые поля с token в имени из потока; при отсутствии — null, это не оценка стоимости.

Статусы: ГОТОВО/ЗАВИС/ОШИБКА. Предел времени обёртки и жёсткий предел набора — ЗАВИС, `print_timeout`; прочие виды: `EOF`, `503 no capacity`, `interrupted`, `прочее`. Отсутствие финальной служебной строки — ОШИБКА. Ошибка инфраструктуры записывается с деталями, очистка — с `cleanup_error`, если не удалась.

`check_ok` — код 0 check.sh **и** отсутствие файлов вне точного списка `allowed_files`. Статус агента хранится независимо: даже после ошибки механика запускается, если подпроцесс был запущен и завершился. Общий предел приёмки — 120 секунд, тестовая команда внутри тоже под `timeout 120`. Проверки выполняются доверенной копией check.sh вне worktree. В плане модели запрещён самостоятельный запуск тестов: их один раз запускает набор. Ошибку теста не маскируют `echo EXIT` или последующий `cd`.

`files_changed`, `lines_added`, `lines_removed` включают staged/unstaged, коммиты относительно исходного main и неигнорируемые untracked. Переименование считается удалением + добавлением, бинарные строки — 0; symlink не разыменовываются. Игнорируемые артефакты вроде `__pycache__` не учитываются. Это git-оценка, не файловая песочница: набор не предотвращает команды модели вне worktree.

Отчёт показывает задачу × режим, итог по режимам, часы/дни по режимам, ошибки и запуски > 300 секунд. «Механика» — принято/всего. «Ревью» — ПРИНЯТО/число попыток с вердиктом; 0/0 означает отсутствие ревью. Последний вердикт на `(runid, task, mode)` относится ко **всем повторам** этой пары в прогоне: ревьюер должен проверить их все. ЗАМЕЧАНИЯ и ОТВЕРГНУТО не считаются принятыми; механика при этом не переписывается. `--since` принимает ISO дату/время, без часового пояса — местная зона. `--label` — точное совпадение.

`review` только формирует `review-<runid>.md`, ничего не запускает. Для полноценного чтения кода нужен `run --keep-all`; если worktree уже удалён, файл ревью явно сообщает об этом. Сравнивать с указанным `base_commit`, а не с изменившейся за это время main. План ревью предполагает чтение и отдельный вердикт, мутационные проверки необязательны и только в изолированном временном каталоге.

## Добавление задачи

Создать `tasks/NN-english-slug/`:

- `task.md`: цель, точные файлы, критерии и ограничения; путь всегда `WORKDIR`; никаких старых имён веток. Тесты выполняет набор, модель делает только py_compile/bash -n. После отчёта модель останавливается, не коммитит, не пушит.
- `meta.json`: `id` совпадает с именем каталога, `type`, `complexity`, `size`, `description`, `acceptance` (одна строка), `allowed_files` (непустой список **точных** относительных путей, без glob).
- `check.sh`: bash, `set -euo pipefail`, выполнение из корня worktree; py_compile и один запуск только затронутых тестов под `timeout 120`. Код 0 означает принятие механикой; пояснения — stdout. Не использовать сеть/настоящий HOME/службы.

Четыре начальных плана перенесены из gemini-trial-component-files и gemini-test-A/B/C; B/C ограничены Этапом 1. Команды П1–П4 сохранены по смыслу, `timeout 420` заменён на 120, проверки статуса дополнены контролем allowed_files в runner. Справка CLI проверяется на наличие --json/--bind, без требования ровно одной строки: argparse может повторять опцию в usage и options.

`gemini-bench import <каталог>` пока возвращает понятную ошибку без изменений. Автоматически превращать произвольный раздел «Команды проверки» из `gt2-N.md` в исполняемый shell ненадёжно (cd/echo могут скрыть ошибку, нет гарантированного allowed_files). Добавлять вручную по схеме выше: читать `gt2-index.md`, переносить `gt2-N.md` в `tasks/1N-…/task.md`, из раздела проверок собирать check.sh с явными проверками кода/вывода, заполнить meta.json и проверить `list`/`bash -n`.

## Проверка самого набора

Без Gemini и сети; все репозитории и worktree в TemporaryDirectory:

```bash
python3 -m py_compile server/agent-tools/gemini-bench/gemini-bench
(cd server/tests && timeout 120 python3 -m unittest -v test_gemini_bench)
```

`GEMINI_TASK_BIN` подменяет исполняемый файл (один путь, без shell-аргументов). `GEMINI_BENCH_HOME` подменяет каталог результатов **и** переносит временные worktree в `<home>/worktrees/`. `GEMINI_BENCH_REPO` подменяет git-репозиторий с main. Для обычного запуска эти переменные не нужны. Полные наборы тестов проекта здесь не запускать.
