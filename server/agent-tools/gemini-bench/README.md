# gemini-bench

Повторяемый прогон готовых задач на Gemini 3.8 Flash с отдельной механической приёмкой и ревью. Python 3.9+, Linux (`fcntl.flock`, `/proc`), git, bash, GNU timeout; для задачи Telegram нужен openssl. Используется установленный `gemini-task`, код обёртки набор не меняет.

Живой запуск расходует квоту Gemini: **только после явного «да» владельца**. Перед запуском посмотреть остаток и время снимка в `~/.cache/remoteagents/agy-usage.json`. Сам набор квоту не запрашивает и в сеть при `list`, `report`, `review`, `show`, `add-verdict` не ходит.

Установка ссылки (выполняет человек после размещения кода по постоянному пути):

```bash
ln -s ~/Disk/AiServerAutoSettings/server/agent-tools/gemini-bench/gemini-bench ~/.local/bin/gemini-bench
```

До слияния можно вызывать файл напрямую из worktree. Ссылку на временный worktree не устанавливать.

```bash
gemini-bench list
gemini-bench run --tasks all --modes low,medium,high --repeat 1
gemini-bench run --tasks 01-component-files-tests --parallel 2 --max-min 10 --keep-all --label trial
gemini-bench report --since 2026-11-21 --label trial
gemini-bench review <runid>
gemini-bench add-verdict <runid> 01-component-files-tests low --round 1 --reviewer codex --verdict ЗАМЕЧАНИЯ --blockers @review.txt --minor "имена" --tag "пропущен риск"
# После отдельного разрешения владельца на живой следующий круг:
gemini-bench retry <runid> 01-component-files-tests low
gemini-bench review <runid>
gemini-bench add-verdict <runid> 01-component-files-tests low --round 2 --reviewer codex --verdict ПРИНЯТО --note "замечания исправлены"
gemini-bench show <runid> 01-component-files-tests low
```

`run` синхронный: агент запускает его через поддерживаемый средой `run_in_background` и ждёт уведомления, без опроса. По умолчанию: все задачи, три режима, один повтор, до четырёх одновременных Gemini, 20 минут на каждый вызов. `--max-min` — целые минуты. Повторов при EOF/503 нет. Код выхода 0 — все вызовы ГОТОВО, механика принята и очистка успешна; 1 — есть неудачи; 2 — ошибка аргументов/подготовки. runid напечатан в начале и записан в каждой строке.

Создание и удаление worktree последовательно под общим git-flock. Каждый прогон фиксирует текущий commit локальной `main`; работа в `~/work/wt-gb-<runid>-<task>-<mode>-<repeat>`, ветки `gb/<…>`. Набор ничего не вливает и не пушит. Удаляет свои worktree с изменениями и свои ветки после сохранения результатов; `--keep-failed` сохраняет ошибки, непринятую механику и нарушения файлов, `--keep-all` сохраняет всё для ревью. Сохранённые worktree и ветки после ревью удаляет человек через `git worktree remove --force <путь>` и `git branch -D <ветка>` (путь/ветка есть в результате).

## Результаты и отчёт

`~/work/bench-gemini/results.jsonl` — одна строка на попытку с `repeat` и `round` (первый круг = 1); `verdicts.jsonl` — накопительная история оценок. Запись JSONL защищена flock. Старые строки без `round` читаются как круг 1.

Артефакты круга 1: `runs/<runid>/<task>-<mode>-<repeat>/`; последующие: там же `round-2/`, `round-3/` и т.д. До удаления worktree сохраняются:

- `patch.diff`: изменения относительно исходного main, включая коммиты агента, staged/unstaged, неигнорируемые untracked, бинарные файлы и symlink. `git add -N` работает только с временным индексом в worktree; обычные индексы не меняются.
- `report.txt`: итоговый ответ Gemini (ИТОГ/ФАЙЛЫ/ПРОВЕРКИ/ПРОБЛЕМЫ), `check.txt`: вывод приёмки и диагностика набора, `gemini.progress`: копия прогресса с conversation id.
- `meta.json`: ключи попытки/круга, base_commit, размер патча в байтах, SHA-256, `patch_dropped` и причина удаления; подставленный `task.md`, доверенная копия `check.sh`, `runner.log`.

`.jsonl` Gemini **не копируется**. Оригинальные журналы обёртки остаются в `~/work/briefs/gemini/`. `progress_file` теперь указывает на сохранённую копию; `source_progress_file` — на оригинал. Если сохранение артефактов не удалось, worktree остаётся с `artifact_error` — его нельзя удалять до разбора.

Срока хранения по времени нет. Лимит одного патча — 200 КиБ (`GEMINI_BENCH_PATCH_MAX_BYTES`, по умолчанию 204800); при превышении остаются размер, SHA-256 и `patch_dropped: true`, самого патча нет. Лимит всего `runs` — 200 МиБ (`GEMINI_BENCH_RUNS_MAX_BYTES`, по умолчанию 209715200). При превышении удаляются только самые старые принятые патчи с записью `patch_drop_reason: runs_limit` и времени в meta.json. Патчи отклонённых кругов, кругов с замечаниями (даже если оценку того же круга позже исправили) и ещё не проверенных кругов защищены. Отчёты, прогресс и оценки сохраняются. Поэтому лимит общий **мягкий**: если защищённое само превышает его, набор предупреждает и сохраняет данные. Лимиты задаются неотрицательным числом байт; 0 разрешён. Очистка проверяется после прогона и записи вердикта.

`seconds` измеряет вызов `gemini-task` монотонным таймером; создание worktree и приёмка в него не входят. `ts`, `hour`, `weekday` — местное время старта попытки с часовым поясом, weekday: Пн=0…Вс=6. `turns` — число служебных строк с `→`, это вызовы инструментов, а не сообщения чата. `tokens` — последние числовые поля с token в имени из потока; при отсутствии — null, это не оценка стоимости.

Статусы: ГОТОВО/ЗАВИС/ОШИБКА. Предел времени обёртки и жёсткий предел набора — ЗАВИС, `print_timeout`; прочие виды: `EOF`, `503 no capacity`, `interrupted`, `прочее`. Отсутствие финальной служебной строки — ОШИБКА. Ошибка инфраструктуры записывается с деталями, очистка — с `cleanup_error`, если не удалась.

`check_ok` — код 0 check.sh **и** отсутствие файлов вне точного списка `allowed_files`. Статус агента хранится независимо: даже после ошибки механика запускается, если подпроцесс был запущен и завершился. Общий предел приёмки — 120 секунд, тестовая команда внутри тоже под `timeout 120`. Проверки выполняются доверенной копией check.sh вне worktree. В плане модели запрещён самостоятельный запуск тестов: их один раз запускает набор. Ошибку теста не маскируют `echo EXIT` или последующий `cd`.

`files_changed`, `lines_added`, `lines_removed` включают staged/unstaged, коммиты относительно исходного main и неигнорируемые untracked. Переименование считается удалением + добавлением, бинарные строки — 0; symlink не разыменовываются. Игнорируемые артефакты вроде `__pycache__` не учитываются. Это git-оценка, не файловая песочница: набор не предотвращает команды модели вне worktree.

Отчёт показывает задачу × режим, итог по режимам, часы/дни по режимам, ошибки и запуски > 300 секунд. «Механика» — принято/всего попыток-кругов. «Ревью» — ПРИНЯТО/число попыток с вердиктом; 0/0 означает отсутствие ревью. Каждому кругу соответствует собственный вердикт; оценки прошлых кругов не заменяются финалом. `--since` принимает ISO дату/время, без часового пояса — местная зона; фильтрует строки попыток по их времени (часть цепочки может остаться вне периода). `--label` — точное совпадение.

Дополнительные таблицы по задачам и режимам считают **цепочки** `(runid, task, mode, repeat)` по последнему кругу: принято с 1-го / после правок / отвергнуто / не прошёл механику / ожидает ревью или правок. Явный финальный вердикт имеет приоритет в этих категориях, механика остаётся в отдельной таблице. «Не прошёл механику» включает ошибку/таймаут Gemini и неуспешный check, если нет финального принятия/отказа. Среднее число кругов — средний максимальный номер круга цепочки. Топ причин учитывает последнюю оценку каждого круга: `--tag`, иначе первые четыре слова блокеров (при отсутствии — note/старый text/minor). Главный показатель ложной уверенности — режим × число **различных задач**, где механика прошла, а ревью дало ЗАМЕЧАНИЯ/ОТВЕРГНУТО хотя бы в одном круге. Исправление во втором круге не стирает это расхождение.

Схема работы: **run → report → review (сейчас Codex) → add-verdict → при замечаниях retry → снова review → add-verdict → report**. `review` только формирует `review-<runid>.md`, ничего не запускает. Ревьюер читает план, сохранённый патч, report/check/progress и сравнивает с `base_commit`. Worktree для чтения патча не нужен; `--keep-all` необязателен для изучения полного дерева. Если патч отброшен, полноценное ревью/восстановление по нему невозможно. Мутационные проверки необязательны, только во временном каталоге.

```text
add-verdict <runid> <task> <mode> --round N --reviewer codex|opus|human
            --verdict ПРИНЯТО|ЗАМЕЧАНИЯ|ОТВЕРГНУТО
            [--repeat N] [--blockers текст|@файл] [--minor текст|@файл]
            [--note текст] [--tag "класс причины"]
```

**Причина отказа/замечаний обязательна**: непустой blockers, minor или note. Блокеры и мелочи хранить отдельно, если ревьюер их разделил. Все оценки дописываются, включая повторную оценку одного круга; в статистике используется последняя оценка этого круга. Без `--repeat` записывается отдельная оценка для каждого повтора указанного круга. Финал — ПРИНЯТО или ОТВЕРГНУТО; если исполнитель так и не смог, записать ОТВЕРГНУТО с этой причиной в `--note`. ЗАМЕЧАНИЯ означает незавершённую оценку, а не окончательный отказ.

Старый короткий формат `add-verdict <runid> <task> <mode> <вердикт> [причина]` поддержан как круг 1, reviewer=human, для всех повторов. Причина для отказа обязательна и в нём. Старые строки verdicts.jsonl без repeat/round по-прежнему относятся ко всем повторам **первого** круга.

`retry <runid> <task> <mode> [--repeat N] [--max-min 20] [--keep-all|--keep-failed]` — живой вызов, требует разрешения владельца. Если повторов несколько, `--repeat` обязателен. Только при ЗАМЕЧАНИЯХ в последнем круге: берёт их текст, создаёт новое worktree от чистой текущей `main`, проверяет хеш и применяет сохранённый patch.diff, запускает `gemini-task --continue <id>` из копии .progress, затем доверенный check.sh и сохранение артефактов круга N+1. Снимок allowed_files берётся из предыдущего результата. При конфликте с изменившейся main попытка помечается ошибкой без вызова Gemini; чистое дерево основного репозитория не меняется. Нет патча/он отброшен или нет conversation id — понятный отказ. Автоматических повторов и бесконечного цикла нет. Параллельные retry сериализованы. `show` печатает отчёты Gemini, все оценки по кругам, финал и пути патчей (в том числе причину удаления).

## Добавление задачи

Создать `tasks/NN-english-slug/`:

- `task.md`: цель, точные файлы, критерии и ограничения; путь всегда `WORKDIR`; никаких старых имён веток. Тесты выполняет набор, модель делает только py_compile/bash -n. После отчёта модель останавливается, не коммитит, не пушит.
- `meta.json`: `id` совпадает с именем каталога, `type`, `complexity`, `size`, `description`, `acceptance` (одна строка), `allowed_files` (непустой список **точных** относительных путей, без glob).
- `check.sh`: bash, `set -euo pipefail`, выполнение из корня worktree; py_compile и один запуск только затронутых тестов под `timeout 120`. Код 0 означает принятие механикой; пояснения — stdout. Не использовать сеть/настоящий HOME/службы.

Четыре начальных плана перенесены из gemini-trial-component-files и gemini-test-A/B/C; B/C ограничены Этапом 1. Команды П1–П4 сохранены по смыслу, `timeout 420` заменён на 120, проверки статуса дополнены контролем allowed_files в runner. Справка CLI проверяется на наличие --json/--bind, без требования ровно одной строки: argparse может повторять опцию в usage и options.

`gemini-bench import <каталог>` пока возвращает понятную ошибку без изменений. Автоматически превращать произвольный раздел «Команды проверки» из `gt2-N.md` в исполняемый shell ненадёжно (cd/echo могут скрыть ошибку, нет гарантированного allowed_files). Добавлять вручную по схеме выше: читать `gt2-index.md`, переносить `gt2-N.md` в `tasks/1N-…/task.md`, из раздела проверок собирать check.sh с явными проверками кода/вывода, заполнить meta.json и проверить `list`/`bash -n`.

## Проверка самого набора

Без Gemini и сети; все репозитории и worktree в TemporaryDirectory:

```bash
python3 -m py_compile server/agent-tools/gemini-bench/gemini-bench
(cd server/tests && timeout 120 python3 -m unittest -v test_gemini_bench)
```

`GEMINI_TASK_BIN` подменяет исполняемый файл (один путь, без shell-аргументов). `GEMINI_BENCH_HOME` подменяет каталог результатов **и** переносит временные worktree в `<home>/worktrees/`. `GEMINI_BENCH_REPO` подменяет git-репозиторий с main. Для обычного запуска эти переменные не нужны. Полные наборы тестов проекта здесь не запускать.
