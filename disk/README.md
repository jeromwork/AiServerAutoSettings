# RemoteDisk

Модуль диска RemoteAgents. Его устанавливает мастер (шаг «Диск») командой
`disk/Install-RemoteDisk.ps1 -Profile <ssh-transport.json>`: без администратора скачивается Syncthing Tray 2.1.9
со встроенным движком 2.1.7 (проверка SHA-256), создаётся состояние в `%LOCALAPPDATA%\RemoteDisk`, лаунчер
запускает `%LOCALAPPDATA%\RemoteDisk\tray\syncthingtray.exe` напрямую. Syncthing Tray управляет
встроенным движком и служит единственным интерфейсом папок, пауз и состояния передачи.
Связь с сервером идёт через транспорт лаунчера (локальный SSH-вход, по умолчанию 127.0.0.1:2222).
`Install-RemoteDisk.ps1 -Uninstall` убирает закрепление Disk в Проводнике; пользовательские файлы сохраняются.
Обновление сохраняет Syncthing, `state/config.xml` и принятые папки. Одноразовая очистка старых меню,
значков и пустых собственных заглушек выполняется при установке либо отдельно с `-CleanupLegacy`;
закрепление Disk в левой панели остаётся.

Через SSH устанавливаются серверный скрипт и правила исключений. Серверная команда `channel-config` читает
серверный sing-box, получает Reality public key через OpenSSL/X25519 и возвращает клиентскую конфигурацию
канала для транспорта лаунчера. Исходная конфигурация сервера не изменяется.

Серверная папка — `~/Disk/<имя>`, одна на проект. ID новой местной папки совпадает с её именем; ID уже зарегистрированных и принятых с компьютеров папок сохраняются. Сервер предлагает папки всем известным устройствам. Серверные папки имеют тип `sendreceive`, `maxConflicts=-1`, включённый watcher и `fsWatcherDelayS=2`; новые папки дополнительно получают поэтапное хранение версий. Паузы и остальные настройки существующих папок сохраняются. Обменом файлов и конфликтами управляет Syncthing. Первое слияние двух уже зарегистрированных непустых папок проверяется `disk/test-wizard-merge.py` на двух настоящих Syncthing 2.1.7; приём нового предложения в занятый каталог ниже специально исключён.

На сервере шаблон `stignore.txt` записывается в `.stignore-remoteagents` внутри каждой папки. В `.stignore` один раз добавляется `#include .stignore-remoteagents`; существующие пользовательские правила и переводы строк сохраняются, права доступа файла при замене не меняются. Если `.stignore` побайтово равен одному из прежних наших шаблонов (их SHA-256 зашиты в `server-disk.sh`), он заменяется одной строкой include: правила теперь в `.stignore-remoteagents`. Любое другое содержимое — правила пользователя. Обновление шаблона меняет только отдельный файл. Историю хэшей сервер не ведёт: список прежних шаблонов зашит в скрипт и не пополняется; пользовательский `.stignore` не служит причиной отказа. В Git `info/exclude` сервер добавляет `.stfolder`, `.stignore`, `.stignore-remoteagents`, `*.sync-conflict-*`. Сам include-файл, секреты и генерируемые каталоги исключаются; обычные исходники внутри `log` и `db` передаются. Как и в Syncthing, порядок правил имеет значение: пользовательские правила перед include сохраняют свой приоритет.

Серверные команды: `bootstrap`, `add-device`, `channel-config`, `install-auto`. `reconcile` — прежнее имя `bootstrap`,
оставлено для systemd-таймеров, поставленных прежним `install-auto`.
`bootstrap` возвращает JSON с `deviceId` и локальным портом `listen`.
`add-device` принимает base64 JSON `{"deviceId":"...","deviceName":"..."}`, регистрирует устройство
и запускает общий reconcile: предлагает ему все папки сервера и принимает уже ожидающие предложения известных устройств. Повтор сохраняет настройки устройства и не создаёт дубликатов.
Для команд с данными второй аргумент — base64 JSON либо `--stdin` с этим же base64 в stdin.

## Автоматическое подключение серверных проектов

Каждая обычная папка непосредственно в `~/Disk/<имя>` автоматически расшаривается всем зарегистрированным устройствам (все peer devices этого отдельного Syncthing). Новое устройство также получает существующие папки. `bootstrap` обнаруживает папки даже до регистрации первого устройства. Удаление каталога не удаляет регистрацию и данные других сторон. Символические ссылки и недопустимые Windows-имена пропускаются. За пределами `~/Disk` сервер не регистрирует папки и не пишет Git exclude, включая внешний gitdir worktree.

Ошибка одной папки (недопустимое имя, права доступа, ошибка REST, git не ответил) выводится в stderr как
`RemoteDisk: <папка>: <причина>`; остальные папки обрабатываются, а `bootstrap` и `add-device` завершаются с кодом 0.
Исключения в Git — косметика: без git или при его зависании папка всё равно предлагается. Сбой обнаружения после
регистрации устройства не отменяет `add-device`, расшаривание повторит cron. Общий сбой (например, `~/Disk` —
символическая ссылка) по-прежнему останавливает `bootstrap` с кодом 1.

### Загрузка с компьютера на сервер

Компьютер расшаривает папку серверу через свой локальный REST Syncthing. Папка может оставаться на любом диске компьютера; SSH для загрузки не нужен. Сервер читает `/rest/cluster/pending/folders` при каждом `bootstrap`/`reconcile` и `add-device`. Принимаются только предложения от peer devices, уже зарегистрированных через `add-device` в отдельном серверном Syncthing. Неизвестные устройства и устаревшие предложения удалённых устройств не принимаются; `autoAcceptFolders` движка не включается.

ID предложения сохраняется. Из его `label` получается безопасное имя непосредственно в `~/Disk`: разделители пути, управляющие и недопустимые символы заменяются, зарезервированные Windows-имена получают префикс, слишком длинные имена сокращаются. Если label пуст, берётся ID. Любой существующий каталог (даже пустой), файл, символическая ссылка или зарегистрированный путь другого ID считается занятым; проверка совпадений не зависит от регистра. Сервер выбирает `<имя> (2)`, `<имя> (3)` и далее. Существующее содержимое не сливается с новой загрузкой. Если ID входящего предложения совпал с именем ещё не зарегистрированной местной папки, загрузка также получает отдельный каталог, а местная папка остаётся нетронутой с диагностикой `ID занят`.

До включения синхронизации создаются правила исключений и локальная отметка `.stfolder/remote-disk-folder-id`. Она связывает каталог с ID: после ошибки PUT следующий reconcile повторяет приём в тот же каталог; незавершённый приём не превращается в отдельную серверную папку. Повтор требует предложения от всё ещё известного устройства. Уже принятый ID не меняет путь и не создаёт дубликатов. Отдельная ошибка приёма не мешает остальным предложениям и местным папкам.

Папка сразу получает `sendreceive`, `fsWatcherDelayS=2`, `maxConflicts=-1`, staggered versioning и расшаривается всем остальным зарегистрированным устройствам. Они получают обычное pending-предложение с окончательным именем каталога в label; клиент может показать по нему облачную заглушку, пока папка не принята локально.

`bootstrap` (включая установщик/мастер), `add-device` и `install-auto` ставят либо обновляют пользовательский systemd timer: первый запуск через 2 секунды, следующий — через 2 секунды после завершения reconcile, `AccuracySec=1`; root не нужен. Старый минутный timer обновляется обычным bootstrap. Неизменённые юниты повторно не записываются и не перезапускаются. Успешный stdout службы подавляется (`StandardOutput=null`, `SyslogLevel=warning`, `LogLevelMax=notice`), ошибки остаются в stderr.

Если user systemd недоступен или не смог включить timer, добавляется запасная минутная строка cron. После успешного включения timer удаляется только эта наша строка; задания пользователя сохраняются. Скрипт не включает linger и не устанавливает пакеты. Длительность reconcile и согласование устройств добавляются к интервалу. Запросы к REST Syncthing: чтение ждёт до 3 с, запись (PUT папки, которой нужен перезапуск) — до 30 с.

### Зависшие соединения после смены сети

Когда у компьютера меняется сеть, туннель (sing-box/relay) рвётся молча: серверный Syncthing видит все соединения как `127.0.0.1:<порт>`, и их локальные сокеты остаются «живыми». Пока Syncthing не признает их мёртвыми (нет данных 300 с, проверка раз в 150 с — до 7,5 минут), он отказывает новым соединениям того же устройства: компьютер видит `Failed to exchange Hello messages … EOF`, а сервер пишет об отказе только на уровне DEBUG. По журналу зависание не отличить: такой отказ бывает и у здорового устройства (на стенде клиент периодически пробует лишнее соединение), а `Failed TLS handshake` пишется, когда соединение оборвалось (клиентом или туннелем) до конца рукопожатия, то есть до проверки числа соединений.

Поэтому признак — молчание, а не журнал. Каждый `bootstrap` (то есть каждые 2 с) читает один `GET /rest/system/connections` и хранит в `connection-watch.json` (каталог состояния скрипта), когда у устройства последний раз менялись входящие байты, набор соединений или их `startedAt`. По протоколу BEP живой peer шлёт по каждому соединению хотя бы пинг раз в 90 с (на 2.1.7 замерено 45–90,6 с). Устройство, у которого ни одно соединение не получило ни байта 120 с (`STALE_AFTER_S`), считается зависшим; устройство, которое обменивается данными, — никогда.

Для зависшего устройства вызываются `POST /rest/system/pause?device=<ID>` и сразу `resume`: старые соединения закрываются, компьютер подключается заново при ближайшей попытке (на стенде с интервалом переподключения 3 с — через 3 с). Не чаще раза в 60 с на устройство (`HEAL_COOLDOWN_S`); после лечения молчание отсчитывается заново. В журнал (stderr службы, уровень warning) пишется одна строка `RemoteDisk: <имя> (<ID>): соединения молчат N с, устройство перезапущено через pause/resume`. Пометка «ставим на паузу» записывается до `pause`: если запуск оборвётся посреди лечения, следующий вернёт устройство из паузы; `resume` в самом запуске повторяется до трёх раз. Устройства на паузе у владельца и неподключённые не трогаются. Сбой проверки печатает `RemoteDisk: соединения устройств: …` и не мешает ни папкам, ни коду возврата. Следит и лечит только `bootstrap` (и его псевдоним `reconcile`), `add-device` не трогает соединения. Чтобы убедиться на сервере: `journalctl --user -u remote-disk-folders.service | grep pause/resume`.

## Приём папок на компьютере

Без списка папки остаются предложениями в Syncthing Tray. Для разового приёма при установке
или применении конфига используйте `disk.folders` либо
`Install-RemoteDisk.ps1 -AcceptFile <JSON>`: `{"folders":[{"id":"Проект"},{"id":"Фото","path":"D:\\Фото"}]}`.
Без `path` используется `<корень Disk>\<id>`. Приём идёт только через REST на `127.0.0.1`,
ожидает предложение выбранного сервера и сохраняет уже принятые ID без изменения пути и настроек.
Пересекающиеся пути и reparse points отклоняются. Слиянием содержимого и конфликтами управляет Syncthing.
После первого знакомства устройств повторная установка не требует SSH. Фоновых выборов и опросов папок нет.

### Команды Проводника и освобождение места

«Загрузить на сервер» переводит существующую регистрацию в `sendreceive`, сохраняя путь, остальные устройства и настройки. Статус «есть локальные изменения» у `receiveonly` запрещает освобождение места. Трей и Проводник показывают успешную синхронизацию только при подтверждённой готовности обеих сторон.

«Оставить только на сервере» сначала принудительно сканирует папку. В течение 30 с ожидаются `idle`, нулевые локальные и серверные needs и completion сервера 100%; локальный sequence проверяется до и после чтения серверной готовности. При его изменении сканирование повторяется. Таймаут оставляет регистрацию и файлы на месте. Только после подтверждения регистрация снимается и Windows Shell переносит папку в Корзину. Используются `IFileOperation`, запрос recycle-only, предупреждение Shell и veto постоянного удаления; запасного безвозвратного удаления нет. Если Корзина недоступна, регистрация восстанавливается, человеку предлагается освободить место или удалить папку вручную.

### Применение на сервере владельцем

Изменения подготовлены в репозитории; эти команды меняют рабочую конфигурацию **только при ручном применении**:

```bash
# Из корня репозитория:
install -m 700 disk/server-disk.sh "$HOME/.local/share/remote-disk/server-disk.sh"
install -m 600 disk/stignore.txt "$HOME/.local/share/remote-disk/"
bash "$HOME/.local/share/remote-disk/server-disk.sh" install-auto
bash "$HOME/.local/share/remote-disk/server-disk.sh" bootstrap
systemctl --user status remote-disk-folders.timer --no-pager
journalctl --user -u remote-disk-folders.service -n 30 --no-pager
```

Автоматизация обслуживается bootstrap: отключённый timer включится при следующем запуске установки или bootstrap. Для остановки автоматизации вместе с движком отключите timer (`systemctl --user disable --now remote-disk-folders.timer`) и уберите запасную строку RemoteDisk из crontab, если она есть.

Изолированные серверные проверки (настоящие движки, временные HOME, без живого SSH и Windows):

```sh
python3 disk/test-disk.py -v
python3 disk/test-wizard-merge.py -v
bash -n disk/server-disk.sh
```

`test-disk.py` проверяет загрузку из папки вне Disk и обратную передачу через watcher, pending-предложение третьему устройству, отказ неизвестному peer до `add-device`, сохранение ID и повтор без изменений, безопасные label с CRLF, занятые имена/ссылки/пути, а также повтор после ошибки REST до записи и после записи с потерянным ответом. Параметры короткого таймера проверяются по создаваемому юниту; настоящий systemd user manager тест не запускает.

После интеграции клиентских меню и заглушек на живом Windows нужно проверить: «Загрузить на сервер» на папке вне Disk, появление её файлов на сервере, облачную заглушку на втором компьютере и отдельное имя при повторной загрузке другой папки с тем же label. Эти проверки не заменяются Linux-стендом.

Для проверки без скачивания задайте `SYNCTHING_ARCHIVE` — путь к архиву Syncthing 2.1.7 для Linux amd64.
При наличии pytest: `python3 -m pytest -q -o 'python_files=test-*.py' disk/`.

## Проверки Windows-скриптов на Linux

Изолированные проверки (PowerShell 7, временные каталоги и подменённые API/реестр/SSH):

```sh
pwsh=$HOME/.cache/pwsh-test/pwsh
for name in accept cleanup install pairing; do
  timeout 120 "$pwsh" -NoProfile -NonInteractive -File "disk/test-$name.ps1"
done
bash app/launcher/tests/run.sh
```

Эти проверки не подтверждают работу UI и Windows PowerShell 5.1 на настоящем компьютере.
Ни стенд, ни автотесты не меняют Windows или живой сервер.
