# RemoteDisk — отдельный переносимый клиент

Без сборки: Windows PowerShell 5.1, штатный OpenSSH, Syncthing 2.1.7.
Не использует установщик, seed, снимки, мост, барьеры свежести или состояние старой синхронизации.

## Запуск владельцем

1. Скопировать `04-disk.cmd` и **весь каталог `disk` рядом с ним** на Windows. Один cmd из старого упаковщика недостаточен: PACKАGE-MANIFEST дополнен только разрешённой строкой запуска.
2. Использовать существующий SSH-профиль обычного пользователя **или root**. Профиль только читается. При входе root все файлы и Syncthing принадлежат обычному пользователю: параметр `04-disk.cmd -ServerUser имя`, иначе поле `serverUser` в `%LOCALAPPDATA%\RemoteDisk\config.json`, иначе выбор из серверных пользователей (UID >= 1000, рабочая оболочка, существующий домашний каталог, кроме nobody). Один кандидат выбирается автоматически с записью в журнал; несколько — в окне; отсутствие кандидатов — ошибка. Пользователи не создаются. Выбор сохраняется в config.json. Имена допускают строчные латинские буквы, цифры, подчёркивание и дефис, начинаются с буквы или подчёркивания, длина до 32.
3. Запустить `04-disk.cmd`. Если найдено несколько профилей, выбрать нужный в окне. Явно:
   `04-disk.cmd -Profile "C:\полный\путь\ssh-transport.json"`.
4. Дождаться значка в трее. Через «Добавить папку» выбрать отдельную папку с тестовыми файлами. Серверная папка создаётся как `~/Disk/<имя>-<уникальный суффикс>`. Одно подключение имеет собственный новый индекс, поэтому старые удаления не применяются при первом соединении.
5. Проверить передачу в обе стороны, паузу, разрыв SSH, восстановление, конфликт и историю `.stversions`. Только после этого подключать рабочие папки.
6. Контекстное меню и автозапуск включаются отдельными пунктами трея, только в HKCU. В Windows 11 меню находится в «Показать дополнительные параметры». Автозапуск ссылается на исходный путь скрипта: после перемещения включить заново.

Локальное состояние: `%LOCALAPPDATA%\RemoteDisk`, настройки схемы 1 — `config.json`.
Папки не должны пересекаться, быть ссылками или содержать чужой `.stignore`.
Первичная настройка обеих сторон создаётся в паузе, проверяется, затем возобновляется.
Защитные исключения совпадают с DENIED/DENIED_EXT из `server-sync.py`; обычные файлы передаются без белого списка.
«Вернуть» убирает только пользовательское исключение, защиту секретов не отменяет.
Исключения относятся к локальному устройству; исключённые файлы физически не удаляются.
При отключении файлов на обеих сторонах не касается, конфигурацию папки удаляет.
Для повторного подключения оставшийся `.stignore` нужно проверить и убрать вручную.
Версии simple хранят полученные изменения/удаления 30 дней; это не резервная копия локальных правок до передачи.

## Подключение и состояние

Один долгий ssh.exe с локальными пробросами транспорта и REST и обратным пробросом транспорта.
Используются исходные `arguments`, включая запасной маршрут; ключи, known_hosts и ssh_config не меняются.
В профиле последний аргумент должен быть `serverAddress`, без удалённой команды.
StrictHostKeyChecking и BatchMode включены. Неизвестный ключ сервера нужно предварительно подтвердить штатным SSH самостоятельно.
GUI и транспорт слушают исключительно 127.0.0.1. Discovery, relay, NAT, upgrades и crash reporting выключены.
При root команды установки, создания папок, запуска и отправки журналов проходят через `runuser -u <пользователь> -- bash -c`; нужен установленный runuser. Домашний каталог и владелец файлов — выбранного пользователя. Сам server-disk.sh по-прежнему отказывается работать под root. SSH-туннели остаются в исходном подключении, отдельный вход пользователя не нужен.
Серверный пользовательский процесс запускается через nohup, не привязан к окну Windows.
Данная минимальная версия рассчитана на один Windows-клиент на серверное состояние RemoteDisk.
Порты выбираются автоматически и сохраняются; при конфликте запуск останавливается с ошибкой, чужие процессы не завершаются.

Цвета: зелёный — синхронизировано, синий — передача, жёлтый — пауза,
серый — нет подключения, красный — ошибка, фиолетовый — конфликт.
Состояние берётся из REST каждые 4 секунды; отсутствие подключения имеет приоритет над успехом.
Процент и оставшиеся байты видны в статусе. Папки имеют отдельные команды паузы и открытия.
Конфликты ищутся как `*.sync-conflict-*`; при большом дереве обход может задерживать UI.

## Если запуск сломался

Первая JSONL-запись создаётся **до WinForms, скачивания и Syncthing**.
После выбора SSH-профиля первая отправка выполняется до установки движка.
Без рабочего профиля/SSH доставка невозможна, записи остаются локально.
Далее отдельный PowerShell worker раз в 30 секунд доставляет журнал короткими SSH,
даже пока установка/GUI ждёт или Syncthing не работает. Неудачные пакеты остаются в `logs\queue`.
Повторная доставка заменяет пакет атомарно, не дописывает дубликаты.
Локальные успешные первоначальные пакеты остаются в `logs\sent`, текущие сессии — `logs\session-*.jsonl`.
Журнал worker — `logs\delivery.jsonl`. Очередь и сессионные журналы автоматически не удаляются;
при долгой эксплуатации контролируйте занимаемое место.

На сервере смотреть от имени выбранного обычного пользователя (пути относятся к его HOME):

```sh
ls -lt ~/.local/share/remote-disk/logs/<имя-компьютера>/
tail -n 80 ~/.local/share/remote-disk/logs/<имя-компьютера>/*.jsonl
tail -n 80 ~/.local/share/remote-disk/syncthing.log
```

Поля: `time`, `stage`, `durationMs`, `hostId`, `message`.
Этапы: `start`, `ssh.start`, `ssh.exit` (код и stderr), `dns`, `tcp`,
`initialize.error`, `syncthing.state`, `power`, `power.resume`, `delivery.retry`, `fatal`.
DNS/TCP — прямые диагностические пробы; их ошибка не доказывает отказ запасного SSH-маршрута.
Если есть `start`, но нет следующих этапов — смотреть локальный журнал/профиль и доставку.
Если серверного журнала вообще нет — сначала профиль, доверие ключу, выбор serverUser при root и stderr локального SSH.
«Собрать диагностику» архивирует только JSONL, без профиля, XML-конфигураций, API-ключей и raw логов Syncthing.

## Реальные проверки

В Linux скачан PowerShell 7.4.13 во временный каталог, все новые ps1 разобраны парсером.
`test-functions.ps1` проверяет чистые функции: статусы, политику версий, исключения,
границы пути, quoting и подмену runuser без root (аргументы, HOME, stdin, сложные кавычки, отказ для неверных имён), редактирование секретов и очередь доставки с имитацией отказа SSH.
Это не проверка Windows PowerShell 5.1 или реального SSH.

`test-disk.py` запускает два настоящих закреплённых SHA256 Syncthing через **этот** server-disk.sh,
с временными HOME, случайными loopback-портами и политикой, экспортированной **этим** RemoteDisk.ps1.
Проверены: начальное объединение без удаления, новые файлы, правки и удаления в обе стороны,
точное содержимое сохранённых версий, конфликт, секреты/.git, пауза/возобновление, обрыв/восстановление.
Старый тест используется как библиотека сценариев, старый runtime не запускается.

```sh
pwsh -NoProfile -File disk/test-functions.ps1 -Export /tmp/disk-policy.json
python3 disk/test-disk.py /tmp/syncthing-linux-amd64-v2.1.7.tar.gz /tmp/disk-policy.json
bash -n disk/server-disk.sh
```

**Только Windows, ещё не проверено:** WinForms/трей и события питания, настоящий ssh.exe и туннели,
установка Windows ZIP, HKCU/AppliesTo, именованный канал/Mutex, автозапуск,
реальная фоновая отправка/диагностика, окно выбора serverUser и настоящий root SSH → runuser с проверкой владельца журналов. Проверку этих пунктов выполняет владелец;
Linux-проверки не являются их приёмкой. Никаких подключений с Windows к VPS при разработке не выполнялось.
