# RemoteDisk

Windows PowerShell 5.1, штатный OpenSSH и Syncthing 2.1.7. Git, агенты,
веб-разработка и localhost работают на сервере. Компьютер получает рабочие файлы
для эмулятора и других тяжёлых приложений; устанавливать Git на компьютер не нужно.

## Модель папок

Каждый каталог первого уровня `~/Disk/<имя>` — отдельная синхронизируемая папка:
обычный git-клон, worktree либо каталог без Git. Основной клон и его worktree можно
одновременно подключить на одном компьютере, к разным локальным путям. Несколько
компьютеров подключаются к одной серверной папке. Локальный путь может быть любым.

Новый id: `disk-` + первые 24 hex SHA-256 от UTF-8 `folder:<имя>`.
Случайных суффиксов и новых серверных копий при повторном подключении нет.
Имя чувствительно к регистру; разрешены буквы, цифры, `_`, `-`, внутренние пробелы
и одиночные точки (до 128 символов). Разделители, `..`, управляющие символы,
имена устройств Windows, завершающая точка/пробел запрещены. На одном компьютере
одна серверная папка подключается только к одному пути; повтор к другому пути
возвращает ошибку с уже подключённым путём.

Старые записи схемы 1 с произвольными id и серверными суффиксами продолжают работать.
Автоматического переноса/переименования нет. Если серверная папка уже имеет старый
индекс, новые компьютеры используют этот индекс: один путь не индексируется дважды.
Поля `deviceName`, `serverId`, `profile` и `folders[].name` дополняют схему 1;
для старых папок имя читается из `remotePath`.

Передача двусторонняя (`sendreceive`). Правка с компьютера становится обычной
правкой Git на сервере. `.git` исключён и как каталог, и как файл worktree;
секреты исключены защитной политикой. На обеих сторонах при наличии Git
`.stignore`, `.stfolder`, `.stversions`, `*.sync-conflict-*` добавляются без дублей
в путь из `git rev-parse --git-path info/exclude`, сохраняя существующее содержимое.
Git исключения старых подключений также проверяются при восстановлении соединения.

Чужой `.stignore` запрещён: локальная проверка выполняется до создания чего-либо
на сервере, сервер повторно проверяет свою папку перед подключением. Точный
собственный защитный набор разрешён при повторном подключении. Пользовательские
исключения локальны; «Вернуть» не снимает защиту секретов. Версии Syncthing отключены на обеих сторонах, включая старые подключения.
Новые каталоги версий/архивов не создаются; уже существующие версии не удаляются.

## Запуск и установка

Скопировать `04-disk.cmd` и весь каталог `disk` рядом с ним на Windows.
Обычный запуск: `04-disk.cmd -Profile "C:\путь\ssh-transport.json"`.
При отсутствии `-Profile` используется сохранённый профиль либо найденный профиль;
если их несколько, интерактивный запуск предлагает выбор.

```powershell
.\04-disk.cmd -Install -Profile "C:\путь\ssh-transport.json"
.\04-disk.cmd -Uninstall
```

`-Install` копирует самодостаточный набор в `%LOCALAPPDATA%\RemoteDisk\app`:
`RemoteDisk.ps1`, `DiskLock.ps1`, `Set-DiskAcl.ps1`, `Watch-Disk.ps1`, `server-disk.sh`.
`Windows.Paths.ps1` не используется и не требуется. Внешние компоненты — штатные
Windows PowerShell 5.1/.NET (WinForms), OpenSSH и загружаемый Syncthing; настройки,
SSH-профиль и ключи остаются вне `app`. Контекстное меню, HKCU-автозапуск и запуск
приложения указывают на копию в `app`. Новый процесс запускается отдельно:
установщик возвращается, не ожидая окончания работы трея.
`-Uninstall` снимает автозапуск и меню, сохраняя файлы и настройки.
Контекстное меню также включается в работающем приложении через
`04-disk.cmd -Command context-on` или пункт трея. В Windows 11 оно может быть
в «Показать дополнительные параметры».

Состояние: `%LOCALAPPDATA%\RemoteDisk`, настройки: `config.json` схемы 1.
SSH-профиль только читается; пользователь процесса сервера — пользователь
SSH-входа, без переключения учётной записи. Старое `serverUser` игнорируется.
Ключи, known_hosts, ssh_config и службы не меняются.

## Добавление и отключение

```powershell
# Без диалогов; при нескольких профилях указать -Profile.
.\04-disk.cmd -Command add -Path "D:\Работа\app" -Remote app
# Без -Path создаётся %USERPROFILE%\RemoteDisk\app.
.\04-disk.cmd -Command add -Remote app
# Явное согласие на смешивание двух непустых папок.
.\04-disk.cmd -Command add -Path "D:\Работа\app" -Remote app -Merge
# Окно выбора серверной папки.
.\04-disk.cmd -Command add -Path "D:\Работа\app"
```

Окно показывает все серверные каталоги, origin без логина/пароля/токенов,
ветку и признак worktree, а также «Создать новую: <имя локальной папки>».
Предварительный выбор — совпадение origin (SSH/HTTPS и окончание `.git`
нормализуются), иначе совпадение имени. Пустой локальный каталог получает серверные
файлы; новая серверная папка получает локальные. Две непустые папки могут смешаться:
окно требует подтверждения, команда с `-Remote` отказывает без `-Merge`.
Отказ не создаёт синхронизируемые каталоги/индексы или служебные файлы в них.
Папки не должны пересекаться или быть ссылками; корень диска не допускается.

Без уже запущенного приложения команда без диалогов поднимает соединение,
подключает папку и запускает установленную копию трея для продолжения передачи.
При работающем трее команда выполняется им через именованный канал, результат
возвращается вызывающему процессу. `add` означает подключение, а не завершение
передачи: перед запуском эмулятора проверять `status -Wait`.

Каждый компьютер имеет постоянное имя устройства в конфиге и собственный
обратный порт. Сервер атомарно выделяет порт под блокировкой и сохраняет
`device-ports.json`. Повтор возвращает тот же порт. Подключение добавляет устройство
к текущей серверной конфигурации, сохраняя чужие устройства и паузу существующей
папки. Отключение в меню убирает только текущее устройство и локальный индекс;
серверная папка, файлы, индекс и остальные компьютеры сохраняются.

Для серверного списка: `bash ~/.local/share/remote-disk/server-disk.sh list`.
JSON содержит `name`, `id`, `path`, `origin`, `branch`, `worktree`, `hasFiles`, `worktrees`, `uncommittedFiles`, `unpushedCommits`.
Для Git добавлены все worktree из `git worktree list --porcelain -z`, включая
расположенные вне `~/Disk`. У каждой записи есть путь, `connectable` и оба числа.
Подключить непосредственно можно только обычный каталог первого уровня в `~/Disk`
с допустимым именем. Внешние worktree перечисляются для информации и не меняются.
Незакоммиченные файлы считаются по porcelain (rename считается одним файлом),
незапушенные коммиты — относительно upstream, а без него относительно всех известных
remote refs. Сеть/fetch для подсчёта не используются; числа отражают локальные refs.
`hasFiles` не считает `.git` и служебные каталоги Syncthing содержимым.
Каталог без Git имеет пустые origin/branch; detached HEAD — пустую ветку.
Неподходящие имена видны с `id: null`, но подключить их нельзя. Ссылки пропускаются.

## Статус для людей и агентов

```powershell
.\04-disk.cmd -Command status
.\04-disk.cmd -Command status -Remote app -Wait 60
if ($LASTEXITCODE -ne 0) { throw 'RemoteDisk ещё не готов' }
```

Команда читает локальный REST без запуска трея, SSH или установки движка.
Вывод всегда JSON-массив: `name`, `path`, `state`, `remainingBytes`,
`remainingFiles`, `lastSync`, `serverConnected`, `locked`, `uncommittedFiles`,
`unpushedCommits`, `message`. `locked` читается из ACL с учётом durable-записи,
а не берётся только из памяти. `null` означает, что проверка невозможна/неуспешна
(в частности, на Linux). Git-числа поступают из последнего ответа сервера в
`server-folders.json`; без ответа — `null`. Это снимок refs, без fetch. Неизвестные счётчики/время —
`null`. `lastSync` берётся из последнего файла Syncthing; при полностью проверенном
`synced` — время перехода локальной базы в idle. Это отметка движка, не время запуска
команды. Остаток учитывает локальную базу и подтверждённую потребность сервера.

Состояния: `synced`, `syncing`, `paused`, `offline`, `conflict`, `error`.
Код 0 — только непустой результат, все папки `synced` и сервер подключён.
Отсутствующая папка/связь или истёкшее ожидание возвращают ненулевой код.
Даже при нулевом остатке без серверного соединения состояние `offline`.
`-Wait` ждёт до указанного числа секунд, проверяя REST повторно; сетевые таймауты
отдельного запроса могут немного продлить ожидание.

Трей обновляет эти же данные каждые 4 секунды; в «Папки» состояние указано у
каждой папки. Подключённая папка имеет пункт «Показать статус», неподключённая —
«Синхронизировать с сервером». Зелёный — synced, синий — syncing, жёлтый — paused,
серый — offline, фиолетовый — conflict, красный — error.
Конфликты ищутся как `*.sync-conflict-*` отдельной фоновой задачей; дерево не
обходится потоком трея. До первого результата нельзя получить `synced` в трее.
CLI выполняет свежую проверку без запуска интерфейса.
`pullErrors` предыдущей попытки не превращает активную повторную передачу в error;
ошибка idle/явное состояние error по-прежнему показываются как ошибка.

Соединение — долгий ssh.exe с локальными пробросами транспорта/REST и отдельным
обратным пробросом каждого компьютера. Используются исходные `arguments` профиля,
включая запасной маршрут. Последний аргумент профиля — `serverAddress`, без команды.
StrictHostKeyChecking и BatchMode включены; неизвестный ключ предварительно
подтверждается штатным SSH. После запуска туннеля REST ожидается коротким опросом
до 8 секунд, вместо фиксированного сна. GUI/транспорт слушают только loopback;
discovery, relay, NAT, upgrades и crash reporting отключены.
При конфликте порта запуск отказывает; чужие процессы не завершаются.
Серверный процесс пользователя запускается через nohup и переживает выход клиента.
Все пути сервера относятся к HOME пользователя SSH-входа, журналы принадлежат ему
и читаются им. При входе root это файлы root; для обычного пользователя нужен его профиль.

## Блокировка при отсутствии связи

По умолчанию подключённые папки на компьютере недоступны для записи без сервера.
Это относится также к старым подключениям со случайным id и исключённым
`build`/`node_modules`. Чтение и запуск остаются разрешены прежними правами.

Контроллер запускается перед сетевой инициализацией приложения: ставит локальные
папки Syncthing на паузу, добавляет на корень наследуемый deny текущему SID на
запись/создание/удаление (`0x10156`, OI/CI) и проверяет ACL дерева. Разблокировка
возможна только при живом туннеле, локальном соединении и подтверждении удалённого
Syncthing, что именно это устройство подключено. Сначала снимается и проверяется
ACL, затем возобновляется локальная папка Syncthing. Пользовательская пауза сохраняется.
При обычном выходе снова ставится запрет. После убийства основного процесса
контроллер также пытается поставить запрет; durable-запись позволяет следующему
запуску повторить/проверить прерванную операцию без накопления deny.

`Watch-Disk.ps1` работает отдельно от потока трея. Сигналы `Process.Exited` и
`SystemEvents.PowerModeChanged` обрабатываются .NET: Suspend блокирует, Resume
сначала блокирует и требует нового подтверждения связи. REST проверяется независимо
от четырёхсекундного таймера трея, с таймаутом запроса 1 секунда. Проверка и применение
ACL выполняются отдельным процессом; большие деревья не обходятся потоком интерфейса.
Ошибка применения DACL, несовпадение DACL или незащищённый дочерний ACL показываются как ошибка,
не как успешная блокировка/разблокировка. Syncthing остаётся на паузе.

Используется `DirectoryInfo.SetAccessControl(DirectorySecurity)` только для секции
`Access`: текущая DACL с ровно одним добавленным/снятым ACE. Операция требует
обычного права изменения DACL своей папки, без повышения прав и привилегии
восстановления. Остальные ACE сохраняются, результат перечитывается. Записи
восстановления, результаты и журнал находятся в `%LOCALAPPDATA%\RemoteDisk\locks`
и `logs/safety.jsonl`, вне рабочей папки.
Вложенные junction и символические ссылки пропускаются без обхода и проверки содержимого; запрет на их цели не распространяется.
Их количество записывается один раз в поле `skippedReparsePoints` результата
операции, включая результат ошибки. Корень-папка с признаком reparse point
по-прежнему запрещён.
Не удаляйте записи `locks` вручную, пока действует запрет.

```powershell
.\04-disk.cmd -Command unlock
.\04-disk.cmd -Command unlock -Remote app
```

Это явное аварийное снятие только запрета RemoteDisk, с проверкой результата.
В работающем приложении исключение действует до следующего запуска/обычного выхода;
без связи Syncthing при этом остаётся на паузе. Пункт «Снять блокировку» есть у папки
в трее. Отключение папки асинхронно ждёт снятия запрета перед удалением подключения.
`-Uninstall` снимает запреты, меню и автозапуск и завершает приложение без повторной
блокировки. Файлы/настройки остаются.

Ограничения самого NTFS: уже открытые дескрипторы записи ACL не отзывает; удаление
корня может разрешаться правами родителя. Права родителя автоматически не меняются.
Защищённые дочерние DACL и явные дочерние allow могут обойти наследуемый deny —
контроллер проверяет это и сообщает ошибку, не переписывая чужие права.
Принудительное убийство одновременно приложения и контроллера не даёт выполнить
обработчик выхода; следующий запуск снова начинает с блокировки.

## Редкая гонка конфликта

Никаких окон или дополнительных архивов. При состоянии `conflict` приложение
асинхронно вызывает `server-disk.sh resolve` для подключённой серверной папки.
Сервер возвращает свою проигравшую копию на основной путь либо удаляет проигравшую
копию клиента, затем сканирует папку. Правка и удаления распространяются Syncthing.
Имена файлов и действия (без содержимого) записываются в `conflicts.jsonl`.

В Syncthing **2.1.7** суффикс конфликтного файла содержит ID входящего победителя,
а не проигравшего. Поэтому решение использует `modifiedBy` конфликтной копии из
индекса Syncthing: серверное происхождение — восстановить; клиентское — удалить.
Это также отличает конфликтные копии, пришедшие от другого компьютера. Неизвестное
или ещё не проиндексированное происхождение вызывает ошибку/повтор, не удаление наугад.
Реальные тесты принудительно создают оба победителя и проверяют этот нюанс.
Более новая правка/удаление сервера сохраняется вместо устаревшей копии; если
основной файл изменился во время решения или ещё не проиндексирован, выполняется повтор.

## Если запуск сломался

Первая JSONL-запись создаётся **до WinForms, скачивания и Syncthing**.
После выбора SSH-профиля первая отправка выполняется до установки движка.
Без рабочего профиля/SSH доставка невозможна, записи остаются локально.
Далее отдельный PowerShell worker раз в 30 секунд доставляет журнал короткими SSH,
даже пока установка/GUI ждёт или Syncthing не работает. Неудачные пакеты остаются в `logs\queue`.
Повторная доставка заменяет пакет атомарно, не дописывает дубликаты.
Локальные успешные первоначальные пакеты остаются в `logs\sent`, текущие сессии — `logs\session-*.jsonl`.
Журнал worker — `logs\delivery.jsonl`. Очередь и сессионные журналы автоматически не удаляются;
при долгой эксплуатации контролируйте занимаемое место.

На сервере смотреть от имени пользователя SSH-входа (пути относятся к его HOME):

```sh
ls -lt ~/.local/share/remote-disk/logs/<имя-компьютера>/
tail -n 80 ~/.local/share/remote-disk/logs/<имя-компьютера>/*.jsonl
tail -n 80 ~/.local/share/remote-disk/syncthing.log
```

Поля: `time`, `stage`, `durationMs`, `hostId`, `message`.
Этапы: `start`, `ssh.login` (сообщение `user=<login>` из профиля), `ssh.start`, `ssh.exit` (код и stderr), `dns`, `tcp`,
`initialize.error`, `syncthing.state`, `power`, `power.resume`, `delivery.retry`, `fatal`.
DNS/TCP — прямые диагностические пробы; их ошибка не доказывает отказ запасного SSH-маршрута.
Если есть `start`, но нет следующих этапов — смотреть локальный журнал/профиль и доставку.
Если серверного журнала вообще нет — сначала профиль, доверие ключу и stderr локального SSH.
«Собрать диагностику» архивирует только JSONL, без профиля, XML-конфигураций, API-ключей и raw логов Syncthing.

## Проверки

Изолированный прогон использует временные HOME, свободные loopback-порты, настоящий
Syncthing 2.1.7 и политику из production PowerShell. Linux-архив скачивается с
официального GitHub-релиза; SHA-256 сверяется со строкой `sha256sum.txt.asc`
(в релизе нет файла без `.asc`):
`2edc416e7ed136b7c858ed5f3f02a3b8316589605e54c380228ceea7acbf0142`.

```sh
# Необязательно: реальная generate/XML-проверка вместо встроенного XML fixture.
export REMOTE_DISK_TEST_ARCHIVE=/tmp/<новый-каталог>/syncthing-linux-amd64-v2.1.7.tar.gz
~/.cache/pwsh-test/pwsh -NoProfile -File disk/test-functions.ps1 -Export /tmp/disk-policy.json
python3 disk/test-disk.py "$REMOTE_DISK_TEST_ARCHIVE" /tmp/disk-policy.json
bash -n disk/server-disk.sh
```

`test-functions.ps1` также запускает полный entrypoint без `-LibraryOnly` с
заглушками Windows API/SSH: проверяет ветку `-Install`, завершение родителя при живом
дочернем трее, пути в меню/автозапуске, удаление исходной папки и запуск копии из пустого рабочего каталога,
сохранение `-Remote` и объектного состояния подключения. AST запрещает совпадения
параметров и `script:`-состояния (включая импорт и функции), запись stdin через
StreamWriter и недоступный в 5.1 `StandardInputEncoding`. Реальный процесс-заглушка
проверяет байты stdin: UTF-8 без BOM, снятие старого ведущего BOM, нормализацию LF.

`test-functions.ps1`: политика, SHA/id, имена, origin SSH/HTTPS, редактирование URL
в журнале, CRLF, предварительные отказы, готовность туннеля, локальные Git-exclude
обычного репозитория/worktree, очередь журналов и восстановление установки.
`test-disk.py`: прежние сценарии двух движков (правки/удаления/разрешение конфликта/
секреты/пауза/восстановление), непрерывный опрос production-статуса при настоящем
конфликте, затем три движка с одним сервером и двумя клиентами. Проверяются
одновременное подключение, разные стабильные обратные порты, передача через сервер
в обе стороны, отключение одного клиента, повтор без дублей, main/worktree,
`.git`-файл, Git-exclude, внешние worktree и их числа, правка клиента как обычное изменение Git, старый id,
читаемость журналов и production CLI status с отключённым сервером и нулевым остатком.
TCP-пробросы теста локальны; это не проверка настоящего SSH.

`test-functions.ps1` также проверяет чистую политику блокировки для старта, связи,
потери связи, Suspend/Resume, ошибки применения DACL и выхода. Платформенные операции DACL в Linux заменены
заглушками: проверяются секция Access, передача ожидаемой DACL, сохранение ошибки
в результате и пропуск вложенных ссылок. Это не применение NTFS ACL.

**Не проверено на Windows:** NTFS-наследование/снятие deny, сохранение чужих ACE,
crash recovery, большие деревья, protected/explicit ACL, реальные power/tunnel events, PowerShell 5.1, WinForms/значки и события питания,
настоящий ssh.exe/туннели, HKCU/AppliesTo, `-Install`/`-Uninstall`, автозапуск,
именованный канал/Mutex, Windows ZIP, фоновая доставка/диагностика и существующая
тестовая папка владельца. Linux PowerShell 7 не подтверждает эти пункты.
Windows и мост при разработке не вызываются; реальные пользовательские состояния
Syncthing и папки сервера не используются.

## Установка Windows-движка и докачка

В каждой попытке подключения серверный bootstrap выполняется асинхронно через выбранный SSH-профиль.
Bootstrap атомарно заменяет серверный скрипт; старый файл с BOM не сохраняется.
После выхода туннеля или ошибки инициализации следующая попытка повторяет bootstrap,
чтобы поднять серверный движок после перезагрузки. Готовый локальный движок проверяется
через REST ping и запускается при необходимости, без статуса и журналов загрузки.
После готовности установки непосредственно перед туннелем один раз выполняются DNS/TCP-пробы
с записями `dns`/`dns.error` и `tcp`/`tcp.error`.
Затем конечный автомат на каждом тике проверяет завершение отдельного процесса.
Прямой путь использует `%SystemRoot%\System32\curl.exe` без окна: ZIP сохраняется в
`syncthing.zip.part`, повторная попытка продолжает файл с текущего размера.
Если curl отсутствует или две попытки подряд не увеличили файл, используется сервер:
`engine-windows prepare` сохраняет проверенный ZIP в `$HOME/.local/share/remote-disk/cache`,
`engine-windows chunk` отдаёт куски до 2 МиБ через тот же SSH-профиль.
Одновременно работает один процесс установки; неудачный кусок повторяется с той же позиции.
На выходе незавершённые curl/SSH установки завершаются. Частичный файл сохраняется для следующего запуска.

Перед распаковкой обязательны размер 14281765 байт и закреплённый SHA256
`3CE7DA770F546A8D02B65B2E7EE31F2A3B8B7C3F990EDE045590CCA4172ECFE1`.
Неверный файл удаляется, установка начинается заново. Старый `syncthing.zip` не используется.
Распаковка проверенного ZIP и Initialize-DiskLocal выполняются в главном потоке.
API-ключ устанавливает сама Initialize-DiskLocal; отдельной задачи установки и logs/engine.jsonl нет.
До готовности значок серый; подсказка и окно статуса показывают объём и выбранный путь.

Журнал: `engine.download.start` (direct/server), `engine.download.progress` (каждые 30 секунд,
байты и байт/с), `engine.download.retry` (код curl и очищенный stderr до 500 символов либо ошибка SSH),
`engine.download.fallback` (причина), `engine.download.done` (длительность), `engine.hash.error`.
curl запускается с `-sS`, без индикатора прогресса в stderr.
`initialize.error`, `tick.error` и `fatal` содержат тип и текст ошибки с редактированием секретов.
`test-functions.ps1` дополнительно запускает поддельные curl/SSH-процессы на pwsh/Linux:
обрыв и докачка, две попытки без роста, повтор куска, CRLF base64, неверный SHA, ограничение stderr, повторный bootstrap после выхода туннеля без загрузки,
проверку готового локального движка, сетевые записи один раз за попытку,
распаковку тестового ZIP в главном потоке и сохранение .part при остановке.
Эти проверки не заменяют настоящую приёмку Windows PowerShell 5.1, WinForms и ssh.exe.
