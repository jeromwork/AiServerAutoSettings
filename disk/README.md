# RemoteDisk

Модуль диска RemoteAgents. Его устанавливает мастер (шаг «Диск») командой
`disk/Install-RemoteDisk.ps1 -Profile <ssh-transport.json>`: без администратора скачивается Syncthing Tray 2.1.9
со встроенным движком 2.1.7 (проверка SHA-256), создаётся состояние в `%LOCALAPPDATA%\RemoteDisk`, движок
запускается без окна (`syncthingtray.exe syncthing serve`) под надзором `Disk.Status.ps1` лаунчера.
Связь с сервером идёт через транспорт лаунчера (локальный SSH-вход, по умолчанию 127.0.0.1:2222).
`Install-RemoteDisk.ps1 -Uninstall` убирает значок Disk в Проводнике; пользовательские файлы сохраняются.

Через SSH устанавливаются серверный скрипт и правила исключений. Серверная команда `channel-config` читает
серверный sing-box, получает Reality public key через OpenSSL/X25519 и возвращает клиентскую конфигурацию
канала для транспорта лаунчера. Исходная конфигурация сервера не изменяется.

Серверная папка — `~/Disk/<имя>`, одна на проект. ID новой папки совпадает с её именем; ID уже зарегистрированных папок сохраняются. Сервер предлагает папки всем известным устройствам, человек принимает их в Syncthing Tray. Серверные папки имеют тип `sendreceive` и `maxConflicts=-1`; новые папки дополнительно получают поэтапное хранение версий. Паузы и остальные настройки существующих папок сохраняются. Обменом файлов, слиянием и конфликтами управляет Syncthing. Первое слияние двух непустых папок проверяется `disk/test-wizard-merge.py` на двух настоящих Syncthing 2.1.7.

На сервере шаблон `stignore.txt` записывается в `.stignore-remoteagents` внутри каждой папки. В `.stignore` один раз добавляется `#include .stignore-remoteagents`; существующие пользовательские правила и переводы строк сохраняются. Обновление шаблона меняет только отдельный файл. История хэшей серверу не нужна, пользовательский `.stignore` не служит причиной отказа. В Git `info/exclude` сервер добавляет `.stfolder`, `.stignore`, `.stignore-remoteagents`, `*.sync-conflict-*`. Сам include-файл, секреты и генерируемые каталоги исключаются; обычные исходники внутри `log` и `db` передаются. Как и в Syncthing, порядок правил имеет значение: пользовательские правила перед include сохраняют свой приоритет.

Серверные команды: `bootstrap`, `add-device`, `channel-config`, `install-auto`.
`bootstrap` возвращает JSON с `deviceId` и локальным портом `listen`.
`add-device` принимает base64 JSON `{"deviceId":"...","deviceName":"..."}`, регистрирует устройство
и предлагает ему все папки сервера. Повтор сохраняет настройки устройства и не создаёт дубликатов.
Для команд с данными второй аргумент — base64 JSON либо `--stdin` с этим же base64 в stdin.

## Автоматическое подключение серверных проектов

Каждая обычная папка непосредственно в `~/Disk/<имя>` автоматически расшаривается всем зарегистрированным устройствам (все peer devices этого отдельного Syncthing). Новое устройство также получает существующие папки. `bootstrap` обнаруживает папки даже до регистрации первого устройства. Удаление каталога не удаляет регистрацию и данные других сторон. Символические ссылки и недопустимые Windows-имена пропускаются. За пределами `~/Disk` сервер не регистрирует папки и не пишет Git exclude, включая внешний gitdir worktree.

`bootstrap` и `add-device` используют общий механизм обнаружения. Cron вызывает `bootstrap` раз в минуту. Команда `install-auto` дополнительно устанавливает пользовательский systemd timer, который вызывает тот же `bootstrap` с интервалом 30 секунд; root не нужен. После обновления скрипта ранее установленный таймер нужно обновить повторным `install-auto`. Если user manager не работает без входа пользователя, автоматизация работает только пока доступна пользовательская сессия (либо через существующий cron). Скрипт не включает linger и не устанавливает пакеты.

Любое содержимое целевой папки, включая только `.git` или скрытые файлы, означает **«папка занята»**. Папка остаётся pending; сообщение записывается в `%LOCALAPPDATA%\RemoteDisk\install.log` (ротация 256 KiB), при ручном запуске также выводится warning. Вложенные/пересекающиеся пути Syncthing и reparse points запрещены. Для уже зарегистрированного ID повтор ничего не меняет. Контекстное меню и явное подключение с подтверждением объединения остаются доступны. Задача требует входа того же Windows-пользователя; длительная недоступность REST видна в журнале.

### Применение на сервере владельцем

Изменения подготовлены в репозитории; эти команды меняют рабочую конфигурацию **только при ручном применении**:

```bash
# Из корня репозитория:
install -m 700 disk/server-disk.sh "$HOME/.local/share/remote-disk/server-disk.sh"
install -m 600 disk/stignore.txt "$HOME/.local/share/remote-disk/"
bash "$HOME/.local/share/remote-disk/server-disk.sh" install-auto
bash "$HOME/.local/share/remote-disk/server-disk.sh" bootstrap
systemctl --user status remote-disk-folders.timer --no-pager
journalctl --user -u remote-disk-folders.service -n 30 --no-pager
```

Выключить дополнительный таймер: `systemctl --user disable --now remote-disk-folders.timer`. Пока остаётся cron bootstrap, он продолжает обнаруживать и предлагать папки; для полного выключения автоматизации требуется убрать именно строку RemoteDisk из пользовательского crontab.

Изолированные серверные проверки (настоящие движки, временные HOME, без живого SSH и Windows):

```sh
python3 disk/test-disk.py -v
python3 disk/test-wizard-merge.py -v
bash -n disk/server-disk.sh
```

Для проверки без скачивания задайте `SYNCTHING_ARCHIVE` — путь к архиву Syncthing 2.1.7 для Linux amd64.
При наличии pytest: `python3 -m pytest -q -o 'python_files=test-*.py' disk/`.

## Выбор, направления и внешние папки

Профиль `disk.folders`: `"all"` (включая будущие серверные проекты), `[]` (ничего), либо строки/объекты `{path,direction}`. Отсутствие поля оставляет выбор владельцу в окне программы. Старый массив строк сохраняет прежнее значение «в обе стороны».

`Disk.Selective.ps1` применяет направления на ПК: both → sendreceive, send → sendonly, receive → receiveonly. Это PATCH типа существующей папки, без удаления её данных. Сервер поддерживает тип sendreceive через bootstrap/add-device. В `selection.json` поле paths содержит `"."` для всех, directions — направления проектов. Периодическая Sync-RemoteDiskFolders учитывает эту политику и подключает будущие проекты.

`disk.external` задаёт абсолютные Windows-пути вне базы и серверное имя. Только управляемые подключения учитываются в `external.json`; чужие регистрации движок не снимает. Add вызывается с Remote/ManagedSelection/Direction, без скрытого Merge. Конфликт двух непустых папок — ошибка с причиной. Убранная внешняя папка или целый проект снимается из конфигурации только на ПК, файлы остаются. Убранные вложенные пути остаются локально и исключаются из обмена через `.stignore`.

DiskTree сообщает direction и localChanges для подключённого верхнего уровня. DiskRevert запрашивает откат местных правок receive-проекта, DiskExternal list возвращает управляемые внешние папки. JSON-контракт: [CONFIG-ENGINE.md](../docs/CONFIG-ENGINE.md); инструкция составления профиля: [CONFIG.md](../docs/CONFIG.md#папки--инструкция-для-ии-агента).

Изолированная проверка с фейковым API (настоящие Select/Add/Sync и временные каталоги):

```sh
timeout 120 ~/.cache/pwsh-test/pwsh -NoProfile -NonInteractive -File disk/test-choice.ps1
```

Ни стенд, ни автотесты не меняют Windows или живой сервер.
