# Лаунчер RemoteAgents

`app/launcher/RemoteAgents.Launcher.csproj` — WinForms / .NET Framework 4.8 для Windows 10/11.
Выпуск — один `RemoteAgents.exe` со встроенным ZIP: рядом не нужны DLL, SDK или установщик.
Сборка выполняется на Linux. JSON читает встроенный `JavaScriptSerializer`; NuGet reference assemblies
нужны только при сборке. Свой код отвечает за трей, процессы и транзакцию обновления;
сеть, VPN, диск и мост остаются модулями.

Задача G реализована в коде; Linux-проверки перечислены в [VPN-LAN.md](VPN-LAN.md).
Приёмка на Windows ещё не выполнена. `--tray --home <тест>` не запускает мастер и не регистрирует Run.

## Компактное окно мастера и настроек (задача O)

Оба EXE используют одно окно `SetupWizard`: 780×460 при 96 DPI,
`AutoScaleMode.Dpi`, без разворачивания. Слева узкий список разделов настроек с ✓/✗/…:
Сервер → Связь → Мост → Диск → Happier → Локальная сеть → VPN → Итог (в настройках —
«Состояние»). При первом запуске («RemoteAgents — настройка») разделы проходятся по
порядку кнопками «Далее»/«Назад», готовые при «Далее» пропускаются; щелчком можно
вернуться к пройденному разделу, но не перейти дальше первого незавершённого
(необязательные завершаются кнопкой «Пропустить»). Из трея («RemoteAgents — Настройки»)
разделы переключаются щелчком свободно, «Применить» («Проверить» в «Состоянии»)
выполняет и проверяет открытый раздел, «Назад» скрыт. «Закрыть» всегда доступна и
отменяет текущую операцию вместе с дочерними процессами. Каталог узлов
редактируется только в «Подробнее…», журнал показывает последнюю строку и раскрывается
отдельной кнопкой. В основном окне — вопрос, текущая операция и короткий результат.
Прогресс читается построчно из отдельного JSONL-файла; пробы связи сообщают название
каждого варианта и результат, в мастере ограничены пятью секундами на вариант.
Корень Disk остаётся одноуровневым; папки сервера принимают в Syncthing Tray.

При обычном запуске и автозапуске сначала появляется трей со статусом «запускается…».
Живые проверки выполняются в фоне: готовый компьютер не открывает мастер, иначе окно
показывает только требующие настройки шаги и автоматически пропускает готовые. После
последнего шага оно закрывается в трей с уведомлением. «Настройки…» открывает то же
окно со всеми разделами и текущими значениями. Диск, Happier, локальную сеть и выключенный VPN
можно оставить ненастроенными; обычная передача файлов не требует повторной настройки.

В приложении один активный сервер. Адрес, логин (сначала `root`) и пароль вводятся
прямо в окне. Сначала проверяется ключ; пароль используется лишь при необходимости,
через одноразовый named pipe с DACL текущего пользователя и `SSH_ASKPASS` того же EXE.
В файлах запроса, argv, окружении и журнале пароля нет. Первый ключ сервера запоминается
OpenSSH (`accept-new`), изменённый ключ отвергается. Root одним вызовом создаёт либо
использует `remoteagents`, идемпотентно добавляет ключ ПК и включает linger; дальнейший
вход — рабочим пользователем по ключу. При смене сервера новый профиль ожидает успешной
пробы связи; рабочая связь до неё сохраняется. Зависимые шаги требуют проверки заново.
Для Disk доступны «Отключить и подключить к новому» (отдельная пустая папка, старые
данные остаются на месте, состояние движка архивируется) и «Остановить синхронизацию,
файлы оставить» (старые файлы и настройки сохраняются, синхронизация отключается).
Автоматического слияния нет. Вопрос задаётся, только если диск на этом ПК установлен.

Необязательная ЛВС работает только на сервере. Выбранный `.ovpn` и соседние ссылки
`ca/cert/key/auth-user-pass` проверяются и собираются в inline-профиль в памяти;
отсутствующие файлы блокируют отправку. Профиль передаётся SSH stdin в
`~/.config/remoteagents/lan/<имя>/profile.ovpn` с правами 700/600, повторный выбор
заменяет тот же профиль. «Файл на сервере ✓» подтверждает только загрузку. Кнопка
копирует команду администратора для существующего `server/lan-vpn.sh`; команда
запрашивает выбранный владельцем HTTPS-сервис проверки внешнего IP. Сеть Windows
не меняется; включение OpenVPN требует отдельной процедуры из [VPN-LAN.md](VPN-LAN.md).

Проверки O выполняются на Linux с фиктивным SSH, настоящим `ssh-keygen` и запуском
скрипта загрузки в изолированном HOME. Проверки на Windows / PowerShell 5.1 и реальном
сервере в этой задаче не проводятся. Готового UI-smoke для создания WinForms без показа
в Linux-стенде нет; компиляция net48 не заменяет живую проверку размеров/DPI.

### Ревью O/N: запуск без окна, бюджеты шагов

- **Запуск без окна**: при `wizard.configured` окна нет никогда; если связь не подтверждена
  5 минут, один balloon. Иначе окно открывается только при ненастроенном обязательном шаге
  (необязательная ЛВС одна окно не открывает); если всё готово, «Итог» выполняется без окна.
  Balloon «Настройка завершена» — только после реального изменения.
- **Вход root**: `PreferredAuthentications=password,keyboard-interactive`; код 255 — ошибка входа,
  иной код — сбой помощника на сервере с хвостом stderr (без секретов).
- **Диск**: мастер устанавливает Syncthing и Syncthing Tray и знакомит компьютер с сервером.
  Папки, паузы и состояние передачи находятся в Syncthing Tray.

## Аккаунты Happier

Happier настраивается в общем окне. Папки принимают в Syncthing Tray; пункт «Disk» в трее RemoteAgents открывает корень в Проводнике.

Текущий сервер — официальный CLI/daemon Happier, а relay/история по умолчанию Happier Cloud;
собственный HTTPS relay задаётся в форме (config.json.happier.serverUrl/webappUrl).
32-байтовый recovery key хранится только в локальном secrets/, передаётся SSH stdin. На VPS каждый
account/relay имеет отдельный HAPPIER_HOME_DIR в ~/secrets/happier/accounts/ и отдельную systemd-службу.
HOME и native подписки Claude/Codex общие. Старый default daemon и другие аккаунты не перезапускаются.
Успех требует authenticated API и online своей machine; меню показывает время последней проверки.
Локальный журнал — logs/accounts.log, безопасный результат — state/happier-account.json.

Установка Disk описана в [disk/README.md](../disk/README.md). Профиль `disk.folders` задаёт
папки для разового приёма; без списка все предложения остаются в Syncthing Tray.

## Долгие операции на сервере и раздел «Установка» (задача P)

Установка Happier (`accounts/bootstrap.sh` → `happier.dev/install`) и сервера диска
(`server-disk.sh bootstrap`, Syncthing) не выполняются внутри шага окна. `server-wizard.sh start <op>`
(`repair` и `ensure happier` вызывают его же) запускает их отсоединённо: `systemd-run --user --scope`
(переживает выход из сессии), без user manager — `setsid nohup`. flock на
`~/.local/state/remoteagents-wizard/<op>.lock` берёт `start` и наследует исполнитель: повторный запуск
видит идущую операцию и вторую не стартует. Состояние `<op>.json` (started, finished, exitCode,
краткая причина — последняя строка журнала без токенов), этап `<op>.step` («k/n текст»), журнал `<op>.log`.
`status` читает их коротким SSH-вызовом; незавершённая запись без удерживаемой блокировки —
«прервана». Закрытие окна или выключение ПК операцию не прерывает.

Окно только собирает ответы: шаги короткие. Раздел, ждущий установку, помечен ⏳ и не блокирует
следующие (`WizardStep.Passable`). Слева появляется пункт «Установка», пока что-то идёт, ждёт
или завершилось ошибкой: «⏳ этап k из n: <этап>, прошло M мин» / «ожидает» / «✓ готово» /
«✗ ошибка: <причина> [Повторить]». Прогноза времени нет — только этап и прошедшее время.
Опрос — раз в 12 с действием `Operation` (без блокировки настроек, 60 с). Состояние для трея и
повторного открытия — `state/server-operations.json` (только публичные поля). Трей показывает
«Идёт установка: x из y», при завершении — «Готово» (или причину ошибки); если окно закрыто,
трей сам опрашивает раз в 15 с. API для других разделов: `SetupWizard.TrackOperation(name)`
(серверная операция добавляется в `server-wizard.sh valid_op`/`run`).

Happier: ключ можно ввести, пока Happier ещё ставится. Он ждёт в `secrets/happier-pending.key`,
публичный запрос — в `state/happier-pending.json`; `Account` вызывает `ensure happier` и при
незавершённой установке возвращает `pending`. Когда установка завершилась, окно (или трей, если
окно закрыто) выполняет `ResumeAccount`: ключ переносится в `happier-account.key`, неудача
восстанавливает прежний ключ и оставляет пробный как `happier-unconfirmed-*.key`. Ключ не попадает
в журналы, вывод шагов, state и argv SSH. Новый ключ, который не был показан, не подключается.

Реальная длительность установки Happier: `happier.dev/install` (~3000 строк bash) запрашивает
метаданные релиза `cli-stable` у GitHub API, скачивает архив `happier-linux-x64.tar.gz`
(~116 МБ, ноябрь 2026) с контрольными суммами и подписью minisign (при отсутствии minisign —
ещё и его архив с GitHub), распаковывает, выполняет `self __install-payload` и `service install`.
Обычно это 1–3 минуты (основное — загрузка 116 МБ); с медленным или ограниченным доступом к GitHub
— десятки минут: у curl инсталлятора нет `--max-time`, есть 3 попытки, предел ставит наш
`timeout 900`. Плюс Node.js 24 (~30 МБ) с nodejs.org, если его нет.

## Отмена мастера

Бюджет шага покрывает самый долгий дочерний процесс (`WizardStep.Timeout`, лимиты детей —
`Invoke-InstallChild -TimeoutSeconds`): «Сервер» 420 с (вход + запуск установок + каталог), Happier 420 с
(Account.ps1 300 с: только адаптер; установка Happier — отсоединённая, см. задачу P), Диск 2100 с (отключение 120 с + установка
900 с + применение 900 с), Связь и Мост 900 с, VPN 600 с, Inspect/Пропустить 300 с,
список аккаунтов 180 с, Итог 180 с, каталог/ЛВС 120 с.
«Закрыть» и крестик отменяют текущий процесс через CancellationToken и существующий kill-on-close
Windows Job, включая дочерние PowerShell/SSH. Ошибка возвращает доступ к кнопкам; «Пропустить диск»
позволяет перейти к следующему разделу, не объявляя диск готовым. События отмены/таймаута пишутся
в локальный launcher.log (формат и сквозная проверка — [LOGS.md](LOGS.md)), причины шагов — в журнал окна и штатные журналы модулей.
Установщик не удаляет принятые папки и пользовательские файлы.
Живая проверка WinForms/PS 5.1/Windows Job остаётся отдельной Windows-приёмкой.

## Автоматическое обновление и первичная установка

`update.enabled=true`, `update.auto=true`, `update.intervalHours=6` по умолчанию, включая конфиги без секции
или отдельных полей. Явные `false` сохраняются. При запуске и затем раз в заданное число часов программа
читает только SSH `manifest.json`. Ошибки связи/манифеста не показывают balloon и не меняют сеть, VPN или Диск;
в окне остаётся честная причина отсутствия проверки. Кнопка «Проверить обновления сейчас» выполняет ту же
проверку сразу (при занятой программе ждёт). `auto=false` оставляет только проверку, в том числе по кнопке.

Новая версия скачивается и устанавливается без нажатий существующим `UpdateEngine`. Применение конфига,
окна мастера с активным шагом, фоновая установка Диска, ожидающие/исполняемые действия Проводника и живые процессы моста откладывают установку.
Для моста используется его `Global\RemoteAgents.Environment.<SID>` и эксклюзивная запись `operations.json`:
проверка PID/start time и резервирование выполняются под одним mutex, новые команды не проскочат между ними.
Перед активацией повторно проверяется хеш конфига, чтобы не установить сборку по устаревшему результату.

После проверки ZIP новый EXE выполняет `--check-update-config <config.json>` без UI, сети, изменения файлов
и чтения vault. Он принимает прежние настройки без schema и схему 1; дополнение значений update выполняется
обычным загрузчиком. Переносимый profile проверяется кодом новой сборки. Неподдерживаемый конфиг оставляет
рабочую версию; одна фраза просит администратора выдать новый конфиг. Отказ запоминается по версии и хешу
конфига; при изменении конфига возможна новая проверка. Секреты остаются на месте и не выводятся.

EXE и бандл переключаются в одной транзакции через `UpgradeInstaller.ActivatePrepared`, даже если у ежедневных
сборок одинаковый FileVersion. Сохраняются прежний EXE и номер бандла. Новый процесс подтверждает здоровье
по событиям: tray (`Application.Idle`), связь, ранее включённый мост, Диск (соединение с сервером),
ранее включённый VPN. Набор берётся из `update-state.json`; последний ожидаемый `block.ready` даёт
`health.accepted` и немедленную приёмку без секундного тика. `block.degraded reason=no-network`
из `transport.localNet=down` тоже засчитывается для транспорта и зависящих от сети disk, vpn, control:
отсутствие локальной сети не делает версию плохой; это приёмка с деградацией, а не подтверждение связи. Рабочее состояние каналов/моста/Диска берётся из прежнего конфига; паузы Syncthing сохраняются
в его настройках. Перезапуск включённого VPN через службу-помощник описан в [VPN-LAN.md](VPN-LAN.md).

При сбое возвращаются прежние бандл и EXE, версия попадает в `bad.txt`. Дополнительно прежний EXE в режиме
`--watch-update` ждёт хэндл нового процесса (PID вместе со временем старта), изменения квитанции
и named event `Global\<InstanceName>.UpdateFailed`. Обработчики `AppDomain.UnhandledException` и
`Application.ThreadException` взводят этот сигнал. Три `component.exit` одного критичного компонента
без его `block.ready` между ними — crash-loop; готовность сбрасывает счётчик, отсчёта по времени нет.
Наблюдатель вооружается до запуска нового трея; имя и доступ привязаны к экземпляру и SID владельца.
При аварийном выходе нового процесса или сигнале отказа он использует штатную остановку установленного экземпляра,
восстанавливает транзакцию и запускает прежний EXE. Если готовность не приходит из-за зависания,
`UpdateNoProgressFuseMs=300000` от последнего нового отчёта готовности даёт только откат, никогда успех.
Прогресс записывается в `exe-upgrade.json.lastHealthUtc`, поэтому внешний наблюдатель работает и при
зависшем UI. До первого отчёта отсчёт идёт от начала активации. Повторы готовности и другая деградация
не продлевают предохранитель. Опрос и окна 120/125 секунд удалены.
Падение до `NoteImageProcess` ещё не имеет хэндла нового процесса: его обнаруживает только этот
5-минутный предохранитель (раньше смерть родителя обнаруживалась за 5 секунд).
При смене PID или времени старта в квитанции наблюдатель заменяет хэндл. Временная ошибка чтения
при атомарной замене квитанции не означает отказ: наблюдатель ждёт следующего файлового события.
При отказе здоровья трей проверяет и `UpdateWatching`, и владение mutex `UpdateObserver`; погибший
наблюдатель запускается вновь из `RemoteAgents.previous.exe` с сохранённым сигналом отказа.
Ошибка остановки журналируется, попытка перезапуска трея выполняется и при ошибке отката.

Штатный выход через трей, `--exit` и завершение сеанса отмечается `cleanExit`; код выхода 0 также
приостанавливает наблюдение без отката и `bad.txt`. Квитанция остаётся; следующий запуск очищает отметку,
публикует новую пару PID/время старта и начинает приёмку заново с новым отсчётом прогресса.
Решение доски `healthAccepted` сохраняется до финализации; ошибки записи/уборки в `CommitHealth`
пишутся в журнал и не превращаются в `UpdateFailed`. Если финализация не закончилась, она повторится
при следующем запуске. Вне транзакции необработанная ошибка UI после записи журнала завершает процесс
с кодом 1; во время приёмки она передаёт отказ наблюдателю.

При откате только лаунчера с прежним бандлом сохраняется одна последняя запись
`bundle/rejected-image.json` с SHA256 отвергнутого EXE. Повторная установка этих байтов запрещена;
явный downgrade/accept допускает повтор по решению пользователя. Рабочий бандл не попадает в `bad.txt`.
OTA не предлагает тот же номер бандла (`UpdateProbe` возвращает `Current`), поэтому этот случай
повторной установки возможен только через скачанный EXE.
Обычный результат — одно уведомление «Программа обновлена до …» или «Обновление … не установлено: …»;
строка трея и окна показывает версию, время успешной проверки, ход обновления либо причину отказа.
Состояние обновления — `bundle/update-state.json`.

Первичная установка и разовый переход со старой программы по-прежнему используют скачанный EXE:


1. Пользователь скачивает новый `RemoteAgents.exe` и запускает из любой папки без аргументов.
2. EXE находит `%LOCALAPPDATA%\RemoteAgents\RemoteAgents.exe`, сравнивает FileVersion установленного
   лаунчера со своей версией, а `bundle/current.txt` — с `bundle-version.txt` в своём ZIP.
   Если обе версии равны, показывает меню работающего трея; если трея нет — запускает установленную копию.
   Если хотя бы одна часть старее, спрашивает об откате, кнопка по умолчанию — «Нет».
3. Для новой версии отправляет работающему экземпляру `--identify` и `--exit` по именованному каналу.
   Ожидает освобождения mutex до 20 секунд. Только при неудаче проверяет путь процесса и завершает
   его дерево `taskkill /T /F`, затем ждёт ещё до 10 секунд. Для прежнего одностороннего IPC есть
   поиск процесса по точному пути установленного EXE. Чужие процессы по одному имени не завершаются.
4. Проверяет ZIP (размер, SHA256, пути, состав), распаковывает в `bundle/<версия>.tmp`, проверяет
   `binaries`, выполняет Windows PowerShell 5.1 `selftest.ps1 -Home <home>`, затем переименовывает
   каталог в `bundle/<версия>`. Ошибка самопроверки оставляет установленную версию; её трей запускается снова.
5. Сохраняет прежний EXE как `RemoteAgents.previous.exe`, копирует себя в установочный путь,
   записывает `exe-upgrade.json`, сохраняет старую версию модулей в `previous.txt` и атомарно переключает
   `current.txt`. Запускает установленный EXE с `--tray --home <home> --after-update`.
   Существующий `config.json`, `secrets/`, `state/` (включая память путей), `logs/` не заменяются.
6. Ожидаемые блоки подтверждают здоровье событиями, затем `health.accepted` принимает бандл и EXE.
   Аварийный выход процесса, `UpdateFailed`, crash-loop или предохранитель отсутствия прогресса возвращают прежние
   бандл и EXE; плохая версия записывается в `bad.txt`. Обновление только лаунчера проходит ту же доску
   готовности и независимое наблюдение прежним EXE. Возраст файла и тик трея в решении не участвуют.

OTA использует проверку здоровья новым лаунчером и независимое наблюдение прежним EXE. Первичная установка
из скачанного EXE использует существующий путь `UpgradeInstaller.Apply`; её Windows-приёмка проводится отдельно.

В обычном home первая установка и служебный `--install` запускают трей с мастером. Запись Run лаунчера
появляется на шаге «Итог» после живой проверки связи. `--uninstall` снимает Run, останавливает трей
и выполняет `build/Uninstall.ps1` (убирает значок Disk в Проводнике). Пользовательские файлы сохраняются.
Рабочая установка допускается только в основном `%LOCALAPPDATA%\RemoteAgents`. `--tray --home <тест>`
не меняет Run/задачи.

Прежнее решение «только вручную» отменено владельцем 16.11.2026. `update.intervalMin` — устаревшее поле;
используется `intervalHours` (1–168). Уже записанный `enabled=false` требует разового явного включения:
он сохраняется как выбор владельца, автоматически отличить его от старого значения по умолчанию нельзя.

```powershell
.\RemoteAgents.exe                       # установка или обновление из скачанного EXE
.\RemoteAgents.exe --install              # открыть мастер первой настройки
.\RemoteAgents.exe --tray
.\RemoteAgents.exe --restart-components
.\RemoteAgents.exe --logs
.\RemoteAgents.exe --rollback             # локальный откат бандла
.\RemoteAgents.exe --exit
.\RemoteAgents.exe --uninstall
```

`--home <каталог>` изолирует данные, mutex и IPC по SID пользователя и хешу абсолютного пути.
Для обычного home сохранено имя mutex прежнего лаунчера. Mutex — Global, IPC закрыт ACL пользователя.
Это позволяет тестам работать рядом с основным треем и мостом. Явный `--tray --home <каталог>` запускает
трей прямо из заданного EXE, без установки и Run; это вход для разработки и smoke-тестов.

## Компоненты трея

`disk` запускает `%LOCALAPPDATA%\RemoteDisk\tray\syncthingtray.exe` с настройками из соседнего
`syncthingtray.ini`. Лаунчер перезапускает процесс при завершении; REST-опросов папок и собственного
меню управления синхронизацией нет. Состояние передачи показывает Syncthing Tray.

`control` запускает только `control/Control.Status.ps1`. Он читает PID, процесс Start-WindowsControl,
последние события control.log, проверяет живой дочерний SSH `-R` с установленным TCP-соединением.
Историческая строка `bridge.connected` без процесса/сокета не даёт `ok=true`. В JSON есть `processAlive`
и `lastContact`; отсутствие инвентаризации отображается как «нет данных». Команды меню управления
вызывают существующие `-Install/-Uninstall`, оставляя монитор работать и показывать выключенное состояние.

## Компоненты и повышенные права

`components.json` — массив или объект с `components`, `menu`, `binaries`:

```json
{
  "schema": 1,
  "components": [{
    "name": "vpn", "title": "VPN (весь трафик)", "exe": "powershell.exe",
    "args": ["-NoProfile", "-NonInteractive", "-ExecutionPolicy", "Bypass", "-File", "{bundle}\\transport\\Vpn.Tun.ps1", "-Home", "{home}"],
    "cwd": "{bundle}", "restart": "never", "healthFile": "status/vpn.json",
    "healthMaxAgeSec": 180, "enabledByDefault": false, "critical": false,
    "commandManaged": true, "stopFile": "state/vpn.stop"
  }],
  "menu": [], "binaries": []
}
```

`name` уникален: `[a-z][a-z0-9_-]{0,63}`. Подстановки `{bundle}`, `{home}`, `{pid}` и переменные Windows
доступны в exe/args/cwd/menu. `{pid}` — PID обычного лаунчера, включая повышенные компоненты.
`restart=always` повторяет запуск с паузами 5, 10, 20, 40, 60 секунд; после 120 секунд здоровья пауза
сбрасывается. `never` означает одну попытку. `menu` — массив `{"title":"…","exe":"…","args":[]}`.

Обычный процесс создаётся приостановленным, включается в Job Object с KILL_ON_JOB_CLOSE и возобновляется.
Выход, выключение, перезапуск и падение лаунчера завершают принадлежащее ему дерево.

`commandManaged=true` запрещает автоматический запуск процесса: модуль управляется явными командами,
а наблюдение использует его свежий статус. Необязательный `stopFile` — относительный флаг остановки в home;
он записывается при выходе/перезапуске. VPN управляется службой-помощником — [VPN-LAN.md](VPN-LAN.md).

Для обычного компонента при `elevated=true` сам трей не повышается. При первом явном включении пользователь видит объяснение,
а Windows запрашивает UAC для `schtasks /Create` с наивысшими правами. Задача привязана к текущему
пользователю (InteractiveToken / HighestAvailable), home и компоненту, не содержит триггеров и паролей.
Она запускает установленный `RemoteAgents.exe --elevated-component <name> --home <home>`;
повышенный помощник запускает только указанный в текущем components.json компонент в отдельном Job Object.
PID/время старта родителя сверяются, помощник наблюдает родителя и собственный stop-флаг;
после выхода/остановки родителя закрывает дерево. Запросы и флаг — `state/elevated/`.
При штатном выключении сначала даётся до пяти секунд на остановку, затем вызывается остановка задачи.
Повторные запуски и обновления используют ту же задачу и стабильный путь установленного EXE.
На автозапуске отсутствующая задача не создаётся молча: компонент остаётся без подтверждённого здоровья;
для создания нужно явно выключить/включить его в трее. Отмена UAC не включает компонент.
Для получения административных прав principal должен иметь соответствующие права Windows.

Здоровье требует живого процесса (для elevated — выполняющейся задачи; для commandManaged — свежего enabled=true), свежего файла,
mtime после старта и `ok:true`. `healthMaxAgeSec` по умолчанию 90. Отсутствующий summary — «нет данных».
Пример: `{"ok":true,"summary":"Путь проверен","updatedAt":"2026-11-09T12:00:00Z"}`.
`status/launcher.json` содержит версии, pending/running/ok и массив name/title/enabled/critical/alive/ok/summary/pid;
для задач PID компонента не заявляется. Журнал хранит коды событий без аргументов, секретов и исключений.

## SSH-источник автообновления

Пример и схема — `app/launcher/config.example.json`, `config.schema.json`.

```json
{"schema":1,"version":1,"components":{},"update":{
  "enabled":true,"auto":true,"intervalHours":6,
  "sshExe":"ssh.exe",
  "args":["-F","C:\\path\\config","user@example.invalid"],
  "remoteDir":"~/.local/share/remote-agents/dist"
}}
```

Если args отсутствует, берётся действующий transport.profilePath; для старых установок без него — первый отсортированный `ssh-profiles/*/project-connections/*/ssh-transport.json`.
Явный `args:[]` запрещает импорт.
Лаунчер добавляет BatchMode/StrictHostKeyChecking, не читает закрытые ключи и не выполняет интерактивный вход.
`viaLocalPort:2222`, `hostKeyAlias` позволяют использовать локальный transport, сохраняя проверку ключа сервера.
Явные update.args используют собственный viaLocalPort.
Удалённые команды — только `cat -- <remoteDir>/manifest.json` и архив, с POSIX quoting; текст приводится к LF.
Таймаут команды — 300 секунд, selftest — 120 секунд.

Manifest: `{version,file,sha256,size,minLauncher,configSchema:1,product,launcher:{version,sha256}}`.
Для OTA обязательны metadata схемы, новый EXE и `selftest.ps1`. Новый EXE сверяет действующий конфиг,
затем выполняется прежняя самопроверка Windows PowerShell 5.1. SHA-256 и FileVersion EXE проверяются
перед переключением, а не после принятия бандла. `configSchema` описывает возможности новой сборки;
более высокий номер сам по себе не означает отказ: окончательное решение принимает её код.
`binaries: [{url:"https://…",sha256:"<64 hex>",path:"tool.exe"}]` остаётся прежним механизмом
проверенного кэша. Сторонние бинарники из первоначального EXE остаются в транспортном кэше.

## Выпустить новую версию

После слияния проверенной ветки, commit/push в main и выбора своего SSH-алиаса:

```bash
flock --close /tmp/heavy-tests.lock ./build/release.sh <ssh-alias> '~/.local/share/remote-agents/dist'
```

### Каналы выпусков (решение владельца 21.11.2026, поправка конституции §7а)

Поддерживаются два изолированных канала выпуска:
1. **Основной канал (`main`, по умолчанию):**
   - Вызов: `./build/release.sh <ssh-alias>` (или `--channel main`)
   - Источник: ветка `main` с HEAD в `origin/main`, чистое дерево.
   - Продукт: `RemoteAgents` (`RemoteAgents.exe`, `-p:UpdateChannel=main`).
   - GitHub: релиз `main-latest`.
   - Сервер: каталог `~/.local/share/remote-agents/dist`.
2. **Тестовый канал (`test`):**
   - Вызов: `./build/release.sh --channel test <ssh-alias>`
   - Источник: ветка `int/vpn-master` (HEAD = `origin/int/vpn-master`), чистое дерево.
   - Продукт: тот же `RemoteAgents` (`RemoteAgents.exe`: имя EXE, продукт, службы, адаптер, порты прежние).
     Отличается только канал обновления: сборка с `-p:UpdateChannel=test` (символ `UPDATE_CHANNEL_TEST`,
     версия с меткой `-test`) берёт обновления из `~/.local/share/remote-agents/dist-test`, а `remoteDir`
     из `config.json` игнорирует (иначе настроенный конфиг вернул бы сборку на основной `dist`).
   - Тестовая сборка устанавливается ВМЕСТО основной и обновляется из `dist-test`. Возврат на основную —
     установить основной `RemoteAgents.exe` (из `main-latest`); он снова обновляется из `dist`.
   - Выходная папка: `build/out-test`.
   - GitHub: prerelease `test-latest` (ассеты перезаписываются).
   - Сервер: каталог `~/.local/share/remote-agents/dist-test`.
   - Изоляция назначения: разрешён только буквальный путь `~/.local/share/remote-agents/dist-test`;
     абсолютные пути, завершающий `/`, `/.` и пути с `..` отвергаются до сборки и публикации.
     Скрипты test-канала используют только тег `test-latest` и не пишут в `dist` или `main-latest`.
   - Если `origin/int/vpn-master` отсутствует, выпуск запрещён; локальная ветка его не заменяет.

Для локальной сборки EXE тестового канала:
```bash
./build/build-exe.sh --channel test
```

Микро-тесты каналов:
```bash
./build/test-release-channel.sh
```

Команда требует ветку и коммит выбранного канала, один раз вызывает `build/build-exe.sh`
и получает один EXE (`RemoteAgents.exe`) и `bundle.zip`
с UTC-версией `yyyyMMdd.HHmmss-<git hash>`. Начальный архив с закреплёнными бинарниками —
`initial-bundle.zip`; OTA-архив `bundle.zip` их не содержит.
`release-github.sh` проверяет коммит, EXE и архив по `release-info.json`, заменяет EXE и метаданные
в релизе выбранного канала, скачивает оба файла обратно и сверяет SHA-256. Затем поток tar
через SSH с проверкой ключа хоста передаёт подготовленный dist. На сервере нужны только
Python 3, POSIX flock, место под текущую/новую сборку и права рабочего пользователя.
Архив и EXE проверяются до публикации manifest; manifest заменяется последним атомарно,
после чего SHA-256 и JSON читаются с диска ещё раз. Номер версии неизменяем: другой архив
с тем же номером запрещён. Два внешних хранилища не образуют общую атомарную транзакцию:
при частичном сбое нужно повторить публикацию той же подготовленной сборки и сверить оба источника:

```bash
build/release.sh <ssh-alias> --prepared build/out
build/release.sh --channel test <ssh-alias> --prepared build/out-test
# Явное назначение также допустимо перед --prepared:
build/release.sh --channel test <ssh-alias> '~/.local/share/remote-agents/dist-test' --prepared build/out-test
```

Повтор использует уже созданный `release-info.json` и требует тот же HEAD выбранного канала.
Лишние аргументы и `--prepared` без папки завершаются кодом 2.
`DOTNET` задаёт SDK, `REMOTEAGENTS_BUILD_OUT` — выходную папку (по умолчанию `build/out`
для main и `build/out-test` для test; для test назначения внутри `build/out` и `release` запрещены); для тестов сборки доступен `REMOTEAGENTS_BUNDLE_VERSION`.
`build/build-exe.sh` только собирает, ничего не выкладывает. Только main копирует EXE и
`Start.cmd` в версионируемый каталог `release/`; test хранит все артефакты в своей выходной папке.
`build/publish.sh <zip> <dist> --launcher <exe>` переиспользует прежний атомарный издатель; реальные назначения
также требуют main. Временные назначения под `/tmp` разрешены для изолированных тестов упаковки.
Тексты при упаковке приводятся к LF, PS1 получают UTF-8 BOM для PS 5.1. Секреты и личные профили не входят в ZIP.

Ручной `--rollback` возвращает previous.txt и перезапускает компоненты; во время скачивания недоступен.
Без работающего лаунчера: завершить его, проверить прежний каталог, вернуть его номер в current.txt,
удалить pending.json; при необходимости вернуть RemoteAgents.previous.exe. Выпуск исправления — новый номер.

## Проверки

```bash
./app/launcher/tests/run.sh
./build/build-exe.sh
file build/out/RemoteAgents.exe
sha256sum build/out/RemoteAgents.exe
```

Linux проверяет упаковку/публикацию, LF/BOM и CRLF-вход, хеши, minLauncher, безопасную распаковку,
selftest, активацию, приёмку/отказ по ручным событиям, откат, сохранение настроек/state/secrets/logs,
обновление только EXE, явное понижение версии, честность свежего/устаревшего статуса и сборку/publish net48.
JSON-адаптер System.Text.Json используется только Linux-стендом.

Микро-тест H2 без реального времени, ожиданий и проверки таймеров:

```bash
timeout 120 dotnet run --project app/launcher/tests/PortableTests.csproj -p:UpdateHealthTests=true -nodeReuse:false -p:UseSharedCompilation=false
```

Ручные события проверяют источник `no-network`, crash-loop/сброс на `block.ready`, приёмку последним
блоком, аварийный и штатный выход процесса, `UpdateFailed` и сигнал предохранителя.
Границы `FuseExpired` проверяются только фальшивыми часами; проверяется сохранение `lastHealthUtc`,
повтор после ошибок чтения квитанции, смена PID/времени старта и запрет повторного отвергнутого EXE. Проверяется возврат байтов прежнего
EXE, бандла, `bad.txt` и сохранность пользовательского state. Windows-хэндлы требуют отдельной
проверки на тестовой программе; компиляция и микро-тест её не заменяют.

На настоящей Windows, без сети, автозапуска, изменения основного home или запуска TUN:

```powershell
$exe=(Resolve-Path '.\build\out\RemoteAgents.exe').Path
$test=Join-Path $env:TEMP ('RemoteAgents-upgrade-'+[guid]::NewGuid().ToString('N'))
$p=Start-Process $exe -ArgumentList ('--selftest-upgrade "'+$test+'"') -PassThru
# Дождитесь завершения изолированного теста.
$p.WaitForExit()
$p.ExitCode
Get-Content (Join-Path $test 'selftest-upgrade-result.json') -Raw
```

Ожидаются exit 0 / ok=true. Тест создаёт установку с синтетическим бандлом, запускает настоящий
изолированный трей, останавливает его по IPC/mutex, применяет общий production-код установки из папки
`downloaded`, проверяет копирование EXE и сохранение данных. Запускает обновлённый трей, проверяет отказ
selftest и откат по вручную поданному `UpdateFailed` с повторным запуском трея.
Использует тот же EXE в роли прежнего образа; сравнение разных версий покрывает отдельный тест ядра.
Heartbeat синтетический и не подтверждает серверную связь. Рабочие home, мост, VPN и HKCU Run не меняются.
Результаты остаются в указанном каталоге. Для общего ядра доступен `--selftest-update <каталог>`.

`app/launcher/tests/windows-smoke.ps1 -Exe <exe>` отдельно проверяет IPC, рестарт, старение/восстановление
health и остановку дочернего дерева. Проверка UI, UAC/планировщика, обновления реального скачанного релиза,
реального SSH и интеграции модулей требует Windows-приёмки. Живой TUN на ноутбуке с MCP-сессиями не тестировать.


## Мастер и настройки

Действующее описание сети: [Локальные сети и VPN](VPN-LAN.md).

Шаги вызывают один `build/Wizard.ps1` / `Wizard.Common.ps1` и при первом запуске, и из
«Настроек». Факт сохранения настроек не служит проверкой здоровья. Кнопка итога повторно
опрашивает SSH, Syncthing, Happier и мост. Журнал событий — `logs/setup.log`; подробные журналы модулей
остаются на своих местах. Пароль SSH вводится в поле общего окна и передаётся одноразовым askpass без второго окна, файлов и argv.

1. **Сервер.** Существующий профиль проверяется настоящим SSH. Серверный скрипт инвентаризации
   проверяет REST Syncthing, наличие Happier, файлов моста и каталога, доступность user systemd.
   Файлы моста обнаруживаются отдельно от живой связи с конкретным ПК. Отметка установки
   разрешает недостающие компоненты: существующие `server-disk.sh`, `accounts/bootstrap.sh`
   и публичные helpers. Работающие службы и чужие аккаунты не пересоздаются.
   Требуются Linux/Python 3, curl, tar, flock и systemd. Вход от root подготавливает рабочего пользователя и linger;
   для ранее настроенного пользователя без user manager показаны `sudo loginctl enable-linger <пользователь>` и
   `sudo systemctl start user@<uid>.service`, выполняемые администратором сервера.
   Смена сервера/логина подготавливает новый профиль и сбрасывает зависимые проверки.
   До успешного preflight действует текущая связь. Для Disk требуется явное решение
   о новом подключении в пустую папку либо сохранении файлов без синхронизации.
2. **Связь.** «Далее» и «Подробнее…» читают серверный каталог с живым сообщением о загрузке. Таблица в подробностях редактирует
   entries/hops/relays/cdn, включая включение/отключение; для входа/SSH-узла используется
   SSH-алиас, для relay — хост/порт, для CDN — домен/entry. Ключи, known_hosts и SSH-алиасы
   промежуточных серверов остаются локальными: один публичный каталог не переносит ключи
   на новый компьютер. Существующие локальные configPath сохраняются в локальной конфигурации.
   Неотмеченное «для всех компьютеров» сохраняет overlay только здесь. Общая запись использует
   compare-and-swap: изменения другого компьютера требуют обновления списка, а не затираются.
   На работающем транспорте сначала выполняется preflight на отдельных портах, затем
   регистрируется независимая задача отката на три минуты. Успех требует свежего `ok`,
   **совпадающей `configRevision`** и настоящего SSH через новый вход. Иначе восстанавливается
   прежняя секция transport; несетевые настройки остаются. Первая настройка запускает
   транспорт под надзором трея, без обязательной локальной установки Disk.
3. **Диск.** Корень по умолчанию `%USERPROFILE%\Disk`, выбранная база хранится в RemoteDisk/base.txt.
   Мастер устанавливает Syncthing и Syncthing Tray и знакомит компьютер с сервером один раз.
   Сервер предлагает все свои папки; человек принимает нужные в Syncthing Tray. Поле `disk.folders`
   позволяет разово принять перечисленные ID через локальный REST. Без поля автоматического приёма нет.
   Обновление сохраняет движок, `config.xml`, принятые папки и файлы. Одноразовая очистка снимает старые
   меню и значки Проводника; закрепление Disk в левой панели остаётся.
4. **Happier.** Публичный список содержит имена и ID аккаунтов. Метка хранится на сервере
   отдельно от credentials, в `~/.config/remoteagents/accounts/<id>.json`. Старый аккаунт без
   метки показан как «Без имени <короткий ID>»; владелец может дать имя после проверки ключа.
   При выборе существующей строки сервер сверяет ID, вычисленный из ключа и API, до входа.
   Чужой аккаунт нельзя присвоить выбором строки. Ключ проходит только через secrets и SSH stdin;
   неудачная попытка восстанавливает прежний локальный ключ, новый остаётся в secrets для восстановления.
   API/Web берутся из пользовательского конфига, ввода или необязательного серверного
   `~/.config/remoteagents/services.json` с полями serverUrl/webappUrl. В EXE нет адреса Happier
   по умолчанию. Для телефона используется тот же recovery key.
   Окно: «У меня уже есть аккаунт» (секретный ключ + имя) или «Создать новый аккаунт» (имя; ключ
   создаётся на ПК в формате base32 по 5 символов и показывается один раз с кнопкой «Скопировать»).
   API/Web и «Получить аккаунты» — за «Подробнее…»; «Открыть Happier» — после подключения.
5. **Мост.** Независимые флаги включения и разрешения shell. Разрешение учитывают и executor,
   и серверная запись этого компьютера; по умолчанию shell запрещён. Включение подтверждается
   аутентифицированным round trip. Выключенный по выбору мост не блокирует принятие миграции.
6. **VPN.** См. [VPN-LAN.md](VPN-LAN.md).
7. **Итог.** Отдельные результаты разделов, причины ошибок, подсказки, локальный журнал.
   Успешная установка диска не объявляется законченной передачей. Итог требует живой проверки
   связи и моста; второй запрос итога проверяет состояние заново.

### Серверный каталог связи

`transport/server-transport-catalog.py get` выдаёт и при отсутствии создаёт закрытый файл
`~/.config/remoteagents/transport-catalog.json` текущего SSH-пользователя:

```json
{"schema":1,"entries":[],"hops":[],"relays":[],"cdn":[]}
```

Формат строк соответствует публичным полям transport: name/enabled, ssh/kinds для entries,
ssh/hostKey для hops, host/port для relays, domain/entry/path для cdn. Секретные и неизвестные
поля, локальные пути, ссылки, недопустимые имена и дубликаты отклоняются. `put` принимает
через stdin `{expected:<прочитанный каталог>,catalog:<новый>}`; запись атомарна и защищена flock.
Серверные SSH-алиасы должны быть настроены на новом ПК пользователем; закрытые ключи не копируются.
Никаких узлов владельца в бандле нет.

### Первое слияние и конфликты: Яндекс.Диск / Syncthing

В официальной справке [Яндекс.Диска 3.0](https://yandex.ru/support/yandex-360/customers/disk/desktop/windows/ru/sync-how-works.html)
описан случай двух разных одноимённых файлов после офлайн-работы: один переименовывается
с суффиксом `(2)`, обе версии сохраняются. Правило выбора стороны справка не определяет.
[Восстановление после переустановки](https://yandex.ru/support/yandex-360/customers/disk/desktop/windows/ru/installation)
повторно синхронизирует оставшиеся файлы, но полного алгоритма слияния произвольной заполненной
папки не публикует. У [Диска 4.0](https://yandex.ru/support/yandex-360/customers/disk/4/windows/ru/synchronization/folder)
при выборе расположения создаётся вложенная папка; обещать универсальную эквивалентность 4.0 нельзя.

RemoteAgents сохраняет проверенный принцип сохранения версий средствами Syncthing:
[новые папки сливаются](https://docs.syncthing.net/users/faq.html#i-am-seeing-the-error-message-folder-marker-missing-what-do-i-do),
[Send & Receive](https://docs.syncthing.net/users/foldertypes.html) передаёт изменения в обе стороны,
а [независимые изменения одного файла](https://docs.syncthing.net/users/syncing.html#conflicting-changes)
сохраняются как `.sync-conflict-<date>-<time>-<device>`.
Это сохранение вариантов, а не содержательное слияние текста. На управляемых папках
`maxConflicts=-1` не ограничивает число конфликтных копий; staggered versioning с `maxAge=0`
сохраняет историю замен без возрастного удаления. Обе исходные версии при первом слиянии
проверяет `disk/test-wizard-merge.py` с настоящими Syncthing 2.1.7. Слиянием, конфликтами и удалениями
в принятых папках управляет Syncthing; его предупреждения и состояние видны в Syncthing Tray.

Изменение DNS/check URL включённого VPN требует сначала выключить его и дождаться очистки
наших маршрутов. Повторное включение проходит обычный preflight и watchdog; чужие маршруты не меняются.

Прежние изменения выбора и переноса описаны в историческом [TASK-M.md](TASK-M.md).
Приёмку на настоящем Windows-компьютере проводят отдельно.

## Disk в Проводнике

Отдельный пункт «Disk» в левой панели Проводника, как у Яндекс Диска и OneDrive, ведёт в корень Disk
(`Get-DiskBase`). Подпись — имя папки корня. Модуль `disk/Disk.NavPane.ps1`: `Install-DiskNavPane`,
`Remove-DiskNavPane`, `Test-DiskNavPane`. Свой код нужен потому, что у Windows нет команды для
закреплённой папки оболочки; используется документированная регистрация делегированной папки
(`{0E5AAE11-A475-4c5b-AB00-C66DE400274E}`, `TargetFolderPath`).

- Только HKCU, без прав администратора и HKLM: `Software\Classes\CLSID\{5D8A825B-EDEA-4B5E-97FC-96ABDC8A78E9}`
  (и копия в `Wow6432Node` для 32-битных диалогов на 64-битной Windows), `Explorer\Desktop\NameSpace\{GUID}`,
  `HideDesktopIcons\NewStartPanel` `{GUID}=1` (не показывать на рабочем столе). GUID постоянный для продукта.
- Установка идемпотентна и перезаписывает все значения, поэтому смена корня переносит пункт. После записи
  `SHChangeNotify(SHCNE_ASSOCCHANGED)`; перезапуск Проводника не требуется. `Test-DiskNavPane` сверяет все значения:
  `installed` — запись есть, `ok` — всё совпадает с ожидаемым корнем.
- Ставится после успешного шага мастера «Диск»; ошибка пишется в `RemoteDisk/install.log` и шаг не ломает.
  `Set-DiskBase` обновляет уже существующий пункт, но не создаёт удалённый.
- Удаляется `Install-RemoteDisk.ps1 -Uninstall` и `RemoteAgents.exe --uninstall` (`build/Uninstall.ps1`).
- Linux-тест `app/launcher/tests/test-navpane.ps1` подменяет четыре функции доступа к реестру хранилищем
  в памяти. Живая проверка в Проводнике Windows ещё не выполнена.
