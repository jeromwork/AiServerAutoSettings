# Лаунчер RemoteAgents

`app/launcher/RemoteAgents.Launcher.csproj` — WinForms / .NET Framework 4.8 для Windows 10/11.
Выпуск — `RemoteAgents.exe` и `RemoteVPN.exe` из одного проекта, каждый с собственным вшитым ZIP: рядом не нужны DLL, SDK или установщик.
Сборка выполняется на Linux. JSON читает встроенный `JavaScriptSerializer`; NuGet reference assemblies
нужны только при сборке. Свой код отвечает за трей, процессы и транзакцию обновления;
сеть, VPN, диск и мост остаются модулями.

Задача G реализована в коде; Linux-проверки перечислены в разделе «Два EXE».
Приёмка на Windows ещё не выполнена. `--tray --home <тест>` не запускает мастер и не регистрирует Run.

## Два EXE

Решение владельца от 10.11.2026; эта секция заменяет прежний план одного EXE.

| | RemoteAgents.exe | RemoteVPN.exe |
|---|---|---|
| Компоненты | transport, disk, control | только командный VPN / Vpn.Tun.ps1 |
| Бандл / откат | `bundle/`, `RemoteAgents.previous.exe` | `vpn-bundle/`, `RemoteVPN.previous.exe` |
| Mutex и IPC | `RemoteAgents.Launcher.<SID>[.<Home hash>]` | `RemoteVPN.Launcher.<SID>[.<Home hash>]` |
| HKCU Run | RemoteAgents | RemoteVPN |
| Статус и журнал | `status/launcher.json`, `logs/launcher.log` | `status/vpn-launcher.json`, `logs/vpn-launcher.log` |

Общий Home — `%LOCALAPPDATA%\RemoteAgents`: один `config.json`, `secrets/`, SSH-профили.
`Product` определяется при сборке, переименование EXE не меняет его роль. В обоих вариантах один C#
проект / .NET Framework 4.8, зависимости рантайма рядом с EXE не нужны. Инициализация config и
переключение компонентов используют тот же общий mutex, что Edit-Transport и Set-VpnEnabled;
секция другого приложения перечитывается перед записью. VPN не пишет намерение восстановления
лаунчера RemoteAgents и не вызывает миграцию/удаление его компонентов.

**Зависимость VPN.** Выбран более простой вариант: RemoteVPN не запускает второй transport.
При включении требуется свежий `transport.ok` из работающего RemoteAgents. Без него выводится
сообщение об установке/запуске RemoteAgents. Включение VPN только из меню с явным UAC;
Run, повторный запуск и обновление его не включают. Выход RemoteVPN останавливает только его TUN;
выход RemoteAgents не завершает RemoteVPN, но потеря проверенного транспорта выключает TUN средствами
Vpn.Tun.ps1. При обновлении выключенного VPN здоровье означает успешную самопроверку модулей;
запуск TUN/UAC для подтверждения обновления не требуется. Цвет VPN зелёный только при свежем `on/ok`.
Обновление из нового EXE и локальный откат независимы; SSH-обновление оставлено только в RemoteAgents.

**Первый двойной щелчок.** Установка новой машины проходит через `FirstInstall.cs` и
`build/FirstInstall.ps1`. Нет профиля — окно адреса сервера и пользователя, затем прежние окна
OpenSSH проверки host key и пароля. `setup-vps-ssh.ps1 -SetupOnly` использует существующее создание
ключа/authorized_keys и проверку входа; экспортирует обычный ssh-transport.json без меню проектов.
Пароль не передаётся в argv, C#, config или файл: его получает прежний SSH_ASKPASS.
Если профиль уже есть (общий config, ssh-profiles или RemoteDisk/profile.txt), окно не показывается;
перед продолжением выполняется настоящий SSH `true` с таймаутом 15 секунд.
Один пустой config, созданный RemoteVPN, ещё не является настроенным подключением.

Для отсутствующих компонентов вызывается `Setup-All.ps1 -LauncherSetup`: прежние
`Install-RemoteDisk.ps1` и `Start-WindowsControl.ps1 -Install`; ошибка дочернего шага теперь
останавливает автоматический сценарий. Затем выполняется `Migrate.ps1` с прежним независимым
watchdog и проверкой связи. При наличии старой полной установки используется сразу миграция.
Отмена окна сохраняет возможность повторить двойным щелчком; после отката он также повторяет установку.
`--install` остаётся служебным. Рабочая установка, включая Run VPN, разрешена только в основном Home.

«Чистая машина» здесь означает Windows без старой локальной установки. Требования прежних
серверных установщиков сохраняются: Ubuntu 24.04 x86_64, проверенный SSH, рабочий пользователь
для диска и доступный серверный канал sing-box/VLESS (его настройки читает server-disk.sh).
Если первоначальный вход root, Setup-All использует существующего рабочего пользователя `remoteagents`.
Мастер не разворачивает sing-box/VLESS и не создаёт пользователей на пустом VPS. Отсутствие этих
предпосылок — ошибка установки, а не готовность. Секреты и endpoints берутся из пользовательских
профилей/серверной конфигурации, личных доменов/IP в новом коде нет.

**Одна серверная иконка.** Disk.Status больше не запускает GUI `syncthingtray --wait`.
Используется встроенная команда того же бинарника:
`syncthingtray.exe syncthing serve --home <RemoteDisk/state> --no-browser --no-restart`.
Надзор держит один engine mutex, проверяет точный exe/state, не запускает второй экземпляр при
чужом владельце state и завершает свой процесс при выходе. Миграция сохраняет старый Run до его
удаления, останавливает GUI раньше headless; независимый recovery содержит Disk.Engine.ps1 и путь state хранится в снимке, вне изменяемого config.
Откат сначала останавливает лаунчер/engine, затем восстанавливает прежний Run и трей.
Обновление уже принятой старой миграции также останавливает оставленный ею GUI по сохранённому state.
В нашем меню доступны папка Disk, веб-интерфейс Syncthing, выбор добавляемой папки и паузы.
В момент работы прежнего установщика до передачи лаунчеру старый трей может кратковременно появиться.

**Чужие VPN.** Find-VpnConflicts считает только поднятый TUN/Wintun/WireGuard/TAP
(кроме OpenVPN/Tailscale/нашего), чужие split-default и default через виртуальный адаптер.
Процессы — отдельная подсказка `processHints`; служба Amnezia без туннеля и старый channel/sing-box
не блокируют включение. Happ `happ-default-tun` / SocksTunnel и `happ-xray` с default выявляются.
Приложение не останавливает чужой VPN; окно выбора сохранено.

**Надзор моста.** SSH уже содержал ServerAliveInterval=15, ServerAliveCountMax=3 и
ExitOnForwardFailure=yes. Они обнаруживают потерю SSH/отказ первоначального bind, но не доказывают
работу reverse forwarding. Прежний цикл после connected ждал только смерти процесса — найденный
пробел в контроле; точную внешнюю причину случая 06:31–14:46 по одному журналу установить нельзя.
Теперь broker каждые 15 секунд делает аутентифицированный `status` через серверный TCP-проброс до
executor и проверяет привязку. Таймаут ответа 5 секунд, три отказа завершают сеанс, старый RetryForever
переподключается. PowerShell непрерывно читает heartbeat, при отсутствии успеха 75 секунд пересоздаёт SSH.
Обновляется атомарный `heartbeat.json` с PID и UTC; исторический connected больше не даёт зелёный статус.
Control.Status принимает только heartbeat текущего PID моложе 40 секунд. После трёх плохих наблюдений,
с начальной отсрочкой 90 секунд и интервалом между перезапусками 120 секунд, он переустанавливает
свою managed-копию через существующий Start-WindowsControl -Install. Старый режим без лаунчера
сохраняет RetryForever и получает тот же контроль reverse forwarding.

**Доставка и проверки.** `build/build-exe.sh` собирает оба варианта в `build/out/` и копирует
`RemoteAgents.exe`, `RemoteVPN.exe`, трёхстрочный `Start.cmd` в корневой `release/`.
Git-исключение `*.exe` отменено именно для release. Корневого `.stignore` в worktree нет;
канонический `disk/stignore.txt` исключает build, но не release и не EXE. На принимающем компьютере
личные дополнительные правила Syncthing нужно проверить отдельно. Start.cmd использует `start`:
постоянного окна консоли нет, при двойном щелчке возможна краткая вспышка cmd.

Linux-тесты используют фиктивные установки/инвентарь, loopback broker и отдельные настоящие
Linux Syncthing peers. Они не подтверждают PS 5.1, HKCU, ScheduledTasks, Job Objects, UAC и Wintun.
Оба `--selftest-upgrade <временный каталог>` расширены проверкой отдельного продукта и сохранности
EXE/указателя бандла соседа, включают настоящий 120-секундный сценарий отката; выполнить их должен
владелец на Windows. Результаты: `selftest-upgrade-result.json` / `selftest-upgrade-vpn-result.json`.
Фактические числа Linux-проверок и сценарий приёмки — в [PLAN-EXE.md](PLAN-EXE.md#два-exe-задача-g).

## Установка и ручное обновление

1. Пользователь скачивает новый `RemoteAgents.exe` и запускает из любой папки без аргументов.
2. EXE находит `%LOCALAPPDATA%\RemoteAgents\RemoteAgents.exe`, сравнивает FileVersion установленного
   лаунчера со своей версией, а `bundle/current.txt` — с `bundle-version.txt` в своём ZIP.
   Если обе версии равны, показывает меню работающего трея; если трея нет — запускает установленную копию.
   Если хотя бы одна часть старее, спрашивает об откате, кнопка по умолчанию — «Нет».
3. Для новой версии отправляет работающему экземпляру `--identify` и `--exit` по именованному каналу.
   Ожидает освобождения mutex до 20 секунд. Только при неудаче проверяет путь процесса и завершает
   его дерево `taskkill /T /F`, затем ждёт ещё до 10 секунд. Для прежнего одностороннего IPC есть
   поиск процесса по точному пути установленного EXE. Чужие процессы по одному имени не завершаются.
4. Проверяет ZIP (размер, SHA256, пути, состав), распаковывает в `bundle/<версия>.tmp`, проверяет
   `binaries`, выполняет Windows PowerShell 5.1 `selftest.ps1 -Home <home>`, затем переименовывает
   каталог в `bundle/<версия>`. Ошибка самопроверки оставляет прежнюю установку; старый трей запускается снова.
5. Сохраняет прежний EXE как `RemoteAgents.previous.exe`, копирует себя в установочный путь,
   записывает `exe-upgrade.json`, сохраняет старую версию модулей в `previous.txt` и атомарно переключает
   `current.txt`. Запускает установленный EXE с `--tray --home <home> --after-update`.
   Существующий `config.json`, `secrets/`, `state/` (включая память путей), `logs/` не заменяются.
6. Критичные компоненты должны подтвердить здоровье за 120 секунд. Иначе возвращаются предыдущий бандл
   и EXE, трей перезапускается, плохой бандл записывается в `bad.txt`. Для обновления только лаунчера
   также действует 120-секундная проверка и возврат прежнего EXE. Дедлайн хранится на диске и переживает
   перезапуск; на первом тике после истечения срока выполняется откат.

Это проверка здоровья работающим лаунчером: если сам EXE вообще не может запуститься или ОС не запускает
его после аварии, независимого watchdog для EXE пока нет. При восстановлении запуска сохранённый дедлайн
снова проверяется. Сетевые изменения самого VPN обязаны иметь собственный независимый откат модуля.

В обычном home первая установка и служебный `--install` вызывают описанный выше мастер/переход. Запись Run лаунчера
появляется после проверки нового транспорта и передачи компонентов. `--uninstall` выполняет тот же
`Rollback.ps1` сразу, включая уже подтверждённую установку. Пользовательские файлы сохраняются.
Рабочий переход допускается только в основном `%LOCALAPPDATA%\RemoteAgents`; для изолированной проверки
предназначен `windows-migrate-dryrun.ps1`. `--tray --home <тест>` не меняет Run/задачи.

Фоновой проверки обновлений нет: ни при старте, ни по таймеру. Старый `update.intervalMin` игнорируется.
Опциональное обновление по SSH доступно только по пункту «Проверить обновления на сервере»
и только при `update.enabled=true`. Без этого флага пункт серый.
Обычный путь обновления — новый скачанный EXE.

```powershell
.\RemoteAgents.exe                       # установка или обновление из скачанного EXE
.\RemoteAgents.exe --install              # переход существующего компьютера с откатом
.\RemoteAgents.exe --confirm-install      # проверить все условия и подтвердить сейчас
.\RemoteAgents.exe --tray
.\RemoteAgents.exe --restart-components
.\RemoteAgents.exe --logs
.\RemoteAgents.exe --rollback             # локальный откат бандла
.\RemoteAgents.exe --exit
.\RemoteAgents.exe --uninstall
```

`--home <каталог>` изолирует данные, mutex и IPC по SID пользователя и хешу абсолютного пути.
Для обычного home сохранено имя mutex прежнего лаунчера. Mutex — Global, IPC закрыт ACL пользователя.
Это позволяет тестам работать рядом с основным треем и мостом. Явный `--tray --home <каталог>` запускает
трей прямо из заданного EXE, без установки и Run; это вход для разработки и smoke-тестов.

## Переход существующего компьютера

Для ветки перехода требуются уже установленный RemoteDisk, рабочий профиль из `RemoteDisk/profile.txt`, sing-box
`RemoteDisk/channel/sing-box.exe`, конфиг канала и прежний установленный мост. Для чистой машины сначала выполняется мастер из раздела «Два EXE». Рабочие профили диска и моста должны вести к одному адресу сервера.
Переход запускают локально в Windows: остановка прежнего моста завершает процессы, запущенные через него.

1. Пользователь запускает новый EXE с `--install`. Установщик показывает окно «RemoteAgents — переход».
   Импортируются отсутствующие `transport.profilePath`, `channelPath`, `singBoxPath`, `syncPort` из
   старого канала; прочие ключи, настроенные порты и существующие узлы сохраняются. Новые `entries`,
   `relays`, `hops`, `cdn` по умолчанию пусты. Узлы добавляются `Edit-Transport.ps1` из активного бандла.
2. Сохраняются прежние HKCU Run `RemoteDisk`, `RemoteAgentsControl`, `RemoteAgents` и enabled/running
   задачи `RemoteDiskChannel`. **До изменения работающей сети** создаётся задача **RemoteAgents rollback**
   с независимым процессом `Rollback.ps1 -Watchdog`. Скрипты копируются в
   `state/migration-recovery/<session>/`, вне очистки бандлов. Задача запускается сразу, до preflight;
   переход требует подтверждённого состояния Running. Watchdog ограничивает ожидание десятью минутами
   по Stopwatch, даже при переводе часов назад. Есть резервные триггеры через десять минут и при входе
   пользователя; задача допускает батарею и повторяет неудачный откат. При перезагрузке ожидание после
   следующего входа ограничено ещё десятью минутами. Журнал — `logs/migration.log`. Ошибка регистрации
   или запуска watchdog оставляет старые работающие компоненты. Состояние перехода записывается с Flush(true).
3. Окно сообщает о проверке временного транспорта. Отдельный Home `state/migration-probe` использует
   свободные временные SSH/sync/API порты и проверенные диапазоны 34000–34127 / 36000–36127 для проб/SOCKS.
   Сохраняются режим pin/auto и память путей; проверяется именно выбранный пользователем режим.
   Старый канал и мост пока работают. Нужны свежий `transport.ok` и реальное выполнение SSH `true`
   через временный вход со строгой проверкой host key. Таймаут транспорта — 180 секунд.
4. После успешной пробы временный демон останавливается. Его рейтинг текущей сети сливается в рабочую
   память с сохранением остальных сетей: рабочий демон сразу перепроверяет известный путь, не выдавая
   remembered за проверенное соединение. При `transport.takeOverChannel=true` старую
   задачу канала **отключают, не удаляют**, останавливают и сразу запускают рабочий трей с транспортом
   на `sshPort`/`syncPort` (обычно 2222/22001). Проверяются его статус и SSH `true` через рабочий вход.
   При ошибке вызывается откат сразу; независимая задача остаётся страховкой на случай зависания.
5. При `transport.routeSsh=true` в SSH config профилей диска и моста добавляется первый управляемый
   блок `# BEGIN RemoteAgents transport <hash Home>` / `# END ...`: `ProxyCommand none`, `ProxyJump none`,
   `HostName 127.0.0.1`, `Port <sshPort>`, `HostKeyAlias <server>`. Блок ограничен `Host "<server>"`, затем
   возвращает область `Host *`. Исходные записи других хостов, CRLF и BOM сохраняются. JSON профилей
   не меняются. Повторное добавление/снятие идемпотентно. Отсутствующий SSH config создаётся;
   откат восстанавливает отсутствие, если пользователь не добавил в него собственные записи.
6. Мост раньше передавал `-p` явно, что сильнее SSH config. Совместимый `Read-ControlProfile` учитывает
   порт управляемого блока. Переход через `-Uninstall -KeepState` останавливает прежний экземпляр,
   сохраняя его PID-файл/копию приложения/конфиг. `-Install -LauncherHome <home>` добавляет отдельную
   копию в `managed-control/app/<content hash>`, сохраняя прежний workspace и читая прежний config.
   Она работает через прежние HKCU Run, mutex и RetryForever, независимо от процесса лаунчера.
   Старый Run сохранён для отката; прежний `control/app` и SSH-профили не перезаписываются.
7. Удаляется Run `RemoteDisk`, прежний GUI Syncthing останавливается, надзор запускает headless, добавляется Run лаунчера.
   В меню появляется «Переход: проверка связи; откат через 10 минут». Цвет иконки по-прежнему показывает
   критичные компоненты; подтверждение перехода проверяет **все** условия отдельно: свежие `transport.ok`,
   `disk.ok` с `connected=true`, `control.ok`, отсутствие `transport.configError`, успешный SSH `true`
   на `127.0.0.1:sshPort` и новый аутентифицированный запрос `status` через серверный сокет моста,
   обратный SSH-туннель и Windows executor. Проверяются hostId, control-привязка и workspace.
   Для запроса используется публичный каталог; секрет сессии остаётся в памяти broker.
8. Три минуты непрерывно зелёных проверок снимают watchdog автоматически. Ошибка, перерыв проверок
   более 35 секунд и новый сеанс лаунчера сбрасывают отсчёт. Можно выбрать «Подтвердить установку
   (проверить связь)» или запустить `--confirm-install`: этот путь тоже требует всех проверок.
   После десятиминутного дедлайна подтверждение запрещено. Успех виден как «Переход: подтверждён».
9. Без подтверждения watchdog останавливает только этот лаунчер, снимает только свой SSH-блок,
   возвращает прежние Run диска/моста и состояние старой задачи канала, запускает прежние компоненты,
   убирает Run лаунчера и выключает его надзор в config. Чужие ключи config остаются. Ошибка одного
   восстановления не мешает остальным; фаза `rolling-back` и журнал показывают неполный откат, который
   можно повторить. Старые session/watchdog не действуют на новую либо подтверждённую установку.

При обычном обновлении лаунчера независимый мост продолжает работать из своей добавленной копии;
выключение/включение управления в меню создаёт копию из текущего бандла.

Повторный `--install` в фазе pending/accepted запускает трей без нового захвата и без продления дедлайна.
В pending дополнительно проверяются срок и наличие включённого watchdog; его потеря вызывает откат.
Команда не останавливает действующий трей до preflight. Mutex миграции/конфига/транспорта — Global,
с отдельным хешем канонического Home, включая нормализацию завершающего разделителя.
Незавершённые preparing/activating сначала откатываются. Обновление EXE во время перехода блокируется.
Первое рабочее включение после preflight запускает отдельное 120-секундное окно здоровья бандла;
повторные запуски это окно не продлевают. Закрытие лаунчера оставляет трей диска и процесс моста живыми,
но останавливает transport: до нового запуска связи через его порты не будет; при pending действует откат.
До принятия установки создаётся отдельная задача `RemoteAgents-Recovery-<hash Home>` (в dry-run —
с тестовым префиксом). При входе пользователя и раз в минуту она запускает неизменяемую копию EXE из migration-recovery в режиме
`--recovery-host`: та проверяет accepted и отметку намеренного выхода, восстанавливает отсутствующий/
повреждённый основной EXE из сохранённого образа при прерванной замене и ждёт завершения основного
`--recover-launcher`. Global mutex исключает второй трей; маркер прерванного обновления разрешает
возобновление после остановки старого трея. Успешный запуск/намеренный выход снимает маркер.
Это восстановление после аварии, не сетевой rollback. Намеренный «Выход» сохраняется; uninstall снимает
задачу восстановления. Если задачу создать нельзя, переход не принимается и watchdog остаётся.
Win32/ScheduledTasks поведение этого нового надзора требует отдельной Windows-приёмки.
`routeSsh`/`takeOverChannel` применяются при явном переходе, не при hot reload транспорта. Если захват
выключен, а старый канал включён/работает, переход отказывается конкурировать за его порты.

Для немедленного возврата — `RemoteAgents.exe --uninstall`. Если EXE не запускается, используйте
`powershell.exe -NoProfile -ExecutionPolicy Bypass -File <bundle>\build\Rollback.ps1 -Home <home> -Uninstall`.
Это сохраняет исходные профили, `control/`, папки Disk, бандлы, настройки и журналы.

`disk` теперь запускает один `Disk.Status.ps1 -Home ... -ParentPid ...`. Он раз в десять секунд читает
локальный REST Syncthing, ограничивается папками сервера из `server.txt`, пишет `{ok,summary,folders:
[{id,label,state,completion}],connected,updatedAt}` в `status/disk.json`. API key не выводится.
Если трей отсутствует, запускает именно установленный exe через Win32_Process Create с `--wait`,
вне Job Object лаунчера. Меню открывает выбранную базу Disk, ставит паузу на 30 минут / 2 часа /
до «Продолжить». Возобновляются только папки, поставленные на паузу нашим меню; прежние паузы сохраняются.
Для срочных пауз ставится отдельная `RemoteAgents-DiskResume-<hash Home>` с добавленной копией команды:
она переживает закрытие лаунчера/очистку старого бандла и не отменяет более новую паузу. Монитор также
проверяет срок. Планировщик требует доступный пользовательский сеанс; после выхода возобновит при входе.

`control` запускает только `control/Control.Status.ps1`. Он читает PID, процесс Start-WindowsControl,
последние события control.log, проверяет живой дочерний SSH `-R` с установленным TCP-соединением.
Историческая строка `bridge.connected` без процесса/сокета не даёт `ok=true`. В JSON есть `processAlive`
и `lastContact`; отсутствие инвентаризации отображается как «нет данных». Команды меню управления
вызывают существующие `-Install/-Uninstall`, оставляя монитор работать и показывать выключенное состояние.

до трёх, включая текущую и предыдущую. Кэш бинарников отдельно не ограничивается.

## Трей, пути и VPN

Левый щелчок показывает небольшое меню состояния: путь, скорость, время проверки, режим,
сеть и её лимитность, диск, мост и VPN. Отсутствующий, повреждённый файл или данные старше пяти минут —
«нет данных». Будущее время более чем на пять секунд также не принимается. Проверяются и mtime,
и `updatedAt`/`updatedUtc`, если timestamp присутствует. Для transport/VPN по согласованному интерфейсу
применяется более строгий предел 15 секунд; меню обновляется раз в секунду. `metered:null` и `kbps:null` не подменяются нулём.
Подсказка иконки — `RemoteAgents: <title> <kbps> КБ/с`, до 63 символов Windows.
Цвет отражает здоровье критичных компонентов; отсутствие критичных или выключенный критичный не дают зелёный.

«Путь к серверу» читает `status/transport.json`: `active`, `title`, `kbps`, `checkedAt`, `mode`,
`network`, `metered`, `candidates: [{tag,title,state,kbps,checkedAt,enabled?}]`.
Для старого формата title/checkedAt берутся из активного кандидата, title затем из tag.
«Автовыбор» отмечен только при `mode=auto`, выбранный кандидат — при `mode=pinned`.
Недоступные/выключенные кандидаты серые; доступность требует `state=ok`.

Выбор выполняет без оболочечного склеивания аргументов:

```powershell
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <bundle>\transport\Set-TransportPath.ps1 -Home <home> -Auto
powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <bundle>\transport\Set-TransportPath.ps1 -Home <home> -Tag <tag>
```

«Узлы и пути → Открыть настройки» открывает config.json в Блокноте;
«Список путей» показывает stdout `Edit-Transport.ps1 -Home <home> -List` в окне с прокруткой.
Настройки, изменённые вручную, применяются обычными компонентами после перезапуска;
transport перечитывает их по своему hot-reload контракту. Переключение компонента перечитывает
последний конфиг и сохраняет прочие секции под той же блокировкой, что команды транспорта.

«VPN (весь трафик)» — переключатель `components.vpn.enabled` (по умолчанию false).
По согласованному интерфейсу `TRANSPORT.md` VPN — `commandManaged` компонент: обычный запуск его
скрипта только читает/инициализирует статус. При явном включении после проверки лаунчер вызывает
`Vpn.Tun.ps1 -Home <home> -Enable -ParentPid <pid>`, при выключении — `-Disable`.
Модуль сам запрашивает UAC для своего broker и создаёт временные задачи worker/отката с наивысшими правами;
сам лаунчер не повышается. Модуль хранит свои рабочие настройки в `vpn`, лаунчер — запрос в `components.vpn`.
При перезапуске Windows, лаунчера или компонентов VPN автоматически не включается. Значение флажка
берётся из свежего `vpn.json`, а не из сохранённого запроса. При выходе/перезагрузке компонентов лаунчер
пишет только свой `state/vpn.stop`; worker также следит за ParentPid. Статусы starting/stopping не означают
подтверждённое включение/выключение, `error/rollback-error` остаются ошибкой.
Перед включением выполняется `Test-VpnConflict.ps1 -Home <home>` с ожидаемым JSON
`{conflict,items:[{kind,name,path,detail}]}`. При конфликте перечисляет VPN и предлагает
«Проверить снова» / «Оставить как есть»; последнее — действие по умолчанию. Чужой VPN не останавливается.
Ошибка проверки или неполный JSON запрещают включение. Реальное состояние берётся из `status/vpn.json`.
При отсутствии скрипта соответствующий пункт выключен с подсказкой «модуль не установлен».
`transport/` развивается отдельно; согласованный интерфейс — раздел «Интерфейс для лаунчера» в `TRANSPORT.md`.

## Компоненты и повышенные права

`components.json` — массив или объект с `components`, `menu`, `binaries`:

```json
{
  "schema": 1,
  "components": [{
    "name": "vpn", "title": "VPN (весь трафик)", "exe": "powershell.exe",
    "args": ["-NoProfile", "-NonInteractive", "-ExecutionPolicy", "Bypass", "-File", "{bundle}\\transport\\Vpn.Tun.ps1", "-Home", "{home}", "-ParentPid", "{pid}"],
    "cwd": "{bundle}", "restart": "never", "healthFile": "status/vpn.json",
    "healthMaxAgeSec": 180, "enabledByDefault": false, "critical": false,
    "commandManaged": true, "stopFile": "state/vpn.stop"
  }],
  "menu": [], "binaries": []
}
```

`name` уникален: `[a-z][a-z0-9_-]{0,63}`. Подстановки `{bundle}`, `{home}`, `{pid}` и переменные Windows
доступны в exe/args/cwd/menu. `{pid}` — PID обычного лаунчера, включая повышенные компоненты.
`restart=always` повторяет запуск с паузами 5, 10, 20, 40, 60 секунд; после 120 секунд здоровья пауза
сбрасывается. `never` означает одну попытку. `menu` — массив `{"title":"…","exe":"…","args":[]}`.

Обычный процесс создаётся приостановленным, включается в Job Object с KILL_ON_JOB_CLOSE и возобновляется.
Выход, выключение, перезапуск и падение лаунчера завершают принадлежащее ему дерево.

`commandManaged=true` запрещает автоматический запуск процесса: модуль управляется явными командами,
а наблюдение использует его свежий статус. Необязательный `stopFile` — относительный флаг остановки в home;
он записывается при выходе/перезапуске. У VPN собственные задачи по интерфейсу transport, поэтому elevated
в его описании не задаётся.

Для обычного компонента при `elevated=true` сам трей не повышается. При первом явном включении пользователь видит объяснение,
а Windows запрашивает UAC для `schtasks /Create` с наивысшими правами. Задача привязана к текущему
пользователю (InteractiveToken / HighestAvailable), home и компоненту, не содержит триггеров и паролей.
Она запускает установленный `RemoteAgents.exe --elevated-component <name> --home <home>`;
повышенный помощник запускает только указанный в текущем components.json компонент в отдельном Job Object.
PID/время старта родителя сверяются, помощник наблюдает родителя и собственный stop-флаг;
после выхода/остановки родителя закрывает дерево. Запросы и флаг — `state/elevated/`.
При штатном выключении сначала даётся до пяти секунд на остановку, затем вызывается остановка задачи.
Повторные запуски и обновления используют ту же задачу и стабильный путь установленного EXE.
На автозапуске отсутствующая задача не создаётся молча: компонент остаётся без подтверждённого здоровья;
для создания нужно явно выключить/включить его в трее. Отмена UAC не включает компонент.
Для получения административных прав principal должен иметь соответствующие права Windows.

Здоровье требует живого процесса (для elevated — выполняющейся задачи; для commandManaged — свежего enabled=true), свежего файла,
mtime после старта и `ok:true`. `healthMaxAgeSec` по умолчанию 90. Отсутствующий summary — «нет данных».
Пример: `{"ok":true,"summary":"Путь проверен","updatedAt":"2026-11-09T12:00:00Z"}`.
`status/launcher.json` содержит версии, pending/running/ok и массив name/title/enabled/critical/alive/ok/summary/pid;
для задач PID компонента не заявляется. Журнал хранит коды событий без аргументов, секретов и исключений.

## Опциональный SSH-источник

Пример и схема — `app/launcher/config.example.json`, `config.schema.json`.

```json
{"schema":1,"version":1,"components":{},"update":{
  "enabled":false,
  "sshExe":"ssh.exe",
  "args":["-F","C:\\path\\config","user@example.invalid"],
  "remoteDir":"~/.local/share/remote-agents/dist"
}}
```

Если args отсутствует, импортируется первый отсортированный `ssh-profiles/*/project-connections/*/ssh-transport.json`,
затем профиль из `%LOCALAPPDATA%\RemoteDisk\profile.txt`. Явный `args:[]` запрещает импорт.
Лаунчер добавляет BatchMode/StrictHostKeyChecking, не читает закрытые ключи и не выполняет интерактивный вход.
`viaLocalPort:2222`, `hostKeyAlias` позволяют использовать локальный transport, сохраняя проверку ключа сервера.
При автоматическом импорте профиля updater учитывает Port управляемого SSH-блока даже при прежнем -p 22.
Явные update.args используют собственный viaLocalPort.
Удалённые команды — только `cat -- <remoteDir>/manifest.json` и архив, с POSIX quoting; текст приводится к LF.
Таймаут команды — 300 секунд, selftest — 120 секунд.

Manifest: `{version,file,sha256,size,minLauncher,launcher?:{version,sha256}}`. `launcher`, если объявлен,
требует соответствующий EXE в ZIP; его замена происходит после подтверждения здоровья бандла.
SHA256 и FileVersion сверяются. Этот источник применяется только по явной кнопке при enabled=true.
`binaries`: `{url:"https://…",sha256:"<64 hex>",path:"tool.exe"}` — отдельные файлы под bundle/bin;
хеш проверяется и при использовании кэша. Сейчас binaries пуст; sing-box/Syncthing не вшиваются.

## Выпустить новую версию

Из корня репозитория на Linux:

```bash
./build/build-exe.sh
```

Пользователю передаётся **один `build/out/RemoteAgents.exe`**. Он запускает его поверх существующей установки.
Бандл получает UTC-версию `yyyyMMdd.HHmmss-<git hash>`; изменённые без коммита файлы тоже входят в выпуск.
Для изменения версии самого лаунчера меняйте Version/AssemblyVersion/FileVersion в csproj (сейчас 1.2.0).
Не смешивайте календарный ряд версий бандлов с semver; числовые части сравниваются как числа.
Для фиксированного номера сборки доступен `REMOTEAGENTS_BUNDLE_VERSION`.

`DOTNET` задаёт путь SDK (по умолчанию `~/.dotnet/dotnet`), `REMOTEAGENTS_BUILD_OUT` — выходной каталог.
Дополнительные initial-bundle.zip и bundle.zip — сборочные/опциональные SSH-артефакты, пользователю не нужны.
`build/bundle-files.txt` включает `transport/*.ps1` и `transport/*.json`, включая команды пути/VPN.
Тексты при упаковке приводятся к LF, PS1 получают UTF-8 BOM для PS 5.1. Личные профили, секреты и скачанные
бинарники запрещены. Коммитов и push сборка не выполняет.

`build/publish.sh` при необходимости собирает и публикует EXE/ZIP и последним manifest.json в серверный dist;
сам факт публикации не инициирует обновлений клиента. Готовый ZIP: `build/publish.sh <zip> <dist>`.
Релизы неизменяемы: другой контент с тем же номером публиковать нельзя.

Ручной `--rollback` возвращает previous.txt и перезапускает компоненты; во время скачивания недоступен.
Без работающего лаунчера: завершить его, проверить прежний каталог, вернуть его номер в current.txt,
удалить pending.json; при необходимости вернуть RemoteAgents.previous.exe. Выпуск исправления — новый номер.

## Проверки

```bash
./app/launcher/tests/run.sh
./build/build-exe.sh
file build/out/RemoteAgents.exe
sha256sum build/out/RemoteAgents.exe
```

Linux проверяет упаковку/публикацию, LF/BOM и CRLF-вход, хеши, minLauncher, безопасную распаковку,
selftest, активацию, восстановление дедлайна 119/120 секунд, откат, сохранение настроек/state/secrets/logs,
обновление только EXE, явное понижение версии, честность свежего/устаревшего статуса и сборку/publish net48.
JSON-адаптер System.Text.Json используется только Linux-стендом.

На настоящей Windows, без сети, автозапуска, изменения основного home или запуска TUN:

```powershell
$exe=(Resolve-Path '.\build\out\RemoteAgents.exe').Path
$test=Join-Path $env:TEMP ('RemoteAgents-upgrade-'+[guid]::NewGuid().ToString('N'))
$p=Start-Process $exe -ArgumentList ('--selftest-upgrade "'+$test+'"') -PassThru
# Тест занимает около 2–3 минут; дождитесь завершения.
$p.WaitForExit()
$p.ExitCode
Get-Content (Join-Path $test 'selftest-upgrade-result.json') -Raw
```

Ожидаются exit 0 / ok=true. Тест эмулирует старую установку синтетическим бандлом, запускает настоящий
изолированный трей, останавливает его по IPC/mutex, применяет общий production-код установки из папки
`downloaded`, проверяет копирование EXE и сохранение данных. Запускает обновлённый трей, проверяет отказ
selftest и реальный 120-секундный откат нездорового бандла/образа с повторным запуском трея.
Использует тот же EXE в роли прежнего образа; сравнение разных версий покрывает отдельный тест ядра.
Heartbeat синтетический и не подтверждает серверную связь. Рабочие home, мост, VPN и HKCU Run не меняются.
Результаты остаются в указанном каталоге. Для общего ядра доступен `--selftest-update <каталог>`.

`app/launcher/tests/windows-smoke.ps1 -Exe <exe>` отдельно проверяет IPC, рестарт, старение/восстановление
health и остановку дочернего дерева. Проверка UI, UAC/планировщика, обновления реального скачанного релиза,
реального SSH и интеграции модулей требует Windows-приёмки. Живой TUN на ноутбуке с MCP-сессиями не тестировать.


### Проверка перехода на Windows без рабочего окружения

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\app\launcher\tests\windows-migrate-dryrun.ps1 -Exe "$env:USERPROFILE\Downloads\RemoteAgents.exe"
```

Укажите фактический путь нового EXE. Скрипт читает его вшитый ZIP как ресурс без запуска Main;
исходный build/ на ноутбуке не нужен. Вместо -Exe можно передать -Bundle <распакованный бандл>;
без обоих параметров используются исходники build/ репозитория, если они доступны.

Сценарий создаёт новый Home в TEMP, уникальные Run/задачи `RemoteAgents-Test-<GUID>-*`, выбирает другие
порты и подменяет только запуск приложений/сетевые ответы. Настоящие HKCU Run и ScheduledTasks проверяются:
импорт и CRLF-блок, передача автозапуска, подтверждение, немедленный откат и **реальный запуск независимой
задачи отката в отдельном PowerShell 5.1** (для теста через пять секунд). По завершении тестовые Run/задачи
удаляются; результат остаётся в `<test>/dryrun-result.json`, ok=true. `-KeepTasksOnFailure` сохраняет только
тестовые задачи для диагностики. Рабочие Run сравниваются без вывода содержимого; рабочий мост не запускается
и не останавливается. Синтетическая сеть не подтверждает реальные SSH, Syncthing, протоколы или EXE --install.

`tests/run.sh` включает `test-migrate.ps1`: Linux/pwsh, временный LOCALAPPDATA, подменяемые платформенные
функции для registry/tasks/processes/REST, настоящий `ssh -G` без соединения. Все PS1 — UTF-8 BOM,
синтаксис 5.1; Linux pwsh не заменяет проверку Windows 5.1. Реальные переход, reboot, CIM detach,
пауза с задачей возобновления и восстановление связи старого моста требуют приёмки на Windows.
