# Автообновление — отчёт ветки app/update

Работа выполнена в `~/work/wt-update`. Main, другие worktree, живые dist/службы, GitHub и компьютеры Windows
не изменялись. Push, merge и выкладки не выполнялись. Изменения предназначены для проверки и последующего
слияния владельцем. Реализация: коммит `153d473` «Автообновление программы и единая выкладка». Этот отчёт фиксируется отдельным
коммитом; оба хеша перечислены в итоговом ответе.

## Реализация по TASK-UPDATE, пункты 1–8

1. `UpdatePolicy` дополняет отсутствующие `enabled=true`, `auto=true`, `intervalHours=6`, стандартный remoteDir.
   Явные false сохраняются. Переносимый конфиг принимает update; Store переносит эти настройки в runtime,
   обычный экспорт/восстановление их сохраняет. Серверный `config export` сразу выдаёт полный раздел;
   администратор может явно переопределить его в настройках выдачи. JSON-схемы и примеры обновлены.
2. `build/release.sh <ssh-alias> [remote-dist]` один раз собирает оба продукта и переиспользует `bundle.py publish`
   и `release-github.sh`. Один UTC-номер бандла, точные одинаковые EXE на GitHub и SSH. В main-latest также
   `release-info.json` с версией, коммитом и хешами обоих EXE. Обратное скачивание с GitHub проверяет все три файла;
   SSH-публикация проверяет оба комплекта до замены manifest, затем перечитывает опубликованные хеши и manifest.
   Реальная выкладка защищена проверкой main/HEAD/origin/main. /tmp допускается для тестов упаковки.
3. Проверка на старте, затем через intervalHours, а также по кнопке. Сначала только manifest. Сбой связи или
   повреждённый manifest — без balloon, с честной строкой статуса и следующей попыткой по расписанию.
   SSH использует активный профиль, BatchMode и StrictHostKeyChecking; сеть и службы не перенастраиваются.
4. Существующий UpdateEngine выполняет проверку размера/SHA-256, безопасную распаковку, binaries, selftest и bad.txt.
   TrySelfUpdate теперь переиспользует образную транзакцию UpgradeInstaller: EXE и бандл переключаются вместе,
   FileVersion ежедневных сборок может совпадать. 120-секундный откат возвращает обе части. Исправлен граничный
   случай, когда бандл уже подтвердил здоровье на границе дедлайна образа. Старый EXE в режиме --watch-update
   дополнительно восстанавливает транзакцию при падении/зависании нового процесса до старта/работы трея;
   PID/start time нового процесса записывается до создания окна, поэтому раннее падение определяется без
   ожидания полного дедлайна. Работающий VPN подтверждает передачу родителя до принятия обновления; на время
   проверки сохраняется ограниченная квитанция для возврата прежнему EXE.
   Установка ждёт MutationConflict, применяющие окна, BackgroundWork.Disk и команды Проводника. Реестр операций моста используется
   под его же mutex: живые PID/start time блокируют установку, эксклюзивная запись закрывает гонку с новой командой.
   Перед активацией повторно сверяется хеш config.json. Диск проверяется через имеющийся REST, мост — своим
   authenticated health, связь — штатным health. Конфиг и настройки Syncthing сохраняют включения и паузы.
   Уже работающий VPN передаёт родителя существующему broker без UAC; квитанция ограничена по времени, session,
   прежнему PID, пути/хешу нового EXE и start time нового PID. Независимый watchdog VPN продолжает проверять сеть.
5. В обоих треях есть строка состояния и «Проверить обновления сейчас». Окно использует существующую строку
   состояния; показаны версия, время успешной проверки, ход установки или причина отказа. Итоговое уведомление
   запоминается на диске и не повторяется для той же версии/причины. При auto=false кнопка только проверяет.
6. Manifest содержит configSchema. Новый EXE до активации запускается с --check-update-config config.json:
   без UI, записи файлов, сети и чтения vault. Поддерживаются прежний локальный формат без schema и schema 1;
   миграция сейчас добавочная — defaults, без смены формата переносимого профиля. Сам профиль проверяет код
   новой сборки. Неподдерживаемый конфиг блокирует установку, рабочая версия сохраняется, одна фраза просит
   администратора выдать новый конфиг. Отказ кешируется по версии и хешу конфига, а не глобально в bad.txt.
   Секреты не копируются, не мигрируют и не попадают в журналы. Для будущей смены schema потребуются код миграции
   и новые исторические фикстуры, как предписывает конституция.
7. RemoteVPN имеет собственный OTA-архив и manifest в dist/vpn, транзакции — vpn-bundle. Обновляется тем же кодом;
   RemoteAgents не включает выключенный VPN. Хранилища двух продуктов и образные backup/квитанции разделены.
8. Обновлены LAUNCHER.md, CONFIG.md, схемы/примеры; в конституции добавлено правило 7б.

Общие с параллельными работами файлы изменены точечно: ConfigBundle.cs — новое поле схемы, перенос update в Store
и recovery profile; ConfigApply.cs — public key и сохранение update. В TrayContext.cs — вызов scheduler, health,
пункты меню и переход образа; основной новый код вынесен в partial-файлы. disk/*, DiskChoice.cs,
HappierWebResolver.cs, ConfigWindow.Main.cs и server/happier_web* не изменялись. В DiskExplorerController.cs добавлен только счётчик ожидающих/исполняемых shell-команд
и свойство Busy, чтобы не оборвать действие Проводника при переключении версии; это место нужно совместить
с веткой Диска. TrayMenuModel.cs получает лишь
свойство подтверждённого соединения с сервером Диска для использования уже выполненного REST-запроса.

## Проверки

Владелец изменил правило проверки во время работы: полные suite больше не запускать, один финальный прогон
только затронутой части, суммарно до 5–7 минут, каждая команда под timeout 420. Полный launcher-прогон прерван
владельцем. Полные app/launcher/tests/run.sh и server/tests/run.sh остаются владельцу при слиянии.

Быстрая компиляция актуального production-кода (после последних изменений):

```bash
timeout 420 "$HOME/.dotnet/dotnet" build app/launcher/RemoteAgents.Launcher.csproj -c Release --no-restore --nologo -p:UseSharedCompilation=false
```

Результат: EXIT 0, 8,77 с, 0 warnings, 0 errors. Bash/Python синтаксис изменённых скриптов также проверен.

Единственная финальная проверка после нового правила:

```bash
timeout 420 flock --nonblock --close /tmp/heavy-tests.lock app/launcher/tests/run-update.sh
```

Результат: **EXIT 0, 75 секунд**. Повторных тестов после этого запуска не выполнялось.
RemoteAgents и RemoteVPN: по 36 новых проверок автоматики и по 108 прежних проверок транзакций;
конфиг/схема/совместимость: ConfigBundle, 177 проверок; фейковая выкладка: 7 тестов; lifecycle: 23 теста;
выдача update с явным отключением: 1 тест. Лог: `/tmp/wt-update-final-focused.log`.
Полный launcher-suite после последнего решения владельца не запускался; старый полный прогон был прерван.
Нельзя указывать для него EXIT 0. Полные suite при слиянии выполняет владелец. Узкий runner выполняет только транзакции
обновления и новую автоматику обоих продуктов, конфиг/совместимость, фейковую выкладку, проверки lifecycle
и один тест выдачи секции update. Каждая дочерняя команда ограничена timeout 420; внешняя команда ограничивает
весь набор семью минутами. Блокировка берётся без ожидания; зависание или внешняя ошибка фиксируются в отчёте.

Первый полный запуск выявил две проблемы стенда: чувствительный к нагрузке бюджет существующего Bootstrap-теста
(3,7 с при лимите 3 с) и чтение тестовой выдачей глобального server-config.json этого хоста. Продуктовую логику
Happier не меняли: Env теста config export теперь явно задаёт пустой server-config.json во временной папке,
а защита путей проверяет и его. Бюджет Bootstrap не ослабляли. До изменения правила отдельный server/tests/run.sh завершился EXIT 0: 223 серверных теста,
34 теста gateway и 11 тестов его установки. Более ранние portable-прогоны обоих продуктов дали 36 новых
и 108 прежних проверок обновления, затем нашли пропущенное поле hint в опубликованной схеме; поле исправлено,
равенство JSON и скомпилированной схемы проверено. Это история проверки до нового правила, не результат
прерванного полного launcher-прогона и не основание обходить окончательные ограничения владельца.

Новые portable-проверки выполняют production-код UpdatePolicy/UpdateSchedule/UpdateProbe/UpdateEngine/
UpgradeInstaller/UpdateEnvironment/VpnUpdateHandoff: старт/интервал, есть/нет/нет связи/битый manifest,
auto=false, bad/minLauncher, ожидание применения/Диска/окон/моста, завершение/повторное использование PID,
старые конфиги с CRLF, отказ до активации, сохранение файлов/секретов, успешная транзакция EXE+бандла и возврат
обеих частей при недоказанном здоровье. Фикстуры — обезличенные примеры прежних форматов из схем/примеров
проекта; это не снимки реальных пользовательских ПК. Прежние selftest дополнительно покрывают провал selftest,
размер/хеш, пути ZIP, отмену и bad.txt. Оба варианта продукта запускаются отдельными portable-прогонами.

`test_update_release.py` выполняет настоящие упаковку, общий release.sh --prepared и удалённый Python-издатель
на временной папке через фейковый ssh, а также release-github.sh через фейковые git/gh. Проверяет общий номер,
точные байты обоих EXE, повтор, повреждение второго продукта без замены manifest, несовпадение версий,
защиту ветки, несовпадение provenance и повреждение скачанного RemoteVPN.exe. Реальные git refs и сеть не меняются.

Linux-проверки не подтверждают работу WinForms, Windows PowerShell 5.1, переименование выполняемого PE,
передачу родителя повышенному broker, независимый процесс-watchdog и восстановление реальных модулей на Windows.
Эти части скомпилированы и требуют живой приёмки ниже. Нельзя выдавать этот отчёт за состоявшуюся приёмку ПК.

## Для выкладки после разрешения владельца

1. Проверяющая сессия сливает согласованные ветки в main, разрешает конфликты общих файлов, повторяет launcher
   и server tests под общим flock и выполняет предусмотренный владельцем push. Эта задача ничего не сливает.
2. На машине сборки: .NET SDK/reference assemblies, проверенный кэш pinned binaries, gh с доступом к существующему
   main-latest, git origin, OpenSSH и заранее проверенный ключ своего сервера. На сервере: Python 3/POSIX flock,
   доступ рабочего SSH-пользователя на запись в выбранный dist и достаточно диска для временного комплекта.
3. Из чистого main с HEAD в origin/main:

   ```bash
   flock --close /tmp/heavy-tests.lock build/release.sh <ssh-alias> '~/.local/share/remote-agents/dist'
   ```

   Команда обновляет существующий main-latest и dist, без новых релизов и сетевых настроек сервера.
   Ключ --close у flock не даёт долгоживущему compiler server унаследовать блокировку.
4. GitHub и SSH не имеют общей атомарной транзакции. Если первый источник обновлён, а второй недоступен,
   сохранить build/out целиком и повторить именно ту же сборку:

   ```bash
   flock --close /tmp/heavy-tests.lock build/release.sh <ssh-alias> '~/.local/share/remote-agents/dist' --prepared build/out
   ```

   Нужны тот же main HEAD и исходники. Повтор проверяет release-info.json против EXE/архивов/коммита. Другие байты
   под прежним номером запрещены; для исправления уже опубликованной битой сборки нужен новый номер версии.

## Живая приёмка Windows — отдельно, только после «да» владельца

На согласованном тестовом ПК с Windows 10/11 и штатным PowerShell 5.1:

1. Установить N из main; включить update.enabled/auto. Зафиксировать версию бандла и хеш установленного EXE,
   работу связи, authenticated мост, Диск/паузы/локальные файлы и Happier. Отдельно повторить с работающим VPN
   и RemoteVPN, затем с выключенным VPN. Проверить отсутствие повторного UAC при передаче работающего broker.
2. Опубликовать N+1 штатной командой. На старте (либо по таймеру, 1 час для приёмки) увидеть автоматические
   скачивание, смену EXE+бандла, перезапуск, подтверждение здоровья и одно уведомление. Кнопка проверяется отдельно.
3. До установки N+1 запустить длительную команду моста, применение конфига и установку Диска — по очереди.
   Убедиться, что переключения нет, команды не прерваны, после освобождения обновление продолжается само.
4. N+2 с падающим selftest: N+1 продолжает работу, одна причина отказа, версия в bad.txt, повторной установки нет.
   Следующий отдельный номер с неработающим health: за 120 секунд возвращаются бандл и EXE N+1.
5. Отдельно проверить аварийное завершение нового EXE/зависание до первого Tick: прежний EXE-watchdog после
   дедлайна восстанавливает N+1. Его остановка экземпляра использует прежние IPC/mutex/проверки PID и пути.
6. Проверить старый конфиг без schema/секции update и переносимый schema 1, неподдерживаемый тестовый профиль,
   auto=false, отсутствие сети и битый manifest. Не использовать реальные секреты в диагностическом выводе.
   При неподдерживаемом профиле активная N+1 остаётся рабочей; после исправления конфига разрешена новая попытка.
7. После каждой ветки проверить мост, связь, Диск (обе стороны/паузы/файлы), Happier, VPN в прежнем состоянии,
   локальные журналы без секретов и отсутствие повторных уведомлений. Сохранять только обезличенные результаты.

Испорченные сборки не публиковать людям: приёмка требует согласованной изолированной раздачи/тестового dist.
Текущий task ничего из этого на живых системах не выполняет.

## Уже выданные компьютеры

Старая сборка фоновой установки не умеет, поэтому один раз нужно запустить новый RemoteAgents.exe из `main-latest`
поверх установки (и RemoteVPN.exe, если он установлен); config.json, secrets и Диск не трогаются.
Записанное старой сборкой `update.enabled=false` новая программа считает не решением, а прежним умолчанием,
и сама включает автообновление (`UpdatePolicy.Defaults`: без поля `auto` → `enabled=true`, `auto=true`; remoteDir и прочее сохраняются).
Явный отказ — только `update.auto=false`/`enabled=false` вместе с полем `auto`. Дальше обновления ставятся сами.
