# Задача: несколько аккаунтов Happier и выборочная синхронизация в RemoteAgents.exe

Решение владельца 10 ноября 2026. Общий подход для любого компьютера, без частных случаев.

## 1. Аккаунты Happier
- На сервере может работать несколько аккаунтов Happier. Каждый — отдельный набор чатов и истории
  со своим секретным ключом.
- При первой настройке компьютера EXE предлагает выбор: подключиться к существующему аккаунту Happier
  или создать новый. Первая настройка — это когда на компьютере ничего не настроено, даже если сервер уже
  настроен.
- Подключение по секретному ключу аккаунта Happier, чтобы любой аккаунт можно было восстановить.
- Подписки (Claude, ChatGPT/Codex и другие) на сервере общие для всех аккаунтов Happier, ничего
  не дублируется и не привязывается к одному аккаунту подписки.
- Идемпотентность: повторный запуск EXE восстанавливает рабочее состояние и не ломает уже работающие
  аккаунты, чаты и подключения других компьютеров.

## 2. Выборочная синхронизация диска
- Каждая папка, подпапка или файл на каждом компьютере либо остаётся только на сервере, либо
  синхронизируется с этим компьютером.
- Можно выбрать всё, часть папок или отдельные подпапки и файлы. Выбор делается при подключении
  и меняется потом.
- Структура сохраняется: если выбрана подпапка, на компьютере создаётся родительская папка, и в ней лежит
  только отмеченное.
- Снятие отметки не удаляет данные на сервере. Локальная копия удаляется только после проверки, что
  последняя версия уже на сервере.
- Отображение диска в дереве Проводника, как у Яндекс Диска, делает другая сессия, здесь оно не
  проектируется.

## Проверка
Проверять на настоящем компьютере, например на стационарном, ничего не сломав: повторный запуск EXE
при уже настроенном сервере, подключение к тому же аккаунту Happier, создание нового аккаунта,
выбор части папок и подпапок.

### Что такое аккаунт Happier в текущей установке

`server-happier.sh` ставит официальный **CLI** в профиль рабочего Unix-пользователя и включает
`happier-daemon.default.service`. Он не разворачивает собственный relay/БД чатов.
В установленном пакете исследован stable **0.2.17** (`~/.happier/cli/versions/0.2.17/package-dist`,
`node_modules/@happier-dev/protocol`); существующие ключи/credentials не читались.
По умолчанию используется API `https://api.happier.dev`, Web/телефон — `https://cloud.happier.dev`.
История аккаунта хранится в Happier relay; VPS запускает daemon и агентов, хранит их локальное состояние.

Ключ восстановления — 32-байтовый seed, base64url либо резервная запись base32 с дефисами.
Ed25519 challenge в `/v1/auth` идентифицирует аккаунт; шифрование/производный ключ машины берутся
из установленного `@happier-dev/protocol`. Обычный CLI не имеет команды «войти по recovery key»,
поэтому маленький адаптер повторяет официальный key-challenge flow и вызывает **штатное хранилище
credentials CLI**, не изобретая формат `access.key` или шифрование. Проверяется политика `/v1/features`;
отказ relay/отключённый key-challenge не выдаётся за успех. Keyless/enterprise входы сюда не входят.
`/v1/auth` у Happier также создаёт аккаунт для нового корректного seed: существование неизвестного ключа
отдельным запросом не устанавливается.

Источники: [официальная документация CLI](https://docs.happier.dev/apps/cli),
[аккаунты с ключами](https://docs.happier.dev/apps/app),
[challenge/token flow](https://github.com/happier-dev/happier/blob/dev/apps/ui/sources/auth/flows/getToken.ts),
[формат backup key](https://github.com/happier-dev/happier/blob/dev/apps/ui/sources/auth/recovery/secretKeyBackup.ts).
Поведение адаптера дополнительно сверено с локальным установленным пакетом, а не только веткой dev.

### Мастер и аккаунты

- После прежней настройки SSH/disk/control основной трей EXE продолжает мастер: существующий ключ или
  новый аккаунт, затем дерево синхронизации. Решение зависит от **локального** наличия ключа/завершения
  выбора, а не от настройки сервера. Отмена оставляет настройку доступной из меню.
- `AccountDiskSetup.cs`: все окна — WinForms внутри EXE. В меню есть «Аккаунт Happier…»,
  «Резервные ключи Happier», «Выбрать папки и файлы…». В форме аккаунта можно указать собственные
  HTTPS API/Web Happier; значения сохраняются в `config.json.happier` под общим mutex.
- Новый seed сохраняется **до** сетевого вызова: повтор после обрыва использует тот же аккаунт.
  `%LOCALAPPDATA%\RemoteAgents\secrets\happier-account.key` и резервные ключи закрыты DACL пользователя.
  При переключении прежний ключ сохраняется в `secrets/happier-backup-*.key`.
  Ключ передаётся только через SSH stdin; argv, журналы, state и stdout его не содержат.
- `accounts/Account.ps1`, `bootstrap.sh`, `server-account.mjs` вызываются по сохранённому рабочему
  SSH-профилю. Bootstrap ставит официальный Happier, если его нет, и при необходимости отдельный
  проверенный Node runtime (тот же pinned Node 24.22.2/hash, что server-devtools.sh); существующий
  глобальный Node не заменяется. Нужен рабочий systemd user manager; недоступность явно останавливает шаг.
- Для пары account public key + relay создаётся стабильный каталог
  `~/secrets/happier/accounts/<sha256>/` и своя служба `remoteagents-happier-<sha256>.service`.
  `HAPPIER_HOME_DIR` изолирует credentials, machine ID, состояние daemon и его журнал.
  Recovery seed на VPS не сохраняется; там только производный ключ в штатных credentials Happier.
- `HOME` Unix-пользователя остаётся общим: нативные входы Claude/Codex и других провайдеров не
  копируются в аккаунты Happier. Это разделение историй Happier, а не изоляция Unix-файлов/прав.
- Повторный вход проверяет API и конкретную online machine, запускает отсутствующую службу через
  `systemctl start`, не перезапускает уже работающую, не применяет `auth --force`, logout или takeover.
  Machine ID/ключи сохраняются; недействительный token обновляется отдельно. Повторный двойной щелчок
  передаёт работающему трею `--setup-check`, поэтому проверка выполняется и без перезапуска трея. Другие account services
  и прежний `happier-daemon.default.service` не меняются. Серверные операции сериализованы flock.
- `logs/accounts.log` содержит только коды этапов. `state/happier-account.json` — результат последней
  проверки и UTC, не постоянный монитор: в меню именно «последняя проверка», а не обещание online навсегда.
  Подтверждение требует systemd active **и** authenticated API, где своя machine действительно active.
- Телефон/браузер восстанавливаются штатной кнопкой **Restore with Secret Key**, с тем же relay и ключом.
  Это отдельный интерфейс самого Happier; приложение не переносит ключ в URL или буфер обмена.

### Выборочная синхронизация и защита удаления

Один штатный Syncthing folder на проект `Disk/<Имя>`. Выбор **локален для устройства**:
`RemoteDisk/selection.json`, `schema=1`; контрольные копии правил — `selection-policies/` вне Disk.
Новая локальная установка записывает пустой выбор **до** запуска установщика диска: серверные предложения
не принимаются до выбора. Для старой установки отсутствие selection.json сохраняет прежний полный выбор.
Новые проекты после явного выбора автоматически не скачиваются; выбранная целиком папка включает будущих детей.

В `.stignore` сначала идут все обязательные `stignore.txt`, затем выбранные пути и завершающий `*`.
Пример для `Project/src/deep` и `Project/README.md`:

```text
#escape=\
// далее полный обязательный stignore.txt, без сокращения
!/README.md
!/README.md/**
!/src/deep
!/src/deep/**
*
```

Родительские `!/src` **не добавляются**, иначе включились бы соседние файлы; Syncthing сам проходит
к отмеченным потомкам и создаёт предков. Метасимволы путей экранируются, `#escape=\` делает правила
одинаковыми на Linux и Windows. Это проще отдельных folder на каждый файл: сохраняются ID, конфликты,
двусторонняя синхронизация и родительская структура. `.stignore` не передаётся другим устройствам.
[Правила Syncthing](https://docs.syncthing.net/users/ignoring.html).

`server-disk.sh tree` отдаёт по SSH только дерево `~/Disk`, без содержимого файлов, ссылок, секретных
и генерируемых каталогов. Непредставимые на Windows имена не предлагаются; дерево ограничено 20 000
дочерних записей, переполнение — явный отказ, а не урезанный успешный выбор. Форма позволяет выбрать
проект, подпапку или файл; оранжевый родитель означает частичный выбор. Настройки/задача прежнего
автоподключения обновляются, чтобы старый companion не принимал все папки поверх нового выбора.

Снятие отметки:

1. Неизвестная `.stignore` или reparse point блокируют операцию. Канонические/legacy правила принимаются
   после нормализации CRLF; один комментарий «managed» не даёт обхода. `Add`/автоподключение сохраняют
   уже проверенную локальную выборочную политику.
2. Запрашивается полный scan; требуется локальное `idle`, `needBytes=0`, `needTotalItems=0`,
   отсутствие pull errors и receive-only изменений. Затем подтверждается реальная пауза folder.
3. Сервер проверяет свой `idle`/отсутствие need/errors и completion именно этого устройства 100%,
   `needBytes=0`, `needItems=0`; возвращает SHA-256 существующих серверных копий.
4. Локальные файлы открываются с запретом записи, проверяются хеши. Несовпадение/отсутствие копии,
   открытый редактор, отсутствие SSH/API или паузы сохраняют файлы и дают ошибку.
5. До удаления атомарно устанавливается новая `.stignore` с Flush(true), временный файл/backup лежат
   внутри нативной `.stfolder`, которая не синхронизируется. Только затем удаляются проверенные файлы;
   пустые невыбранные каталоги убираются без рекурсивного удаления содержимого. Секреты, зависимости,
   `.git`, `.stversions` и ссылки не удаляются. Пауза снимается в finally; при неподтверждённой паузе
   оставляется честная ошибка и пауза, а не риск удаления.
6. Ничего на сервере не удаляется/не отвязывается. Повторный выбор скачивает актуальную серверную версию.
   Ошибка среди нескольких проектов может оставить уже применённые проекты; окно сообщает о неполном
   применении, остальные файлы сохраняются, повтор безопасен. Это не транзакция сразу всех проектов.

Собственный код отвечает только за UI/правила/проверку перед освобождением места; передачу данных,
версии и конфликты выполняет Syncthing. Отображение в дереве Проводника не добавлялось.

### Живая проверка владельцем на стационарном

Все действия ниже — локально, двойным щелчком и через окна/трей, без команд через Windows-мост.

1. Сохранить резервную копию своего ключа Happier через «Резервные ключи Happier»; убедиться, что текущие
   чаты и подключение второго компьютера доступны. Запустить новый `release/RemoteAgents.exe` поверх
   установки, сервер не сбрасывать, профили/канал/папки не удалять. Дождаться штатной проверки перехода.
2. При первом локальном выборе подключить **существующий** ключ. В браузере/телефоне восстановить тот же
   аккаунт. Убедиться, что прежние чаты остались, серверная machine доступна, второй компьютер работает.
   Снова запустить EXE: ключ повторно не запрашивается, новой machine для этого account/relay не появляется.
3. В дереве оставить одну безопасную тестовую папку, одну её подпапку и один файл другого проекта.
   Проверить `Disk/<Имя>/<подпапка>`: только отмеченное, соседние файлы остаются на сервере;
   `.env`, `.git`, `node_modules` не передаются. На старой установке уже скачанное удаляется только после проверки.
4. Изменить безопасный тестовый файл при отключённом соединении и снять отметку: должен быть отказ,
   локальная правка остаётся. После восстановления соединения дождаться синхронизации и повторить:
   локальная копия убирается, последняя правка есть на сервере. Снова поставить галочку — файл возвращается.
5. Через «Аккаунт Happier…» создать новый; сохранить его ключ. В другом профиле браузера восстановить его:
   история отдельная, серверная машина своя, прежний аккаунт по старому ключу по-прежнему доступен.
   Открыть тестовый чат Claude/Codex с **native** provider authentication: используются прежние подписки.
6. Подключить старый ключ обратно, повторить запуск EXE и проверить обе истории и второй компьютер.
   Проверить отмену формы, недоступность SSH и API: неподтверждённое состояние не показывается успешным.

Остаётся живая проверка PS 5.1/WinForms, ACL и FileShare.Delete на NTFS при открытом редакторе,
systemd+реальный Happier relay/online machine, штатное восстановление ключа на телефоне и доступность
нативных подписок из обоих аккаунтов. Linux fixtures и успешная сборка этого не заменяют.
