# Настройка сервера из мастер-конфига

`server/server-apply.sh` запускается на сервере. Он читает тот же мастер-конфиг,
который принимает приложение. Разделы компьютера (`device`, `disk`, `vpn`,
`bridge` и остальные) не устанавливают ничего на сервере. C#-движок вызывает общий reconciler через `Wizard.ServerApply.ps1`: один профиль и отдельный канал секретов, затем plan/apply/новый SSH/confirm.

```bash
sudo server/server-apply.sh plan --config /root/master-config.json
sudo server/server-apply.sh apply --config /root/master-config.json
sudo server/server-apply.sh status --config /root/master-config.json --json
# Конфиг можно передать вместо файла:
sudo server/server-apply.sh plan < /root/master-config.json
```

`plan` и `status` только читают состояние. Они не создают каталогов, временных
файлов или журналов, не устанавливают пакеты и не перезапускают службы.
Русский вывод предназначен владельцу; `--json` возвращает `schema`, `command`,
`parts`, `actions`, `ok`. Состояния частей: `ready`, `change`, `waiting`,
`pending`, `blocked`, `error`. Успешный повторный `apply` возвращает пустой
список `actions`. Ошибка или ожидание в `apply` даёт код возврата 1;
`plan`/`status` успешно возвращают сам отчёт даже при незавершённых частях.

## Что устанавливается

Сначала проверяется программа, которая пускает трафик сервера через выбранный
внешний выход: служба sing-box, её системный перехват трафика, правила
9000–9010 (включая частичную пропажу правил с одинаковым приоритетом), основной выход `proxy-out` и фактический внешний IP. Проверка curl
игнорирует переменные прокси. Ожидаемый IP берётся из `proxyOut.exitIp`, иначе
из `proxyOut.server`. Если сервер прокси задан DNS-именем, `exitIp` обязателен.
Если правила исчезли, `apply` перезапускает sing-box и повторяет проверку.
Если выход остался неверным, остальные части не устанавливаются. Поле `proxyOut.ipv6` задаёт отдельное решение для IPv6:
`"block"` запрещает исходящие IPv6-соединения, `"allow"` разрешает прямой IPv6.
Если поле не задано, программа, серверный движок и экспорт добавляют `block`.
Явный `allow` пока читается для совместимости. В новых конфигурациях используйте `block`.
При `block` таблица `inet remoteagents_ipv6` разрешает loopback, ответы
(`ct direction reply`, established/related) и ICMPv6 для соседей и PMTU
(destination-unreachable, packet-too-big, time-exceeded, parameter-problem,
router/neighbor solicitation/advertisement). Остальной исходящий IPv6,
включая ранее установленные исходящие соединения и echo-request, запрещён.
`allow` снимает только собственную таблицу запрета, чужие firewall не меняет.
Изменение самого прокси делает прежний `proxy_out.py`: его проверка кандидата,
таймер отката и подтверждение сохраняются. Отсутствующий пароль не очищает
действующий рабочий прокси.

Далее ставятся сторож выхода, ЛВС, штатный Tailscale, шлюз Telegram и права
агента. Публичные результаты `apply` записываются в root-журнал
`/var/log/remoteagents/server-apply.log`; это служебная запись, не действие по
изменению настроек. `plan` и `status` этот журнал не пишут. Сторож `remoteagents-egress-watch.timer` проверяет выход каждую минуту,
при пропаже правил выхода или неверном внешнем IP перезапускает sing-box.
При пропаже защиты входящих он восстанавливает только собственную таблицу nft
и правило ответов, без перезапуска sing-box. События видны через
`journalctl -u remoteagents-egress-watch.service -t remoteagents-egress-watch`.
Повторная неудача записывается с уровнем `daemon.crit`; публичная сводка
`/var/lib/remoteagents-status/egress.json` отображается в `status`.
Проверки сторожа и изменения ЛВС/прокси используют общий сетевой замок.

Ответы на входящие SSH, VPN, Telegram и другие подключения защищаются
отдельно от исходящего выхода. Таблица `inet remoteagents_inbound` отмечает
новые соединения с внешнего интерфейса `ct mark 0x5241` в prerouting mangle;
цепочка **route output** mangle переносит эту метку в `meta mark`.
Правило `pref 8990 fwmark 0x5241 lookup main` направляет ответы в основную
таблицу раньше sing-box. Внешний интерфейс берётся из default таблицы main
с наименьшей метрикой, имя `eth0` в коде не закреплено. Для IPv6-перехвата
sing-box добавляется такое же правило IPv6.
Ручная заплатка с теми же параметрами признаётся действующей и не дублируется.
Чужое правило на приоритете 8990 вызывает понятный отказ без его удаления.
Защита ставится до возможного перезапуска sing-box.

`remoteagents-network-guard.service` включается на загрузку перед sing-box,
после сети и nftables; читает публичный `watch.json`, заново определяет интерфейс,
восстанавливает защиту ответов и выбранное правило IPv6. Код и конфиг принадлежат
root. Сторож каждую минуту проверяет их действующее состояние и исправляет его.
`plan/status` отдельно показывают действующую защиту и необходимость установить
постоянную службу. Временная ручная заплатка сама по себе не переживает загрузку.

Если защиты нет **или** таблица sing-box (обычно 2022) не содержит default,
появляется предупреждение: «ответы на входящие подключения (SSH, VPN) уйдут
в sing-box — мосты компьютеров отвалятся». При установленной защите отчёт
явно сообщает об этом: отсутствие default остаётся опасным условием,
защита предотвращает потерю ответов. Сторож не меняет эту таблицу и не
перезапускает sing-box из-за одного этого предупреждения: старые исключения
удаляет миграция ЛВС при enable/старте/переподключении. При неудаче восстановления
защиты сторож пишет критическое событие и не перезапускает sing-box.

ЛВС применяется существующим `lan_vpn.py`: профиль импортируется, сеть включается,
проверяется `host:port`, проверяются маршруты действующих SSH-клиентов.
`testHost`/`testPort` задают проверяемый хост и порт; прежние `host`/`port` поддерживаются как алиасы. Противоречащие друг другу алиасы отклоняются. `subnets` — дополнительные частные подсети,
остальные частные подсети могут прийти от шлюза. `directEndpoint` разрешает
обращаться к шлюзу напрямую только процессу OpenVPN с закреплёнными
IP/протоколом/портом. Подсети ЛВС и шлюз обходят перехват через
ранние правила маршрутизации, без добавления исключений TUN; подробнее в [LAN.md](LAN.md). `dnsDomain` и `dnsServer` задаются вместе.
Одинаковый подтверждённый профиль и параметры не переустанавливаются. Замена
профиля/отпечатка использует снимок прежнего файла клиента и прежних настроек.
При ошибке прежний механизм отката выключает клиентов и возвращает настройки;
он намеренно не обещает сам переподключить прежние сети.

Для снятия таймера нужен **внешний** проверяющий: он открывает новое SSH-соединение
после изменения, затем в нём повторяет `apply --confirm-ssh-checked`. EXE делает это сам. Флаг подтверждает только изменение, ожидавшее подтверждения до начала команды.
Если сеть включается в этом запуске впервые, даже с флагом остаётся таймер: новое
SSH можно проверить только после изменения. Один только `ip route get`
не заменяет новое SSH. Без флага таймер остаётся и через пять минут откатывает
неподтверждённое изменение. Если несколько ЛВС требуют изменений, каждую
сетевую транзакцию надо подтвердить до следующей; разные части при этом
показывают свои независимые результаты.

Если CA в `.ovpn` не содержит keyUsage, команда показывает его SHA-256 как
**кандидат** для сверки и поля `serverFingerprint`, останавливая эту часть.
Это не доказательство того, какой сертификат предъявит удалённый шлюз: его
нужно сверить у администратора. Автоматического принятия найденного сертификата
нет. Профиль хранится во временном root-файле 0600, после импорта файл удаляется.
После обычного переподключения статус сохраняет прежнее подтверждение с датой;
это не выдаётся за новую проверку доступности хоста.

Tailscale устанавливается из официального репозитория `pkgs.tailscale.com`
для Debian/Ubuntu. До установки пакета готовится `/etc/default/tailscaled`;
по умолчанию служба работает без собственного сетевого интерфейса
(`userspace: true`). Она не меняет маршруты клиники и не раздаёт подсети или
выход в интернет. Ключ входа используется только для ещё не вошедшего узла,
через временный файл 0600. В этом режиме системные программы автоматически
не получают доступ к адресам 100.x; для их исходящих подключений нужен
отдельно настроенный прокси Tailscale для исходящих программ. `userspace: false` теперь отклоняется: серверный Tailscale не должен создавать интерфейс/маршруты.

Миграция тестового узла выполняется **только отдельной явной командой**:

```bash
sudo server/server-apply.sh tailscale-migrate --from /путь/к/копии/statedir --user рабочий_пользователь
```

Она останавливает штатную службу и пользовательскую `ts-test.service`,
копирует `tailscaled.state` с правами 0600 и включает штатную службу. Пакет
Tailscale и штатная служба должны быть установлены до миграции; команда сама
не загружает пакеты и не выполняет новый вход.
Существующее штатное состояние перезаписывать отказывается. Имя и адрес узла
сохраняются его состоянием. На сервере 109 эта команда в рамках задания не запускалась.

Шлюз Telegram устанавливается от имени `server.login` через `runuser`, с
включённым `linger`. Действующая служба с тем же портом, автозапуском и успешной
защищённой проверкой `/health` остаётся без изменений. Внешних секретов для
установки нет: сертификат и клиентские ключи создаёт сам установщик.
Выдача доступа клиентам — отдельная команда из [TG-GATEWAY.md](TG-GATEWAY.md).

`agent.sudo` по умолчанию равен `apply`: устанавливается root-копия кода
в `/usr/local/lib/remoteagents/server/`, правило
`/etc/sudoers.d/91-remoteagents-apply` разрешает только её `server-apply.sh`.
Код и каталоги принадлежат root и недоступны рабочему пользователю для записи.
Такой делегированный запуск не может расширить sudo или сменить рабочего пользователя;
`tailscale-migrate` выполняет только администратор с полными правами.
`full` означает NOPASSWD ALL в `90-remoteagents`; `none` убирает оба управляемых
правила. Удаление или замена существующих прав происходит только при **явном**
`agent.sudo`. Перед записью проверяется кандидат через `visudo -cf`.

## Чистый VPS и единый движок программы

Первое создание системного sing-box разрешается явным `serverNetwork.enabled: true`.
Нужны Debian/Ubuntu, systemd и Python 3, доступ к официальным подписанным apt-репозиториям,
HTTPS-проверка IP и доступный SOCKS5/HTTP-прокси. Пример без доступов:
[server-bootstrap.example.json](../server/server-bootstrap.example.json).

```json
"serverNetwork": {
  "enabled": true,
  "tunAddress": "172.30.250.1/30",
  "tunName": "ra-tun",
  "inboundPorts": [22, 443, 37091],
  "inbounds": {"secret": "server-inbounds"}
}
```

`proxyOut` содержит протокол `socks|http`, `server`, `port`, при необходимости
публичный `login` и ссылку `password`; при первом включении обязательны `exitIp`,
`checkUrl`; `ipv6` по умолчанию `block`. `tunAddress` — свободная RFC1918-подсеть /24…/30;
по умолчанию 172.30.250.1/30, имя интерфейса — ra-tun. Пересечение с маршрутами
контейнера/сервера вызывает отказ. Это параметры **первоначального создания**:
действующие чужие входы и TUN существующего sing-box не заменяются.
Если конфиг sing-box уже существует, но TUN не найден, автоматическая замена запрещена.

Секрет `server-inbounds` необязателен: JSON-массив обычных inbound-объектов sing-box
без TUN (например, VLESS/Reality с ключами). Он проверяется штатным `sing-box check`.
Сгенерированные системный TUN и локальный mixed `127.0.0.1:1080` добавляются отдельно.
Значения входов остаются в секрете; в переносимом конфиге только ссылка.
Порты 443/канала не открываются пустыми заглушками: соответствующий вход должен быть
описан этим секретом или обслуживаться другой службой. `inboundPorts` перечисляет
**реальные входящие TCP-порты**, которые компьютер проверит перед confirm; SSH-порт
из `server.port` добавляется автоматически. Они должны быть доступны компьютеру.
TCP-проверка доказывает доступность порта; она не заменяет прикладной тест VLESS/Reality.

Порядок: разрешение секретов и конфликтов → подписанный пакет sing-box и зависимости →
`sing-box check` → проверка прокси напрямую с ожидаемым IP → root-owned recovery-код →
снимок исходного config/службы/собственных nft-таблиц/правил → таймер 5 минут →
ct-mark/правило 8990 и IPv6-политика → TUN → полная проверка 9000–9010 и выхода.
Готовность правил после запуска службы ожидается ограниченное время. В sing-box 1.14+
для нового TUN задан `dns_mode: disabled`, чтобы не включить неописанный DNS-перехват.
Публичные адреса не добавляются в `route_exclude_address`.

Без нового SSH начальная сеть остаётся `pending`. Программа проверяет входящие порты
и подтверждает её **в следующем отдельном SSH-процессе**; ControlMaster/ControlPath/
ControlPersist отключены. Нельзя подтвердить изменение флагом, переданным до его начала.
Изменение конфига/секрета входов во время pending запрещает confirm. Потеря EXE/SSH —
откат по `remoteagents-base-network-rollback.timer`; ошибка проверки — немедленный откат.
`remoteagents-base-network-recover.service` восстанавливает снимок до sing-box при reboot.
Пакеты и root-owned исполняемые файлы после отката остаются установленными.

Прокси и ЛВС используют свои прежние транзакции, по одной за раз. После каждого
нового pending цикл снова проверяет входящие и открывает новый SSH. Сторож выхода
не вмешивается в незавершённое первоначальное включение.

«Применить» в EXE подключает/создаёт рабочего пользователя и вызывает этот цикл.
Существующий sudo используется автоматически; ограниченное sudo вызывает только
установленный root-owned `server-apply.sh`, произвольный staging-код через него не запускается.
Для первой установки без sudo используется `server.rootPassword` через in-memory askpass.
Пароль root удаляется из vault только после успешного серверного развёртывания.
При ограниченном sudo обновление установленного root-кода требует администратора.

`ConfigSession.Plan` сверяет сервер через `status`; периодический/повторный вызов
не запускает apply. При явном применении сначала вызывается `plan`, а `apply` вызывается,
только если есть `change`/`pending`. Совпавший план возвращает `actions: []`.
Сводка частей видна в Настройки → Сервер / Локальные сети, в Диагностике и журнале;
локальная копия отчёта — `state/server-apply.json` (без значений секретов).

CLI-обёртка того же PowerShell-движка для стенда/диагностики:

```powershell
# stdin: JSON конфига, строка ---remoteagents-stdin---, JSON секретов.
# HomePath содержит уже проверенный SSH-профиль программы.
powershell -NoProfile -File build/ServerApply.ps1 -HomePath <папка-программы>
# Только чтение:
powershell -NoProfile -File build/ServerApply.ps1 -HomePath <папка-программы> -StatusOnly
```

## sshd и экспорт

Apply ставит `/etc/ssh/sshd_config.d/10-remoteagents-startups.conf` с `LoginGraceTime 30`
и `MaxStartups 30:30:150`, проверяет `sshd -t` и эффективные значения `sshd -T`, затем
делает reload `ssh.service`/`sshd.service`. При отказе восстанавливает прежний файл.
Если drop-in перекрыт или включён после Match, выдаётся ошибка с восстановлением файла.

После полностью успешного apply сохраняется публичный снимок
`/var/lib/remoteagents-status/server-config.json`. `remoteagents config export` подхватывает
из него `serverNetwork`, `proxyOut`, `lan`, `tailscale`, `telegramGateway`, `agent`.
В настройках выдачи можно явно задать `serverConfig` — путь к публичному снимку.
Снимок проходит ту же JSON-схему; в разделах секреты остаются ссылками, а в экспорте
добавляются пустые слоты имён. Обычный экспорт оставляет значения серверных секретов для отдельного переноса
или полного экспорта vault компьютера. После успешного apply их также включает явный
root-only `--include-server-secrets --output …` (описан ниже). Старый сервер без такого снимка продолжает выдавать
прежний конфиг подключения; для клонирования ему нужен `serverConfig` или успешное
применение мастер-конфига. Ручной sing-box с произвольными правилами не объявляется
полностью восстановимым по одному публичному снимку.

## Воспроизводимый изолированный стенд

```bash
python3 server/tests/autodeploy/run.py
```

Тест создаёт собственные Docker network/Ubuntu/systemd/sshd, HTTP CONNECT с TLS-оракулом,
OpenVPN со своим CA без keyUsage и публичными push. Только Tailscale — мок.
Проверяет CRLF, применение программным движком, Telegram, входящие 22/443/37091,
повторное `actions: []`, read-only status, экспорт ссылок и настоящий пятиминутный откат
после отзыва ключа для нового SSH. Прямой доступ к IP-оракулу запрещён на шлюзе:
успешный ответ проходит через прокси. Стенд требует Docker с systemd; VPS-контейнеры
запускаются privileged в собственных namespaces, единственный bind mount — исходники
read-only. В finally удаляются контейнеры, сеть, образ и временные секреты.
Это не проверка Windows PowerShell 5.1, DPAPI или настоящего Tailscale control plane.

## Какие секреты нужны

Публичный [пример 109](../server/server-apply.example.json) не содержит значений
секретов и не является полным восстановительным экспортом.

| Имя | Для чего |
|---|---|
| `proxy-out-password` | Пароль для нового/изменённого исходящего прокси, если он требует входа; логин — `proxyOut.login`. |
| `lan-clinic-ovpn` | Полный `.ovpn` со встроенными CA/сертификатом/закрытым ключом. |
| `lan-clinic-auth` | JSON-строка с `username` и `password` для клиники; оба значения остаются в секрете. |
| `tailscale-auth-key` | Первоначальный вход штатного узла Tailscale. |

Ранее существовавшие `lan[].login` и `password` читаются для совместимости;
для новых конфигов используйте `auth: {"secret":"lan-имя-auth"}`.
Без закрытого ключа внутри `.ovpn` профиль клиники не восстановится.
SSH-ключ сервера, ключ Happier, ключи VPN-входа/Reality и пароли SSH-переходов
также не восстанавливаются из открытого конфига; соответствующие установщики
находятся за пределами этой серверной команды.

Секреты берутся из `secrets` полного экспорта. Для `enc1:` используется прежняя
расшифровка `remoteagents_config.unprotect`. С файлом-конфигом мастер-пароль
запрашивается без эха в терминале. Для автоматического вызова после строки
`---remoteagents-stdin---` передаётся JSON: либо словарь `имя: значение`, либо
`{"masterPassword":"…","secrets":{"имя":"…"}}`. Если конфиг идёт на stdin,
сначала передаётся JSON конфига, затем отдельная строка-маркер и JSON секретов.
С файлом-конфигом добавляется `--secrets-stdin`; перед маркером может остаться
строка пароля sudo — она отбрасывается. В командной строке секретов нет.
Не вставляйте значения в чат, аргументы команд, подсказки или журнал.

При отсутствии секрета часть пишет «ждёт секрет», остальные продолжают работу,
если внешний выход проверен. Неоткрытый защищённый экспорт тоже даёт список
недостающих имён. Для аудита действующей ручной установки без её закрытых файлов
есть `plan/status --public-only`: показываются служба и публичная сводка ЛВС,
с явной пометкой, что исходный профиль и параметры без полного экспорта не сравнены.
Это не подтверждает совпадение профиля по хэшу.

Официальные инструкции: [пакеты Tailscale](https://pkgs.tailscale.com/stable/),
[режим без интерфейса](https://tailscale.com/docs/concepts/userspace-networking),
[ключ входа из файла](https://tailscale.com/docs/reference/tailscale-cli/up),
[пакеты sing-box](https://sing-box.sagernet.org/installation/package-manager/).

Описание используемых механизмов: [селекторы ip rule](https://github.com/iproute2/iproute2/blob/main/man/man8/ip-rule.8.in),
[марки соединений и route output в nftables](https://www.netfilter.org/projects/nftables/manpage.html).


## Восстановление подтверждённой установки

`deployment.method` по умолчанию `host`. `docker` с `dockerfile`/`image`
валиден как формат, но EXE и reconciler возвращают «ещё не поддерживается» до
развёртывания. [Dockerfile-скелет и границы](../server/docker/README.md).

Первичный root-bootstrap ставит отсутствующие зависимости Debian/Ubuntu до
первого Python-вызова: Python, curl/CA, архиваторы, git, cron, sudo, iproute2,
jq/nftables, DBus/user-session, python3-cryptography для защищённого экспорта. Для нового канонического пользователя
`remoteagents` записывает совместимую метку `managed-user-v1`; уже существующего
чужого пользователя автоматически управляемым не объявляет. Установка пакетов
в парольном SSH имеет лимит 600 с, вместо прежних 30 с. Эти начальные загрузки
пока выполняются до включения proxyOut; это ограничение bootstrap.

После полностью успешного apply сервер сохраняет
`/etc/remoteagents/server-apply/recovery.json`: root:root 0600, каталог 0700.
Внутри серверная проекция конфига и только секреты, на которые она ссылается.
Root-пароль, клиентский SSH-ключ, несвязанные секреты и мастер-пароль не сохраняются.
Лимит внутреннего снимка 32 МиБ, внешний переносимый конфиг по-прежнему 4 МиБ.
После каждого нового успешного применения снимок обновляется атомарно.

`remoteagents-reconcile.timer`: через 15 с после загрузки и через 30 с после
окончания предыдущей сверки; service имеет TimeoutStartSec=90. Сверка сериализуется
с apply, использует общий сетевой lock. Любая pending-транзакция base/LAN/proxy/
port-leak останавливает сверку: собственное новое SSH сторож не подтверждает.
Сначала возвращаются ct mark/8990 и IPv6 block, затем повреждённый sing-box
проверяется через `sing-box check`, возвращается подтверждённая копия и запускается
служба. Проверяются полный набор policy rules, внешний выход и защита входящих;
при неудаче замены файла возвращается прежний файл. Это восстановление ранее
проверенного состояния; новая конфигурация по-прежнему требует внешнего SSH.

Владение sing-box записывается только после confirm первоначального создания.
Произвольный существующий ручной sing-box не становится управляемым: для него
сторож чинит guard/службу, но не перезаписывает приватный файл. Для подтверждённых
ЛВС сохраняются client.conf и настройки. Их восстановление останавливает службу,
возвращает копии и запускает штатные OpenVPN hooks; локальный хост ЛВС проверяется
заново. Ожидание systemctl не держит network.lock, чтобы hooks не заблокировались.
Другие серверные разделы проверяются прежним Engine; новая pending остаётся pending.
Публичная сводка последней сверки — `/var/lib/remoteagents-status/recovery.json`.

Таймер не является полной резервной копией: не восстанавливает удалённого рабочего
пользователя/authorized_keys, произвольные ручные unit/drop-in, авторизации агентов,
идентичность Syncthing/Telegram/Happier и данные проектов. Установка Codex/Claude,
project views, idle chats и desktop пока не сведены в единую декларацию. Поэтому
требование «целиком как живой сервер» ещё не закрыто.

Tailscale сервера работает исключительно с `--tun=userspace-networking` и без
subnet routes. Его netstack доставляет входящий TCP на 100.x к localhost:тому же
порту sshd ([официальный исходник](https://github.com/tailscale/tailscale/blob/main/wgengine/netstack/netstack.go#L1714)).
Клиенту нужен работающий обычный Tailscale с TUN. Программа берёт единственный peer
по настроенному `tailscale.hostname`, выбирает IPv4 100.64/10 и добавляет кандидата
«Tailscale» в общий транспорт. Он проходит обычные пробы с закреплённым SSH-ключом
основного сервера. Истёкшие/неоднозначные узлы отбрасываются; Online не считается
проверкой SSH. Другие пути сохраняются. Это SSH-канал, не раздача ЛВС клиники и не
отдельный VPN-выход компьютера. [Формат status](https://github.com/tailscale/tailscale/blob/main/ipn/ipnstate/ipnstate.go).

Полный медленный стенд подключён к runner по явному флагу:

```sh
SERVER_AUTODEPLOY_E2E=1 bash server/tests/run.sh
# либо только Docker-стенд:
python3 server/tests/autodeploy/run.py
```

Его VPS-образ содержит systemd+sshd; отдельный gateway содержит тестовые службы.
Первичный вход действительно идёт по root-паролю через Invoke-WizardLogin, с
синтетическим askpass; затем тот же PowerShell ServerApply, что в EXE, включает
сеть/OpenVPN/Telegram. Tailscale control plane остаётся мокированным. После
перезапуска контейнера и порчи конфигов/правил/остановки служб проверка ждёт
готовность до 120 с, вызывая только status. Fixture-unit восстанавливает только
маршрут к тестовому шлюзу после перезапуска — это топология стенда. Реальный
пятиминутный откат при отказе нового SSH сохранён. Windows PS 5.1/DPAPI/WinForms
и настоящий tailnet проверяются отдельно; Linux-прогон их не подтверждает.

Для полного переноса серверных секретов появился **явный root-only** экспорт:

```sh
sudo server/remoteagents config --config /путь/к/публичным-настройкам-выдачи.json export \
  --name Restore --happier new:Restore --include-server-secrets \
  --master-password-stdin --output /защищённый-каталог/restore.json
```

В терминале мастер-пароль вводится скрыто. `--include-server-secrets` требует root
и `--output`; файл создаётся 0600 с отказом перезаписи. Обычный экспорт продолжает
выдавать пустые слоты серверных секретов. Полный режим сравнивает публичный и
восстановительный снимки, берёт только нужные именованные значения из root-копии,
генерирует рабочий SSH-ключ для нового компьютера и упаковывает всё в один
принимаемый программой JSON (при мастер-пароле — enc1). Пропавший/чужой снимок,
недостающий секрет и коллизии имён вызывают отказ; значения не печатаются.
Это включает серверные разделы, уже охваченные reconciler, и существующие возможности
экспорта пользовательского подключения; ручные идентичности других служб не извлекает.
На живом 109 такой экспорт в этой задаче не запускался.
