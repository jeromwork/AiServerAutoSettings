# Настройка сервера из мастер-конфига

`server/server-apply.sh` запускается на сервере. Он читает тот же мастер-конфиг,
который принимает приложение. Разделы компьютера (`device`, `disk`, `vpn`,
`bridge` и остальные) не устанавливают ничего на сервере. C#-движок применения
в этой задаче не менялся; автоматический вызов из EXE относится к заданию B.

```bash
sudo server/server-apply.sh plan --config /root/master-config.json
sudo server/server-apply.sh apply --config /root/master-config.json
sudo server/server-apply.sh status --config /root/master-config.json --json
# Конфиг можно передать вместо файла:
sudo server/server-apply.sh plan < /root/master-config.json
```

`plan` и `status` только читают состояние. Они не создают каталогов, временных
файлов или журналов, не устанавливают пакеты и не перезапускают службы.
Русский вывод предназначен владельцу; `--json` возвращает `schema`, `command`,
`parts`, `actions`, `ok`. Состояния частей: `ready`, `change`, `waiting`,
`pending`, `blocked`, `error`. Успешный повторный `apply` возвращает пустой
список `actions`. Ошибка или ожидание в `apply` даёт код возврата 1;
`plan`/`status` успешно возвращают сам отчёт даже при незавершённых частях.

## Что устанавливается

Сначала проверяется программа, которая пускает трафик сервера через выбранный
внешний выход: служба sing-box, её системный перехват трафика, правила
9000–9010 (включая частичную пропажу правил с одинаковым приоритетом), основной выход `proxy-out` и фактический внешний IP. Проверка curl
игнорирует переменные прокси. Ожидаемый IP берётся из `proxyOut.exitIp`, иначе
из `proxyOut.server`. Если сервер прокси задан DNS-именем, `exitIp` обязателен.
Если правила исчезли, `apply` перезапускает sing-box и повторяет проверку.
Если выход остался неверным, остальные части не устанавливаются. Поле `proxyOut.ipv6` задаёт отдельное решение для IPv6:
`"block"` запрещает исходящие IPv6-соединения, `"allow"` разрешает прямой IPv6.
Если поле не задано, `plan/status` честно предупреждают о возможном обходе
sing-box; остальные части устанавливаются. Автоматического запрета нет,
ранее установленный запрет при удалении поля сохраняется.
При `block` таблица `inet remoteagents_ipv6` разрешает loopback, ответы
(`ct direction reply`, established/related) и ICMPv6 для соседей и PMTU
(destination-unreachable, packet-too-big, time-exceeded, parameter-problem,
router/neighbor solicitation/advertisement). Остальной исходящий IPv6,
включая ранее установленные исходящие соединения и echo-request, запрещён.
`allow` снимает только собственную таблицу запрета, чужие firewall не меняет.
Изменение самого прокси делает прежний `proxy_out.py`: его проверка кандидата,
таймер отката и подтверждение сохраняются. Отсутствующий пароль не очищает
действующий рабочий прокси.

Далее ставятся сторож выхода, ЛВС, штатный Tailscale, шлюз Telegram и права
агента. Публичные результаты `apply` записываются в root-журнал
`/var/log/remoteagents/server-apply.log`; это служебная запись, не действие по
изменению настроек. `plan` и `status` этот журнал не пишут. Сторож `remoteagents-egress-watch.timer` проверяет выход каждую минуту,
при пропаже правил выхода или неверном внешнем IP перезапускает sing-box.
При пропаже защиты входящих он восстанавливает только собственную таблицу nft
и правило ответов, без перезапуска sing-box. События видны через
`journalctl -u remoteagents-egress-watch.service -t remoteagents-egress-watch`.
Повторная неудача записывается с уровнем `daemon.crit`; публичная сводка
`/var/lib/remoteagents-status/egress.json` отображается в `status`.
Проверки сторожа и изменения ЛВС/прокси используют общий сетевой замок.

Ответы на входящие SSH, VPN, Telegram и другие подключения защищаются
отдельно от исходящего выхода. Таблица `inet remoteagents_inbound` отмечает
новые соединения с внешнего интерфейса `ct mark 0x5241` в prerouting mangle;
цепочка **route output** mangle переносит эту метку в `meta mark`.
Правило `pref 8990 fwmark 0x5241 lookup main` направляет ответы в основную
таблицу раньше sing-box. Внешний интерфейс берётся из default таблицы main
с наименьшей метрикой, имя `eth0` в коде не закреплено. Для IPv6-перехвата
sing-box добавляется такое же правило IPv6.
Ручная заплатка с теми же параметрами признаётся действующей и не дублируется.
Чужое правило на приоритете 8990 вызывает понятный отказ без его удаления.
Защита ставится до возможного перезапуска sing-box.

`remoteagents-network-guard.service` включается на загрузку перед sing-box,
после сети и nftables; читает публичный `watch.json`, заново определяет интерфейс,
восстанавливает защиту ответов и выбранное правило IPv6. Код и конфиг принадлежат
root. Сторож каждую минуту проверяет их действующее состояние и исправляет его.
`plan/status` отдельно показывают действующую защиту и необходимость установить
постоянную службу. Временная ручная заплатка сама по себе не переживает загрузку.

Если защиты нет **или** таблица sing-box (обычно 2022) не содержит default,
появляется предупреждение: «ответы на входящие подключения (SSH, VPN) уйдут
в sing-box — мосты компьютеров отвалятся». При установленной защите отчёт
явно сообщает об этом: отсутствие default остаётся опасным условием,
защита предотвращает потерю ответов. Сторож не меняет эту таблицу и не
перезапускает sing-box из-за одного этого предупреждения: старые исключения
удаляет миграция ЛВС при enable/старте/переподключении. При неудаче восстановления
защиты сторож пишет критическое событие и не перезапускает sing-box.

ЛВС применяется существующим `lan_vpn.py`: профиль импортируется, сеть включается,
проверяется `host:port`, проверяются маршруты действующих SSH-клиентов.
Поля `host`/`port` имеют смысл тестового хоста и порта: отдельные
`testHost`/`testPort` не добавлены. `subnets` — дополнительные частные подсети,
остальные частные подсети могут прийти от шлюза. `directEndpoint` разрешает
обращаться к шлюзу напрямую только процессу OpenVPN с закреплёнными
IP/протоколом/портом. Подсети ЛВС и шлюз обходят перехват через
ранние правила маршрутизации, без добавления исключений TUN; подробнее в [LAN.md](LAN.md). `dnsDomain` и `dnsServer` задаются вместе.
Одинаковый подтверждённый профиль и параметры не переустанавливаются. Замена
профиля/отпечатка использует снимок прежнего файла клиента и прежних настроек.
При ошибке прежний механизм отката выключает клиентов и возвращает настройки;
он намеренно не обещает сам переподключить прежние сети.

Для снятия таймера нужен **внешний** проверяющий: он открывает новое SSH-соединение
после изменения, затем в нём повторяет `apply --confirm-ssh-checked`. EXE будет
делать это сам. Флаг подтверждает только изменение, ожидавшее подтверждения до начала команды.
Если сеть включается в этом запуске впервые, даже с флагом остаётся таймер: новое
SSH можно проверить только после изменения. Один только `ip route get`
не заменяет новое SSH. Без флага таймер остаётся и через пять минут откатывает
неподтверждённое изменение. Если несколько ЛВС требуют изменений, каждую
сетевую транзакцию надо подтвердить до следующей; разные части при этом
показывают свои независимые результаты.

Если CA в `.ovpn` не содержит keyUsage, команда показывает его SHA-256 как
**кандидат** для сверки и поля `serverFingerprint`, останавливая эту часть.
Это не доказательство того, какой сертификат предъявит удалённый шлюз: его
нужно сверить у администратора. Автоматического принятия найденного сертификата
нет. Профиль хранится во временном root-файле 0600, после импорта файл удаляется.
После обычного переподключения статус сохраняет прежнее подтверждение с датой;
это не выдаётся за новую проверку доступности хоста.

Tailscale устанавливается из официального репозитория `pkgs.tailscale.com`
для Debian/Ubuntu. До установки пакета готовится `/etc/default/tailscaled`;
по умолчанию служба работает без собственного сетевого интерфейса
(`userspace: true`). Она не меняет маршруты клиники и не раздаёт подсети или
выход в интернет. Ключ входа используется только для ещё не вошедшего узла,
через временный файл 0600. В этом режиме системные программы автоматически
не получают доступ к адресам 100.x; для их исходящих подключений нужен
отдельно настроенный прокси Tailscale или осознанный выбор `userspace: false`.

Миграция тестового узла выполняется **только отдельной явной командой**:

```bash
sudo server/server-apply.sh tailscale-migrate --from /путь/к/копии/statedir --user рабочий_пользователь
```

Она останавливает штатную службу и пользовательскую `ts-test.service`,
копирует `tailscaled.state` с правами 0600 и включает штатную службу. Пакет
Tailscale и штатная служба должны быть установлены до миграции; команда сама
не загружает пакеты и не выполняет новый вход.
Существующее штатное состояние перезаписывать отказывается. Имя и адрес узла
сохраняются его состоянием. На сервере 109 эта команда в рамках задания не запускалась.

Шлюз Telegram устанавливается от имени `server.login` через `runuser`, с
включённым `linger`. Действующая служба с тем же портом, автозапуском и успешной
защищённой проверкой `/health` остаётся без изменений. Внешних секретов для
установки нет: сертификат и клиентские ключи создаёт сам установщик.
Выдача доступа клиентам — отдельная команда из [TG-GATEWAY.md](TG-GATEWAY.md).

`agent.sudo` по умолчанию равен `apply`: устанавливается root-копия кода
в `/usr/local/lib/remoteagents/server/`, правило
`/etc/sudoers.d/91-remoteagents-apply` разрешает только её `server-apply.sh`.
Код и каталоги принадлежат root и недоступны рабочему пользователю для записи.
Такой делегированный запуск не может расширить sudo или сменить рабочего пользователя;
`tailscale-migrate` выполняет только администратор с полными правами.
`full` означает NOPASSWD ALL в `90-remoteagents`; `none` убирает оба управляемых
правила. Удаление или замена существующих прав происходит только при **явном**
`agent.sudo`. Перед записью проверяется кандидат через `visudo -cf`.

## Чистый VPS: существующее ограничение

Полный запуск на чистом VPS пока **не реализован до конца**. Одна команда

```bash
sudo server/server-apply.sh apply --config /root/master-config.json
```

честно остановится на сообщении «нужен базовый сетевой конфиг с правилами
сохранения SSH», если sing-box не установлен или нет системного перехвата.
Пакеты и остальные части в этом случае не ставятся через собственный адрес VPS.

Причина: переносимый формат пока описывает исходящий прокси, но не базовую
сеть сервера: адреса перехвата IPv4/IPv6 и конфликты, входящие SSH/RDP и их
допустимые прямые ответы, вход VPN и ключи Reality. Образец
`/tmp/server-deploy/singbox-109-redacted.json` содержит ручные исключения целой
сети провайдера и портов. Копировать такие исключения на любой VPS означало бы
самовольно разрешить выход мимо прокси. Требуется решение владельца о формате
базовой сети и правилах её первоначального включения с откатом.

Поиск источника входов: `server-happ.sh` создаёт **отдельный Xray**,
`transport/entry/install-entry.sh` — отдельный sing-box промежуточного узла
в `/opt/rd-entry`; `server_node_catalog.py` ведёт привязки мостов, сеть не создаёт.
Кода, который создаёт именно системные `vless-in`/`mixed-in` из образца 109,
в текущем репозитории не найдено. Они остаются нетронутыми: изменение proxy-out
делегируется установщику, сохраняющему прочие входы и правила.

## Какие секреты нужны

Публичный [пример 109](../server/server-apply.example.json) не содержит значений
секретов и не является полным восстановительным экспортом.

| Имя | Для чего |
|---|---|
| `proxy-out-password` | Пароль для нового/изменённого исходящего прокси, если он требует входа; логин — `proxyOut.login`. |
| `lan-clinic-ovpn` | Полный `.ovpn` со встроенными CA/сертификатом/закрытым ключом. |
| `lan-clinic-auth` | JSON-строка с `username` и `password` для клиники; оба значения остаются в секрете. |
| `tailscale-auth-key` | Первоначальный вход штатного узла Tailscale. |

Ранее существовавшие `lan[].login` и `password` читаются для совместимости;
для новых конфигов используйте `auth: {"secret":"lan-имя-auth"}`.
Без закрытого ключа внутри `.ovpn` профиль клиники не восстановится.
SSH-ключ сервера, ключ Happier, ключи VPN-входа/Reality и пароли SSH-переходов
также не восстанавливаются из открытого конфига; соответствующие установщики
находятся за пределами этой серверной команды.

Секреты берутся из `secrets` полного экспорта. Для `enc1:` используется прежняя
расшифровка `remoteagents_config.unprotect`. С файлом-конфигом мастер-пароль
запрашивается без эха в терминале. Для автоматического вызова после строки
`---remoteagents-stdin---` передаётся JSON: либо словарь `имя: значение`, либо
`{"masterPassword":"…","secrets":{"имя":"…"}}`. Если конфиг идёт на stdin,
сначала передаётся JSON конфига, затем отдельная строка-маркер и JSON секретов.
С файлом-конфигом добавляется `--secrets-stdin`; перед маркером может остаться
строка пароля sudo — она отбрасывается. В командной строке секретов нет.
Не вставляйте значения в чат, аргументы команд, подсказки или журнал.

При отсутствии секрета часть пишет «ждёт секрет», остальные продолжают работу,
если внешний выход проверен. Неоткрытый защищённый экспорт тоже даёт список
недостающих имён. Для аудита действующей ручной установки без её закрытых файлов
есть `plan/status --public-only`: показываются служба и публичная сводка ЛВС,
с явной пометкой, что исходный профиль и параметры без полного экспорта не сравнены.
Это не подтверждает совпадение профиля по хэшу.

Официальные инструкции: [пакеты Tailscale](https://pkgs.tailscale.com/stable/),
[режим без интерфейса](https://tailscale.com/docs/concepts/userspace-networking),
[ключ входа из файла](https://tailscale.com/docs/reference/tailscale-cli/up),
[пакеты sing-box](https://sing-box.sagernet.org/installation/package-manager/).

Описание используемых механизмов: [селекторы ip rule](https://github.com/iproute2/iproute2/blob/main/man/man8/ip-rule.8.in),
[марки соединений и route output в nftables](https://www.netfilter.org/projects/nftables/manpage.html).
