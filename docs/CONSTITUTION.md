# Конституция проекта

Правила обязательны для людей и агентов. Изменяет их только владелец.

## 1. Приложение универсальное

Продукт работает у любого пользователя на любом подходящем сервере, а не только в нашей конфигурации.

- Домен, сервер, хостинг, прокси, DNS-провайдер, промежуточный хост и VPN-маршрут задаёт пользователь. В коде их значений нет.
- Если для функции нужен домен, приложение предлагает настроить свой и объясняет, что сделать. Если домена нет, оно говорит, что без него доступно.
- Наши значения (`corenetai.ru`, конкретный VPS, конкретный прокси) допустимы только в личном `config.json`, который не хранится в Git.
- Сторонний сервис подключается как сменный вариант, а не как условие работы продукта.
- Проверка правила: новый пользователь со своим сервером и доменом проходит мастер без правки кода.

## 2. Минимум своего кода

Там, где есть живое решение (Syncthing, sing-box, OpenSSH), пишем настройку и управление, а не свою реализацию. Если свой код всё же нужен, рядом указывается причина.

## 3. Настройки в конфиге, секреты отдельно

- Настройки хранятся в `config.json` со схемой и версией. В Git только схема и пример.
- Секреты в Git не попадают, в журналы и вывод не выводятся.
- Отметка «этап пройден» не заменяет проверку: перед пропуском этапа выполняется реальный тест.

## 4. Изменения сети обратимы

Любое изменение сети на сервере или компьютере проверяется до применения и имеет автоматический откат. Связь с компьютером не должна зависеть от того, что мы сейчас меняем.

## 5. Честный статус

Приложение и агенты показывают только проверенное состояние. Отсутствие подключения, паузу и ошибку не выдают за успешную работу. Проверка на заглушках не считается проверкой на реальной системе.

## 5а. Явные журналы

Журналы включены всегда и не зависят от компонента, который могут диагностировать: локальный файл пишется без сети, отправка на сервер не использует Syncthing и мост. Секреты в журнал не попадают.

## 6. Подключение остаётся своим

Подключение компьютера к серверу не выдаёт себя за чужой сервис. Основной путь: HTTPS к серверу пользователя под доменом пользователя.

## 6а. Как работают агенты

- Поиск в интернете выполняет субагент, а не Claude. Пока это Codex на `gpt-6.1-sol`; Gemini (`agent:agy`) отложен до отдельной проверки. Вывод проверяется перед использованием.
- Код пишет Codex на `gpt-6.1-sol` с уровнем `high`. Модели Luna не используются.
- Выбор готового компонента делается сравнением по условиям продукта: лёгкий, просто встраивается в `.exe`. То, что компонент уже стоит в проекте, не является аргументом.

## 6б. Переводы строк: CRLF ломает Linux

На Windows файлы проекта хранятся с CRLF. Это постоянный источник ошибок: лишний `\r` ломает команды bash, here-документы, имена и сравнения, а тесты на Linux этого не видят.

- Всё, что передаётся с Windows на Linux (команды, stdin, скрипты, файлы), приводится к LF в одном общем месте.
- Весь вывод, полученный с другой системы, очищается от `\r` перед разбором и сравнением.
- Код, работающий на обеих системах, проверяется и с CRLF-входом: автотест обязан подавать `\r\n`.
- Сравнивается содержимое, а не байты переводов строк, если формат строк явно не важен.

## 6в. PowerShell 5.1 и 7 ведут себя по-разному

Приложение работает на Windows PowerShell 5.1. Прохождение тестов на PowerShell 7 это не подтверждает: например, `ConvertFrom-Json` в 5.1 отдаёт массив одним объектом. Такие места пишутся так, чтобы работали в обеих версиях, а итоговая проверка выполняется на настоящем Windows.

## 6г. Где лежат проекты: папка Disk

Один проект — одна папка с одним и тем же именем на сервере и на каждом компьютере.

- Сервер: `~/Disk/<Имя>`. Компьютер: `%USERPROFILE%\Disk\<Имя>`, как у Яндекс Диска. Другую базу может выбрать только пользователь, она хранится в `%LOCALAPPDATA%\RemoteDisk\base.txt` (`Get-DiskBase` в `disk/Disk.Common.ps1`).
- Уровень один: `<Имя>` — это имя папки проекта (`BackendLaravel`, `diqi`). Группирующих папок нет: `Disk\eastclinic\BackendLaravel` недопустим. Допустимые символы проверяет `folder_path` в `disk/server-disk.sh`.
- Других мест для проектов нет: `C:\work`, `Projects`, `source\repos` и любые придуманные пути не используются. Проекты размещаются в Disk; приём серверных папок и управление синхронизацией выполняются в Syncthing Tray.
- Исходники и Git живут на сервере. `.git`, секреты (`.env*`, ключи) и генерируемое (`vendor`, `node_modules`, `build`, `dist` и т. д.) не синхронизируются, список в `disk/stignore.txt`. Зависимости ставятся на месте (`composer install`, `npm ci`), `.env` создаётся на каждой стороне отдельно.
- Агент не правит копию на Windows через мост: правка делается на сервере, дальше синхронизация.
- Агент не придумывает пути и имена: он сверяется с этим разделом и с кодом RemoteDisk.

## 6д. Мост выдаётся с командами

Мост ставится, чтобы агент мог работать с компьютером. Без выполнения команд он не может даже прочитать журналы и
разобрать сбой, а владельцу приходится ещё раз переделывать конфиг (на этом спотыкались много раз, решение владельца 16.11.2026).

- `bridge.enabled=true` и `bridge.allowShell=true` по умолчанию везде: в выдаваемом конфиге, при применении конфига, в мастере, в примерах и документации.
- Если секции `bridge` или отдельного поля нет, его значение считается `true`. В мастере обе галочки включены по умолчанию; отдельно об их включении владельца не спрашивать.
- `false` ставится только по явному решению владельца для конкретного компьютера. Владелец не должен помнить о включении моста и команд.
- `config export` по умолчанию добавляет `"agent": {"sudo": "full"}`. Явный другой выбор — `--agent-sudo none|apply|full`. Без явного `agent.sudo` настройка ПК останавливалась на шаге `agent: blocked` (16.11.2026).

## 6е. Конфиг выдаётся сразу со всеми путями связи и всеми включёнными возможностями

Выданный конфиг должен подключаться с первого раза в любой сети, а владелец не должен помнить флаги
(решение владельца 16.11.2026). Прямой SSH к серверу режут провайдеры (ТСПУ); конфиг только с ним
не подключился 16.11.2026 после многих прогонов, где правильный состав уже был выяснен.

- В конфиг сразу кладутся **все** пути связи, которые есть на сервере: прямой маршрут, канал сервера
  (`vpn.bootstrap.channel`), все узлы входа, переходы и ретрансляторы каталога с их секретами. Переключать
  пути и включать VPN владелец может на компьютере, не запрашивая новый конфиг.
- `config export` без `--vpn` выдаёт `channel`: все пути есть, VPN (TUN) выключен, подключение идёт через канал.
  `--vpn on` — то же самое, но VPN включён. `--vpn off`, то есть только прямой SSH, выдаётся лишь по явному решению
  владельца для конкретного компьютера, `export` при этом печатает предупреждение.
- Новый путь связи (узел, ретранслятор, переход) после настройки на сервере сразу вносится в каталог
  (`transport-catalog.json`, `vpnBootstrap`). Без этого он не попадёт в конфиги, и его будто бы нет.
- В том же конфиге по умолчанию включены мост с командами и полные права агента (раздел 6д), а аккаунт
  Happier берётся из настроек выдачи (`happier.account`), его не нужно указывать при каждом экспорте. Если сервер не может выдать полный конфиг, он отказывает с причиной,
  а не выдаёт урезанный.
- Агенты не выдают конфиг «попроще» или «для проверки». Владелец получает только полный конфиг.

## 7. Git

Весь код и документация находятся в Git. Изменение истории, push и видимость репозитория решает владелец.

## 7а. Одна программа — одна сборка

Программа одна, и её код весь в `main` (решение владельца 16.11.2026). Готовая работа сливается в `main`,
а сборка делается только из `main`.

- На GitHub держится один релиз — `main-latest`, ссылка на него постоянная:
  `https://github.com/jeromwork/AiServerAutoSettings/releases/download/main-latest/RemoteAgents.exe`.
- Новая сборка заменяет файлы в этом релизе (`build/release-github.sh`). Отдельные релизы под каждую сборку
  или задачу (`…-test-…`, `…-happier2` и т. п.) не заводятся.
- Ветки `app/*` в отдельных worktree — это только временная работа сессии до слияния, а не версии программы.
  Владельцу их не выдают и сборки из них не раздают.
- Когда заработает обновление с сервера, установленные программы будут получать ту же сборку из `main` и без скачивания.

## 7б. Автообновление

Обновление программы включено по умолчанию: программа сама проверяет и устанавливает новую версию в безопасный
момент. Отключение — только явный выбор владельца. Новая сборка принимает конфиги всех прежних схем; изменение
формата сопровождается миграцией и тестами. Неподдерживаемый конфиг блокирует обновление, сохраняя рабочую версию.
