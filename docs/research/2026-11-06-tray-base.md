# Основа Windows-трея: практическая проверка SyncTrayzor

Дата: 2026-11-06. Окно исследования: начало 14:05 UTC, срок сдачи 14:20 UTC (15 минут).

**Рекомендация: свой WinForms-трей с выборочным переносом MIT-модулей.** Форк пригоден как источник кода и функциональный ориентир, но его модель владения Syncthing и большая WPF-оболочка не сокращают основной объём требований RemoteAgents. Удаление Chromium технически просто; оно не решает SSH, безопасность первой синхронизации, контекстное меню и обязательную диагностику.

## Реальная сборка

Исходная команда (в каталоге клона):

```sh
PATH="$HOME/.dotnet:$PATH" timeout 480 dotnet build src/SyncTrayzor/SyncTrayzor.csproj \
  -c Release -p:EnableWindowsTargeting=true -m:1 -p:UseSharedCompilation=false
```

**Исходный выпуск целиком НЕ собрался**, 3 мин 14 с. Restore и WPF/XAML/C# прошли, `SyncTrayzor.dll` создана. Встроенный `PublishProcessRunner` выполнил self-contained publish **linux-x64**, включая trimming, а `CopyProcessRunnerBuild` потребовал `/ProcessRunner/ProcessRunner.exe`: `MSB3030`. Причины: вложенному `dotnet publish` не передаётся Windows RID; `IntermediateOutputPath` используется в свойстве слишком рано, и ожидаемый путь расходится с фактическим.

Удаление CefSharp без остальных исправлений тоже проверено отдельной полной сборкой: WPF/C# прошли, итог снова `MSB3030`, 1 мин 32 с. В подробном журнале подтверждены `Fody 6.9.3`, `PropertyChanged v4.1.0`, `Finished Fody 1229ms`; Fody не отключался. RestEase SourceGenerator оставлен, ошибок от него не было. Это отделяет работоспособность WPF/Fody от ошибки завершающей упаковки.

Команды для своего приложения выполнены **на копии app**, каждая с `timeout 120`, `-c Release -r win-x64 -m:1 -p:EnableWindowsTargeting=true -p:UseSharedCompilation=false -p:DebugType=None -p:DebugSymbols=false`, каталог `-o ../own-<variant>`:

- compressed: то же + `-p:EnableCompressionInSingleFile=true` — exit 0;
- fdd: `--self-contained false -p:PublishSingleFile=true` — exit 0;

Framework-dependent имеет смысл только при управляемой установке Windows Desktop Runtime .NET 10 x64; его размер в строку пакета не включён. Для самостоятельной поставки предпочтительнее проверенный self-contained compression. Самодостаточность .NET не означает отсутствие требований к компонентам Windows.

Для Syncthing скачан [официальный Windows amd64 v2.1.7](https://github.com/syncthing/syncthing/releases/tag/v2.1.7), без запуска. `syncthing.exe`: **34 802 944 байта**, SHA-256 `cd9aea20afda2b9bdba5aff2e6ac964ed5c2e741ed4ceb48ad9e1be096ca7891`. EXE размещён в `data/syncthing.exe` форка согласно Portable config; сравнения остальных вариантов включают тот же бинарник рядом. ## Настройка без правки ядра и ограничения

[App.Portable.config](https://github.com/GermanCoding/SyncTrayzor/blob/v2.2.0/src/SyncTrayzor/App.Portable.config) содержит `DefaultUserConfiguration`, `PathConfiguration`, `UpdateApiUrl`; пользовательские настройки — XML v10. Без правки Syncthing можно задать `SyncthingCustomPath`, `SyncthingCustomHomePath`, `SyncthingAddress`, `SyncthingCommandLineFlags`, `SyncthingEnvironmentalVariables`, `StartSyncthingAutomatically`, минимизацию, уведомления и автозапуск. Настройки папок, sendreceive, versioning/30 дней, исключения задаются в конфигурации/API самого Syncthing. Для нашей Конституции нужен адаптер от версионированного `config.json`; секреты нельзя помещать в XML настроек/его резервные копии.

Важные препятствия по коду:

1. `SyncthingManager.StartAsync()` сначала вызывает `processRunner.Start()`, затем запускает API-клиент. `StartSyncthingAutomatically=false` лишь отключает автозапуск, режима attach-only нет. При выходе/завершении сеанса менеджер останавливает локальный процесс. Это хорошо для собственного дочернего Syncthing и непригодно для чужого действующего экземпляра.
2. `ApiKey` генерируется в конструкторе, getter-only; перед запуском `ProcessStarting()` выбирает свободный GUI-порт и устанавливает `--gui-address`, `STGUIAPIKEY`. `SyncthingAddress` — предпочтительный host:port, а не неизменяемый удалённый URL. Переопределение `STGUIAPIKEY` через пользовательский environment рассинхронизирует ключ менеджера и процесса. Для фиксированного ключа/attach нужен другой менеджер или правка интерфейса; API-ключи не читались.
3. Порядок для RemoteAgents: локальный журнал → конфиг/секреты → проверка SSH/туннеля → дочерний Syncthing/API → реальные состояния трея. Это надо ввести отдельным coordinator; вставка только в XAML недостаточна. Форк уже имеет наблюдение за процессом, перезапуск и события сна, но восстановление SSH оттуда не следует.
4. Обновления оболочки по умолчанию идут на `https://synctrayzor.germancoding.com/version-check`. Для продукта ставить `NotifyOfNewVersions=false` и пустой `UpdateApiUrl` в поставляемой конфигурации; удалить/заменить ручную проверку обновлений: `CheckForAcceptableUpdateAsync()` — отдельный публичный путь. `SyncthingDenyUpgrade=true` даёт `STNOUPGRADE=1`, **но не блокирует явный `upgrade`**, который `ConfigurationApplicator` назначает через `DoSyncthingUpgrade = configurationProvider.SyncthingInstalled`. Для жёсткой фиксации v2.1.7 отключить и этот путь. В экспериментальном пакете эти продуктовые изменения не сделаны.
5. TFM форка `net10.0-windows10.0.17763.0`: заявленная нижняя API-граница Windows 10 1809. Это не доказательство поддержки всех таких ОС текущим .NET 10 и зависимостями; реальная матрица Windows, Server, автозапуск и права не проверены. На Windows 7/8 этот выпуск рассчитывать нельзя.

### Объём работ (инженерная оценка, не измеренная реализация)

- Форк: ориентировочно **3–6 тыс. новых/изменённых строк** в 20–40 файлах для coordinator/SSH, provisioner/первого подключения, timed pause, shell/IPC, логов/диагностики, адаптации конфигурации и меню; сопровождение ещё ~20 тыс. строк существующего C# и XAML. Удаление CEF — только 595 затронутых строк, не стоимость готового продукта.
- Свой трей: **4–7 тыс. строк нового/адаптированного кода**, включая те же общие сервисы; **1–3 тыс. строк выборочного переноса** DTO/events/conflict/history при необходимости. Не нужно переносить все managers и WPF/Stylet/Fody. Существующий каркас не обеспечивает фактической синхронизации: пауза локальная, реального прогресса и честного сбора ошибок нет.
- Размеры исходных кандидатов для переноса: ApiClient 36 файлов/1525 строк; EventWatcher 16/545; Folders 8/529; TransferHistory 6/477; Conflicts 2/692; IPC 3/330. Это кандидаты, а не независимые готовые пакеты: есть зависимости на Stylet, модели и вспомогательные классы, их надо отделять.

Оба пути оставляют все 12 приёмочных сценариев SPEC-SYNC непроверенными. Для небольшого трея выгода готового UI форка меньше, чем его сопряжение с собственной моделью запуска/конфига. Выборочный перенос MIT сохраняет пользу зрелого кода, а WinForms без Chromium даёт существенно более простой состав поставки.

## Непроверенное

WPF и WinForms на Windows **не запускались**; наличие EXE означает успешную кросс-сборку/упаковку, а не работоспособность UI, TLS, внешнего браузера, single-file extraction, сна, автозапуска или взаимодействия с Syncthing 2.1.7. Никакие настоящие пары Syncthing и каталоги пользователя не использовались. Полная проверка утечек секретов, реального ограничения скорости, конфликтов/первого объединения, RAM при запуске и юридических notices не выполнена. Compression уменьшает файл поставки, а не обязательно RAM и каталог извлечения .NET; framework-dependent требует отдельно установленный подходящий Windows Desktop Runtime.
