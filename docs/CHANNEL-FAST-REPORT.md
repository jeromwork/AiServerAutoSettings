# Канал до сервера: быстрый и видимый отказ

12.11.2026, ветка `app/config`. Продолжены сохранённые изменения после прерывания; соседние потоки B/C не переносились.

## Изменения

- `build/Wizard.Engine.ps1`: запуск возвращает процесс, время запуска и задачу чтения обоих потоков; stdout/stderr перезаписываются в закрытый `logs/transport-daemon.out`. Небольшой помощник .NET нужен для параллельного чтения без PowerShell callbacks на потоках без runspace; использует API .NET 4.8. Повторное открытие файла допускает ещё работающий первый процесс. Второй производственный вызов, из «Связи», подавляет возвращаемый объект, сохраняя прежний контракт.
- `build/Wizard.Bootstrap.ps1`: ожидание по умолчанию 25 с (параметр `TimeoutSeconds`), опрос через 200 мс. Завершение процесса и все включённые кандидаты `fail` немедленно дают ошибку. Причина берётся из свежих `fatal`/`process-failed` и первых строк вывода через существующую санитизацию; «Транспорт уже запущен» выделяется явно. Диагностические файлы читаются с явным UTF-8 для PS 5.1.
- Там же: список кандидатов, изменения их состояний с кодом причины/временем пробы; без статуса — прогресс раз в 5 с; несовпадение ревизии более 5 с — предупреждение и `error`/`configError`. Свежий fatal с пустой ревизией принимается по времени запуска, старый игнорируется.
- Bootstrap сохраняет `probeTimeoutSec=12` только при отсутствии значения; «Связь» переносит его, явное новое значение имеет приоритет. 12 с оставлены: это сокращает ожидание мёртвого пути, сохраняя запас относительно указанного владельцем ответа relay за 0,5 с. Достаточность на настоящей мобильной сети здесь не проверена; пользовательское значение не заменяется.
- `transport/Transport.Daemon.ps1`: fatal отмечается в статусе, входная ревизия вычисляется до потенциального отказа инициализации, после синхронизации кэша уточняется; статус кандидата получает `probeMs`. Вывод процесса задаётся в UTF-8.
- `transport/Transport.Common.ps1`: сохранена подготовленная нормализация Home и написания путей в ревизии. `Get-TransportCandidates`, `Invoke-TransportText` и наследование маршрута прежней установки не менялись в этом потоке.
- Тесты: `app/launcher/tests/test-config-bootstrap.ps1`, `test-config-engine.ps1`, `transport/test-transport-config.ps1`. Изменённые `.ps1` — UTF-8 с BOM, CRLF.

## Почему не было статуса на Windows и границы проверки

По данным, переданным владельцем для соседнего потока, причина установлена: Bootstrap наследовал overlay-hop прежней установки, новый профиль не содержал `known_hosts-hop`, `ssh-keygen` завершался ошибкой, демон падал fatal «SSH не выполнен» до вычисления ревизии. Получался статус с пустой ревизией, который ожидание игнорировало. Исправление кандидатов/наследования выполняет поток B; сценарий поверх прежней установки и кодировку общего журнала — C.

В этом потоке проверено, что изменение другого раздела config не меняет transport-ревизию, а эквивалентное написание Home на Linux её не меняет. Расхождение путей на Windows и влияние Happ/привязки к физическому интерфейсу здесь не подтверждены как причины; новую диагностику они больше не должны скрывать за полным таймаутом при завершении демона.

Windows, PowerShell 5.1/.NET 4.8, Happ TUN и настоящая мобильная сеть не проверялись. Сквозной сценарий использует настоящие локальные sshd, sing-box и TCP relay; Bridge/Account — стендовые. Сценарий прежней установки потока C здесь не запускался. Живой сервер, `~/.ssh`, службы, мост и Windows не затрагивались; push/merge не выполнялись.
