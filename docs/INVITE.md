# Один EXE для подключения компьютера

Приглашение подключает компьютер к существующему рабочему пользователю сервера,
его Disk, агентам и подпискам. Нового пользователя для работы не создаёт.
Первоначальный мастер администратора остаётся прежним.
Эта ветка **не установлена на живой сервер и компьютеры владельца**.

## Что делает получатель

1. Открывает ссылку и скачивает **один `RemoteAgents-Имя-номер.exe`**.
   ZIP, распаковка и второй файл не нужны.
2. Запускает EXE один раз. Программа сама применяет полученные настройки связи,
   пробует включить свой VPN и только затем регистрирует ключ компьютера.
   Системное подтверждение Windows UAC для TUN остаётся: обойти его нельзя.
   Адрес сервера, пароли, ключи и настройки обходов человек не вводит.
3. Если работает Happ или другой VPN, остаётся существующее окно
   «Проверить снова / Оставить как есть». Программа не выключает и не меняет его.
   Если наш VPN не подтвердился, программа всё равно пробует маршруты приглашения.
4. После подключения появляется **только выбор папок**. Это дерево Disk сервера
   и компьютера: «только на сервере», «только здесь», «в обоих».
   Папки из приглашения уже выбраны; вложенные папки раскрываются по необходимости.
   Можно забрать папку с сервера, добавить местную папку из Disk или выбрать часть
   проекта. Выбор работает в обе стороны через существующий RemoteDisk/Syncthing.
   Папки вне Disk добавляются штатным пунктом «Синхронизировать с сервером».
5. Нажимает «Подключить». Мост, выбранный администратором Happier и автозапуск
   настраиваются автоматически. Итог показывает отдельно подтверждение связи
   и VPN. Завершение настройки не означает окончания передачи файлов:
   её состояние видно в Диске.

EXE и ссылка **секретные, как пароль**. Их передают только получателю.
После регистрации пропуск удаляется из рабочей папки secrets; установленный EXE
и его резервные копии содержат чистый лаунчер без приглашения. Скачанный файл
программа пробует удалить, если он уже не исполняется и права позволяют.
Если он остался, повторный запуск в том же профиле сообщает «приглашение уже
использовано»; на другом компьютере одноразовый пропуск отвергает сервер.
Остальные исходные/пересланные копии администратор и получатель удаляют сами.
Прерванная настройка продолжается по сохранённому этапу и собственному ключу,
не восстанавливая уже стёртый пропуск.

## Подготовка администратором

Сначала приёмка на **отдельном тестовом сервере и чистой Windows**.
Требуются Linux, Python 3.10+, OpenSSH с `restrict` и `expiry-time`, ssh-keygen,
useradd, sudo и visudo. Для Windows сохраняются требования обычного мастера.

1. Собрать `build/build-exe.sh`, разместить исходники и `release/RemoteAgents.exe`,
   например в `/opt/remoteagents`. `create` берёт этот штатный EXE побайтно;
   персонального изменения кода или повторной сборки для получателя нет.
2. Подготовить `/etc/remoteagents/invite/config.json` по
   [примеру](../server/invite-config.example.json) и
   [схеме](../server/invite-config.schema.json). Конфиг и предки принадлежат root
   без записи группе/остальным, конфиг 0600. `sandbox` отсутствует или false.
   Указать своего рабочего пользователя, адрес/SSH-порт сервера, пути
   authorized_keys, releaseExe, stateDir, outputDir, enrollHelper, sudoersFile.
   `hostKeys` — публичные ключи sshd (`тип base64`), полученные через уже
   доверенный доступ; pinning не скачивается из недоверенной сети.
3. Указать `catalogFile` — **существующий общий каталог связи**
   `~рабочего-пользователя/.config/remoteagents/transport-catalog.json`.
   Это тот же источник, который обычный мастер получает через
   `transport/server-transport-catalog.py` / `Get-WizardCatalog`.
   Без явного пути используется именно этот путь HOME рабочего пользователя.
   Каталог читается с проверкой существующей схемы, без изменений на сервере.
4. Для VPN подготовить `vpnBootstrap`:

   - `channelFile`: защищённая копия существующего канала сервера, JSON 0600.
     Обычный мастер получает его через `disk/server-disk.sh channel-config`
     (для VLESS) либо из `~/.local/share/remote-disk/ports.json` (канал SSH).
     Приглашение требует готовый снимок, чтобы не обращаться к серверу до VPN.
   - `entryFiles`: соответствие имени узла каталога пути к его `client.json`
     (0600). Это тот же кэш, который `Sync-TransportEntryCache` получает из
     `/opt/rd-entry/client.json`. Нужны все включённые entries. В конфиге только
     пути; содержимое, включая секреты VPN, попадает внутрь персонального EXE.
   - `hops`: переносимые настройки каждого включённого SSH-перехода каталога:
     `host`, `port`, `user`, `keyFile` (0600). Закреплённые `hostKey` берутся из
     каталога. На компьютере создаются свои пути к ключу и SSH-конфигу;
     серверные пути и пользовательские SSH-алиасы не предполагаются готовыми.
   - `singBoxExe`: локальный Windows `sing-box.exe` из проверенного
     администратором дистрибутива. Он также включается в персональный EXE;
     первая загрузка VPN не зависит от доступности GitHub на новом компьютере.
   - `vpn.checkUrl`, `vpn.dnsServer`: свой HTTPS-адрес проверки и выбранный DNS.
     Они обязательны, значения инфраструктуры не зашиты в приглашения.

   Публичный каталог содержит только адреса/имена и **не содержит** секретов
   каналов; сам по себе он не позволяет поднять VPN. Поэтому снимок канала,
   кэши узлов и ключи переходов передаются отдельно внутри секретной нагрузки.
   На момент создания администратор обеспечивает актуальность этих снимков.
   Если каталог не содержит работающего пути с интернетом TCP/UDP, VPN не будет
   объявлен включённым: останется попытка регистрации по direct/proxy/hop.
5. Если аккаунтов Happier несколько, указать `happierAccount` из существующего
   списка аккаунтов. Секрет Happier в EXE не включается. `same` использует
   действующий серверный аккаунт; `new:Имя` проходит существующий путь создания
   с отдельным ключом компьютера после регистрации.
6. Создать защищённый каталог helper (root:root, 0755) и установить код:

   ```sh
   bash /opt/remoteagents/server/install-invite.sh \
     /etc/remoteagents/invite/config.json \
     /usr/local/lib/remoteagents /usr/local/bin/remoteagents
   ```

   Установщик копирует код, включая парсер overlay и проверку каталога.
   Он не меняет пользователей, sshd или службы. Первый `create` идемпотентно
   создаёт одного `ra-enroll`, заблокированный пароль, root-owned authorized_keys
   и одну узкую sudoers-строку на helper. Рабочий пользователь уже существует.
   `/bin/sh` нужен OpenSSH для forced command; произвольный shell недоступен,
   а `/usr/sbin/nologin` заблокировал бы также регистрацию. Если AllowUsers,
   AllowGroups или AuthenticationMethods запрещают служебный вход по ключу,
   администратор отдельно решает это на тестовом сервере.
7. Выпустить файл:

   ```sh
   remoteagents invite create --name "Ноутбук" --hours 24 \
     --happier same --folders "Project,Project/docs" --vpn on
   remoteagents invite list
   remoteagents invite revoke <id>
   ```

   `--vpn on` — значение по умолчанию. `--vpn off` не требует `vpnBootstrap`
   и не включает VPN, но каталог всё равно применяется **до** регистрации.
   Без `--publish` команда выводит путь к одному EXE (0600, каталог 0700).
   Срок — больше нуля, до 720 часов. `revoke` отменяет пропуск, но не ключ уже
   подключённого компьютера. Статусы: open/reserved/used/expired/revoked.
   События без секретов: `<stateDir>/invite-events.log`.

## Маршруты и VPN

`routes` — явный порядок попыток из настроек сервера:

```json
[
  {"kind":"direct"},
  {"kind":"proxy","proxy":{"type":"socks","host":"127.0.0.1","port":1080}},
  {"kind":"hop","hop":{"name":"my-hop","ssh":"relayuser@relay.example.invalid:22","hostKey":"ssh-ed25519 BASE64","keyFile":"/root/secrets/relay-ed25519"}}
]
```

Для пароля SSH-перехода используется `passwordFile` (0600) вместо `keyFile`;
нужен явный логин. Локальный прокси должен работать на компьютере получателя.
Проверка ключей серверов строгая, кнопки «принять всё равно» нет.
Маршруты использует существующий код мастера, выбранный маршрут сохраняется.
После регистрации компьютер входит своим ключом. Секрет выбранного маршрута
остаётся в защищённой папке отдельно от стёртого одноразового пропуска.

Второй `RemoteVPN.exe` не нужен: в основном бандле размещено то же описание
компонента, что в `build/components-vpn.json` (commandManaged, по умолчанию off).
Его обслуживает тот же лаунчер и штатный `transport/Vpn.Tun.ps1`: обнаружение
чужого VPN, UAC, задачи TUN, независимый watchdog и очистка своих маршрутов.
Отдельный продукт RemoteVPN продолжает собираться как прежде.
Приглашённый RemoteAgents показывает существующие управление и статус VPN;
сохранённое намерение включать его применяется при автозапуске после готовности
транспорта. Явное выключение в меню отменяет это намерение.

До регистрации SSH-проба невозможна: своего разрешённого ключа ещё нет.
Начальный этап выбирает путь из каталога реальным HTTPS через временный
локальный HTTP-прокси sing-box, затем включает штатный TUN и проверяет его
маршруты, DNS и HTTPS. Никакой успешный статус SSH-транспорта не подделывается.
Для SSH к серверу через TUN используется служебный адрес из настроек VPN с
сохранённым pinning исходного сервера: внешний endpoint самого VPN исключён
из TUN, поэтому попытка обратиться только к его обычному адресу могла бы
снова попасть под фильтр провайдера. Затем выполняется регистрация, обычная
проверка транспорта собственным ключом и снимается начальный режим.
Неудача VPN не выдаётся за успех и не отменяет попытки direct/proxy/hop.

## Как устроен один файл

Формат: неизменный штатный PE → 16-байтовый маркер `RAINVITE-OV1\r\n\x1a\n` →
нагрузка → длина нагрузки uint64 LE → SHA-256 всех предшествующих байтов → маркер.
Внутри нагрузки технически ZIP только как контейнер для `invite.rainvite` и
`sing-box.exe`; человек получает **EXE**, не архив. Маркер проверяется также
сразу после конца PE: потерянный трейлер не превращается в обычный запуск.
Проверяются границы PE, точная длина, допустимые имена, размер и SHA-256.
Хеш охватывает также штатный EXE, обнаруживая его замену/порчу. Это проверка
целостности, **не цифровая подпись издателя**; файл передают доверенным каналом.
Чистый EXE без нагрузки продолжает обычную установку/мастер. Запасной режим
`.rainvite` рядом с EXE, перетаскивание и вставка пути сохраняются.

## Ссылка

`--publish downloads` публикует тот же один EXE на `publishNodes.downloads`.
Узел сменный, адреса в коде нет. Пример локального backend:

```json
{"directory":"/var/lib/remoteagents/downloads","baseUrl":"https://download.example.invalid/invites","listenHost":"127.0.0.1","listenPort":8098}
```

На выделенном узле: `remoteagents invite serve --node downloads`.
Для удалённой публикации на основном сервере:

```json
{"ssh":"publisher@relay.example.invalid","sshConfig":"/root/.ssh/invite-publish.conf","baseUrl":"https://download.example.invalid/invites"}
```

`sshConfig` содержит отдельные ключи, порт и доверенные known_hosts узла;
StrictHostKeyChecking включён. На узле доступна команда
`remoteagents invite receive --node downloads` с подходящим конфигом/правами.
Receive и serve не требуют root или provision: доверенный владелец их конфига
и предков — root либо этот существующий пользователь, без записи другим.

Ссылка содержит случайный секрет 256 бит и оканчивается `.exe`.
Backend проверяет целостность EXE перед сохранением, отдаёт его один раз и
удаляет по сроку. GET расходует ссылку до отправки тела: после обрыва нужна новая
публикация; Range/resume не поддерживается. HEAD не скачивает файл.
Внешний HTTPS/reverse proxy с `/invites/` владелец настраивает самостоятельно:
без caching, access log URL, буферизации и повторных GET. Без `--publish`
программа не открывает портов и не запускает HTTP.

## Приёмка владельцем

1. На отдельном сервере с уже работающими мостом, Disk и Happier подготовить
   конфиг, каталог и снимки VPN. Создать `--vpn on --folders Project,Project/docs`.
   Получить **один EXE**, проверить совпадение его начала с releaseExe.
2. На чистой Windows скачать один файл и запустить. Никаких ZIP/распаковки,
   ручного адреса, root-пароля, ключей или настроек связи. При необходимости
   подтвердить только системное UAC. Сначала каталог и VPN, потом ra-enroll.
3. На тестовой сети перекрыть прямой доступ к серверу. Проверить работающий путь
   из каталога и SSH-переход; затем отдельно SOCKS/HTTP и SSH-парольный переход.
   Подтвердить живой статус TUN, собственный SSH-ключ, мост и тот же Happier.
   Повторить с `--vpn off`: TUN не должен запускаться, маршруты работают.
4. С работающим Happ/TUN убедиться: окно выбора сохранено, чужие процессы,
   адаптеры, маршруты и настройки не меняются. При неудаче нашего VPN попытки
   регистрации продолжаются, итог честно сообщает отсутствие VPN.
5. Увидеть только дерево выбора папок с предвыбором. Раскрыть вложенный уровень,
   снять отметку, выбрать местную папку в Disk. Проверить передачу с сервера на
   компьютер и обратно, отдельно дождаться синхронизации. Перезапустить EXE и
   Windows: собственный ключ, маршруты, мост и автозапуск продолжают работать.
6. Проверить `invite list`: used; один `ra-device:Имя` в рабочем authorized_keys;
   в secrets нет invite-pass и invite.rainvite, установленный EXE без нагрузки.
   Повторить исходную копию EXE: понятное сообщение об использованном приглашении
   (в новом профиле отказ подтверждает сервер). Оставшиеся копии удалить.
7. Новыми приглашениями проверить короткий срок, revoke, две одновременные
   регистрации, изменение ключа хоста, закрытие/возобновление настройки,
   `new:Имя`. Проверить дерево с локальными и серверными папками и частичный
   выбор в большом/неполном уровне. Обычный EXE без нагрузки и ссылка
   «Настроить сервер вручную» должны по-прежнему открывать прежний мастер.
8. Проверить повреждённый/обрезанный EXE и отдельно внешний HTTPS download:
   первый GET 200 с EXE, второй 404, срок удаляет файл. Проверить настоящие
   PowerShell 5.1, UAC, TUN, задачи watchdog и откат при потере пути/сбое.

Автотесты используют только loopback sshd, временные HOME и изолированные файлы.
Создание пользователя/sudo проверяется подменой вызовов ОС, VPN — заглушками
без TUN. Проверки CLR/PE на Linux подтверждают загрузку и исполнение read-only
входа `--selftest-invite-overlay`, а не GUI Windows или обход реального ТСПУ.
Команды: тесты `server/tests/test_invite.py`, полный `app/launcher/tests/run.sh`,
`transport/test-transport-config.ps1` и `build/build-exe.sh`.
