# Подключение по приглашению

Приглашение подключает ещё один компьютер к существующему рабочему пользователю,
его Disk, агентам и подпискам. Первоначальный мастер администратора не меняется.
Код не развёрнут на живом сервере. Команды установки ниже выполняет владелец
после приёмки, сначала на отдельном тестовом сервере.

## Сервер: установка владельцем

Требуются Linux, OpenSSH с `restrict` и `expiry-time`, Python 3.10+, ssh-keygen,
useradd, sudo и visudo. Для клиента остаются требования существующего мастера.

1. Собрать `build/build-exe.sh`. На тестовом сервере разместить исходники и
   `release/RemoteAgents.exe` в каталоге администратора, например `/opt/remoteagents`.
2. Под root подготовить `/etc/remoteagents/invite/config.json` по
   `server/invite-config.example.json` и `server/invite-config.schema.json`.
   Конфиг и все его предки принадлежат root, без записи группе/остальным;
   файл имеет права 0600. В конфиге обязательно заменить адрес, SSH-порт,
   рабочего пользователя и его authorized_keys, расположение EXE, пути служебного
   пользователя/helper/sudoers. `sandbox` отсутствует (либо false).
   `hostKeys` — строки `тип base64` из публичных ключей sshd тестового сервера,
   полученные администратором через уже доверенный доступ. Сеть для получения
   pinning не используется. `happierAccount` — ID существующего аккаунта, если их
   несколько (публичный список: существующий раздел Happier мастера).
3. Создать защищённый каталог для `enrollHelper` (по примеру
   `/usr/local/lib/remoteagents`, root:root, 0755), затем под root выполнить:

   ```sh
   bash /opt/remoteagents/server/install-invite.sh \
     /etc/remoteagents/invite/config.json \
     /usr/local/lib/remoteagents /usr/local/bin/remoteagents
   ```

   Установщик копирует только код. Он не меняет sshd, пользователей и службы.
   При первом `create` создаётся единственный служебный пользователь из конфига
   (обычно `ra-enroll`), заблокированный пароль, защищённый authorized_keys и
   одна sudoers-строка только на установленный helper. Повторный `create` не
   создаёт второго пользователя. Рабочий пользователь должен уже существовать.
   Требование «без shell» означает отсутствие доступа к произвольной оболочке:
   `/bin/sh` нужен OpenSSH для исполнения forced command; `/usr/sbin/nologin`
   заблокировал бы также регистрацию. Все ключи служебного пользователя имеют
   `restrict,expiry-time,command`; никаких обычных ключей ему не добавлять.
   Если действующие AllowUsers/AllowGroups/AuthenticationMethods не разрешают
   этому пользователю вход по ключу, владелец отдельно решает это на тестовом
   сервере. Эта реализация не редактирует sshd.
4. Под root:

   ```sh
   remoteagents invite create --name "Ноутбук" --hours 24 --happier same --folders "Project,Project/docs"
   remoteagents invite list
   remoteagents invite revoke <id>
   ```

   В выводе предупреждение о секрете и путь ZIP (0600 в каталоге 0700).
   EXE в ZIP побайтно совпадает с `releaseExe`, меняется только `invite.rainvite`.
   Отзыв отменяет пропуск, но не отзывает уже зарегистрированный ключ компьютера.
   Статусы: open/reserved/used/expired/revoked. События без секретов:
   `<stateDir>/invite-events.log`.

## Маршруты

Явный массив в порядке попыток; поле `kind`, вложенные поля совпадают с запросами
мастера из 8254876. Пустые необязательные маршруты не добавляются.

```json
[
  {"kind":"direct"},
  {"kind":"proxy","proxy":{"type":"socks","host":"127.0.0.1","port":1080}},
  {"kind":"hop","hop":{"name":"my-hop","ssh":"relayuser@relay.example.invalid:22","hostKey":"ssh-ed25519 BASE64","keyFile":"/root/secrets/relay-ed25519"}}
]
```

Для пароля промежуточного SSH-сервера вместо `keyFile` используется `passwordFile`.
Файл ключа/пароля — отдельный секрет с правами 0600; его содержимого в config нет.
Локальный прокси должен уже работать на подключаемом компьютере. Адреса в примере
нужно заменить своими. Ключ промежуточного сервера также закреплён, строгая проверка.
Для пароля требуется явный логин промежуточного сервера. После регистрации пароль
маршрута хранится только в защищённой папке `secrets` компьютера; ProxyCommand
содержит путь, askpass использует существующий канал PasswordRelay. Это отдельный
секрет маршрута, а не пропуск регистрации. Он необходим для дальнейшего доступа
через этот маршрут. Пропуск удаляется. Выбранный маршрут сохраняется для SSH и
OpenSSH-транспорта, остальные существующие способы связи берутся из каталога сервера.

## Ссылка (необязательный сменный backend)

Без `--publish` команда не открывает порты и не запускает HTTP. ZIP передаётся
владельцем по выбранному им каналу. Чтобы получать ссылку, настроить узел
`publishNodes` и запустить backend на выделенном узле. Пример узла:

```json
{"directory":"/var/lib/remoteagents/downloads","baseUrl":"https://download.example.invalid/invites","listenHost":"127.0.0.1","listenPort":8098}
```

На узле получения загрузки (`remoteagents invite serve --node downloads`) требуется
конфиг сервера версии 1 с `publishNodes.downloads`, включая этот backend.
Команды `receive` и `serve` могут работать обычным существующим пользователем:
конфиг, его предки и каталог загрузок должны принадлежать root или этому
пользователю, без записи группе/остальным. Они не вызывают provision/sudo/useradd.
Внешний HTTPS/reverse proxy с префиксом `/invites/` владелец направляет на backend
без префикса. Отключить proxy caching, access log URL и буферизацию/повторные GET.
HEAD не скачивает ZIP, GET расходует ссылку перед отправкой тела: после обрыва
нужна новая публикация. Поддерживается один GET, без возобновления Range.
Срок проверяется при GET, просроченные файлы удаляются backend также по таймеру.

На основном сервере для удалённого узла:

```json
{"ssh":"publisher@relay.example.invalid","sshConfig":"/root/.ssh/invite-publish.conf","baseUrl":"https://download.example.invalid/invites"}
```

`sshConfig` содержит ключи, порт и доверенные known_hosts узла; строгая проверка
включена. На узле команда `remoteagents invite receive --node downloads` должна
быть доступна этому логину с нужными правами на конфиг и каталог. Публикация:

```sh
remoteagents invite create --name "Ноутбук" --publish downloads
```

В выводе случайная ссылка (256 бит); сама ссылка также секрет. Для локального
backend вместо `ssh/sshConfig` задаются `directory/baseUrl`. Автоматическое
развёртывание HTTP/HTTPS, reverse proxy и служб не выполняется.

## Приёмка владельцем на тестовом сервере и чистой Windows

1. Установить серверную часть по инструкции выше на отдельном сервере с уже
   работающими связью, мостом, диском и Happier. Проверить конфиг и публичные
   ключи через доверенный канал. Создать приглашение `same` с двумя папками.
2. Передать ZIP на чистую Windows, распаковать в отдельную папку, запустить EXE.
   Должно сразу появиться окно приглашения с этапами, без адреса, root-пароля и
   ключей. Должен появиться только выбор папок диска с отмеченными папками
   приглашения; снять одну отметку и завершить.
3. Проверить реальный статус связи, доступность моста, тот же аккаунт Happier и
   синхронизацию выбранной папки (это отдельная проверка от окончания настройки).
   В `invite list` — used; рядом с исходным EXE и в `secrets` нет `.rainvite` и
   `invite-pass`; на сервере один ключ с `ra-device:Ноутбук`. ZIP удалить вручную
   во всех исходных/скачанных копиях: извлечённое приглашение удаляется, архив не
   переписывается и остаётся секретом.
4. Попробовать исходный ZIP на другой чистой Windows/в новом профиле: отказ
   «использовано/отозвано/истекло». Проверить короткий срок и revoke на двух новых
   приглашениях. Изменить hostKeys ещё одного приглашения: понятный отказ,
   регистрации нет, кнопки «принять всё равно» нет.
5. Проверить прямой путь, затем отключить его на тестовом стенде и проверить
   локальный прокси и промежуточный SSH отдельно с ключом и с паролем. Перезапуск
   EXE/Windows должен использовать собственный ключ и сохранённый маршрут.
6. Проверить `new:Имя`: новый аккаунт с отдельным секретом только в secrets,
   повтор после ошибки использует тот же новый ключ. Подписки провайдеров и Disk
   остаются у того же Linux-пользователя. Проверить ссылку «Настроить сервер
   вручную» и обычный запуск без приглашения: первоначальный мастер работает.
7. Проверить приглашение рядом с EXE, перетаскивание на EXE/первый экран и вставку
   пути Ctrl+V; ошибки с возможностью повторить; закрытие/перезапуск посередине.
   Проводить на настоящей Windows PowerShell 5.1 (проверки Linux используют 7).
8. Если нужен backend ссылки: отдельно проверить HTTPS извне на выбранном узле,
   первое скачивание 200, второе 404 и удаление по сроку. Внешнюю сеть/ТСПУ и
   установленную службу backend в этой среде не проверяли.

Автотесты Linux: `python3 -m unittest discover -s server/tests -p test_invite.py -v`,
полный `app/launcher/tests/run.sh`, сборка `build/build-exe.sh`. Тестовый sshd
привязан только к 127.0.0.1, имеет отдельные config/hostkeys/authorized_keys/HOME.
Два пользователя эмулируются одним UID и разными файлами ключей. Настоящее создание
служебного пользователя и sudo проверяются только подменой OS-вызовов, что не
подтверждает их работу в реальной системе. Работа GUI, UAC, PowerShell 5.1,
служб и полного подключения диска/моста/Happier на Windows требует шагов выше.
