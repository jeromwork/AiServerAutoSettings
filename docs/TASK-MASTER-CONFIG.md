# Задача: мастер-конфиг сервера — клонирование и восстановление

Поставлена владельцем 13.11.2026. Расширяет задачу CONFIG (`docs/TASK-CONFIG.md`,
`docs/CONFIG.md`) до полного жизненного цикла сервера. Ветка — отдельный worktree от `main` (см. AGENTS.md).

## Что хочет владелец (его словами)

> Нужен один конфиг со всеми ключами (ключи в соседнем файле), которые потом сливаются в один конфиг.
> Это сейчас так работает [имеется в виду `.ovpn` + соседние `ca/cert/key`].
> Когда захотим заново настроить другой сервак — ИИ-агент на основании одного конфига составляет другой
> конфиг для другого сервака. А если этот сервак слетит — через конфиг всё должно восстановиться,
> правда пожалуй кроме приватных ключей.

## Суть

Один **мастер-конфиг** полностью описывает установку (сервер, связь, мост, Happier, диск, VPN, прокси,
локальные сети, компоненты). Из него делаются три операции:

1. **Снимок текущего сервера.** `config export` / «Сохранить полный конфиг» собирает рабочий конфиг
   действующего сервера 109 целиком: публичная часть — `config.json`, секреты — соседний `secrets/`,
   связь по именам (`{"secret":"имя"}`). Пароль root в снимке заменён рабочим SSH-ключом, который
   программа уже поставила на сервер (см. `docs/CONFIG.md`, `server.rootPassword`).

2. **Клонирование на другой сервер.** Владелец покупает новый VPS и просит ИИ-агента: вот экспорт
   «для ИИ» (без секретов, значения `"<есть, скрыт>"`) этого сервера — составь конфиг для нового
   (другой адрес/порт/логин, те же компоненты и папки). Агент правит только публичную часть,
   секреты не читает; новые секреты задаёт владелец через `secret set`/`secret import`.

3. **Восстановление после сбоя.** Сервер «слетел» → вставка полного конфига на новом железе
   поднимает всё без вопросов, **кроме приватных ключей**: их нельзя восстановить из публичного
   конфига, они лежат в `secrets/` и переносятся отдельным файлом (резервная копия у владельца /
   в менеджере паролей). Что именно невосстановимо без `secrets/`, перечислить явно
   (SSH-ключ сервера, ключ Happier, приватный ключ `.ovpn` клиники, пароли прокси/hop).

## Границы и проверки

- Повторное применение того же конфига ничего не меняет (идемпотентность) — уже есть в задаче CONFIG.
- Экспорт «для ИИ» не содержит ни одного значения секрета (тест поиском).
- Клонирование: из экспорта одного сервера агент получает валидный по схеме конфиг другого; sanity —
  применение на стенде (loopback sshd) поднимает связь.
- Восстановление: полный конфиг + `secrets/` на чистой машине → рабочее состояние; без `secrets/` —
  честный список того, что не поднимется, и запрос недостающих секретов.
- root на сервере — только у владельца; агент готовит конфиг и команды, применяет владелец.

## Развёртывание под root из конфига — без ручных шагов (поставлено 15.11.2026)

Владелец: «то, что есть в основном конфиге, должно разворачиваться автоматически под root, если ещё не
настроено. Сейчас мы сделали на коленке, а на следующем сервере нужно разворачивать автоматом».

15.11 сеть клиники на сервере 109 поднята **вручную** (`server/lan-vpn.sh` под sudo). Что потребовалось
и должно делаться само из раздела `lan[]` конфига:
- проверка до включения: весь трафик сервера идёт через proxy-out (sing-box TUN, правила `ip rule` 9000–9010
  на месте); если правил нет — починить (перезапуск sing-box) и проверить выход 104, а не отказывать молча;
- `--direct-endpoint` (шлюз OpenVPN напрямую, только процесс OpenVPN, только его ip/proto/port);
- `--server-fingerprint` — если шлюз предъявляет сам CA без keyUsage (NethServer). Отпечаток — поле конфига
  `lan[].serverFingerprint`; программа может предложить его при первом подключении (с показом владельцу);
- `--subnet` дополнительные подсети (`lan[].subnets`), публичные push-маршруты шлюза отбрасываются;
- логин/пароль — из `secrets/` (`--auth-stdin`), без вывода; профиль `.ovpn` — из секрета;
- `test` до хоста ЛВС (`lan[].testHost`/`testPort`) и `confirm` автоматически; «новый SSH проверен» —
  программа сама открывает новое SSH-соединение после включения, а не просит владельца;
- идемпотентность: уже включённая ЛВС с тем же профилем/параметрами — ничего не делать.

То же для остальных серверных частей, сейчас поднятых руками или «тестово»:
- Tailscale на сервере — сейчас тестовый `tailscaled` без root в `~/work/ready-tools-test`; нужен штатный
  (служба), раздача сети клиники — только по отдельной команде (см. LAN.md / решение 13.11);
- шлюз Telegram (`app/tg-gateway`, не влит в main: конфликт с мастером) — установка из конфига;
- sing-box сервера (proxy-out), его сторож: пропажа правил TUN = утечка через 109 (было 13–15.11);
- sudo для агента (`/etc/sudoers.d/90-remoteagents`) — сейчас выдан вручную; решить, ставит ли его установка.

Проверка: чистый VPS + полный конфиг + `secrets/` → всё поднимается без единой ручной root-команды;
повторное применение ничего не меняет; на 109 применение текущего конфига ничего не ломает.
