12.11.2026, ветка `app/channel-speed` (от `app/config` 4521b78). Блок подготовки transport в `Start-WizardBootstrap`,
`Get-TransportCandidates` и `Invoke-TransportText` (поток `app/channel-clean`) не менялись.

временем в мастере и демоне (после замера удалены). Bootstrap раздела (вместе с запуском pwsh мастера): 8,8 с / 10,5 с,

Разброс: машина нагружена соседними агентами (load average 4,4 на 4 ядрах). Первая компиляция `Add-Type` одна и та же
стоила от 0,8 до 2,0 с. Больше всего от нагрузки зависят старты pwsh и компиляции.

**Выбросы 28,8 с и 50 с.** Это не канал. В упавшем прогоне sing-box демона завершался и перезапускался каждые ~4 с
(`restartDelaySec` 3 с + `check`): «sing-box завершился, ожидается перезапуск», шесть циклов, затем таймаут 25 с. Стенд
берёт случайные `apiPort`/`channelSocksPort`/`sshPort`/`syncPort`, но `probePortBase` (26000) и `socksPortBase` (28000) у
него фиксированные. Параллельный прогон из другого worktree занимает те же порты, и `sing-box run` не может их открыть.
По словам координатора, такие параллельные прогоны были. Сквозные прогоны теперь идут под общим замком
`/tmp/ra-e2e.lock`. Если стенду нужно работать параллельно, ему стоит брать и эти две базы из свободного диапазона.

В журнал владельца (строки `· `) добавлены этапы: `· подготовка и запуск модуля связи N мс`,
`· статус модуля связи N мс`, `· модуль связи готов N мс от запуска процесса` (это строка демона: старт powershell,
настройки, sing-box). Вместе с прежними `· <кандидат>: ok N мс` и `· канал поднят за N мс` по журналу с Windows видно,
какой этап дорогой. Стенд `test_config_e2e.py --scenario channel` при успехе печатает строки `[Bootstrap]`.

**Ожидаемо на стенде:** Bootstrap ~5,5–7 с вместо 8,8–10,5 с, экономия 2,5–3,5 с. Цифра по сумме этапов, не по
прогону: сквозные прогоны «после» по решению владельца выполнит координатор после слияния.

## Почему не ≤ 3 с и что дальше (не сделано)

После правок на стенде остаются примерно 5 с постоянных затрат. Из них только проба (0,65–0,9 с) — сам канал.

1. Два старта PowerShell: мастер (1,3–1,6 с, его стартует окно и для других разделов) и демон (1,0–1,5 с). На Windows
   PS 5.1 они дороже. Убрать второй можно, только если не запускать отдельный процесс демона — это смена архитектуры:
   например, демон трея уже работает и перечитывает config.
2. Оставшийся `Add-Type` в демоне (0,8–2,0 с, на PS 5.1 — `csc.exe`). Он происходит внутри `Get-TransportCandidates` →
   `Get-TransportHostKeys` → `Invoke-TransportText` (`ssh-keygen -F`) — это зона `app/channel-clean`. Варианты: собрать
   помощник один раз в DLL в кэше и грузить `Add-Type -Path`, либо читать `known_hosts` без `ssh-keygen` и без процесса.
3. Подготовка 0,6 с: на Linux это chmod-процессы, на Windows там вызовы ACL API, вероятно дешевле.
4. Проба живости 64 КБ оставлена. Она ловит «замирание после ~16 КБ», которое бывает у ТСПУ. На стенде объём ничего не
   стоит, на мобильной сети 64 КБ — это доли секунды поверх рукопожатия SSH.
