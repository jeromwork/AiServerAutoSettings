# Транспорт RemoteAgents

`transport/Transport.Daemon.ps1` — компонент лаунчера для Windows PowerShell 5.1 и sing-box **1.14.4**. Сам демон не устанавливает задачи планировщика и не меняет системные маршруты. Системный VPN вынесен в отдельный `Vpn.Tun.ps1` и по умолчанию выключен. Старую задачу `RemoteDiskChannel` нужно отключать только при переходе лаунчера с проверкой и откатом: иначе рабочие порты заняты. Этот модуль переход не выполняет.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Transport.Daemon.ps1 -Home "$env:LOCALAPPDATA\RemoteAgents" -ParentPid 1234
.\Get-TransportStatus.ps1 -Home "$env:LOCALAPPDATA\RemoteAgents"
```

`-ParentPid` — PID лаунчера; без него компонент работает самостоятельно. Для остановки создайте `<Home>\stop` (общий флаг лаунчера) или `<Home>\state\transport.stop`. Флаг сохраняется: удалите перед следующим запуском. При остановке/закрытии родителя завершаются sing-box и SSH; на Windows дерево SSH закрывается через `taskkill /T`. Один Home допускает один экземпляр. Ошибка запуска возвращает код 1.

## Настройки и пути

Настройки — секция `transport` в `<Home>\config.json`. [Пример](../transport/config.example.json) содержит вымышленные значения; [схема](../transport/config.schema.json) описывает именно значение секции, её нужно включить в общую схему лаунчера. Версию всего `config.json` задаёт лаунчер. Home по умолчанию — `%LOCALAPPDATA%\RemoteAgents`.

| Параметр | По умолчанию / назначение |
|---|---|
| `profilePath` | SSH-профиль `ssh-transport.json`; если не задан, путь читается из `%LOCALAPPDATA%\RemoteDisk\profile.txt` |
| `channelPath` | `%LOCALAPPDATA%\RemoteDisk\channel\config.json`: оттуда VLESS и **порт назначения** входа `sync` |
| `singBoxPath` | `sing-box.exe` рядом со скриптом |
| `sshPort`, `syncPort` | 2222, 22001, только loopback; назначения на сервере `127.0.0.1:22` и порт Syncthing из канала |
| `probePortBase`, `socksPortBase`, `apiPort` | 26000, 28000, 29090; порты не должны пересекаться |
| `bindPhysical` | `true`: auto_detect_interface и привязка внешних сокетов sing-box к физическому NIC; `ssh -D` напрямую получает `-b` IPv4 этого NIC. `false` разрешает системную маршрутизацию |
| `openSsh` | `true`: добавить OpenSSH напрямую и через SSH-переходы, используя локальные SOCKS-входы `ssh -D` |
| `metered` | `auto`, `true`, `false` (строки или boolean для последних двух); явное значение переопределяет Windows |
| `activeProbeBytes`, `activeIntervalSec` | 65536 байт каждые 120 секунд |
| `meteredActiveIntervalSec` | 300 секунд на лимитной сети |
| `rankProbeBytes`, `rankIntervalSec` | 262144 байта на путь каждые 1800 секунд |
| `topOnMetered` | 3 лучших известных пути; без истории — ограниченный набор кандидатов |
| `stallSeconds`, `probeTimeoutSec` | 5 секунд без новых байтов после первого; общий срок пробы 45 секунд |
| `restartDelaySec` | 3 секунды перед повторным запуском упавшего процесса |
| `entries[]` | `{name, ssh, enabled?, kinds?, configPath?}`: имя узла, SSH-алиас или host, по умолчанию enabled=true и все kinds |
| `relays[]` | `{name, host, port, enabled?}`: TCP-ретранслятор до VLESS сервера без расшифровки |
| `hops[]` | `{name, ssh, enabled?, configPath?, hostKey?}`: SSH-переход. `hostKey` — массив полных публичных OpenSSH host keys |
| `cdn[]` | `{name, domain, path?, entry, enabled?}`: VLESS-WS через домен любого CDN; uuid и путь по умолчанию из кэша entry |
| `disabledTags[]` | Отключённые отдельные tag, независимо от enabled узла |

Профиль должен содержать `sshExecutable`, `serverAddress`, `login`, `keyPath`, `knownHostsPath`; порт прямого SSH берётся из `arguments` (`-p`, иначе 22). Пользователь — рабочий, не root. Для native SSH sing-box ключ хоста извлекается через соседний `ssh-keygen.exe -F` из known_hosts профиля, включая hashed-записи. Для перехода используются known_hosts из `ssh -G` либо явный `hostKey`. Новые ключи автоматически не принимаются. Зашифрованные приватные ключи, требующие интерактивного ввода, нужно предварительно подготовить для фонового запуска.

Доступны VLESS напрямую, через relay/SSH-переход, native SSH sing-box, OpenSSH напрямую/через переход, Hysteria2, Hysteria2+salamander, TUIC, Trojan, Reality, ShadowTLS+Shadowsocks, VLESS-WS напрямую и через CDN. Формирование узлов повторяет рабочий `Test-Transports.ps1`; CDN-кандидат добавляется при наличии `domain`, без предварительного DNS-запроса. Для собственного сертификата узла сохранён флаг `insecure` из формата установщика; WS напрямую повторяет режим тестера (`insecure=true`). На переходах OpenSSH внешний сокет создаёт SSH из ProxyCommand: его маршрут задаётся SSH-конфигурацией/системой; `-b` применяется к прямому OpenSSH.

## Проверки и переключение

Один конфиг `<Home>\state\transport-sing-box.json`: рабочие входы ведут в selector `active`, отдельные `26000+i` ведут каждый в своего кандидата, всегда на SSH сервера. Управление — локальный Clash API с Bearer-секретом из `state\transport-secret.json`; `PUT /proxies/active` переключает selector с `interrupt_exist_connections=false`. Обычное переключение не перезапускает sing-box и сохраняет существующие пользовательские соединения. Упавший sing-box перезапускается. При смене физического NIC/IP с `bindPhysical=true` процесс пересоздаётся для обновления привязки сокетов; старые соединения могут оборваться. Без доступного физического NIC в этом режиме запуск ожидает восстановления сети.

Проба использует `ssh.exe` профиля, его ключ и known_hosts, `HostKeyAlias=serverAddress`, `ProxyCommand=none`, `head -c N /dev/urandom`. Полный рейтинг идёт параллельно при запуске, смене сети и по интервалу; активная проба продолжает обслуживаться во время фонового рейтинга. После отказа активного пути сразу выбирается лучший ранее проверенный живой, при отсутствии — лучший из памяти с неподтверждённым статусом, затем запускается рейтинг. `slow` не считается живым: нужны все N байтов без остановки.

Байты stdout считаются в маленьком .NET Stream, без файлов и накопления содержимого. Он нужен, чтобы PowerShell polling не ограничивал скорость; остальные соединения реализуют sing-box/OpenSSH. Скорость `kbps` — **КиБ/с**, по времени и байтам после первой полученной порции. Если поток пришёл одной порцией, скорость неизвестна (`null`), успешность получения N при этом подтверждена. Параллельные измерения делят общий канал и дают сравнительный рейтинг в текущих условиях.

Отпечаток сети — SHA-256 нормализованного MAC шлюза физического интерфейса по умолчанию и имени `Get-NetConnectionProfile`. Виртуальные Tailscale/OpenVPN/Happ/Wintun/TAP/TUN исключены. Без шлюза/имени сеть неизвестна, чужая память не используется. Рейтинг хранится отдельно для каждой сети в `state\transport-memory.json`: сохранённая скорость не подтверждает текущую доступность, до новой пробы `ok=false`. Стоимость в auto берётся из Windows.Networking.Connectivity; если API недоступен, статус `metered=null`, применяется экономный режим. Для явного fallback задайте `metered=true` или `false`.

`status\transport.json` заменяется атомарно и содержит `{ok, summary, active, mode, pinnedTag, kbps, network, metered, candidates:[{tag,title,kind,via,state,kbps,checkedAt,enabled}], updatedAt, error, configError}`. Отключённые кандидаты имеют `enabled=false, state="disabled"`, не проверяются и не участвуют в selector. Состояния: `unknown`, `remembered`, `ok`, `frozen`, `slow`, `fail`. `Get-TransportStatus.ps1` считает запись старше 15 секунд устаревшей. Журнал `logs\transport.log` всегда локальный, содержит только фиксированные события, ротируется при 1 МиБ с одной предыдущей копией. Секреты/адреса процессов и необработанный stderr в журнал не попадают; конфиг sing-box и файлы состояния с секретами закрыты ACL текущего пользователя.

## Трафик

Полезные данные активной проверки — около **1,875 МиБ/час** (64 КиБ / 120 с) или **0,75 МиБ/час** на лимитной сети. Рейтинг — **0,5 МиБ/час на кандидата**, на лимитной сети для трёх — **1,5 МиБ/час**. Сверху идут SSH/TLS/QUIC и повторы; новый запуск, смена сети и отказ активного пути вызывают дополнительные проверки. Неуспешная проба может скачать только часть объёма. Все объёмы и интервалы настраиваются.

## Добавить узел

1. На своём узле подготовьте upstream сервера и выполните `transport/entry/install-entry.sh` по инструкции установщика. Узел должен иметь рабочий `/opt/rd-entry/client.json` и SSH-алиас на Windows; host key предварительно проверяется пользователем.
2. Добавьте `{ "name": "edge", "ssh": "entry-example", "enabled": true }` в `transport.entries` либо выполните `Edit-Transport.ps1 -AddEntry edge -Ssh entry-example`. Имена — буквы, цифры, `_`, `-`; адреса и пароли не помещаются в имя.
3. Запустите `.\Update-Entries.ps1 -Home ...`. Скрипт получает только `cat /opt/rd-entry/client.json`, нормализует CRLF, сохраняет `secrets\entries\edge.json` с ACL только текущему пользователю. Содержимое не печатается. Для полной валидации используйте тестер/демон; неудачная загрузка не заменяет старый кэш.
4. Проверьте статус: демон обнаруживает изменение локального конфига/кэша без перезапуска лаунчера. Для нового включённого entry без кэша фоновая подготовка сама получает `client.json` по проверенному SSH. Существующий кэш обновляется только явной `Update-Entries.ps1`; новые host keys автоматически не принимаются.

## Проверки разработки

```powershell
.\transport\test-transport-config.ps1 -SingBox C:\tools\sing-box.exe
```

Тест работает в Windows PowerShell 5.1 и pwsh, использует фиктивный client.json, CRLF, синтетические потоки и временный SSH-ключ. Без sing-box проверяется структура; с `-SingBox` дополнительно проверяются настоящий `sing-box check` и локальный Clash API (без открытия внешних путей). Для этой проверки нужен `ssh-keygen` из OpenSSH. `-OutputConfig` сохраняет тестовый JSON для внешней проверки (ссылки на временные файлы ключей после теста уже не действуют).

Дополнительно на Linux: `python3 transport/test-transport-daemon.py /path/to/pwsh`. Это локальный стенд с имитаторами SSH/sing-box и loopback API: проверяет stall/failover без рестарта, перезапуск движка, stop и ParentPid с завершением дочерних процессов. Он не подтверждает работу протоколов, Windows ACL/WinRT/NetTCPIP и реальной сети. Приёмка на настоящей Windows PowerShell 5.1 и проверка всех путей рабочим тестером остаются обязательными перед внедрением.


## Ручной выбор и изменение списков

```powershell
.\transport\Set-TransportPath.ps1 -Home $root -Auto
.\transport\Set-TransportPath.ps1 -Home $root -Tag ws-direct-edge
.\transport\Edit-Transport.ps1 -Home $root -List
.\transport\Edit-Transport.ps1 -Home $root -AddEntry ru-in -Ssh my-ru-vps -Kinds ws-direct,trojan
.\transport\Edit-Transport.ps1 -Home $root -AddRelay relay-two -Host 203.0.113.40 -Port 8443
.\transport\Edit-Transport.ps1 -Home $root -AddHop jump-two -Ssh my-jump
.\transport\Edit-Transport.ps1 -Home $root -AddCdn my-cdn -Domain cdn.example.com -Entry ru-in -Path /my-ws
.\transport\Edit-Transport.ps1 -Home $root -Disable ru-in
.\transport\Edit-Transport.ps1 -Home $root -Disable vless-direct
.\transport\Edit-Transport.ps1 -Home $root -Enable vless-direct
.\transport\Edit-Transport.ps1 -Home $root -Remove my-cdn
```

`$root` здесь — каталог Home установки. Команды возвращают JSON и ненулевой код при ошибке. `-List` выводит секцию transport; интерфейс списка **состояний путей** — `status/transport.json`. Все изменения JSON атомарны, edit-команды используют общую межпроцессную блокировку и сохраняют соседние поля конфига. Имена узлов уникальны во всех четырёх списках; `Enable/Disable` сначала ищет имя, иначе считает аргумент tag. CDN, ссылающийся на entry, нужно удалить раньше entry. Для совместимости с задачей A читаются также `alias` вместо `ssh` и `server` вместо `host`.

Допустимые `entries.kinds`: `hy2`, `hy2obfs`, `tuic`, `trojan`, `reality`, `shadowtls`, `ws-direct`, `ws-cdn`. Отсутствие или пустой массив означает все доступные типы. WS возможен только если client.json содержит WS-секреты. `cdn[].entry` выбирает кэш с uuid/путём; домен, SNI и Host берутся из `domain`, path можно переопределить. Приложение не настраивает CDN у провайдера: пользователь должен направить домен на нужный entry, включить WebSocket и подготовить сертификат. Отключённый entry может оставаться источником секретов для отдельно включённого CDN.

Pin хранится отдельно в `state/transport-pin.json`: `{ "mode": "auto", "tag": null }` либо `{ "mode": "pinned", "tag": "ws-direct-edge" }`. При работающем движке демон читает файл раз в секунду и применяет выбор через Clash API за ≤5 секунд после записи. Проверки скорости и подготовка новой конфигурации не блокируют этот цикл. При недоступном API статус сообщает ошибку и команда переключения повторяется; применить selector остановленного/недоступного движка невозможно. Pin сохраняется при смене сети и перезапуске.

В pinned рейтинг продолжает измеряться, но не меняет выбор. Мёртвый pin даёт `ok=false` и «Закреплённый путь не работает». Отключённый/удалённый tag остаётся `active/pinnedTag`, а selector направляется в локальный недоступный SOCKS `unavailable` (127.0.0.1:1); сетевого fallback нет. Из-за `interrupt_exist_connections=false` уже существующие соединения прежнего пути могут жить до естественного завершения. Вернуться к автоматическому выбору можно только через `-Auto`.

Изменения config.json.transport, профиля/канала и кэшей обнаруживаются по содержимому. Подготовка кандидатов и `sing-box check` идут в фоновом PowerShell job. Невалидная подготовка сохраняет прежний работающий процесс и публикует `configError`; повтор — через 30 секунд. После успешной проверки перезапускается только транспортный sing-box; неизменившиеся OpenSSH -D продолжают работать, удалённые/изменённые заменяются. Входы SSH/Syncthing снова слушают прежние настроенные порты. При этом TCP-сессии самого sing-box могут оборваться: sing-box 1.14 не умеет заменять весь набор listeners/outbounds через selector API. Лаунчер, диск и мост не перезапускаются. Применение только `vpn.enabled` транспорт не перезапускает.

## Системный VPN: отдельный компонент

Настройки — **соседняя** секция `config.json.vpn`, [схема](../transport/vpn.schema.json). Отсутствие секции эквивалентно `enabled=false`. Главный транспорт продолжает обслуживать свои loopback-порты независимо от VPN.

```json
{
  "vpn": {
    "enabled": false,
    "excludeCidrs": [],
    "interfaceName": "RemoteAgents-TUN",
    "address": ["172.31.255.1/30", "fdfe:7261::1/126"],
    "probeAddress": "198.18.0.1",
    "dnsServer": "1.1.1.1",
    "checkUrl": "https://example.com/"
  }
}
```

DNS и внешний HTTPS для проверки можно заменить своими; DNS IP должен поддерживать UDP и DoH `/dns-query`. Bootstrap DNS внешних endpoints идёт по физическому NIC, пользовательский DNS — DoH через выбранный путь. Из-за `strict_route=false` это не режим защиты от всех DNS-утечек. Адреса TUN и служебной пробы следует выбрать без пересечения с сетями пользователя; `probeAddress` резервируется только для TCP:22 проверки. IPv4/IPv6 пользовательские адреса и маски валидируются до запуска.

```powershell
.\transport\Test-VpnConflict.ps1 -Home $root
.\transport\Vpn.Tun.ps1 -Home $root                      # JSON последнего статуса
.\transport\Vpn.Tun.ps1 -Home $root -Generate -OutputConfig C:\Temp\vpn.json
# Следующие команды предназначены для будущей приёмки Windows. В задаче C не выполнялись:
.\transport\Vpn.Tun.ps1 -Home $root -Enable -ParentPid 1234
.\transport\Vpn.Tun.ps1 -Home $root -Disable
```

`Generate` читает инвентарь Windows, разрешает адреса endpoints, создаёт JSON и выполняет только `sing-box check`. Этот режим не создаёт задач, не повышает права и не запускает TUN. Linux-тесты передают фиктивный инвентарь и ответы DNS прямо в функции, поэтому сеть им не нужна.

Выбран `stack=system`: TCP/IP обрабатывает стек Windows, без дополнительного TCP стека gVisor. Это инженерный выбор с меньшим числом слоёв; сравнительная надёжность на реальной Windows пока не измерена. В sing-box 1.14 доступны system/gvisor/mixed. `auto_route=true`, `strict_route=false`; внешние сокеты жёстко привязаны к физическому интерфейсу. [Формат TUN 1.14](https://github.com/SagerNet/sing-box/blob/v1.14.0/docs/configuration/inbound/tun.md).

Исключаются RFC1918, loopback, 100.64/10, 169.254/16, 224/4, IPv6 local/link-local/multicast; public IP сервера, endpoints кандидатов, relay/CDN, SSH-переходы и закэшированные entries, включая отключённые. Доменные endpoints разрешаются в A/AAAA, результат повторно проверяется раз в 30 секунд; ошибка разрешения запрещает применение нового TUN. Маршруты адаптеров с OpenVPN в Name/InterfaceDescription дают дополнительные подсети и адреса шлюзов; default и split-default не добавляются в исключения, иначе исключили бы весь интернет. Дополняется `vpn.excludeCidrs`. Настройки/службы OpenVPN и Tailscale не изменяются.

TUN запускает **второй** sing-box и использует копию ровно выбранного поддерживаемого outbound с его зависимостями. Он не выбирает лучший путь независимо от транспорта. При изменении выбранного пути/config/exclusions его процесс проверяется и пересоздаётся, возможен разрыв VPN-сессий. На узле-entry `final=upstream` должен вести к VLESS сервера, а на сервере должен быть разрешён выход в интернет и UDP. SSH/OpenSSH и VLESS с SSH detour не включаются в TUN: они не дают требуемый серверный TCP/UDP egress. При выборе такого пути или потере проверенного транспорта VPN отключает себя; автоматически подменять выбор другим кандидатом он не будет. Поддержка UDP конкретным CDN/WS/сервером зависит от их конфигурации и не подтверждается проверкой TCP.

Перед включением проверяются процессы Happ*, v2ray*, xray*, чужой sing-box*, clash*, nekoray*, hiddify*, wireguard*, amnezia*; активные TUN/Wintun/WireGuard/TAP кроме OpenVPN/Tailscale; чужие split-default 0/1 и 128/1. JSON: `{conflict,items:[{kind:"process"|"adapter"|"route",name,path,detail}]}`. Для процесса path — executable, без командной строки/секретов. Наш процесс исключается только по PID, exe, пути конфига и времени старта, а не имени sing-box. Ошибка инвентаризации блокирует включение. Чужие VPN не останавливаются; существующий интерфейс с именем нашего TUN тоже не переиспользуется.

**Права и откат.** Автоматическая настройка TUN/маршрутов Windows требует администратора: [требования Windows API маршрутов](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-createipforwardentry2). `Enable` сначала выполняет проверку без изменения сети, затем вызывает системный Windows PowerShell через `RunAs`. UAC подтверждает человек один раз на включение. Повышенный broker регистрирует одноразовую задачу worker с `RunLevel=Highest`, interactive logon текущего пользователя, без пароля; отдельную задачу отката через пять минут он ставит **до** старта worker. Для рабочей установки предполагается повышение той же учётной записи; запуск с чужими административными credentials и их ACL не проверен. Административные права не обходятся. Простая запись `vpn.enabled=true` сама по себе не запускает привилегированный компонент: лаунчер должен вызвать `-Enable`.

Имена задач имеют вид `RemoteAgents-TUN-<hash Home>` и `RemoteAgents-TUN-Rollback-<hash Home>`; задачи разных Home не пересекаются. Сеанс имеет случайный идентификатор: старый rollback не действует на новое включение. При каждом пересоздании TUN watchdog снова ставится на пять минут. Он снимается только после успешной проверки: маршрут служебного адреса проходит через наш интерфейс, SSH с закреплённым host key получает 64 КиБ с сервера, DNS отвечает, все адреса внешнего checkUrl маршрутизируются через TUN и HTTPS без proxy возвращает 2xx. Служебное route-правило переписывает адрес назначения на `127.0.0.1:22` удалённой стороны; сервер должен разрешать этот адрес. Без такой политики проверка честно завершится отказом и откатом. [Route overrides 1.14](https://github.com/SagerNet/sing-box/blob/v1.14.0/docs/configuration/route/rule_action.md#route).

Если проверка не прошла, worker выключает свой процесс сам; независимая задача закрывает только подтверждённый наш VPN PID и свою worker-задачу, если worker завис. После остановки дополнительно удаляются оставшиеся маршруты **только** записанного GUID нашего нового интерфейса. Одного убийства PID недостаточно для обещания отката: [закрытие Wintun](https://github.com/SagerNet/sing-tun/blob/v0.9.0-beta.4/tun_windows.go). Ошибка очистки даёт `rollback-error`, её нельзя показывать как успешное отключение. После успешной очистки задачи удаляются. `-Disable`, общий Home/stop, смерть ParentPid и `vpn.enabled=false` завершают worker и очищают его маршруты. Общий stop нужно удалить перед следующим включением.

`status/vpn.json`: `{ok,enabled,state,conflict,summary,updatedAt}`. `conflict` содержит объект того же формата, что Test-VpnConflict; `enabled` отражает запущенный/запускаемый компонент, `ok=true` только после проверки. Состояния: `off`, `awaiting-uac`, `starting`, `on`, `stopping`, `conflict`, `error`, `rolled-back`, `rollback-error`. Журнал `logs/vpn.log` локальный, ротируется при 1 МиБ, пишет время и категорию; секреты и stderr не публикуются.

## Интерфейс для лаунчера

- Запуск транспорта: `Transport.Daemon.ps1 -Home <Home> -ParentPid <launcherPID>` как обычный пользователь. Статусы читать раз в секунду, запись старше 15 секунд считать устаревшей. `ok=false` и `error/configError` отображать явно.
- В меню путей показывать `title`, `kind`, `via`, `enabled`, `state`, `kbps` (**КиБ/с**) и `checkedAt` (UTC ISO 8601, null = не проверен). Текущий tag — `active`; галочка «Автовыбор» определяется `mode`, закреплённая строка — `pinnedTag`. Tag — стабильный идентификатор для команды, не подпись для человека. Не считать remembered подтверждённым подключением.
- Выбор пути: запуск `Set-TransportPath.ps1 -Auto` или `-Tag <tag>`, затем ждать статус. JSON команды подтверждает запись запроса, не успешность соединения. Отключённые строки не предлагать для выбора; уже закреплённую отключённую/удалённую строку показать с ошибкой.
- Добавить/удалить/включить/выключить узел либо tag: вызывать Edit-Transport с параметрами из примеров; не переписывать весь config из устаревшей копии. `-List` даёт настройки, status даёт проверенные состояния. Ошибка нового config появляется в `configError`, старый транспорт продолжает работать до успешного reload.
- «Включить системный VPN»: сначала Test-VpnConflict. При conflict рисовать окно с items и действиями «Отключу другой VPN самостоятельно» / «Оставить другой VPN, наш не включать». Приложение не завершает чужие процессы. После устранения вызвать `Vpn.Tun.ps1 -Enable -ParentPid <launcherPID>`; компонент повторит проверку и попросит UAC. Сам лаунчер остаётся без повышения прав. Не запускать worker напрямую и не включать VPN автоматически после перезапуска Windows.
- «Выключить системный VPN»: `Vpn.Tun.ps1 -Disable`. Ждать `off/rolled-back`; `stopping` означает запрос, а `error/rollback-error` — проблему. `enabled=true` без свежего `ok=true, state=on` не считать проверенным VPN. Пока идут UAC/starting, показать ожидание, а не зелёный статус. При отмене UAC/ошибке предложить повторное явное включение.
- Для статуса VPN не требуется постоянно держать ещё один непривилегированный daemon: worker живёт в своей одноразовой задаче и следует ParentPid/config/stop. Лаунчер читает vpn.json и вызывает команды по действиям пользователя. При выходе лаунчера worker видит завершение PID и выключает TUN. На старте создайте `off` через вызов Vpn.Tun без ключей, если файла ещё нет; старую запись `on` со старым updatedAt показывайте как устаревшую.

## Результаты разработки задачи C

Все `.ps1` сохранены в UTF-8 BOM и используют синтаксис PowerShell 5.1. Расширенный `test-transport-config.ps1` проверяет CRLF, pin/auto, реальные edit-команды, metadata/disabledTags/kinds/CDN, конфликты на фиктивном инвентаре, исключения и запрет SSH в TUN, выбор маршрута пробы, построение watchdog на пять минут и идентификацию своего PID, UTC в PS 5.1/7 и очистку маршрутов только своего GUID. С `-SingBox` выполняется `check` обычного транспорта и каждого из десяти поддерживаемых TUN-кандидатов. Ни один TUN в тестах не запускается. Локальный Python-стенд дополнительно проверяет pin за ≤5 секунд после записи, удержание мёртвого pin, возврат в auto, hot reload с прежними портами и сохранение рабочего процесса при невалидном config.

Фактический прогон: Linux, pwsh **7.4.13**, sing-box **1.14.4** — **212 проверок без сети**, отдельный Python-стенд завершился `OK`; обе JSON-схемы и config.example.json прошли jsonschema Draft 2020-12. Это не приёмка Windows PowerShell 5.1. Живые TUN, UAC, ScheduledTasks, Wintun/DNS/маршруты Windows, административные ACL, реальный конфликт с другим VPN, серверный internet egress и UDP пока **не проверены**. До отдельной приёмки включение TUN на компьютере с рабочими MCP-сессиями запрещено решениями владельца.


## Интеграция перехода (задача E)

`status/transport.json.summary` всегда содержит проверенный путь и измеренную скорость либо
«нет связи: <причина>». `kbps=null` не превращается в ноль. `transport.routeSsh` и
`transport.takeOverChannel` — boolean, применяются только явным `build/Migrate.ps1` / EXE --install.
Сам демон не меняет SSH config, Run или задачи; при переходе они изменяются только после временной пробы
и постановки независимого отката. Детали и Windows dry-run: [LAUNCHER.md](LAUNCHER.md#переход-существующего-компьютера).
При импорте берётся старый sing-box из RemoteDisk/channel; entries/relays/hops/cdn по умолчанию пустые.
Прямые SSH и пробы транспорта используют -F NUL и явный HostKeyAlias, поэтому управляемый блок
пользовательского SSH config не замыкает транспорт на собственный локальный вход.

Ревью F: управляющий цикл демона ждёт 300 мс; сетевые интервалы, счётчик байтов и требование pin ≤5 с
сохранены. Журнал транспорта записывает только фиксированные коды событий: текст исключений может
содержать короткий пароль, который нельзя надёжно замаскировать регулярным выражением. Пробы и
OpenSSH используют внутренние кавычки в UserKnownHostsFile для путей с пробелами. Стенд демона
дополнительно проверяет завершение всех SSH-проб после stop и смерти родителя. CPU на Windows
после изменения интервала ещё не измерен.

Старый `Test-Transports.ps1` не содержит личных маршрутов по умолчанию; его временный каталог и
конфиг закрыты ACL, журнал движка отключён, сырой stderr в отчёт не попадает, запуск/остановка общие
с демоном. `Update-Entries.ps1` скрывает текст исключения JSON. `test-diagnostics.py` проверяет это
на локальных имитаторах. Серверные `entry/*.sh` остаются только в исходниках: они меняют ufw/nginx/
systemd без независимого автоматического отката и не включаются в Windows-бандл до отдельной
серверной доработки и приёмки. Миграция Windows их не вызывает.
