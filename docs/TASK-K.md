# Задача K: отчёт и живая приёмка

Рабочая ветка `app/wizard`, каталог `/home/remoteagents/work/wt-wizard`.
Коммитов и push не выполнялось. Windows, MCP-мост владельца и рабочие серверные службы
не использовались: все исполнения — Linux, временные HOME/LOCALAPPDATA, фиктивный SSH
или локальные Syncthing-процессы стендов.

## Сделано по шагам

| Шаг | Реализация и граница подтверждения |
|---|---|
| 1. Сервер | Один раздел с адресом/пользователем, прежний SSH askpass → ключ. Реальная инвентаризация SSH, REST диска, файлов Happier/моста, user systemd, каталога. Явная установка только недостающего; ошибка с действиями администратора при отсутствии user manager. Рабочий профиль не подменяется другим сервером. |
| 2. Связь | Автоматическое чтение каталога SSH-пользователя; таблица entries/hops/relays/cdn, добавление и отключение, локальный overlay либо CAS-запись «для всех компьютеров». Приватные поля и пути не публикуются. H-ссылки сохраняются. Работающая связь: отдельный preflight, независимая задача отката, проверка новой ревизии и SSH. |
| 3. Диск | `%USERPROFILE%\Disk` либо выбранный корень, в том числе заполненный. Объединённое дерево с тремя пометками; исходно всё выбрано. Политика до подключения, sendreceive, удаление подтверждённых локальных копий по J. Невыбранные файлы только на ПК сохраняются. Перенос корня использует существующий механизм паузы/переноса и переносит квитанцию selective policy. |
| 4. Happier | Имена управляемых J-аккаунтов текущего SSH-пользователя; старые без метки получают читаемую подпись. Свой сохранённый ID выделяется, выбранный ID доказывается ключом до входа. Новый аккаунт с именем. API/Web только из пользовательских/серверных настроек. При неудаче прежние ключ и настройки восстанавливаются, новый ключ сохраняется в secrets как unconfirmed. Чужие службы/чаты не удаляются. |
| 5. Мост | Включение и отдельное разрешение shell; permission сверяется в серверной записи и аутентифицированном status executor. Уже здоровый мост с нужным permission не перезапускается. Выключенный мост не мешает принятию миграции. При обновлении старой установки UI сохраняет прежнее намерение включения, не выключает мост пустым значением нового поля. |
| 6. VPN | Выключен по умолчанию; прежние conflict detector, broker/UAC и watchdog; свой DNS/check URL. Чужой VPN не отключается программой. Запрос запуска показан как ожидание, не как работающий TUN. |
| 7. Итог | Результат/причина/подсказка каждого шага и журнал. После первого запуска перехода можно заново проверить живой итог: SSH, Syncthing, Happier API/machine, мост, VPN, фаза миграции. Передача в фоне и pending не объявляются готовыми. |
| Настройки | То же окно и тот же dispatcher; доступно обоим треям, также через `--settings`. Старые пункты аккаунта/папок открывают нужный раздел общего окна. Общий mutex мастера; первый RemoteVPN тоже ведёт настройку, RemoteAgents затем применяет сохранённые настройки без повторного ввода. |

Незавершённая часть требования «изменение любого параметра»: **полная смена сервера/SSH-пользователя
существующего профиля пока блокируется**. Отдельного безопасного переноса устройства между серверами
с перепривязкой диска здесь нет. Нельзя считать задачу K целиком принятой до решения этого ограничения
и живой Windows-приёмки. Ещё одна граница текущего RemoteDisk: файлы прямо в корне
показываются, но для синхронизации их нужно поместить в папку проекта; автоматического
переноса или отдельной root-share нет. Они не удаляются и не скрываются из дерева. На новом сервере также нужны доступные системные предпосылки; мастер
не вводит sudo-пароли в скрытом процессе и не обходит права администратора.

## Что установлено о Яндекс.Диске

Официальная [справка Диска 3.0](https://yandex.ru/support/yandex-360/customers/disk/desktop/windows/ru/sync-how-works.html)
описывает сохранение двух разных одноимённых файлов после офлайн-работы, переименовав один с `(2)`.
Полный алгоритм первого слияния и выбор переименуемой стороны там не определены.
У [Диска 4.0](https://yandex.ru/support/yandex-360/customers/disk/4/windows/ru/synchronization/folder)
иная схема выбора расположения — вложенная папка; переносить обещания 3.0 на 4.0 нельзя.

Использован документированный [merge новых папок Syncthing](https://docs.syncthing.net/users/faq.html#i-am-seeing-the-error-message-folder-marker-missing-what-do-i-do)
и [сохранение конфликтов](https://docs.syncthing.net/users/syncing.html#conflicting-changes).
Два заполненных дерева синхронизируются в sendreceive, оба исходных варианта одноимённого файла
остаются в обычном файле и `.sync-conflict-*`. Число конфликтных копий не ограничено; версия замен
защищается staggered versioning. Это не обещание семантического объединения текста и не запрет
обычных синхронизируемых удалений. Подробности/источники — в LAUNCHER.md.

## Сценарий живой проверки на стационарном

1. На стационарном сохранить резервную копию **текущих** config.json, RemoteDisk/selection.json,
   RemoteDisk/base.txt, SSH-профилей и secrets в закрытом месте вне синхронизации. Не выводить
   содержимое secrets в консоль, журнал, скриншоты или чат. Старую установку, задачи и канал
   заранее не удалять и не отключать.
2. Скопировать новый `release/` привычным способом. Для первой пробы запустить RemoteAgents.exe.
   Если старый переход уже принят, открыть трей → «Настройки…». На шаге «Сервер» оставить
   прежние адрес/пользователя; сначала проверить **без** установки. Должны быть отдельно видны
   обнаруженные компоненты и отсутствующие/неотвечающие. Только действительно недостающее
   разрешить установить. При запросе SSH проверить отпечаток лично.
3. «Связь» должна сама получить каталог. Первый проход — не менять рабочие пути и не ставить
   «для всех компьютеров». Проверить сохранение импортированного H-перехода. Для безопасной
   отрицательной пробы после принятия миграции добавить только локально **новый** включённый
   entry с заведомо несуществующим SSH-алиасом: preflight должен отказать до изменения рабочей
   связи; закрыть окно без применения других правок. Не отключать единственный рабочий путь.
4. «Диск»: оставить прежний корень и все прежние отметки. На первом проходе только обновить
   дерево: проверить три пометки на известных файлах. Для испытания передачи создать отдельный
   небольшой проект под Disk с явно выбранным вами новым именем и несекретными файлами:
   один только на сервере, один только на ПК, два разных варианта одного имени. Отметить только
   этот дополнительный проект, сохранив прежний выбор остальных. После синхронизации проверить
   обе стороны и `.sync-conflict-*`. Снять отметку с файла только на ПК — он должен остаться;
   для подтверждённой серверной копии локальное освобождение допустимо только после проверки.
   Не испытывать конфликт на рабочем исходнике; root-перенос на первом проходе не выполнять.
5. «Happier»: выбрать **свой** аккаунт; имя не даёт доступа. Проверить сохранённый ключ либо
   ввести свой в закрытое поле; не создавать лишний аккаунт для этой проверки. Убедиться,
   что прежние чаты, другие имена и другие компьютеры сохранились. API/Web должны совпадать
   с используемым владельцем сервисом, без подстановленного адреса приложения.
6. «Мост»: сохранить прежнее намерение включения; отдельно проверить shell только в выбранном
   разрешённом режиме. Не выключать текущий мост во время удалённой сессии. Изменение permissions,
   HKCU Run и реальная повторная установка проверяются лично у стационарного с местным доступом.
   «VPN» оставить выключенным. UAC/TUN и конфликт с другим VPN — отдельная очная проверка,
   когда от текущей сети не зависит удалённый доступ; чужой VPN отключает только владелец.
7. «Итог»: запустить переход только после проверки выбранных значений. Увидеть pending,
   затем три зелёных минуты и accepted в трее. При отказе ожидать автоматического возврата
   старого канала; читать причину и журналы, а не удалять Home/задачи. Для ручного возврата
   использовать прежний `RemoteAgents.exe --uninstall` (это откат перехода, не удаление файлов).
8. Закрыть/снова открыть «Настройки…»; проверить сохранённые значения и новый живой итог.
   Затем запустить RemoteVPN.exe и Start.cmd: повторного ввода данных быть не должно,
   два мастера не должны одновременно применять настройки. Проверить 100/150/200% DPI,
   клавиатурную навигацию, длинные русские имена, ошибку сети, отмену askpass и восстановление.

Требуют именно живой Windows: WinForms/DPI, Windows PowerShell 5.1, SSH askpass/host key,
HKCU Run, одновременный Start.cmd, Task Scheduler и аварийное завершение мастера до срабатывания
независимого отката, файловые ACL/перенос корня, UAC/TUN, настоящие серверные службы и повторный вход
после перезагрузки. Ничего из этого Linux-стенды не объявляют подтверждённым.
