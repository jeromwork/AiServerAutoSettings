# Независимое ревью Диска в Проводнике

Дата: 13.11.2026. Проверены изменения `app/config..0416aae` в ветке
`app/explorer-disk`, оба брифа и отчёта, правила `docs/CONSTITUTION.md`.
Исправления ревью находятся после `0416aae`; история не переписывалась.

## Найдено и исправлено

### 1. P1: ложная синхронизация при локальных изменениях receive-only

`DiskSyncStatus.Complete` учитывал need-счётчики, но игнорировал
`receiveOnlyChangedFiles`, `receiveOnlyChangedBytes`, `receiveOnlyTotalItems`.
Syncthing может иметь `state=idle`, `needFiles=0`, `needBytes=0` и одновременно
локальные изменения, которые не отправлены серверу. Окно называло такую папку
синхронизированной, счётчик включал её в завершённые, Explorer показывал зелёную
галочку и подсказку «На компьютере и на сервере».

Исправлено общей проверкой `HasLocalChanges`: предупреждение с причиной,
незавершённый статус и жёлтый значок. Проверка освобождения места использует тот
же критерий, её отказ сохранён. Файлы: `DiskSyncStatus.cs`,
`DiskExplorerPresentation.cs`, `DiskShellModel.cs`.
Коммит: `b0e7358` — «Ревью: не считать локальные изменения receive-only синхронизацией».

Регрессия: `DiskFoldersModelTests.cs`, 9 проверок трёх счётчиков — текст,
значок и общий счётчик. На прежнем коде тест упал с
`receive-only changes cannot show success: receiveOnlyChangedFiles`.

Сценарий дополнительно подтверждён настоящим Syncthing **2.1.7** в отдельном
временном HOME: receive-only папка с двумя локальными файлами вернула
`idle`, нулевые needFiles/needBytes и `receiveOnlyTotalItems=2`.
Пробный движок остановлен, временные данные удалены.

### 2. P1: потеря части команд множественного выбора до named pipe

`Program.Run` требовал mutex установщика с `WaitOne(0)` даже от
`--disk-shell`. Explorer запускает отдельный процесс для каждого элемента:
пока первый процесс пересылал свою команду, второй мог получить
«Установка уже выполняется» и завершиться, не передав путь в очередь.
Окно сбора аргументов в трее не могло восстановить потерянную команду.

Захват вынесен в `LauncherInstallerGate`: команды Explorer проходят к существующему
instance mutex и named pipe без захвата mutex установщика. Обычная установка
по-прежнему требует этот mutex. Файлы: `Program.cs`, `WindowModel.cs`.
Коммит: `166484c` — «Ревью: не терять команды Проводника на mutex установщика».

Регрессия: `WindowModelTests.cs` удерживает настоящий `Mutex` в одном потоке и
делает 15 обращений из другого потока с кириллицей и пробелами в пути. Все команды
Explorer допускаются без владения установочным mutex; конкурирующая установка
отвергается. При прежнем безусловном захвате тест упал на первом элементе:
`multiselect command reaches pipe despite another launch holding installer mutex: 0`.
Это проверка конкуренции mutex; настоящий Explorer/Windows named pipe здесь не запускался.

### 3. P2: PowerShell-очистка не восстанавливала исходный ReadOnly

`Remove-DiskExplorerFolderMetadata` восстанавливал `OriginalReadOnly=0`, но
для `OriginalReadOnly=1` сохранял текущий бит. Если его сняли после оформления,
удаление программы оставляло папку с другими атрибутами, чем до оформления.
C#-очистка уже восстанавливала оба значения.

PowerShell теперь тоже восстанавливает оба записанных значения, сохраняя
остальные атрибуты. Файлы: `disk/Disk.Explorer.ps1`, `disk/test-explorer.ps1`.
Коммит: `ce99f91` — «Ревью: восстанавливать исходный ReadOnly при удалении оформления».

Регрессия: записать `OriginalReadOnly=1`, снять текущий ReadOnly, удалить
оформление, проверить возвращённый бит. На прежнем коде тест упал с
`cleanup restores recorded ReadOnly even if it was cleared after decoration`.
После исправления группа проходит 39 проверок.

### 4. P2: незакрытый HTTP-ответ при отказе проверки перед Корзиной

`DiskLocalRest.Request` закрывал успешные ответы через `using`, но в
`catch (WebException)` оставлял `Response` незакрытым. Повторные REST-отказы
оставляли HTTP-ресурсы до последующей сборки мусора; для .NET Framework это
также может задерживать освобождение соединений.

Ответ закрывается до обработки отмены и формирования безопасного отказа.
Добавлен узкий подменяемый вызов получения ответа для проверки освобождения.
Файлы: `DiskEvictionSafety.cs`, `tests/DiskShellTests.cs`.
Коммит: `93729fb` — «Ревью: закрывать HTTP-ответ при отказе проверки Корзины».

Регрессия проходит через настоящий `DiskLocalRest.File/Request`, подставляя
ошибочный `WebResponse` с наблюдаемым `Close`. Проверены обычная ошибка и отмена
в момент ответа. На прежнем обработчике тест упал с
`HTTP error response closed even during cancellation: False`.
После исправления shell/safety группа содержит 57 проверок.

## Проверенные защитные условия

В рассмотренных сценариях новый воспроизводимый дефект потери пользовательских
данных не найден. Это не гарантия отсутствия всех возможных гонок файловой системы.

- Перед Корзиной проверяются реальное состояние/связь Syncthing, completion именно
  сервера, версии и доступность файлов, хэши содержимого, повторный локальный
  инвентарь и подтверждённое отсутствие папки в конфигурации движка. Неполная,
  неизвестная или изменившаяся копия оставляет файлы. Нет fallback на безвозвратное
  удаление при ошибке/отмене Корзины.
- Инвентаризация и очистка проверяют reparse points; удаление собственного junction
  использует нерекурсивное удаление ссылки. Подменённый target не принимается за
  собственный junction. Тесты сохраняют реальные файлы внешнего источника.
- Чужой `desktop.ini` и ссылки на него пропускаются. Заглушка перестаёт считаться
  заглушкой после появления пользовательских файлов. Проверены повторная установка
  и очистка, сохранность посторонних атрибутов и внешних каталогов.
- Исключение `(?i)/desktop.ini` ограничено корнем проекта; вложенные файлы не
  скрываются этим правилом. История хэшей объединяется при установках разных
  версий, включая CRLF. Имеющиеся интеграционные тесты проверяют обе стороны и
  путь загрузки помощников мастера.
- UI использует фоновое чтение и проекции снимка; выбранные пути вкладки
  перепроверяются после ожидания. Кэш и запись метаданных имеют отдельные блокировки.
  В просмотренных путях взаимная блокировка UI и фонового потока не воспроизведена.

## Проверки

Исходный `SKIP_LAUNCHER_EXE=1 app/launcher/tests/run.sh` завершился с **exit 1**:
известный `PermissionError` LAN-теста на `/var/lib/remoteagents/lan/pending`.
Этот запуск не объявляется зелёным.

Первый полный прогон с внешней LAN-фикстурой завершился с **exit 1** в известном
нестабильном `transport/test-engine-loopback.py`: request-файл исчез до `chmod`.
Отдельный повтор неизменённой команды
`python3 transport/test-engine-loopback.py --without-disk` прошёл с **exit 0**.

Затем повторён **весь** runner после всех четырёх исправлений:

```sh
SKIP_LAUNCHER_EXE=1 PYTHONPATH=/tmp/folders-status-test-isolation app/launcher/tests/run.sh
```

Результат — **exit 0**, включая loopback в составе общего запуска, все 76
серверных тестов, portable обоих продуктов, CONFIG по 134 проверки,
CONFIG/e2e с настоящими SSH и sing-box, тестовый ZIP и явный SKIP сборки/publish EXE.
Это успешный единый прогон, а не составление результата из отдельных групп.

Использована прежняя внешняя фикстура из `FOLDERS-STATUS-REPORT.md`:
`sitecustomize.py` подменяет только `lan.PENDING` временным каталогом в
`test_lan_vpn.SafetyTests.test_timer_failure_prevents_network_mutation` и затем
восстанавливает его. Исходники VPN, утверждения теста и настоящий
`/var/lib/remoteagents` не изменены. Без этой фикстуры исходный запуск на данном
исполнителе остаётся неуспешным по указанной причине.

Журналы текущего исполнителя: `/tmp/explorer-review-baseline.log`,
`/tmp/explorer-review-full.log`, `/tmp/explorer-review-loopback-retry.log`,
`/tmp/explorer-review-full-retry.log`.

Отдельно прошли portable-проверки после всех исправлений: 112 проверок окна и
маршрутизации, 286 модели папок, 53 метаданных Explorer, 57 shell/safety и остальные
группы portable-набора. Проверка PowerShell Explorer прошла 39 проверок.

Весь WinForms-код обоих продуктов скомпилирован Roslyn в **временные библиотеки**
против reference assemblies .NET Framework 4.8 с C# 7.3. Ошибок компиляции нет;
остаётся прежнее предупреждение CS1701 о reference assemblies Compression.

## Не подтверждено и не менялось

- Windows 10/11, Windows PowerShell 5.1, настоящий HKCU, отображение AppliesTo,
  view реестра при 32-битном запуске, Корзина, SHChangeNotify и вид значков требуют
  ручной приёмки на Windows. PS-тесты здесь выполнены на PowerShell 7; компиляция
  против net48 не заменяет выполнение приложения на Windows. HKLM в новых путях
  регистрации не используется; PowerShell использует явный Registry64.
- Корзина не является транзакцией с одновременно пишущим сторонним приложением:
  остаётся интервал между последней проверкой и вызовом файловой операции.
  Конкретная потеря данных в этом интервале не воспроизведена; алгоритм удаления
  без Windows-стенда и доказанного сценария не переделывался.
- Запуск Syncthing Tray с отдельным ini требует проверки числа процессов и
  автозапуска на поставляемой Windows-сборке. Повторный Syncthing, постоянная утечка
  процессов/таймеров или зависание окна здесь не подтверждены; код запуска не менялся.
- Смена сервера/выключение компонента в момент фонового запроса контроллера может
  дать короткое устаревшее оформление до следующего цикла. Постоянный неверный
  статус или операция над другим сервером не воспроизведены; дополнительных
  изменений контроллера по предположению нет.

EXE не собирался и не выкладывался. Компьютеры владельца, рабочие проекты,
действующий сервер и `/var/lib/remoteagents` не изменялись. Транспорт, VPN, мост и
Happier не правились; их тесты выполнялись только штатным общим runner.
