# Диск: действующий контракт

Редакция 1, 16.11.2026. Единственный нормативный документ жизненного цикла Диска.
DISK-MATRIX.md — исторический аудит исходного поведения, а не требования.
При противоречии PLAN-DISK, SPEC-SYNC, EXPLORER-* и FOLDERS-STATUS-REPORT действует этот контракт.

## Инварианты и принятые решения Q1–Q10

1. **Q1. Допуск.** Проект сервера — настоящий git top-level непосредственно в `~/Disk/<Имя>`.
   `.git` может быть каталогом или корректным gitdir-файлом (worktree); унаследованный родительский repo,
   сломанный gitdir и symlink не подходят. Внешний gitdir допустим, но сервер не пишет в его exclude.
   Наличие origin проверяется без чтения/журналирования URL: без него публикация разрешена,
   статус/журнал — «без удалённого репозитория». Сервер origin никогда не придумывает.
   Новую папку с ПК создаёт только Upload: ID `rd-upload-v1-<32 lowercase hex>` (случайный UUID N).
   Имя находится в label и передаётся без преобразования. Формат — маркер версии намерения,
   а не криптографическое доказательство нажатия кнопки: доверенный peer способен его воспроизвести.
   Legacy/ручные ID (включая Infraagent, PlainTest и ID из старого installer fallback) не принимаются.
   До регистрации входящей папки сервер выполняет `git init` и один пустой начальный коммит:
   файлы ещё не получены, индекс не заполняется, содержимое не коммитится. Это единственное
   исключение Q9. Повтор приёма не коммитит правки. Незавершённый приём имеет marker и повторяет тот же путь.
2. **Q2. Коллизия.** Имя занято (сравнение без регистра), путь зарегистрирован или пересекается — отказ
   «имя занято на сервере», без суффиксов `(2)`, без слияния. Человек выбирает другое имя либо
   явно объединяет локальную копию с уже существующим серверным ID.
3. **Q3. Пути.** На ПК только прямые дети выбранной базы Disk (по умолчанию `%USERPROFILE%\Disk`).
   Внешние и вложенные регистрации не поддерживаются; внешний перенос отсоединяет старую привязку.
   desktop.ini/значок без актуального config не доказывает синхронизацию; наше оформление по возможности очищается.
4. **Q4. Корень на ПК.** Delete корня D или P — локальное отсоединение, сервер сохраняется, P появляется вновь.
   Rename корня — отсоединение старого ID/пути; новое имя — обычная J без автоматического Upload.
   Delete файлов внутри существующего D — обычное двустороннее удаление Syncthing.
5. **Q5. Освобождение.** Keep разрешён только после свежего подтверждения обеих сторон и проверки
   всего локального инвентаря. Уникальные ignored (.env, vendor и прочие), несинхронизированные
   и поздние правки — отказ со списком путей. Никакие уникальные данные не перемещаются в Корзину.
   Безопасная Корзина обязательна; при отмене/ошибке восстановить регистрацию, сохранить файлы.
6. **Q6. Снятие сервером.** Исчезновение/rename каталога после непрерывного grace 30 с при доступном
   непустом корне, ручное удаление регистрации или смена её пути создают вечный tombstone старого ID.
   Tombstone записывается до DELETE; тот же ID никогда не публикуется и не принимается ни от одного ПК,
   даже если прежний каталог вернули. На ПК — «удалена на сервере», локальные данные сохраняются,
   регистрация отсоединяется. Новое намеренное создание требует нового ID, без слияния со старым.
   Пустой/недоступный/подменённый корень не доказывает удаление последнего проекта: нет DELETE,
   приёма, создания Disk/проектов; наблюдение отсутствия сбрасывается. Восстановить доступность,
   затем выполнить явное снятие регистрации при необходимости (оно оставит tombstone и при пустом корне).
7. **Q7. Reinstall.** Непустая локальная копия не принимается автоматически: отдельное явное
   «Объединить с сервером» с сохранением обеих конфликтных версий. Чужое оформление не перезаписывается.
8. **Q8. Исключения.** Обязательный include стоит первым, до любого пользовательского `!`/include,
   BOM не меняет приоритет. `.git`, `.env*`, ключи, `*.pem`, `*.crt`, `*.crt?`, `token*.json`,
   credentials/secrets, зависимости, `.venv`, `venv`, `__pycache__`, локальные `*.sqlite*`, `*.db*`,
   дампы `*.dump`, `*.bak`, `*.sql`, `*.sql.gz`/bz2/xz/zst, `*.sql.zip` не передаются.
   Точный исполняемый перечень — `disk/stignore.txt`. SQL-исходник вроде db/schema.sql
   также исключён: для передачи схемы использовать миграции другого расширения.
   Это политика имён, без обещания анализа содержимого или обнаружения неизвестных секретов.
   Политику нужно применять до первого scan и обновлять у существующих регистраций на каждой стороне.
9. **Q9. Версии.** Для новых и существующих папок `staggered`, `maxAge=2592000` (30 дней),
   `cleanInterval=3600`, `maxConflicts=-1`. Версии Syncthing не заменяют git и не гарантируют
   хранение каждой промежуточной правки. После единственного init-коммита Q1 программа не коммитит;
   commit/push — работа владельца/агента. Конфликты показываются явно и блокируют Keep до разрешения.
10. **Q10. Источники истины.** Отдельной служебной синхронизируемой папки-каталога нет.
    Используются локальный config/pending, память подтверждения, серверные tombstones и журнал.
    Pending не доказывает доставку файлов, git-admission или актуальную доступность сервера.
    Все пользовательские действия ПК — локальный REST Syncthing; SSH нужен установке/выкладке,
    а не кнопке download/upload/Keep. По умолчанию ПК получает только прозрачные пустые заглушки.

## Имена, идентичность и долговечность

Имя уже в Unicode NFC, 1–128 символов и не более 240 UTF-8 байт. Первый символ — Unicode буква,
число либо `_`; далее те же символы, пробел, `.`, `(`, `)`, `-`. Комбинируемые знаки отдельно
не допускаются. Запрещены `..`, завершающие пробел/точка, CON/PRN/AUX/NUL/COM1–9/LPT1–9
(также COM/LPT с ¹²³), в том числе перед расширением. Никаких strip, обрезания, нормализации
или замены символов. Коллизии сравниваются casefold; два серверных имени с таким совпадением
оба требуют исправления человеком. Внутренние недопустимые Windows имена — явная ошибка,
без молчаливого переименования/потери.

ID и путь — разные поля. Сохраняются действующие ID; старый tombstone не снимается.
При серверном rename старый ID снимается, новый путь — новый проект/предложение;
входящий marker старого ID не является разрешением воскресить его. Нельзя автоматически
сливать переименованный проект с оставшейся копией ПК. Восстановление — явное новое создание/привязка
с новым ID после проверки данных. Сервер не удаляет данные проектов при обслуживании конфигурации.

`missing-folders.json` хранит наблюдения, `published` (последние подтверждённые управляемые
ID/пути), вечные `removed` и факт миграции guard. Отсутствие прежде опубликованного ID в
успешно прочитанном config означает ручное снятие. Это наблюдение снимков: удаление и возврат
конфига между двумя запусками без наблюдаемого промежуточного состояния установить невозможно.
При первом запуске инвентаризируется текущий config; события до установки без старого состояния
не восстанавливаются догадками. Битые/недоступные долговечные tombstones останавливают изменения,
их нельзя молча заменять пустым списком. Наблюдения времени можно сбрасывать без снятия tombstones.

`project-journal.jsonl` — локальные JSON-строки: время, projectID, source, hostID (ID серверного
Syncthing), device (ID предлагающего ПК или пусто), outcome, reason. Содержимое файлов, origin URL,
ключи и конфиги в журнал не попадают. Одинаковые неизменные решения не печатаются каждые 2 с.
Журнал не передаётся как проект. `vanish-guard.json` импортируется до discovery: paused ID
становятся tombstones, управляемые регистрации снимаются при безопасном корне; исходный файл
сохраняется для расследования/отката. Параллельный старый сторож перед выкладкой останавливается.

`disk/test-disk.py`; «часть» — проверяет указанную серверную часть перехода. `ПК: имя` —

## Границы этапа 1 и разбор app/disk-pc-vanish

Серверный этап закрывает H01, сервер H02/H11/H12/H17/H24/H26, H05 и H23.
Он не объявляет закрытыми клиентские H03/H04/H07/H08/H09/H10/H13–H22/H25
и клиентские части H02/H11/H12/H17/H26. В частности, старый Upload с ID=basename
после серверного обновления намеренно отвергается: генератор нового Upload-ID и клиентские
сообщения отказа входят в клиентский этап. Поэтому выкладка сервера сама по себе не означает
готовность всей функции; приведённые в README команды здесь не выполняются.

Разобраны a0c081c, a175d75, 4d89432. a0c081c даёт полезное monotonic-наблюдение
и локальный DELETE регистрации, 4d89432 корректно сбрасывает NaN/Infinity/битые timestamps.
Переносить их целиком нельзя: они обслуживают и внешние пути, не решают ложный перенесённый ini,
не дают полной гарантии cross-volume delete. a175d75 согласуется с Q7: отдельная команда
явного merge и LocalCopy. В следующем этапе переносить выборочно, с проверкой прямого ребёнка
базы, действующей server identity, обязательных первых ignores, 30-дневных версий и тестами
всех фаз. В этом серверном этапе C# и ветка-источник не меняются.

Доказательство готовности серверного этапа и оставшиеся проверки — `docs/DISK-STAGE1-REPORT.md`.
