## Как фактически устроена система

1. Сервер: отдельный Syncthing 2.1.7, `bootstrap` под flock; discovery и приём pending запускаются таймером. Номинально интервал — 2 с **после завершения** предыдущего запуска, плюс `AccuracySec=1`; cron fallback — минута. Это не SLA «всё за 2 секунды» (`S:160–189,427–497`).
2. Все известные серверному Syncthing устройства включаются во все обнаруженные папки (`S:273,316–323`). Встроенный `autoAcceptFolders=false` не отменяет самописный автоприём в `accept_pending` (`S:49–86`).
3. Папки сервера предлагаются ПК через Syncthing. C# читает локальные `config/folders`, `cluster/pending/folders`, `db/status`, `db/completion`; отдельного достоверного полного каталога проектов нет (`R:90–128`). Никаких файлов проекта по умолчанию не принимает; создаёт реальные пустые каталоги с desktop.ini.
4. Три shell-команды идут через HKCU → EXE → IPC → C# → **локальный REST 127.0.0.1**, без SSH на действие (`K:47–66`, `Q:50–179`, `R:23–69`; `Program.cs:152–165`, `TrayContext.cs:759–768`). Название download сейчас «Скачать на компьютер», а не «Забрать с сервера» (`M:14`).
5. События Syncthing обновляют оформление; самостоятельного наблюдателя Windows за переездом/удалением заглушки нет (`X:53–94`). Корневой desktop.ini — локальный, исключён из обмена (`G:55–56`). Это значок целой папки, не Cloud Files placeholder и не overlay каждого файла.
6. Установщик — отдельный путь. Именно он допускает список немедленного приёма и fallback после 30 с без предложения (`C:332–357`). `disk.folders` — команда «допринять», а не постоянное желаемое состояние. Удаление записи из списка не отключает уже принятую папку (`D:12–17`, `C:287–293`).
7. «Оставить только на сервере» сканирует, ждёт готовности, снимает локальную регистрацию, проверяет снятие, перемещает **всю** папку в Корзину и создаёт заглушку (`Q:114–179`). Это освобождает рабочий путь, но место на томе может оставаться занятым Корзиной.

## Что именно уезжает при переносе в Windows

`.stfolder` — проверка наличия корня движком, **не указатель на новое местонахождение**. `.stfolder/remote-disk-folder-id` создаётся сервером для входящего проекта и не передаётся как обычные данные клиенту. Локальный path хранится в конфигурации Syncthing; desktop.ini не содержит ID привязки и хранит лишь Owner/Placeholder/CreatedDirectory/OriginalReadOnly и IconResource (`S:38–39,75–76`, `F:197`).

При обычном переносе целиком на том же диске folder path в Syncthing остаётся прежним. Поэтому новая папка с зелёным ini может уже не синхронизироваться. Скопированный ini может размножить ложный значок. Возврат на прежнее место с marker обычно даёт движку снова увидеть каталог; возврат в другое место не исправляет конфиг. Для безопасного намеренного переноса нужен отдельный сценарий detach → move → re-add того же ID с проверкой результата и откатом, а для произвольного Explorer move — обнаружение пропавшего старого пути без распространения удаления.

Это соответствует [официальному FAQ о перемещении](https://docs.syncthing.net/users/faq.html#how-do-i-rename-move-a-synced-folder) и [проверке marker в исходниках Syncthing v2.1.7](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/model/folder.go). Windows Shell в этой работе не запускалась; особенно для межтомного переноса результат промежуточного удаления требует отдельного теста.

## Живой скрипт и временная защита: это разные реализации

Побайтовый diff прочитан. SHA-256:

| Файл | SHA-256 |
|---|---|
| S, репозиторий | `946d6d6a61bc8669369dba7a8f5f57557d60166cfacd6d237ac71dfa4256eadf` |
| L0, установленная копия при первом чтении | `7e5a1a6d92d8421f9ec5b5bc4b5f2cb8a4c20c004c39350d2b49ad5c8eeeb1a9` |
| L1, тот же рабочий файл при финальной сверке | `946d6d6a61bc8669369dba7a8f5f57557d60166cfacd6d237ac71dfa4256eadf` (равен S) |
| V, временная защита | `2e56521ac02e6267349efb7664c8628ed05598c29b4ec228a860a964f04f37bc` |

В первоначальной L0 отсутствуют `math`, `missing_watch`, `disk_generation`, `save_missing`, `forget_missing` и 30-секундный протокол; `accept_pending` не принимает removed и не запрещает повторный приём снятого ID. Отсутствуют восстановление ID по tombstone и его снятие после возвращения проекта. Остальные показанные diff участки объясняются удалением этого механизма. Это соответствовало `STATUS.md:5` на момент первого чтения. На конец аудита **diff S/L1 пуст**, так что фраза STATUS «скрипт НЕ ставился» уже не описывает факт наличия файла. Применён ли файл работающим таймером, перенесены ли его состояния и выключен ли V — без живой проверки не установлено.

V не делает DELETE: на втором последовательном наблюдении отсутствия ставит PATCH paused=true; после возвращения снимает **свою** паузу (`V:13–28`). В V нет 30-секундного monotonic grace, общей блокировки с bootstrap, проверки поколения Disk и последней проверки отсутствия перед PATCH. Интервал установленного таймера в этом аудите не читался, поэтому «два наблюдения» нельзя переводить в конкретные секунды. Пустой Disk V пропускает. Наличие V на диске и запись STATUS не доказывают, что таймер сейчас активен.

Совместная будущая работа V и S не продумана как миграция: например, V может уже поставить исчезнувшую папку на паузу, а основной reconcile сохраняет paused у существующей папки (`S:311–323`). Нельзя просто объявить проблему закрытой наличием 8bac10f. Нужны версионированный переход, обработка guard-owned pauses и проверка двух клиентов; здесь ничего не применялось.

## Предлагаемая последовательность работ

1. **Зафиксировать контракт, не переписывать UI ещё раз.** Утвердить ответы Q1–Q6; таблица переходов и server project registry — единственная нормативная модель. Стабильный project ID не зависит от имени и пути; локальное «держать/не держать» относится к конкретному ПК.
2. **Закрыть допуск и секреты.** H01/H02/H10/H11: discovery только git+origin, никакого installer fallback-create, никакого несанкционированного auto-accept. Новый upload без серверного Git-репозитория не появляется в Disk. Обязательные исключения не переопределяются пользовательским `!`.
3. **Свести серверный жизненный цикл.** Каталог/поколения/tombstones, create/rename/retire/restore, последний проект, запрет воскрешения от любого старого peer. Сначала изолированные fixtures; никакого прогрева на `~/Disk/Test` владельца.
4. **Свести локальный жизненный цикл.** download/merge/Keep/move/detach/reinstall используют один admission и journal. Отдельно arbitrary Explorer delete/move и потеря тома; пользователь не должен получать зелёный ini без рабочей привязки.
5. **Обновление и два ПК.** Версии/identity/custom-home, защита от отката серверного helper, миграция V и L. Один manifest объясняет, что установлено на сервере и каждом ПК. Все изменения — будущая отдельная задача с обычным workflow репозитория.
6. **Приёмка по матрице.** На временных HOME вне `~/Disk`/`~/work` с отдельными Syncthing и синтетическими секретами прогнать каждую строку, затем Windows 10/11 + WinPS 5.1 + реальные HKCU/Shell/Корзина. После каждого сценария сверять filesystem, folder IDs/paths/devices, git/origin и фактические hashes файлов на сервере/ПК1/ПК2; повтор действия и перезапуск обязаны давать тот же результат без дубликатов.
7. **Только после приёмки — отдельная контролируемая поставка.** Не смешивать её с аудитом. Итоговый критерий: у каждой клетки есть детерминированный исход, путь восстановления и воспроизводимый тест. «Проблем больше никогда» нельзя доказать количеством патчей; можно перестать оставлять неопределённые переходы.

Небольшая служебная папка каталога/запросов нужна потому, что локальный REST управляет **локальным** Syncthing и не умеет сам создать GitHub/GitLab origin или отдать достоверную серверную историю проектов. Если выбрать такой протокол, его файлы должны жить вне каталога проектов, передавать только метаданные и иметь отдельную схему/подтверждения. Это позволяет сохранить принцип «без SSH на пользовательское действие». Альтернатива — сервер заранее провизионит все допустимые git-проекты, а новая Upload лишь выбирает один из них; UX такого выбора тоже надо определить.

## Вопросы владельцу, где решение не следует из принципов

Это список для следующего проектирования, не запрос разрешения на какие-либо действия сейчас.

1. **Q1. Что значит «Загрузить новую папку», если origin ещё не существует?** Предлагаемый вариант: человек выбирает существующий remote либо указывает место создания remote, сервер создаёт git+origin перед допуском. Нужен выбор GitHub/клинический GitLab и политика для отсутствующего VPN/прав создания. Автоматически придумывать origin нельзя. Допустим ли режим «сначала создать remote отдельно»?
2. **Q2. Что делать при занятом имени?** Рекомендация: отказ с выбором «подключить существующий проект» или дать другое имя **на обоих концах**; никакого молчаливого `(2)`/merge. Если пользователь хочет объединить данные, нужна отдельная явная команда по стабильному ID.
3. **Q3. Внешние пути на ПК — рабочий поддерживаемый сценарий?** Текущая программа разрешает их, Конституция запрещает. Предпочтение для предсказуемости: одна база Disk, отдельный управляемый перенос по желанию. Если `C:\works\eastclinic` нужен как активная копия, определить, должна ли она продолжать синхронизацию после явного переноса и как показываться в Disk; обычный drag-and-drop не может молча означать всё сразу.
4. **Q4. Что означает Delete корня проекта на ПК?** Рекомендация: локальное отключение/убрать копию с сохранением сервера; удаление содержимого D остаётся двусторонним. Delete P — «скрыть на этом ПК» или она должна возвращаться? Переименование на ПК — только локальное имя либо переименование проекта для всех? Это три разные операции.
5. **Q5. Как поступать с локальными ignored при Keep?** Рекомендация: отказ с понятным списком уникальных данных и отдельным выбранным способом сохранить их. Разрешено ли переносить `.env`, зависимости и `.stversions` в Корзину целиком, зная, что сервер их не хранит и свободное место сразу не увеличится?
6. **Q6. Папка исчезла/снята сервером: что показывать каждому ПК?** Рекомендация: локальную D сохранить как отсоединённую копию, P убрать только по подтверждённому retire; restore только явной командой. Надо ли скрывать старую копию из общего каталога или оставлять заметное «проект удалён на сервере»?
7. **Q7. После переустановки с теми же исходниками объединять автоматически или спрашивать?** Рекомендация: предложить явное merge с существующим ID и сохранить обе версии конфликта. Полностью новый пустой ПК продолжает ничего не скачивать.
8. **Q8. Какой утверждённый перечень секретов/локального состояния обязателен помимо текущего G?** Нужны правила для произвольных конфигов с паролями, PEM/token.json, `.venv` и локальных баз. Рекомендация: mandatory policy + тестовые примеры; приём неизвестного содержимого не называть гарантированно очищенным от любых секретов.
9. **Q9. Какая политика версий/конфликтов и заполнения диска?** Старый SPEC обещает 30 дней, текущий new_folder — staggered maxAge=0, README говорит про все версии. Рекомендация: явный срок/лимит и предупреждение, запрет Keep при неразрешённом конфликте. Server/PC versioning не равен git commit/push: должна ли программа когда-либо коммитить синхронизированные изменения сама, или это только работа агента/владельца?
10. **Q10. Служебные метаданные всегда доступны на обоих ПК?** Рекомендация: разрешить маленькую отдельную служебную синхронизацию каталога и запросов без исходников, вне `~/Disk`, чтобы реализовать admission/rename/tombstones через локальный REST. Если это не допускается, новая загрузка может работать только для заранее подготовленных сервером git-проектов.

Не требуют повторного обсуждения: серверные проекты — git+origin в `~/Disk/<Проект>`, никаких non-git копий/тестов там; default ПК без скачивания исходников; действия через локальный REST; `.git`, секреты и зависимости не передаются.

## Тестовая база и пределы доказательств

Прочитаны `disk/test-disk.py` (discovery, pending, collision, unknown peer, slow/lost REST, grace/tombstones, reconnect/stale connections), `disk/test-wizard-merge.py`, PowerShell-проверки установки/accept/pairing/путей/запуска/cleanup, `DiskExplorerTests.cs`, `DiskChoiceTests.cs`, `test-disk-explorer-engine.py`, `test-disk-safety-engine.py`, связанные проверки трея/значков/ошибок. Основные текущие команды подключены в `app/launcher/tests/run.sh:47–49,84–88`.

`disk/test-disk.py` использует настоящие Syncthing во временных HOME, но cron/systemd имитирует (`:114–155`). C# engine-тесты используют настоящие REST/файлы и Linux move вместо Windows Корзины (`test-disk-explorer-engine.py:57–60,93–100`). Metadata fixtures частично имитируют атрибуты и реестр (`DiskExplorerTests.cs:91–108,181–187`). Это сильные проверки движка, но не доказательство поведения реального Explorer, межтомного move, WinPS 5.1, значков и Shell recycle.

`EXPLORER-DISK-REPORT.md`, `EXPLORER-REVIEW.md`, `FOLDERS-STATUS-REPORT.md` прочитаны как **исторические отчёты** 13.11. Их `DiskEvictionSafety`, selective/union/junction, hash proof, пятикомандное меню и периодические деревья нельзя приписывать текущему упрощённому launcher. `STATUS.md` утверждает прошлые полные прогоны, но отдельно отмечает неподставленный серверный скрипт. `docs/TODO.md` не содержит полного жизненного цикла папок — его следует добавить на основании данной матрицы.

Проверена официальная семантика, без взаимодействия с живыми установками:

- [Syncthing FAQ: marker и перенос папки](https://docs.syncthing.net/users/faq.html#how-do-i-rename-move-a-synced-folder): путь не следует за обычным переносом; перенос требует управляемого переподключения. Отдельно [исходники v2.1.7 folder.go](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/model/folder.go) и [FolderConfiguration](https://github.com/syncthing/syncthing/blob/v2.1.7/lib/config/folderconfiguration.go) проверяют path/marker поставляемого поколения.
- [Ignoring Files](https://docs.syncthing.net/users/ignoring.html): `.stignore` локальный; первое подходящее правило решает; `!` включает файл; include не имеет магического приоритета над предшествующими правилами.
- [Understanding Synchronization](https://docs.syncthing.net/users/syncing.html): конфликтные копии — обычные синхронизируемые файлы; case-conflicts зависят от файловой системы; изменения/удаления распространяет движок.
- [File Versioning](https://docs.syncthing.net/users/versioning.html): версии сохраняются при полученных удалённых изменениях, а staggered прореживает интервалы даже без максимального возраста.

Выводы о реальном происхождении неназванных в истории папок, фактических версиях EXE двух ПК, активности guard.timer и порядке Windows cross-volume move остаются **не установленными**. Их нельзя подменять догадкой или выводом из одного зелёного значка.
