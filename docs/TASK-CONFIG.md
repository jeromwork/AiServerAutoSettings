# Задача CONFIG: настройка вставкой конфига вместо мастера

12 ноября 2026, решение владельца. Делать в отдельном worktree от `app/windows` (после слияния `app/invite`), ветка `app/config`.
Правила: `docs/CONSTITUTION.md` (§1 — ничего не вшивать, §3 — секреты отдельно, §4 — откат сети, §5 — честный статус, §6б — CRLF, §6в — PS 5.1).

## Что нужно владельцу

Пошаговый мастер с «Далее» неудобен: надо помнить, куда что вставлять, держать бумажки, а подключение идёт 5–10 минут.
Нужно как в Happ: **вставил конфиг (или ссылку) → большая кнопка «Запустить» → через десятки секунд работает**.

1. **Запуск EXE.** Уже настроено → маленькое окно с большой кнопкой «Включить» (без вопросов); после нажатия программа
   запускается и уходит в трей с заметным уведомлением «RemoteAgents работает, значок в трее» — люди должны видеть, что она
   запустилась, а не думать, что её нет. (Автозапуск при входе в Windows по-прежнему без окна.)
   Не настроено → окно поверх всех с выбором: **«Вставить конфиг»** (основной, крупно) или **«Пройти по шагам»**
   (существующий мастер остаётся как запасной путь). После вставки — кнопка «Запустить».
2. **После «Запустить»** — под полем конфига идёт выполнение: по каждому разделу (сервер, связь, мост, Happier, диск, VPN,
   прокси, локальные сети) своя полоска/строка ⏳/✅/❌ с текущим действием, ниже — журнал, который видно сразу, при ошибке — причина простыми словами и «Повторить» для этого раздела.
   Независимые разделы идут **параллельно**. Долгие установки на сервере — в фоне с честным статусом, не блокируют остальное.
3. **Папки** — единственное, что показывается визуально: дерево диска (существующее ленивое дерево «только на сервере /
   только здесь / в обоих»), предзаполненное папками из конфига. Изменения папок пишутся обратно в конфиг.
4. **Готово** → окно закрывается, программа в трее.
5. **Настройки из трея**: вкладка «Конфиг» — текущий конфиг текстом (без секретов): «Скопировать», правка/вставка,
   «Применить». Применяются только изменившиеся разделы, тем же движком. Вкладка «Папки» — то же дерево.
   Существующие разделы настроек остаются как «Подробно» для точечной правки — они меняют тот же конфиг.
   Принцип: **поменял конфиг — поменялась работа программы**.
6. **Приглашение = готовый конфиг.** `.rainvite` / нагрузка в EXE — это частный случай того же конфига (с одноразовым
   пропуском). Один формат или явное однозначное преобразование; один движок применения. Существующий поток приглашения не ломать.

## Формат конфига

- JSON со `schema`/`version`, схема в `app/launcher/` рядом с `config.schema.json`, пример `config.paste.example.json`
  без наших значений (§1). Документ `docs/CONFIG.md`: короткое описание каждого поля — по нему ИИ-агент должен уметь
  составить конфиг владельцу.
- Разделы: сервер (адрес, порт, логин, ключи хоста — необязательно, маршруты direct/proxy/hop в формате маршрутов мастера),
  связь, мост (вкл, shell), Happier (тот же аккаунт / новый с именем / подпись, адреса API и веба), диск (корень, папки),
  VPN, прокси сервера, локальные сети, компоненты. Отсутствующий раздел = «не трогать».
- **Название компьютера** (`device.name`, например «Ноутбук», «Компьютер сына») — в конфиге или в настройках, по умолчанию
  предлагается при первой настройке. Название уходит на сервер и становится `deviceName` моста в реестре (`windows_devices`),
  чтобы агенты и люди различали компьютеры по-человечески, а не по `WIN-…`. Смена названия в настройках — сразу на сервер.
- **Конфиг самодостаточный.** Пароли и ключи МОГУТ лежать в конфиге: пароль — текстом, SSH-ключ — текстом внутри конфига
  (а не путём к файлу), ключ Happier, логин/пароль прокси и hop. Поле заполнено → используется молча.
  Поле пустое → программа спрашивает в окне с объяснением: у стандартных полей объяснение встроено («Пароль root сервера X —
  его присылает хостинг при покупке сервера»), у любого поля может быть своя подсказка `hint` из конфига.
- **Конфиг можно закрыть паролем** (по выбору): весь конфиг шифруется одним паролем владельца, при вставке спрашивается только он.
  Без закрытия — тоже допустимо. Шифрование — стандартные средства .NET 4.8 (PBKDF2-SHA256 + AES + HMAC или проверенная
  библиотека без зависимостей; причину своего кода указать рядом, §2). Формат с версией.
- **«Сохранить полный конфиг»** после успешной настройки: программа собирает конфиг для восстановления, где пароль root уже
  заменён ключом, который она поставила на сервер. Вставка этого конфига на том же или новом компьютере восстанавливает работу
  без вопросов.
- **«Скопировать конфиг» (для ИИ и для чужих глаз)** всегда без секретов: значения заменены пометкой `"<есть, скрыт>"`.
- **Настройку ведёт ИИ-агент, пароли ему не видны.** Типичный путь: владелец запускает на компьютере агента (Gemini и т. п.),
  тот по `docs/CONFIG.md` расспрашивает, что настроить, и пишет конфиг. Поэтому на диске **два файла, связанных по именам**:
  `config.json` — настройки, агент читает и правит свободно; `secrets` — значения секретов, агент их не читает и не пишет напрямую.
  В конфиге секретное поле — ссылка по имени: `"password": {"secret": "server-root", "hint": "пароль из письма хостинга"}`.
  Стандартные имена и объяснения — в схеме и `docs/CONFIG.md`; нестандартные агент придумывает сам.
- **Команды для агента** (одинаковые в EXE и на сервере, вывод без значений):
  `RemoteAgents.exe secret set <имя> --why "<объяснение для человека>"` — на экране человека окно со скрытым вводом
  (на сервере — скрытый ввод в терминале), агенту возвращается только «сохранено» / «отменено»;
  `secret status` — список имён: есть / нет / на что ссылается конфиг, но не задано;
  `secret import --from env:ИМЯ | bitwarden:<объект>/<поле>` — взять значение из переменной окружения или Bitwarden, не печатая.
  Применение конфига, если секрет не задан, само показывает то же окно с объяснением (`why`/`hint`).
- **Хранение секретов**: на Windows — зашифровано DPAPI текущего пользователя, на сервере — файл 0600. Честно в документации:
  агент под тем же пользователем технически может их расшифровать; защита — от случайного попадания в чат/журналы/контекст,
  плюс правило в `docs/CONFIG.md` «не читать секреты, не просить человека писать пароль в чат».
- **Одна вставка для человека**: «Сохранить полный конфиг» склеивает `config.json` + секреты в один текст (по желанию закрытый
  паролем); при вставке программа сама раскладывает его обратно на два файла.
- Источники: вставка текста; ссылка `https://…` (скачать с лимитом размера, только JSON, тот же маршрут/прокси, что и связь);
  перетаскивание файла; `.rainvite` рядом с EXE / нагрузка в EXE.
- Экспорт: «Скопировать конфиг» (без секретов) и «Сохранить полный конфиг» в настройках; на сервере `remoteagents config export`
  (для ещё одного своего компьютера; с одноразовым пропуском — это `remoteagents invite create`).

## Движок применения (общий для первого запуска и настроек)

- Желаемое (конфиг) сравнивается с текущим (реальная проверка, §3) по разделам → план → выполнение.
- Шаги переиспользуют существующие действия `build/Wizard*.ps1` (Server, Connection, Bridge, Account, Disk, Vpn, Proxy, Lan, Inspect,
  Activate, приглашение). Не переписывать их логику без нужды (§2).
- Сначала доступ к серверу: маршруты пробуются **одновременно**, побеждает первый рабочий. Затем независимые разделы параллельно.
  Общий замок мастера заменить узкими замками по ресурсам (конфиг, сеть, диск), чтобы параллельность была настоящей.
- Время каждого этапа пишется в журнал. Цель: от «Запустить» с готовым конфигом до «связь работает» ≤ 60 с на нормальном канале.
  Опираться на разбор `~/.cache/exe-plan/SPEED.out.md` (что сериализуется и повторяется зря).

## Конфликты

Конфликт — когда конфиг расходится с уже настроенным так, что применение что-то потеряет или переключит: другой сервер,
другой аккаунт Happier, другой корень диска, убранные папки диска. Такие разделы **не применяются сами**:
окно показывает список «сейчас / в конфиге» с выбором «Взять из конфига» / «Оставить как есть» и кнопкой
**«Скопировать для ИИ»** — в буфер готовый запрос: ссылка на `docs/CONFIG.md`, текущий конфиг, вставленный конфиг,
список расхождений (всё без секретов) и просьба вернуть исправленный конфиг. Остальные разделы применяются.

## Границы

- Ничего не делать на Windows-компьютерах владельца и не менять живой сервер (sshd, authorized_keys, службы). Проверки — на стендах.
- Commit в `app/config` можно, push и merge — нет.
- Не трогать живой мост ноутбука. CRLF и PS 5.1 — как в конституции.
- Короткие таймауты на тесты (`timeout 60`, максимум 120 на файл), полный `app/launcher/tests/run.sh` — один раз в конце.
- Строку прогресса писать в `/tmp/agent-config-status.txt` («этап k/n: что делаю»).

## Проверки

- Разбор конфига: схема, мусор, CRLF, лишние/неизвестные поля, секреты в обычном конфиге — отказ с понятной причиной.
- Ссылка: лимит размера, не-JSON, редирект на http — отказ.
- Движок: план по разнице (повторное применение того же конфига ничего не меняет), параллельный запуск независимых разделов
  (тест, что они реально перекрываются по времени), гонка маршрутов (первый рабочий побеждает, остальные отменяются),
  конфликт не применяется без выбора, «Скопировать для ИИ» без секретов.
- Секреты: пустое поле спрашивается с объяснением/подсказкой; закрытый паролем конфиг — неверный пароль/порча/подмена отказ;
  экспорт без секретов не содержит ни одного значения секрета (тест поиском); `secret set/status/import` не печатают значения;
  полный конфиг раскладывается на два файла и склеивается обратно без потерь.
- Название компьютера доходит до реестра моста на стенде.
- Приглашение через новый путь проходит существующие invite-тесты.
- Сквозной тест на стенде (loopback sshd): вставка конфига → связь → итог; замер времени в отчёте.
- Сборка `build/build-exe.sh`, SHA-256 в отчёте.

## Отчёт

Коротко: что сделано, файлы, проверки с цифрами (включая время от «Запустить» до «связь работает» на стенде),
что не проверено на реальной системе, и инструкция приёмки владельцем.
