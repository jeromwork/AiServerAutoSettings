# Журналы RemoteAgents

Цель: когда у человека «не включился VPN» или «пропала связь», по журналам видно, что делали, где, куда, сколько попыток и
на какой ступени сломалось. Журналы ведутся на компьютере и сами доезжают на сервер, в том числе после возвращения сети.

## Где лежат

| Место | Файлы |
|---|---|
| Компьютер, `%LOCALAPPDATA%\RemoteAgents\logs\` | `launcher.log`, `transport.log`, `helper.log` (зеркало журнала помощника), `core.log` (зеркало sing-box), `config-window.log`; архивы `.1…5` |
| Компьютер, `%ProgramData%\RemoteAgents\Helper\` (только SYSTEM и администраторы) | `helper-events.log` (3 архива), `helper.log` (старый формат), `vpn-core.log` (вывод sing-box) |
| Сервер, `~/work/logs-in/<имя>--<компьютер>/` | `<поток>-YYYY-MM-DD.log`, `.cursors.json`; общий журнал приёма `~/work/logs-in/_receiver.log` |

Ротация на компьютере: при 2 МиБ `x.log` → `.1` → … → `.5`, не больше 12 МиБ на поток и 60 МиБ на каталог. Новый файл создаётся
с BOM UTF-8. На сервере хранится 30 суток и не больше 200 МиБ на устройство. Новые каталоги закрыты
правами 0700, файлы — 0600; символические ссылки не открываются. Строки обрезаются до 8 КиБ после
дедупликации по исходным байтам, управляющие символы удаляются.

## Формат строки

Одна строка — одно событие, UTF-8:

```
2026-11-20T09:13:05.123Z 12:13:05.123+03:00 WARN  vpn       on.response    s=7f3a att=on-091305-2c state=on stage=ready ms=1834
```

Поля: UTC с мс и `Z`; местное время с поясом; уровень (`DEBUG INFO WARN ERROR`); компонент; событие (`[a-z0-9.-]+`); `s=` — сессия
процесса (4 hex); `att=` — попытка (`on-ЧЧммсс-xx`, `off-…`); затем `ключ=значение`. Значение в кавычках, если в нём пробел, `"`, `=`,
перевод строки или оно пустое; внутри `\"`, `\\`, `\n`. Строка не длиннее 4096 символов (иначе `…[cut]`). Причина ошибки — `reason=`,
`err=`, `msg=`.

Компоненты: `launcher vpn helper core transport net conflict ship happier config disk update bridge`.

## Главные события

| Событие | Что значит |
|---|---|
| `launcher.start` | запуск: версия, помощник, ОС, пользователь, имя устройства, компьютер |
| `vpn.click.on/off`, `vpn.on.step`, `vpn.on.response`, `vpn.on.ok` | попытка включения/выключения (`att=`), шаги с `ms=` |
| `vpn.inventory phase=before/after` | адаптеры, полные маршруты, DNS, процессы и службы до и после |
| `conflict.detected` / `conflict.suspect` / `conflict.clear` | чужой VPN: имя, интерфейс, маршрут, метрика, причина / только подозрение |
| `core.start`, `core.exit`, `core.restart`, `core.line` | sing-box: pid, код выхода, хвост вывода, перезапуск, строки уровня warn |
| `cmd.recv`, `cmd.done`, `vpn.monitor`, `stage` | команды помощника, смена состояния монитора |
| `net.e2e` | сквозная проверка после включения: итог, ступень, причина, время по ступеням, выходной IP |
| `net.state` | переход сторожа `ok → fail` и обратно (`down_ms=`); `net.heartbeat` — сводка раз в 15 мин |
| `path.check`, `switch`, `network-change`, `restart` | транспорт: проверка пути, переключение с `why=`, смена сети |
| `ship.failed`, `ship.gap` | отказы отправки и потеря файла; `ship.gap` — один раз на разрыв |

## Лестница проверок и коды отказов

Диагноз — первая упавшая ступень.

| # | Ступень | Код |
|---|---|---|
| 1 | есть сеть с шлюзом (не наша, не loopback) | `no-local-net` |
| 2 | нет чужого VPN с полным маршрутом | `conflict` |
| 3 | транспорт (`status/transport.json`) жив | `transport-down` |
| 4 | локальные порты слушают: `ssh`, при `channelFirst` — `channel-ssh` и `channel-socks`, при VPN — `vpn-in`, веб Happier | `port-closed` |
| 5 | баннер `SSH-2.0` на локальном входе (редко: раз в 5 мин, при смене результата ступени 4, при сквозной проверке) | `channel-no-banner` |
| 6 | (VPN) маршрут к 1.1.1.1 идёт через `RemoteAgents-*` | `route-not-ours` |
| 7 | (VPN) DNS `www.gstatic.com` | `dns-fail` |
| 8 | (VPN) HTTP `generate_204` | `http-fail` |
| 9 | (VPN, только сведения) выходной IP | — |

Сторож при включённом VPN: ступени 1–6 раз в 30 с, 7–8 раз в 120 с; при выключенном: 1–4 раз в 60 с. В журнал попадают только переходы.
Фраза «VPN включён, но интернет через него не идёт» показывается в подсказке трея только при отказе ступеней 6–8.

## Чужие VPN

Правило: журналировать и показывать, чужое не отключать, блокировать включение только при явном чужом полном маршруте (0/0, ::/0 или пара /1).
Физический адаптер с обычным шлюзом конфликтом не считается; запущенный, но не работающий клиент (Happ, Tailscale, WireGuard…) — `suspect`.

## Отправка на сервер

Лаунчер раз в 60 с (через 5 с после ошибки или отказа сторожа, при выходе — не дольше 5 с) шлёт новые строки пачками до 512 КиБ
по SSH тем же ключом: сначала через канал (`127.0.0.1:<порт>`), затем напрямую. Курсор (`state\log-ship.json`: отпечаток файла + смещение)
двигается только после ответа `OK`; ротация файла не ломает курсор. Тело сегмента передаётся исходными байтами, включая неверный UTF-8.
Приёмник пропускает повреждённый сегмент с записью `bad-segment` в `_receiver.log`, продвигает его курсор до `to`,
сохраняет остальные сегменты и отвечает `OK`. После неудачи пауза 60 → 120 → 300 с, новые ошибки её не сокращают.
`ship.ok` имеет уровень DEBUG и отфильтровывается при записи: успешная отправка не создаёт себе новые строки.
При выходе общий срок включает чтение журнала помощника и не более двух пачек, до остановки канала. Приёмник — `server/logs_in.py`,
его исходник приезжает в каждой команде (отдельной службы нет). Журнал помощника доходит до пользователя командой `log.read` через pipe
(права каталога ProgramData не меняются); лаунчер зеркалит его в `helper.log`/`core.log`.

## Как читать

```
server/agent-tools/ra-logs list
server/agent-tools/ra-logs show <устройство> [--hours 6] [--comp vpn,net] [--att on-…] [--level WARN] [--grep текст]
server/agent-tools/ra-logs diag <устройство> [--hours 6]      # попытки, переходы, конфликты, переключения, падения ядра, пропуски; «Ступень отказа»
```

## Маскирование

Одни и те же правила в C# (`LogMask.cs`), PowerShell (`Protect-RaLogText`) и Python (`logs_in.mask`), общий файл
`app/launcher/tests/fixtures/logging/mask-cases.json`: значения секретных ключей (`token`, `password`, `accessToken`, `secretKey`,
`psk`, `Authorization`…), `Bearer`/`Basic`, `user:pw@` в URL, приватные и публичные ключи, UUID, длинные base64/hex, известные
значения секретов из конфигурации. Содержимое конфигов в журнал не пишется.
Исправленный поиск полей входит в помощник версии 11 (закреплённый хеш исходников обновлён).
При откате этого релиза выставить `HelperVersion = 12` и обновить `NetHelperSources.json`: установленная версия 11
заменяется только при `version.txt < HelperVersion`, поэтому возврат меньшего номера не переустановит помощник.

## Если журналы не доходят

1. `ra-logs list` — когда был последний приём. 2. На компьютере в `launcher.log`: `ship.failed` (`path`, `err`, `exit`, `stderr`) и
`helper.unreachable` (помощник старой версии не опрашивается). 3. `ship.gap` — файл журнала не найден по отпечатку, часть строк потеряна.
4. Файлы на компьютере остаются целыми до 12 МиБ на поток: ничего не теряется, пока не пройдёт ротация.
