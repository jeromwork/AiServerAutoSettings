## Сделано

- `app/launcher/ConfigBundle.cs`: интерфейс соглашения целиком — Parse/Unlock/Conflicts/Store/Export/ExportForAi;
  строгий JSON с защитой от повторных ключей, мусора, неизвестных полей, неверных типов, CRLF/BOM, неоднозначных
  маршрутов и опасных относительных путей. Ограничения размера, глубины, количества полей, KDF. Подсказки и Missing.
- `config.paste.schema.json`, `config.paste.example.json`: опубликованная схема и пример без доступов. Схема
  скомпилирована в EXE из того же описания, тест проверяет равенство. Пример проверяется тестом.
- `enc1`: точные PBKDF2-SHA256 → AES-256-CBC/PKCS7 + HMAC-SHA256 по контракту; случайные соль/IV; check;
  HMAC проверяется до CBC. Неверный пароль/подмена не меняют исходный ParsedConfig и не пишут на диск.
- `SecretVault.cs`: Windows DPAPI CurrentUser (нативный crypt32, без добавления пакетов); Linux открыто с явным
  `plaintext-linux`, файлы 0600/каталоги 0700. Закрытые права до записи, атомарная замена файлов, общий короткий
  config-mutex, запрет симлинков/reparse points и выхода за home. Секреты отделены от profile.
- Materialize: SSH, root-пароль, pending Happier, proxy-out, маршруты hop/proxy, канал/entries/VPN-hop, LAN OVPN/auth.
  Точная таблица и манифест без значений — `docs/CONFIG.md`. Файлы ключей/OVPN нормализуются в LF; значения vault
  и парольные строки сохраняются без изменения переводов строк. Весь план проверяется до первой записи.
- Конфликты: сервер (включая порт/логин), аккаунт Happier (включая замену значения ключа), корень Disk и снятие выбора.
  Без явного принятия раздел и связанные секреты сохраняются прежними; остальные разделы сохраняются. Первое создание
  profile переносит известные legacy-настройки и SSH/Happier/proxy-секреты; публичный выбор Disk берётся из соседнего
  стандартного RemoteDisk. Это миграция известных полей, не произвольных старых transport-расширений.
- `SecretPrompt.cs`: WinForms со скрытым вводом, многострочная вставка и выбор файла; отмена возвращает null;
  STA-переход. Терминальный скрытый ввод не принимает redirected stdin.
- `SecretCommand.cs`: set/status/import env:/bitwarden:, только статусы/имена, без значений и без чужого stderr;
  native bw/bw.exe, без shell, закрытый stdin, таймаут 15 с, ограничение ответа. Bitwarden уже разблокирован человеком.
- `docs/CONFIG.md`: каждое поле, стандартные секреты, интерфейс/пути, ограничения, правило «не читать секреты и не
  просить пароль в чат», честное описание технической доступности DPAPI/файлов агенту под тем же пользователем.

## Решения в пользу безопасности

- Непустые значения при `protected` принимаются только как enc1; все значения проверяются до выдачи plaintext.
  Итерации 200000–2000000, соль 16–64 байта. Без `protected` значения — буквальный текст, даже с префиксом enc1,
  согласно контракту; это также проверено roundtrip-тестом.
- Существующий действующий SSH-ключ не заменяется непроверенным: другой ключ получает отдельный путь в манифесте.
  Ключ из профиля допускается только внутри `home/secrets` или `home/ssh-profiles`, не в служебный JSON/скрипт/EXE.
  Materialize не переключает публичный transport и не удаляет прежние файлы, необходимые для отката.
- При недостающей ссылке Materialize отказывает до записи; не использует старый файл как незаметную замену.
  Явно очищенный секрет не восстанавливается автоматически из старого файла при экспорте.
- Уровень проектов в конституции не переопределяется: `Project/docs` — выбор содержимого одного проекта, как уже
  реализовано в Disk.Selective.ps1, а не создание вложенного проекта. Первоначально рассматривался полный запрет
  вложенного выбора, но чтение существующей реализации показало, что он сломал бы соглашение и текущий Disk UI.
- Имена секретов с кириллицей разрешены; транспортные имена entries/hops остаются совместимы с Assert-TransportName.
  Unicode LAN-имя материализуется в безопасный hash-basename; системное имя сети согласует движок.
- Старые plaintext-файлы материализации остаются необходимыми адаптерами существующих PowerShell/SSH-компонентов;
  DPAPI защищает vault, а доступ к производным файлам ограничивается ACL/0600. Не выдаём это за изоляцию от того же UID.

## Интеграция с другими потоками

1. **D:** подключить `SecretCommand.Run` до обычного запуска/ограничения single-instance. Для защищённой вставки один
   запрос мастер-пароля → Unlock; недостающие ссылки сверить с `SecretVault.Has` и спросить через SecretPrompt,
   затем добавить полученные значения в ParsedConfig.Secrets или vault. Значения в RequestFile/argv/логи не писать.
2. **D:** перед Store показать Conflicts. `acceptSections` — имена явно принятых конфликтных разделов
   (`server`, `happier`, `disk`), а не строки описаний. Независимые разделы сохраняются автоматически; для пропуска
   другого раздела его нужно убрать из входного patch. Store только сохраняет; **Materialize вызывается отдельно**.
   Подробные настройки/дерево должны менять тот же profile, иначе экспорт не увидит их изменения.
3. **C/D:** потреблять `secrets/materialized.json` по таблице CONFIG.md: serverKeyFile → проверка входа/Request.keyFile,
   channelPath → transport.channelPath, hops/routes → текущие overlay, LAN auth → secretPipe, root → PasswordRelay.
   После проверки нового ключа переключить SSH-профиль. Не подбирать произвольные старые секретные файлы.
   Для авторизованного route-proxy, парольных hop и Unicode LAN-имён нужен этот адаптер; старый invite-код не вызывается.
4. **C/D:** после доказанного bootstrap перенести рабочий ключ в vault/profile, обновить login, убрать rootPassword,
   очистить бывшее значение через SecretVault.Set(home, имя, ""). A не угадывает успех по PID, wizard-флагу или файлу.
5. **B:** использовать опубликованную схему/enc1 и совпадающие имена; серверный CLI secret и выдача ключей — B.
6. **Координатор:** прогнать отдельный запуск ConfigTests=true вместе с общими проверками и собрать итоговый EXE.

## Найденные расхождения с текущими соседними worktree (только чтение)

Проверены текущие `wt-config-d/app/launcher/ConfigApply.cs` и `ConfigWindow.cs`, чужие файлы не менялись.
При слиянии обязательно согласовать следующие места (это не выполненная сквозная интеграция):

- `ConfigRequests.SecretFile` сейчас предполагает `secrets/config/<имя>`. Такого пути нет в исходном соглашении;
  A использует существующие пути PowerShell и манифест, как требует задача. D должен брать `serverKeyFile`,
  `routes[].hop.keyFile`, `lan[].file` из манифеста; особенно важен отдельный путь нового непроверенного SSH-ключа.
- `ConfigSession.Available` проверяет vault, но `Value` сейчас возвращает только значение словаря вставки. При
  повторном открытии настроек имеющиеся root/hop/proxy/LAN-пароли так не попадут в relay. Доступен внутренний
  `SecretVault.Get(home, name)` для чтения самой программой. После Store нельзя передавать в сессию необработанные
  секреты отвергнутых разделов: нужно брать принятый profile и значения vault, иначе отказ от конфликта обходится
  через оставшийся словарь вставки.
- `AskMissing` выбирает ключ **или** пароль; Materialize проверяет все сохранённые ссылки. Неиспользуемые пустые
  ссылки нужно убрать из желаемого состояния либо заполнить до Materialize; для нового Happier создать ключ до
  материализации либо пока не добавлять его ссылку. Отмена не должна приводить к подбору старых файлов.
- `ConfigRequests.IpCheckUrl` сейчас ищет `proxyOut.ipCheckUrl`, тогда как схема A использует `proxyOut.checkUrl`
  (тот же термин, что vpn.checkUrl); нужен перевод в поле запроса PowerShell `ipCheckUrl`. LAN имеет собственный
  `checkUrl`, который также нужно учитывать. Это новые поля вне примера контракта; каноническое описание — CONFIG.md.
- Удаление `rootPassword` после bootstrap нужно делать явным `ConfigProfile.Update` под существующим config-mutex,
  а не отсутствием поля в patch Store: patch намеренно сохраняет неуказанные свойства. Затем очистить старое значение.

## Не проверено / приёмка

DPAPI, Windows ACL, фокус/скрытый ввод/многострочная вставка WinForms, UAC и PS 5.1 требуют **отдельного Windows-стенда**.
Проверка на компьютере владельца не выполнялась. Не проверены настоящий Bitwarden, SSH loopback, связь и восстановление
сервера после revoke: это сквозная приёмка объединённых потоков. Время «Запустить → связь» здесь не измерялось.

Проверить на стенде: secret set/cancel/status/import без значений в захваченном выводе; vault не расшифровывается другим
Windows-пользователем; вставка открытого/защищённого файла → экспорт → восстановление; неверный пароль/подмена не меняют
файлы; неподтверждённый конфликт оставляет прежний доступ; новый SSH-ключ проверяется до переключения профиля.

Атомарность записи — по отдельным файлам, не общая файловая транзакция materialization. Ошибка ввода/схемы/мастер-пароля
не пишет ничего; ошибка диска во время записи производных файлов может оставить часть файлов обновлённой. Движок обязан
сохранить откат работающего подключения и не сообщать готовность до своих живых проверок; повтор материализации допустим.
