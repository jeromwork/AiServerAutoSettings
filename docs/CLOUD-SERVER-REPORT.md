# Серверная синхронизация Диска с облаком

Ветка `app/cloud-server`, база `0a3d3a8`. Реальный `~/Disk` и Облако Mail при разработке не использовались. EXE не собирался. Windows использует официальный клиент провайдера; серверный компонент не зависит от Syncthing.

## Файлы и устройство

- `cloud/server-cloud.sh` — устанавливаемый помощник с `apply`, `status`, `remove` и внутренней командой службы `_run`. Python внутри одного shell-файла нужен только для JSON, проверки конфигурации, очереди событий, состояния и установки. Готовые движки выполняют работу: `rclone bisync`, системный `inotifywait`, systemd, `flock(2)`, `apt-get`, `dpkg`, `curl`. Это также позволяет передавать ровно два файла, без скрытых зависимостей на исходники репозитория.
- `cloud/filter.txt` — шаблон из существующего серверного фильтра. Применяется `--ignore-case`. Пути Laravel `/*/storage/...` изменены на `/storage/...`: теперь каждый bisync работает относительно отдельного проекта. Для фильтра закреплён LF в `.gitattributes`.
- `build/Wizard.Common.ps1` — оба файла добавлены в `Send-WizardHelpers`; используется существующая общая нормализация LF, проверка хешей и атомарная передача. `build/Wizard.Engine.ps1` включает их в список файлов runtime.
- `cloud/tests/test_server_cloud.py`, `cloud/tests/run.sh` — Linux-тесты с временными HOME, локальными папками и WebDAV на loopback.

Состояние, инструменты и настройки находятся в `~/.local/share/remoteagents-cloud/`: `rclone.conf` (0600), `config.json` без пароля, `filter.txt`, `tools/`, отдельные `state/<sha256 имени проекта>/`, `status.json`, `logs/cloud.log`. Журнал ограничен 2 MiB, сохраняются три предыдущих файла. Каталог службы имеет режим 0700. Unit: `~/.config/systemd/user/remoteagents-cloud.service`, `Restart=on-failure`, `RestartSec=5`, `UMask=0077`, остановка всей группы процессов.

`inotifywait` устанавливает рекурсивное наблюдение **до** первого прохода. События передаются с NUL-разделителями и объединяются по проекту; ожидание тишины — 2,5 с. Исключённые деревья не нагружают наблюдение. Событие проекта запускает только его bisync, без обхода соседних проектов. Опрос облака открывает список проектов и последовательно обходит объединение локальных, облачных и ранее известных папок; период по умолчанию 20 с, отсчитывается после завершения опроса. Параллельных проходов нет: единственный worker удерживает `flock` для синхронизации. Отдельный flock каталога `.local/share` сериализует управление и не оставляет файл после удаления.

Потеря наблюдения, переполнение очереди, удаление корня и ошибки утилиты становятся ошибкой службы с последующим перезапуском. Отдельная ошибка проекта отражается в его состоянии; остальные проекты могут продолжать работу.

## Версии и провайдеры

Закреплён официальный **rclone 1.76.0, Linux amd64**. Установка получает [SHA256SUMS релиза](https://downloads.rclone.org/v1.76.0/SHA256SUMS), проверяет закреплённый хеш архива и скачанный ZIP, извлекает только бинарник, проверяет версию. При повторном apply проверяется SHA256 установленного бинарника по квитанции первоначальной установки. Никакой зависимости от `ready-tools-test` нет.

SHA256 архива `rclone-v1.76.0-linux-amd64.zip`:

```text
b00f00b3266c3764413afe599d3ec316f6f43b3e0ea8a0bc1d186d2133e46df7
```

Для inotify сначала проверяется работоспособность найденного `inotifywait`. При доступном root / `sudo -n` / уже настроенном `SUDO_ASKPASS` разрешена установка `apt-get install`. Иначе выполняются `apt-get download inotify-tools libinotifytools0` и `dpkg -x` в собственный `tools/`; предусмотрено имя библиотеки `libinotifytools0t64`. APT проверяет пакеты по индексам репозитория. Локальная библиотека подключается через `LD_LIBRARY_PATH`. При недоступных пакетах или инструментах выдаётся русская ошибка с требуемым действием, без обещания успешной синхронизации.

Таблица `PROVIDERS` отделяет публичный идентификатор из конфига от параметров rclone:

| vendor конфига | type rclone | URL | vendor rclone |
| --- | --- | --- | --- |
| `mailru` | `webdav` | `https://webdav.cloud.mail.ru` | `owncloud` |

URL в таблице является публичным адресом сервиса, пользовательские аккаунты и серверы не зашиты. Следующий WebDAV-провайдер добавляется строкой таблицы. Пароль Mail — именно **пароль для внешних приложений**. Он поступает только из JSON stdin и передаётся в `rclone obscure -` через stdin. В argv, environment, JSON состояния и журнале его нет. Obscure обратим: защиту файла обеспечивают права доступа. Произвольные ответы WebDAV не попадают в журнал; первая ошибка преобразуется в безопасную категорию (например, HTTP 401, тайм-аут, ошибка listings).

## Bisync и удаления

Каждый проект использует собственный workdir и параметры:

```text
--resilient --recover --max-lock 2m
--conflict-resolve newer --conflict-loser num
--compare size,modtime --max-delete 100 --force
--filters-file <filter.txt> --ignore-case --create-empty-src-dirs
```

`--resync` добавляется только до первого успешного прохода проекта. Он объединяет начальные данные, при совпадении имён приоритет у локального Path1. Ошибки действующего bisync не маскируются автоматическим resync, способным воскресить удаления. Фильтр контролируется также встроенным механизмом bisync; его изменение требует отдельной явной повторной инициализации. Повторный apply сохраняет listings. Смена аккаунта, провайдера или корней запрещена без remove/apply, чтобы старые listings не удалили данные другого хранилища. Смена пароля и периода допускается.

**Пустые проекты:** rclone 1.76.0 имеет отдельную защиту полностью пустого listing, которую `--force` не отключает. Поэтому в каждом проекте с обеих сторон создаётся пустая служебная папка **`.remoteagents-cloud-check/`**; она учитывается стандартным `--create-empty-src-dirs`. Даже после удаления всей папки проекта помощник восстанавливает только пустой корень и эту папку, а обычный bisync передаёт удаления пользовательских файлов. Собственного алгоритма удаления нет. Пустой проект остаётся; имя служебной папки зарезервировано. Remove не удаляет её из данных, поскольку по контракту не меняет локальное и облачное содержимое.

Источники: [bisync и его флаги](https://rclone.org/bisync/), [проверка пустого listing в v1.76.0](https://github.com/rclone/rclone/blob/v1.76.0/cmd/bisync/listing.go#L401), [WebDAV owncloud и modtime](https://rclone.org/webdav/), [JSON-статистика rclone](https://rclone.org/docs/#use-json-log). Owncloud имеет точность времени в секунду: одинаковый размер при изменённом mtime обнаруживается; одинаковые размер **и** mtime — нет.

## Контракт

Запускать помощник через `bash ~/.local/share/remoteagents-cloud/server-cloud.sh <команда>`. Нужны Python 3, curl, Linux amd64, доступный user manager systemd. Для постоянной работы после выхода пользователя администратор должен включить linger; apply сам прав администратора не требует.

`apply` получает один JSON-объект на stdin, включая CRLF-вход:

```json
{"vendor":"mailru","login":"user@mail.ru","password":"<пароль приложения>","remoteRoot":"Disk","localRoot":"~/Disk","pollSeconds":20}
```

`remoteRoot`, `localRoot`, `pollSeconds` имеют показанные значения по умолчанию. Успех: exit 0 и JSON `{"ok":true,"serviceActive":true,"state":"starting",...}`. Это подтверждает установку и запуск unit; состояние первой синхронизации следует читать отдельно. Ошибка: ненулевой exit, первая содержательная строка stderr по-русски. Не помещать JSON с настоящим паролем в аргументы команды или историю shell.

`status` возвращает сохранённое состояние и наблюдаемое `serviceActive`. Поля верхнего уровня: `schemaVersion`, `state`, `updatedAt`, `projects`, при общей ошибке `error`. Состояния: `not-configured`, `starting`, `syncing`, `watching`, `error`, `stopped`. В каждой записи проекта: `startedAt`, `finishedAt`, `result` (`running`, `ok`, `error`, `interrupted`), `reason` (`event`/`poll`), `transferred` (число файлов), `bytes`, `deleted` (число файлов), `firstError`. Счётчики берутся из последней накопительной JSON stats записи rclone. Данные предыдущего прохода при неактивном unit остаются историей, а `serviceActive=false` сообщает отсутствие работающей службы.

`remove` останавливает/отключает unit, удаляет его и собственный каталог, выполняет daemon-reload. Повторный remove допустим. Локальные и облачные проекты не меняются. Если пакеты были установлены через APT системно, они не удаляются: ими могут пользоваться другие программы.

## Проверки на Linux

Команды:

```sh
bash cloud/tests/run.sh
python3 -m unittest discover -s server/tests -p test_proxy_out.py -v
bash -n cloud/server-cloud.sh
git diff --check
```

Основной тест использует настоящий скачанный rclone и извлечённый без root inotifywait; подменяется только systemctl. WebDAV защищён тестовыми `--user/--pass`. Его `--dir-cache-time 0s --poll-interval 0s` отключают пятиминутный VFS-кэш, иначе изменения непосредственно в каталоге стенда не видны WebDAV. Тестовый пароль fixture присутствует в argv **тестового сервера**, как задано условием; argv продуктового worker/rclone проверяются отдельно.

Отдельный тест запускает сгенерированный unit через настоящий user systemd с уникальным runtime-именем и временным `HOME/Disk`; после SIGKILL проверяет автоматический перезапуск и передачу следующей правки по событию. Unit и его runtime-ссылка очищаются. Если user systemd отсутствует, этот тест явно пропускается. Unit также проходит `systemd-analyze --user verify`.

Покрытие: первая выгрузка и облачный проект без локальной папки; событие при часовом периоде опроса и отсутствие прохода по другому проекту; опрос облака; same-size/modtime в обе стороны; удаления в обе стороны, всех файлов и целого проекта; `.env`, `.git`, `node_modules`, регистр и Laravel; последовательность проходов и второй worker на том же flock; сохранение listings при apply; сохранность данных после remove; права конфига и отсутствие пароля в продуктовых argv/журнале; CRLF JSON через настоящий shell; недоступный inotifywait, rootless-пакеты, неверный SHA256SUMS, ротация, безопасные ошибки.

## Проверка владельцем на живом облаке и ограничения

1. На отдельном тестовом проекте применить свой аккаунт Mail и пароль приложения; дождаться `projects.<имя>.result=ok`, проверить WebDAV и официальный Windows-клиент.
2. Проверить одинаковый размер с разными mtime, двусторонние удаления, конфликт двух одновременных правок и сохранение проигравшей версии с числовым суффиксом.
3. Проверить смену пароля, временную недоступность Mail, перезагрузку сервера с linger, реальные большие деревья и лимиты inotify/API провайдера.
4. Проверить развёртывание Windows PowerShell 5.1: helper upload использует существующий механизм, фактический запуск из Windows и EXE здесь не выполнялись.

Гарантия ≤10 с проверяется на маленьком loopback-стенде при свободном движке. На живом облаке задержка зависит от текущего последовательного прохода и сети. Период опроса добавляется ко времени самого прохода. Папки верхнего уровня — проекты, отдельные файлы в корне Диска не синхронизируются. Символьные ссылки не обходятся как проекты. Имя служебной папки зарезервировано. Нормальная работа требует свободного места, корректных часов, системных лимитов и совместимой версии inotify-tools с NUL-форматом/`--no-newline`. Нет теста настоящего Mail, официального Windows-клиента, смены аккаунта на рабочем хранилище или аварийного восстановления после повреждения listings; такие случаи не объявляются проверенными.
