# ЛВС с Linux-сервера

Статус: подготовлен код и выполнены проверки без root. Настоящие OpenVPN, nftables,
systemd, split-DNS, перезагрузка, SSH и доступ к ЛВС этим изменением **не проверены**.
На сервер ничего не установлено и не применено. Коммитов и push нет.

После настройки агент использует обычные `ssh user@LAN_IP`, `scp`, `rsync` и средства
деплоя непосредственно на сервере. Windows и MCP-мост для этого не нужны.
Здесь `LAN_IP`, адрес VPN, подсети, DNS-домен и сервис определения внешнего IP
задаёт владелец; значений конкретной установки в коде нет.

## Граница и устройство

`server/lan-vpn.sh` — Bash-точка входа; `server/lan_vpn.py` разбирает OpenVPN,
CIDR, JSON и управляет штатными OpenVPN/iproute2/nftables/systemd. Собственный
парсер нужен, чтобы не исполнить от root команды из импортированного `.ovpn`
и не вывести inline-ключи в диагностике. Python 3 входит в Ubuntu.

Поддерживается до 64 ЛВС с непересекающимися **IPv4-подсетями RFC1918**.
Имена: 1–7 символов `[a-z][a-z0-9]*`, интерфейс `tun-lan-ИМЯ` (лимит Linux 15 байт).
IPv6 ЛВС, публичные подсети, CGNAT и маршруты default/split-default не разрешены.
IPv6 внутри LAN TUN блокируется nft; системный IPv6 вне LAN TUN не меняется.
Это сознательное ограничение первой версии; публичную корпоративную сеть
нельзя сделать разрешённой просто добавлением `--subnet`.

Профиль импортируется по allowlist. Неизвестная директива, `config`, `plugin`,
произвольные hooks, management, `<connection>`, внешние файлы сертификатов,
паролей или ключей приводят к отказу. Нужен самодостаточный inline-профиль
(`<ca>`, `<cert>`, `<key>`, `<tls-auth>`, `<tls-crypt>`, `<tls-crypt-v2>`,
`<auth-user-pass>` по необходимости); интерактивная авторизация не поддержана.
CRLF/BOM нормализуются. Профиль с `route` сохраняет только проверенные частные
подсети; default и два `/1` отбрасываются. Другие публичные route вызывают отказ.
Профиль не должен создавать особые локальные `ifconfig`/скрипты: они отклоняются.

Сгенерированный конфиг содержит `route-noexec`, фильтры redirect-gateway,
redirect-private, dhcp-option, route-ipv6, ifconfig-ipv6, block-ipv6 и доверенный
route-up. Входные `pull-filter` удаляются: ранний `accept` не может обойти фильтры.
Pushed routes читаются из окружения route-up, проходят ту же проверку и объединяются
с `route` из профиля и повторяемыми `--subnet`. Список хранится в
`/etc/remoteagents/lan/ИМЯ/subnets`, настройки со схемой `version: 1` — в
`config.json` (схема — `/etc/remoteagents/lan/config.schema.json`), секретный клиент — в `client.conf`: root:root, файлы 600, каталог 700.
На reconnect разрешён только тот же набор push-подсетей. Для изменения списка
нужны `disable`, затем `enable`; для смены исходного профиля — `remove`, затем `add`.

До создания TUN атомарно загружается своя таблица `inet remoteagents_lan`:

- `output` и `postrouting` разрешают исходящие IP-пакеты только в подсети
  соответствующей ЛВС; остальное через `tun-lan-*` отбрасывается, включая IPv6.
  Проверка в postrouting покрывает изменение маршрута после output.
- `input` принимает только `established,related` из разрешённых подсетей;
  остальное с `tun-lan-*` отбрасывается. Сервер инициирует SSH/деплой, поэтому
  оснований разрешать новые входящие соединения из ЛВС нет.
- `forward` запрещает транзит в обе стороны через LAN TUN. Приложения сервера,
  включая уже настроенный sing-box direct-out для private, используют output.
- Неизвестное имя с префиксом `tun-lan-` тоже закрыто. Этот префикс, таблицы
  маршрутизации 42000–42063 и приоритеты policy rules 1000–1063 зарезервированы
  за скриптом. При конфликтах до включения выполняется отказ.

Существующие таблицы firewall не очищаются. `accept` нашей цепочки не отменяет
`drop` другого firewall. Исчезновение или изменение нашей таблицы (проверяется
содержимое JSON без динамических handles) приводит к остановке всех ЛВС.
Гарантия относится к IP-пакетам через управляемые TUN при действующем kernel guard.
Root, удаливший firewall, может нарушить её до очередного запуска сторожа;
помешать привилегированному администратору удалить защиту этот скрипт не может.
Сторож ограничивает время обнаружения минутой. Прокси-приложение внутри разрешённой
ЛВС требует отдельной политики доступа приложений: nft фильтрует IP назначения.

## Совместимость с sing-box

В живой конфигурации без раскрытия адресов/ключей проверены: версия 1.14.4,
`vless-in`, `tun-in` с `auto_route: true`, `strict_route: false`, `mixed-in`,
`final=proxy-out`, private → direct-out; `route_exclude_address` отсутствует.

Одного private → direct-out недостаточно, чтобы доказать путь к TUN ЛВС.
Для включённых подсетей скрипт добавляет `route_exclude_address` в TUN sing-box,
а также отдельную таблицу маршрутов на каждую ЛВС и destination policy rules
**раньше** правил sing-box. В таблице есть unreachable default: исчезновение
маршрута TUN не вызывает переход к следующей таблице. Приоритет 0 (`local`)
остаётся первым. Нестандартные более ранние policy rules и `auto_redirect`
вызывают отказ. Реальный путь доказывается `ip route get` для подсетей и тестового
хоста: требуются именно `tun-lan-ИМЯ` и назначенная таблица.

Меняется только `route_exclude_address`; исходящие proxy/direct, системный DNS,
final, параметры TUN и входы sing-box сохраняются. Изначальные exclusions
сохраняются и не считаются собственностью скрипта. Перед каждой заменой выводится
точный diff изменённых значений поля (без соседних секретных строк), выполняется
`sing-box check -c КАНДИДАТ`. Далее конфиг атомарно заменяется с исходными
владельцем/группой/правами, sing-box перезапускается и проверяется его активность.
Каждый nft batch сначала проверяется `nft -c -f`, затем применяется атомарно.
CIDR, конфликты policy priorities/table IDs и допустимость маршрутов проверяются
до применения; у iproute2 нет режима проверки всей серии route/rule без применения.
После установки обязательно проверяется фактический результат.

OpenVPN-транспорт идёт через существующую исходящую политику сервера; отдельный
обход proxy-out не добавляется. Если исходящая политика запрещает UDP, UDP-профиль
не заработает: запросите у администратора ЛВС профиль TCP, не меняйте интернет-маршруты.
`route-noexec` не отменяет автоматически создаваемую kernel connected route
самого TUN. Разрешена частная connected-сеть линка; она не попадает в nft allowlist
автоматически. Публичная connected route вызывает остановку. Служебные IPv6
link-local routes могут существовать, но IPv6-пакеты через TUN запрещены.

## Команды владельца по порядку

Все команды ниже выполняет владелец в своей SSH-сессии. Агент их с sudo не запускает.
Сначала выберите HTTPS-сервис, который возвращает **только публичный IP** plain text.
Это сменный сервис, адрес намеренно не зашит в приложение. Его IP не печатается:
сохраняется только SHA-256 исходного ответа. Каждый тест сравнивает системный выход
без явного прокси, SOCKS `127.0.0.1:1080` и исходный хеш; оба адреса обязаны совпасть.
Проверка показывает наблюдаемый путь к выбранному сервису, а не доказывает все
возможные интернет-маршруты; границу назначения пакетов обеспечивает nftables.

В репозитории (без sudo, без изменения сети):

```bash
cd /home/remoteagents/work/wt-lan
bash -n server/lan-vpn.sh server/close-port-leak.sh
python3 -m unittest discover -s server/tests -v
```

Введите свои значения; shell-переменные ниже нужны только для удобства команд.
Не вставляйте секретный профиль или ключи в терминал/чат. `.ovpn` должен уже
лежать вне репозитория. `LAN_SUBNET` опционален, если маршруты приходят в push.

```bash
read -r -p 'Имя ЛВС (1–7 символов): ' LAN_NAME
read -r -p 'Абсолютный путь к inline .ovpn: ' LAN_OVPN
read -r -p 'HTTPS URL определения IP: ' LAN_IP_CHECK_URL
read -r -p 'IPv4 хоста ЛВС для проверки: ' LAN_HOST
read -r -p 'TCP порт проверки (например SSH): ' LAN_PORT
sudo apt-get update
sudo apt-get install -y nftables iproute2 curl iputils-ping python3
sudo bash server/lan-vpn.sh add "$LAN_NAME" "$LAN_OVPN" --ip-check-url "$LAN_IP_CHECK_URL"
```

OpenVPN устанавливается самим `add`, если отсутствует. Для ручной подсети вместо
последней команды: `sudo bash server/lan-vpn.sh add "$LAN_NAME" "$LAN_OVPN"
--subnet "$LAN_SUBNET" --ip-check-url "$LAN_IP_CHECK_URL"` (одной строкой).
`--subnet` можно повторять. Если connect/push не пришёл за 20 секунд, выполняется
откат, профиль остаётся выключенным. Исправьте доступность и используйте `enable`.
Повторный `add` с тем же профилем идемпотентен; подмена профиля под тем же именем
отклоняется. Не выполняйте `add`/`enable`, пока другая транзакция ждёт подтверждения.

После успешного `add`, **в течение пяти минут**:

```bash
sudo bash server/lan-vpn.sh test "$LAN_NAME" "$LAN_HOST" "$LAN_PORT"
sudo bash server/lan-vpn.sh status
sudo systemctl list-timers remoteagents-lan-rollback.timer --no-pager
```

Откройте **новое** SSH-соединение к серверу в другом терминале, выполните `true`.
Старое established-соединение само по себе не подтверждает доступность нового SSH.
Убедитесь, что host/port ЛВС отвечает (команда `test` выше), затем:

```bash
sudo bash server/lan-vpn.sh confirm "$LAN_NAME" --ssh-checked
sudo bash server/lan-vpn.sh list
```

`confirm` требует успешного `test` после начала транзакции, не старше двух минут;
повторно проверяет routes, nft и внешний IP. `--ssh-checked` — явное подтверждение
владельца; скрипт не выдаёт его за автоматически проверенный SSH. Только после
confirm включается постоянный автозапуск клиента.

Для другой ЛВС повторите процедуру с другим именем. Одновременно ожидается
подтверждение только одной сетевой транзакции. Скрипты port-leak и LAN пользуются
общим lock и запрещают изменения поверх неподтверждённого изменения другого скрипта.

## Split-DNS (необязательно)

По умолчанию DNS из VPN полностью игнорируется. Если действительно нужен домен
ЛВС, при `add` дополнительно задайте обе опции `--dns-domain "$LAN_DNS_DOMAIN"`
и `--dns-server "$LAN_DNS_SERVER"`. Требуется работающий systemd-resolved;
DNS-сервер обязан входить в разрешённую подсеть ЛВС. Скрипт назначает сервер
**только интерфейсу ЛВС**, routing domain `~ДОМЕН` и `DefaultRoute=no`. Глобальные
серверы/домен и `/etc/resolv.conf` не меняются. При остановке вызывается
`resolvectl revert tun-lan-ИМЯ`; изменение включено в тот же откат.

После применения дополнительно проверьте `resolvectl status "tun-lan-$LAN_NAME"`,
`resolvectl query "$LAN_FQDN"` и обычное внешнее имя. Проверка FQDN не заменяется
тестом по IP. Если используемое приложение обходит systemd-resolved, split-DNS
этого приложения нужно настроить отдельно; глобальный DNS автоматически не меняется.

## Остановка, откат, удаление

```bash
# Откат текущей неподтверждённой транзакции (не требует имени):
sudo bash server/lan-vpn.sh rollback
# Остановить ЛВС, убрать её policy rules/routes/exclusions и DNS:
sudo bash server/lan-vpn.sh disable "$LAN_NAME"
# Снова включить сохранённый профиль, затем test + новый SSH + confirm:
sudo bash server/lan-vpn.sh enable "$LAN_NAME" --ip-check-url "$LAN_IP_CHECK_URL"
# Удалить также профиль, inline-секреты, subnets и статус этой ЛВС:
sudo bash server/lan-vpn.sh remove "$LAN_NAME"
```

`add`/`enable` **перед первым изменением сети** ставят transient-таймер
`remoteagents-lan-rollback.timer` на пять минут через systemd-run. Снимки исходных
sing-box, своей nft-таблицы, ownership/mode и метаданных лежат только root в
`/var/lib/remoteagents/lan/pending`. Если команда завершилась с ошибкой, откат
выполняется сразу; если терминал/процесс потерян — таймером. Reboot теряет transient
таймер, поэтому отдельный boot recovery до sing-box восстанавливает pending.
Снимки секретного sing-box никогда не выводятся, файлы 600 в каталогах 700.

Откат намеренно останавливает **все управляемые ЛВС**, восстанавливает исходные
sing-box и свою nft-таблицу (либо её отсутствие), а автозапуск ЛВС выключает.
Это безопасное состояние, не восстановление прежних VPN-сессий. Ранее активные
ЛВС включаются и проверяются заново. Чужие nft-таблицы не сохраняются/не меняются.
`disable`/`remove` тоже проверяют кандидаты и ставят таймер; после успешной
локальной проверки удаления он снимается автоматически. Последняя выключенная
ЛВС удаляет общую nft-таблицу и выключает общие guard/watch/recovery units.
Root-owned исполняемые файлы и определения units остаются как установленное ПО;
профилей, маршрутов, DNS и активного firewall для удалённой ЛВС не остаётся.

Сторож `remoteagents-lan-watch.timer` запускается раз в минуту. Проверяет все
таблицы IPv4/IPv6 на default/public через `tun-lan-*`, ожидаемые маршруты,
содержимое своей nft-таблицы и активность клиентов. При нарушении немедленно пытается поставить
deny-only guard и останавливает **все** клиенты, выключает их автозапуск, удаляет свои policy routes,
ставит deny-only guard и пишет ошибку. Автоматического перезапуска после этого нет.
Он не утверждает доступность хостов без `test`.

Статусы: `/var/lib/remoteagents/lan/ИМЯ.json`, поля `ok`, `summary`, `updatedAt`.
`status`/`list` дополнительно проверяют, активен ли сейчас systemd-клиент.
`ok=true` появляется только после test/confirm; сторож сообщает отдельный результат
проверки защиты с `ok=false`, потому что доступность хоста он не проверяет.
Локальный независимый журнал включён всегда:

```bash
sudo tail -n 50 /var/log/remoteagents/lan.log
sudo journalctl -u remoteagents-lan-watch.service --since '-10 min' --no-pager
```

В журнал идут фиксированные события без выводов subprocess/ключей/UUID/адресов
прокси. Сырой OpenVPN stdout/stderr отключён, чтобы сервер VPN не заставил
записать присланные секреты/текст. Причины ошибок обобщены намеренно.

## Отдельно: утечка через port/source_port

`server/close-port-leak.sh` раньше сужал только `port`, оставляя `source_port`
неограниченным. Теперь оба direct-out bypass для 22/3389/37091 ограничиваются
`inbound: ["tun-in"]`. Правила с другими портами разделяются. Дополнительно direct-out исключения
по ip_cidr вне RFC1918/ULA ограничиваются tun-in: иначе более позднее правило
позволяло бы обойти port-ограничение. Значения адресов сохраняются, в diff вместо
них показывается заглушка. Правило ip_is_private и исходящие компоненты не меняются.
Это не аудит всех возможных direct-out предикатов. Проверка с настоящим
VLESS-клиентом обязательна.

Выполняйте отдельно, без pending-транзакции LAN:

```bash
sudo bash server/close-port-leak.sh apply --ip-check-url "$LAN_IP_CHECK_URL"
```

Скрипт показывает изменения только затронутых правил, выполняет sing-box check,
сравнивает выход через системный маршрут и SOCKS, ставит независимый таймер на
пять минут и boot recovery, применяет и проверяет sing-box. В течение пяти минут
откройте новый SSH к серверу; с реального VLESS-клиента подключитесь к своему
контрольному TCP-серверу на каждом из портов 22/3389/37091 и проверьте на принимающей
стороне: peer IP принадлежит внешнему прокси, а не серверу. Потом:

```bash
sudo bash server/close-port-leak.sh confirm --ssh-checked --vless-checked
# Либо немедленно вернуть снимок текущей неподтверждённой транзакции:
sudo bash server/close-port-leak.sh rollback
# Старый синтаксис --rollback тоже поддержан.
```

Подтверждённый снимок не хранится как бессрочная резервная копия. Не применяйте
старый `.bak-portleak` поверх новых сетевых настроек. При неподтверждении или
ошибке восстанавливается именно снимок текущей транзакции с исходными правами.

## Что проверяют тесты

`python3 -m unittest discover -s server/tests -v` работает без root. Фикстура
содержит только **явные синтетические заглушки**, не рабочие ключи. Проверены CRLF,
inline payload без вывода, удаление redirect/DNS/default и раннего accept-filter,
отказ executable/file directives, pushed routes, IPv4 private-only, генерация
nft с раздельными allowlist, отсутствие секретного контекста в diff, идемпотентность
sing-box/port-leak преобразований, права создаваемого файла, отказ при невозможности
поставить таймер и остановка всех клиентов сторожем. Два изменённых фикстурных
конфига проходят **настоящий** `sing-box check` версии 1.14.4 из PATH.
OpenVPN, nft, ip и systemd в тестах реально не запускаются.

Первоисточники: [OpenVPN 2.6 manual](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual/),
[sing-box TUN](https://sing-box.sagernet.org/configuration/inbound/tun/),
[версия 1.14.4](https://raw.githubusercontent.com/SagerNet/sing-box/v1.14.4/docs/configuration/inbound/tun.md),
[nftables manual](https://www.netfilter.org/projects/nftables/manpage.html),
[ip-rule](https://www.man7.org/linux/man-pages/man8/ip-rule.8.html).

Дополнительно оба преобразования проверены `sing-box check` на временных копиях
живого конфига сервера; копии с режимом 600 удалены, исходный файл не менялся.
