# План: VPN и приложение Windows

Статус: выполняется. Дата: 6 ноября 2026.

## Цель

Один `.exe` настраивает сервер по этапам и живёт в трее: VPN, SSH, RDP, синхронизация с показом статуса, MCP-мост, контекстное меню папок. Подключение компьютера к серверу выглядит тем, чем является: HTTPS к своему серверу под своим доменом, без маскировки под чужие сервисы.

## Правила для исполнителя

1. **Сетевая граница.** Не менять исходящую сторону сервера: `tun`, `proxy-out`, `direct-out`, DNS и маршруты к интернету. Менять можно только участок компьютер — сервер. Каждое изменение `/etc/sing-box/config.json` показывать владельцу как diff до применения.
2. **Права.** `sudo` на сервере требует пароль. Исполнитель готовит скрипт и точную команду, запускает её владелец. Обходить это нельзя.
3. **Секреты.** Не выводить и не коммитить ключи, UUID, `shortId`, адреса прокси. Проверять перед каждым коммитом.
4. **Git.** Коммиты в ветку `app/windows`. Push и изменение видимости репозитория только по отдельному согласию владельца.
5. **Windows.** Сеть менять только через этап 2 с автооткатом. `VpnLock` в тестах не запускать. Не редактировать принимающую копию.
6. **Таймауты.** Сервер и интернет: 10–20 с. Windows: 60–120 с. Долгие операции в фоне, с контролем прогресса.
7. **Отчёт.** Разделять проверенное и непроверенное. При `conflict/busy/offline/stale` останавливаться и сообщать причину.

## Порядок работ

Владелец изменил порядок 6 ноября 2026: **первой идёт синхронизация папок**, аналог Dropbox (этапы 3 и 5 в минимальном объёме), затем VPN (этапы 0–2), затем остальное. Правила продукта: [CONSTITUTION.md](CONSTITUTION.md). Все значения в плане, включая `panel.corenetai.ru`, относятся только к нашей установке; продукт спрашивает их в мастере.

## Состояние синхронизации 6 ноября 2026

На сервере 8 привязок. Все серверные Syncthing запущены, состояние `idle`, ошибок получения 0. У всех `connected: false`, а порт туннеля не слушается: ни один Windows не подключён. Модель сейчас односторонняя: сервер `sendonly`, Windows только принимает.

## Установленные факты

- Сервер: sing-box 1.14.4, вход VLESS+REALITY на 443 с чужим именем `dl.google.com`, `tun`, локальный прокси на 1080, выход через SOCKS5 на порту 8017 без логина.
- UDP на сервере блокируется правилом маршрута.
- Настройка sing-box не описана в проекте; `server-happ.sh` ставит другую, не запущенную схему.
- Старые ключи REALITY лежат в публичной истории GitHub (коммит `930deeb`).
- Файлы `/etc/sing-box/config.json*` читаются всеми пользователями сервера.
- Порт 80 не слушается, `sudo` без пароля недоступен.

## Гипотеза для первой проверки

Правило `source_port` отправляет напрямую ответы только портов 22, 3389 и 37091, порта 443 в нём нет. Если ответы VLESS уходят в `tun` и дальше в прокси, клиент не получит рукопожатие. Это могло бы объяснить неработающий VPN. Гипотеза не проверена; проверяется с Windows и через `tcpdump` от владельца, а затем решается, нужно ли правило для ответов порта 443.

## Этапы

### 0. Гигиена и Git

- Ключи: новые REALITY-ключи, UUID и `shortId`; затем импорт новых профилей.
- Права: `root:sing-box`, режим `640` для конфига и его копий.
- Git: ветка `app/windows` от `5099548`; `test-*.json`, `My-server-HAPP.json`, разовые сетевые скрипты в репозиторий не попадают.
- Сканер секретов перед коммитом, `config.schema.json`, `config.example.json`.
- Готово, когда: сканер чист, старый ключ отклоняется, новый принимается.

### 1. Вход на сервер: свой поддомен

- Поддомен пользователя (у нас `panel.corenetai.ru`), запись A в режиме DNS only.
- Сертификат через DNS-01, порт 80 не открываем.
- Настоящий сайт на 443: страница входа личной рабочей среды. Туннель на отдельном пути через WebSocket к sing-box на `127.0.0.1`.
- Применение: `sing-box check`, затем таймер автоотката на 3 минуты, подтверждение снимает таймер.
- Выходная часть конфига побайтно та же; это проверяется сравнением.
- Готово, когда: страница открывается, туннель отвечает, сравнение выходной части без различий.

### 2. Проверка с Windows

Шаг А, без изменения сети: локальный прокси на `127.0.0.1`. Для каждого маршрута: вход, 50 МБ вниз, 50 МБ вверх, 10 минут стабильности.

Маршруты по порядку:
1. Напрямую: поддомен пользователя.
2. Через свой промежуточный сервер: пересылка TCP без расшифровки. Только с разрешения владельца.
3. Сервис туннелей из РФ: только TCP со сквозным TLS и только если нет своего сервера.

Шаг Б, системный VPN: только для прошедшего маршрута, адреса сервера и промежуточного хоста мимо туннеля. Перед включением задача Windows с автоотключением через 5 минут. Сначала один компьютер, второй запасной.

Шаг В, профили трафика: см. раздел ниже. Только если тесты покажут обрывы или замедление.

Готово, когда: выходной IP совпадает с прокси, мост жив, откат проверен.

### 3. Каркас приложения

- C#/.NET, один экземпляр, трей, автозапуск через `HKCU` без прав администратора.
- `%LOCALAPPDATA%\RemoteAgents\config.json` без секретов, со схемой и версией. Секреты отдельно через DPAPI.
- Импорт `profile.json`, `ssh-transport.json`, `project.json`, `runtime.json`.
- Отметка этапа в конфиге не заменяет проверку: перед пропуском выполняется реальный тест.
- Сборка на VPS с `EnableWindowsTargeting`; окна проверяет владелец.
- Готово, когда: приложение видит существующие серверы и проекты, ничего не меняя.

### 4. Обёртка готового

- Скрипты PowerShell остаются, меню заменяются параметрами и JSON-событиями.
- Готово, когда: RDP, SSH и статус VPN работают из трея без консоли.

### 5. Синхронизация как у Яндекс Диска

- Статус и прогресс через API Syncthing, пауза на 30 минут, 2 часа или до включения, список ошибок.
- На паузе показывать, что команды агента не пройдут проверку свежести.
- Готово, когда: пауза, возобновление и ошибка проверены на реальной папке.

### 6. MCP-мост и контекстное меню

- Мост под контролем приложения, перезапуск после сна и обрыва. В трее видно, что управление компьютером включено, и есть выключатель.
- Контекстное меню в `HKCU`, команда передаётся через именованный канал.
- Готово, когда: агент работает без открытых окон, папка подключается правым кликом.

### 7. Мастер нового сервера

- SSH → пользователь → рабочий стол → VPN и прокси → агенты; прерванный шаг можно продолжить.
- Спрашивает поддомен и напоминает добавить IP нового сервера в разрешённые у провайдера прокси, если доступ разрешён по IP.
- Готово, когда: чистый VPS настроен целиком.

### 8. Поставка

- Установщик, обновления, удаление BAT-файлов.
- Готово, когда: новый компьютер настраивается одним `.exe`.

## Профили трафика

Сайт на поддомене пользователя по-настоящему выполняет то, что объясняет трафик:

| Функция сайта | Какой трафик объясняет |
|---|---|
| Файловое хранилище | Большие объёмы в обе стороны: seed и синхронизация |
| Рабочий стол и терминал в браузере | Долгие WebSocket-соединения: RDP и SSH |
| Просмотр видео | Большой поток вниз: просмотр сайтов и загрузки |

Дополнительно по результатам тестов: разделение потоков, ограничение времени жизни соединения, включение через туннель только нужных приложений. Имитация формы трафика под видео не входит в первый выпуск: она добавляет задержки SSH и RDP и не подходит для загрузки данных.
