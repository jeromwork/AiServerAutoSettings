# Локальные сети и VPN

Это две независимые вещи в одной программе RemoteAgents. «Локальные сети»
подключаются автоматически и дают доступ к указанным частным сетям через сервер.
Переключатель «VPN» направляет обычный интернет компьютера через сервер.
Выключение VPN сохраняет локальные сети, Диск, мост и связь с сервером.

## Как идёт трафик

- Локальная сеть: приложение на ПК → `RemoteAgents-LAN` → защищённый канал
  программы → сервер → серверный OpenVPN → нужный хост ЛВС.
- Интернет при включённом VPN: приложение → `RemoteAgents-TUN` → тот же канал
  программы → сервер → настроенный выход сервера в интернет.
- Связь с сервером, мост и Диск идут своим служебным путём. Адреса узлов канала
  исключаются из общего перехвата, чтобы канал не замыкался сам на себя.

Работу обоих адаптеров обеспечивает служба-помощник. Для локальных сетей она
добавляет только разрешённые частные подсети. Прямое обращение к IP работает
из обычных приложений; для внутренних имён нужны `domains` и `dnsServers`.
Локальный DNS этих доменов идёт к DNS ЛВС через канал. Интернет через ЛВС сервера
не разрешается. IPv6 локальных сетей пока не поддерживается.

Канал открывает `lan-in` и `vpn-in` только на `127.0.0.1`, с именем `ra-helper`
и случайным паролем из `<Home>/state/helper-socks.json` (доступ владельцу и SYSTEM).
Настройки портов: `transport.lanProxyPort` (17880) и `transport.vpnInPort` (17881).
Их фактические значения выбираются без пересечений и публикуются как
`status/transport.json.helper.{lanInPort,vpnInPort,udp}`. `lan-in` разрешает только
подсети включённых сетей, затем отклоняет остальные назначения; `vpn-in`
использует выбранный `active`. Обычный SSH/SOCKS-путь не переносит UDP:
локальные сети по TCP доступны, общий VPN требует путь с поддержкой TCP/UDP.

## Конфиг

Версия переносимого конфига остаётся `schema: 1`. Пример публичных настроек ПК:

```json
{
  "kind": "remoteagents-config",
  "schema": 1,
  "lan": [{
    "name": "office",
    "testHost": "10.123.0.10",
    "testPort": 443,
    "share": {
      "subnets": ["10.123.0.0/24"],
      "domains": ["*.office.example.org"],
      "dnsServers": ["10.123.0.53"],
      "hosts": ["portal.office.example.org"],
      "enabled": true
    }
  }],
  "vpn": {"enabled": false, "checkUrl": "https://example.org/", "dnsServer": "1.1.1.1"}
}
```

Это пример: сеть, DNS и HTTPS-адрес проверки выбирает владелец.
Полный конфиг также содержит сервер, все доступные пути канала и ссылки на секреты;
его выдаёт `remoteagents config export`. Формат остальных полей — [CONFIG.md](CONFIG.md).

`lan[]` хранит несколько сетей с уникальными именами. `share.subnets` —
канонические подсети IPv4 RFC1918. `share.domains` — точные имена или `*.домен`
(без самого корневого домена). Для доменов нужен непустой `dnsServers`: до четырёх
IPv4, каждый внутри подсети **этой** сети. `enabled` по умолчанию `true`.
`testHost:testPort` должен входить в разрешённые назначения этой сети;
прежние `host:port` принимаются как алиасы. Без `dnsServers` и доменов остаётся
доступ по IP. Неизвестный DNS программа не угадывает.

`share.hosts` (необязательно, до 100 имён) — явный список полных имён хостов
этой сети для блока hosts (раздел «Имена ЛВС при чужом VPN с защитой DNS»).
Каждое имя — в нижнем регистре, без `*`, под одним из `share.domains`
(`portal.eastclinic.ru` под `eastclinic.ru` или `*.eastclinic.ru`), без повторов;
нужен непустой `dnsServers`. Пустой список в экспорт не попадает. Служба при
получении 6 или 7 ключей сети принимает обе формы, поэтому старый трей и новая
служба во время обновления совместимы. Формат поля описан в схеме конфига
(`config.paste.schema.json`, `lan[].share.hosts`).

Экспорт ПК выдаёт публичные `name/kind/testHost/testPort/share` без серверного
профиля и паролей OpenVPN. Если прежний серверный снимок не имел `share`, экспорт
формирует его из `subnets` и `dnsDomain/dnsServer`. Явный `share` имеет приоритет.
Запись с `kind: "openvpn"` и `ovpn: {"secret": "…"}` означает управление
клиентом **на сервере**; ссылки `auth/password` также относятся к серверу.
Выбор `.ovpn` в мастере загружает его серверу, сетевой клиент на ПК не ставится.
Старое `share.forwards` принимается для совместимости, игнорируется и не экспортируется.

Запись только с `share` (без `ovpn/auth/password`) — доступ с этого ПК к сети, которая уже есть на сервере.
При применении программа спрашивает сервер (`lan-vpn.sh public-status` через мастер `NetStatus`, без root): сеть, поднятая вручную, тоже засчитывается.
Нет сети на сервере → «сеть X не подключена на сервере»; есть, но не работает → «сеть X на сервере не работает: …».
Сервер не ответил → проверка по списку сетей этого ПК с пометкой «состояние сервера не получено».

`vpn.enabled` задаёт сохранённое намерение. При обычном запуске полный VPN сам
не включается: владелец нажимает переключатель. `checkUrl` — HTTPS с доменом без
пароля (параметр совместимости конфигурации, периодическая HTTPS-проба удалена);
`dnsServer` — выбранный IP DNS. `vpn.bootstrap` несёт канал и каталог путей.
Экспорт по умолчанию выдаёт канал со всеми путями и выключенным TUN; `--vpn on`
добавляет намерение включить VPN. Прямой SSH без канала выдаётся только при явном
`--vpn off`. Секреты передаются отдельно, в интерфейс и журналы не печатаются.

## Помощник на Windows

Служба `RemoteAgentsNet` запускается от LocalSystem. Программа предлагает
«Установить помощник»: требуется одно подтверждение UAC при установке.
При изменении версии помощника требуется одно подтверждение обновления.
Отмена UAC оставляет честное «помощник не установлен»; включение VPN не считается
успешным. Повторное включение сетей использует уже установленную службу.

EXE и ядро помощника находятся в `%ProgramFiles%\RemoteAgents\Helper`,
его журнал и рабочие данные — в `%ProgramData%\RemoteAgents\Helper`.
Доступ к именованному каналу ограничен SID владельца, SYSTEM и администраторами;
клиент проверяет, что отвечает действительная служба. Служба запускает только
свои закреплённые ядра, не принимает произвольные команды или пути с ПК.

Закрытие/авария программы, разрыв канала, остановка службы или истечение защитной
аренды сначала закрывают Jobs сетевых процессов, затем убирают свои DNS-правила
и завершают службу. Чужие маршруты и DNS-политики не удаляются. Правила NRPT имеют
наш префикс владения. При удалении программы `RemoteAgents.exe --uninstall`
помощник удаляется с повышением прав; пользовательские файлы Диска сохраняются.

Обновление программы сохраняет намерение ранее включённого VPN. На время
перезапуска соединение прерывается: прежний помощник закрывает свои Jobs,
новая программа подключается к службе и включает VPN заново после проверки
живого канала. Новый успех проверяется по статусу помощника. Передачи управления
прежнему повышенному процессу больше нет.

## Совместимость с другими VPN

| Ситуация на ПК | Локальные сети | Общий VPN RemoteAgents |
|---|---|---|
| Других сетей нет | Автоматически по конфигу | По переключателю при живом TCP/UDP-пути |
| Чужая частная сеть, подсети не пересекаются | Разрешённые подсети подключаются | Известный частичный OpenVPN/WireGuard допускается |
| Подсеть занята физической или чужой сетью | Эта подсеть исключается, показывается имя занятой сети; остальные работают | Чужие маршруты сохраняются |
| Чужой VPN с default или двумя `/1` | Подсети проверяются отдельно | Включение отклоняется: сначала выключить другой общий VPN |
| Неизвестный активный TUN | Проверка пересечений | Консервативный отказ с названием адаптера |
| Частичная сеть со своим DNS/NRPT | Свои правила только для доступных доменов ЛВС | `strict_route=false`, предупреждение о частичной защите DNS |
| Нет помощника | «Помощник не установлен» | Не включается |

При `strict_route=true` используются динамические WFP-фильтры sing-box;
закрытие ядра снимает принадлежащие ему объекты. При сохранении чужого split-DNS
защита DNS частичная: Windows может отправить запросы через другие интерфейсы.
Программа показывает это в карточке и диагностике, не обещает полной защиты DNS.
Фактическую уборку WFP при kill проверяют на настоящей Windows.

Помощник проверяет занятость подсетей каждые 30 секунд. Для локальных сетей
проверка контрольного хоста идёт через правильный TUN, с общим бюджетом 2 секунды
на сеть; проверка повторяется каждые 10 секунд. После сбоя ядра используются
задержки повторов 1, 2, 5, 10, 30 секунд. Проверка контрольного хоста считается
успешной, только если с дальнего конца пришёл ответ: TLS-рукопожатие
(443, 8443, 465, 636, 993, 995, 5986), DNS по TCP (53), HTTP `HEAD` (80, 8080)
или баннер сервера (например, SSH 22). Одного TCP-соединения недостаточно:
его принимает локальный TUN.

Работающий общий VPN не выключается при потере канала, отсутствии UDP, смене
пути, сети или конфигурации канала. Служба читает статус канала каждые 500 мс;
при проблеме сохраняет TUN и процесс sing-box, публикуя `state=searching`,
`enabled=true`, `ok=false` и `reason={code,text,since}` в `status/vpn.json`.
Причина транспорта передаётся с существующей маскировкой секретов. Когда путь
снова готов, состояние возвращается в `on` без выключения и повторного включения.
Периодической HTTPS-пробы и правила «два провала — выключить» больше нет;
автоповтор включения через 10 секунд удалён. Пока идёт поиск, интернет через
VPN может быть недоступен; пользователь может выключить VPN переключателем.
Если сам процесс sing-box завершился, служба показывает поиск и запускает его
снова внутри своего Job (при повторных падениях — не чаще раза в секунду).

После включения раз в 5 секунд запрашивается снимок адаптеров и маршрутов.
Это фоновая задача: медленный PowerShell не задерживает основной цикл, снимки
не перекрываются; после завершения долгого запроса следующая проверка — через
5 секунд. Появился чужой общий VPN — `state=conflict`, `enabled=true` с текстом
«Сейчас работает X. Отключите его…». Служба не останавливает свой VPN и не меняет
чужие процессы, маршруты или DNS. После исчезновения конфликта статус
восстанавливается. Ошибка снимка видна как `searching`, без остановки ядра.
При первом включении конфликт и отсутствие готового UDP-пути по-прежнему
проверяются до создания TUN.

Независимая аварийная защита остаётся: цикл службы или владельца TUN не
продвигается более 2,5 секунды — закрывается принадлежащий ему Job.
Отсутствие подтверждённого здоровья за 4,5 секунды больше не причина закрытия.
Сохраняются явное выключение, остановка службы и `ConnectionExpired`
(30 секунд без клиента). Старый файл статуса помощника сам по себе не доказывает
выключение VPN: чтение сохраняет `enabled` и состояние, ставит `ok=false`,
`statusStale=true` и поясняет, что помощник не отвечает; файл не переписывается.

## Имена ЛВС при чужом VPN с защитой DNS

Happ (и похожие клиенты) ставят фильтры WFP, которые закрывают порт 53 для всех
процессов, кроме самого клиента, на любом адресе, включая loopback. Правило NRPT
`.домен → DNS ЛВС` в таком случае только вредит: каждое обращение к `*.домен`,
в том числе к публичным `www` и корню, ждёт около 7 секунд. NRPT не умеет
нестандартный порт, а системный резолвер Windows 10 не умеет DoH, поэтому
локальный DNS-посредник невозможен. Выбран источник, который Windows читает до DNS
и которого Happ не касается, — файл `hosts`. Его ведёт служба `RemoteAgentsNet`
(LocalSystem), а имена она берёт по пути, который при Happ работает: DNS по TCP
через SOCKS нашего канала (lan-in) к `share.dnsServers`.

- **Список.** Только имена из `share.hosts`; шаблон `*.домен` в hosts невозможен,
  а перечислить зону нельзя (AXFR у клиники запрещён). Новое имя добавляют в
  профиль, программа подхватывает его при следующем применении конфига.
- **Смена сети.** Служба раз в 30 секунд снимает адреса адаптеров; смена
  физической сети (другой адаптер или адрес, кроме нашего TUN) сразу запускает
  обновление блока, иначе оно идёт раз в 10 минут.
- **Разрешение.** Запрос A по TCP через SOCKS 127.0.0.1:порт с логином и паролем
  канала, цепочка CNAME до 8 шагов, 3 секунды на запрос, не больше 4 запросов
  одновременно, DNS-серверы сети по очереди.
- **Фильтр.** В hosts попадают только адреса IPv4 из `share.subnets` этой сети.
  Публичный адрес (например, корень `eastclinic.ru` снаружи) не пишется никогда:
  имя пропускается, в `lan-hosts.log` строка `hosts-skip public`.
- **Когда обновляется.** После готовности канала, каждые 10 минут (±60 с), при
  смене сети или подсетей и при каждом `lan.apply`. DNS не ответил — остаётся
  последнее хорошее значение до 24 часов (`lan-hosts.json` в каталоге данных
  помощника), позже имя убирается. Возраст проверяется при обновлении, а оно идёт
  только при живом канале: если канала нет дольше 24 часов, старые частные адреса
  остаются в hosts до его возвращения (так принято: адреса частные и без канала
  недоступны). Ответ «нет такого имени» убирает имя сразу.
  Краткая потеря канала блок не трогает.
- **Запись.** Свой блок в конце файла между строками
  `# RemoteAgents:lan begin - managed by the program, do not edit` и
  `# RemoteAgents:lan end`; строки блока:
  `192.168.88.167 portal.eastclinic.ru # RemoteAgents:clinic`. Пишется только при
  изменении содержимого: временный файл рядом, `File.Replace` с копией
  `hosts.ra-bak` (ACL сохраняется), первая правка делает `hosts.ra-orig`; кодировка
  и CRLF сохраняются, чужие строки не меняются байт в байт. После записи сбрасывается
  кэш DNS. Файл занят — повтор через 60 секунд, ЛВС не останавливается.
- **Принятие ручных строк.** Строка вне блока, все имена которой входят в наш
  список, а адрес — в подсети сети (например, от `RA-portal-hosts-add.cmd`),
  при записи блока удаляется (`hosts-adopt`, прежняя версия — в `hosts.ra-bak`).
  Если имя в списке, но сейчас не разрешается, ручная строка остаётся. Строка с
  нашим именем и адресом вне подсетей сети или вперемешку с чужими именами не
  трогается (`hosts-conflict`), это имя в блок не пишется.
- **Когда блок снимается.** Остановка ЛВС (`lan.stop`), сеть выключена или список
  имён пуст, удаление службы (`--uninstall`). Остановка самой службы блок не снимает:
  это не дёргает hosts при обновлении программы.
- **NRPT только без блокировки.** Раз в 60 секунд и при смене сети служба
  пробует TCP-соединение с первым `dnsServer`:53 через наш TUN. `10013`
  (AccessDenied) — режим `dns=hosts`: наш NRPT снимается, публичные имена идут
  через DNS другого клиента без задержки. Успех — режим `dns=nrpt`, как раньше,
  NRPT покрывает все поддомены. Неопределённый результат режим не меняет. Блок
  hosts ведётся в обоих режимах. Режим, число имён и время обновления
  входят в статус сети (`dns`, `hostsNames`, `hostsUpdated`).

Файлы журналов: `helper.log` (категории `hosts-updated`, `hosts-adopt`,
`hosts-conflict`, `hosts-skip-public`, `hosts-write-failed`, `hosts-expired`,
`lan-dns-hosts`, `lan-dns-nrpt`) и `lan-hosts.log` (подробности без секретов).

Проверка при включённом Happ: `transport\diag-lan-happ.ps1 -Mode check`
(без прав администратора, ничего не пишет в систему). Проверки A–F: A — TCP 443 с
`--resolve`; B — DNS по TCP через SOCKS; C — прямой запрос к DNS ЛВС (при Happ
ожидаемо не проходит); D — системный резолвер **с** учётом hosts; E — HTTPS по имени;
F — `Resolve-DnsName www.…` быстрее 2 секунд. A и B зелёные, C красная — это Happ,
работают через hosts; A или B красные — неисправна наша сторона. `VERDICT: ok`
означает D и E в порядке.

## Статус → что значит → что делать

| Статус | Что значит | Что делать |
|---|---|---|
| `ok` / работает | Контрольный хост ответил через нужный адаптер на уровне протокола | Пользоваться; доступность остальных сервисов проверять их приложением |
| `busy` | Подсеть уже принадлежит другой сети | Посмотреть имя адаптера; изменить конфиг или отключить конфликтующую сеть |
| `channel-down` | Нет подтверждённой связи с сервером | Проверить канал и выбранный путь |
| `host-down` | Контрольный хост не отвечает или не удалось запустить локальную сеть | Посмотреть `stage`, серверную ЛВС и хост; по одной пробе нельзя различить все причины |
| `no-helper` | Помощник отсутствует | Установить/обновить помощник, подтвердить Windows |
| `starting` / проверяется | Результата ещё нет | Дождаться проверки |
| `off` | Общий VPN выключен | При необходимости нажать «Включить VPN» |
| `searching` | VPN включён, но ищет путь; причина в `reason.text` | Дождаться восстановления канала или выключить VPN вручную |
| `conflict` | Чужой общий VPN или неизвестный TUN; при появлении после включения наш TUN остаётся включён | Отключить указанный VPN; при отказе первого включения нажать «Включить VPN» снова |
| `no-udp` / `no-path` | Первое включение отклонено: нет готового UDP-пути | Выбрать готовый путь канала и включить VPN; при уже работающем TUN эти причины дают `searching` |
| `watchdog-stalled` | Цикл самой службы завис, сработало аварийное закрытие Job | Сохранить диагностику; после восстановления помощника включить VPN вручную |
| `statusStale=true` | Давно не получен новый статус помощника, фактическое выключение не подтверждено | Проверить помощник и диагностику |
| `rollback-error` | Уборка своих сетевых изменений не подтверждена | Сохранить диагностику, выполнить предложенную уборку прежней версии |

Статус локальных сетей приходит от помощника по каждой сети: подключённые и
исключённые подсети, `busyReason`, `dnsServers`, `nrptOk`, `stage`, режим имён `dns`
(`nrpt` или `hosts`), `hostsNames`, `hostsUpdated`. Общий VPN —
`status/vpn.json`, владелец `net-helper`; канал — `status/transport.json`.
Свежесть важна: сохранённое успешное состояние не заменяет новую проверку.

## Сервер: подключение и границы доступа

`server/lan-vpn.sh` вызывает `lan_vpn.py` и штатные OpenVPN, iproute2, nftables,
systemd. Собственный разбор профиля нужен, чтобы команды из импортированного
файла не исполнялись от root. Поддерживаются до 64 непересекающихся IPv4 ЛВС;
имя — 1–7 символов `[a-z][a-z0-9]*`, интерфейс `tun-lan-ИМЯ`.
Публичные/CGNAT-подсети и default/split-default через ЛВС не разрешены.

Профиль самодостаточный, сертификаты/ключи inline. Мастер подставляет соседние
`ca/cert/key/auth-user-pass` в памяти до загрузки. Неизвестные директивы, hooks,
plugins, management и внешние файлы отклоняются. CRLF/BOM нормализуются.
`route-noexec` и pull-фильтры не дают шлюзу поменять общий default и DNS.
Push-подсети проверяются как частные; на reconnect разрешён тот же набор.
Для изменения подсетей нужны `disable`/`enable`, профиля — `remove`/`add`.

Секретные файлы: `/etc/remoteagents/lan/ИМЯ/client.conf`, `config.json`, `subnets`
(root:root, файлы 600, каталог 700). Если CA шлюза не содержит keyUsage/EKU,
администратор отдельно сверяет SHA-256 сертификата шлюза и задаёт
`--server-fingerprint`; мастер показывает только кандидат для сверки.
Подмена автоматическим доверием не допускается.

Своя таблица `inet remoteagents_lan` разрешает output/postrouting только к
подсетям соответствующей ЛВС, input — только ответы established/related,
forward и IPv6 через LAN TUN запрещает. Неизвестный `tun-lan-*` закрыт.
Чужие nft-таблицы не очищаются; их запрет может дополнительно ограничить доступ.
Сторож не защищает от root, намеренно удалившего firewall.

Для каждой сети выделена policy-таблица 42000–42063 с unreachable default и
правилом приоритета 1000–1063, раньше sing-box 9000–9010. Реальный маршрут
проверяется через `ip route get`: нужны правильный интерфейс и таблица.
`auto_redirect` и конфликт более ранних правил вызывают отказ.
Подсети и шлюзы не добавляются в `route_exclude_address` серверного sing-box:
такие исключения способны разрушить default и ответы входящих соединений.
Прежние управляемые исключения убираются при enable/start/reconnect с проверкой
кандидата; чужие сохраняются. Защита ответов сервера описана в [SERVER-APPLY.md](SERVER-APPLY.md).

`add --direct-endpoint` разрешает только OpenVPN-транспорт root к закреплённым
публичным IPv4 шлюза, выбранным протоколу и порту. До старта ставятся nft-правила
и `ip rule` приоритета 2000–2063 с `uidrange 0-0`, proto/dport и lookup main.
Адрес шлюза видит настоящий IP сервера. Это не разрешает интернет через ЛВС.
Если адрес шлюза изменился, требуется повторный импорт профиля.

`lan_share.py` добавляет точные разрешения к известным завершениям канала:
`/etc/sing-box/config.json` и `/usr/local/etc/remoteagents-happ/config.json` (Xray).
Правила sing-box ограничены именованными входами канала, без системного TUN/mixed;
частные назначения идут в выход соответствующей ЛВС, публичные адреса разрешённых доменов —
в прежний `route.final`. У Xray разрешения стоят перед запретом private.
Неизвестная структура отклоняется. Кандидат проходит штатный check/-test;
права и владельцы сохраняются, nft и маршруты эта часть не меняет.

Для каждой ЛВС с `share` в серверный sing-box добавляется свой выход
`lan-ИМЯ-out` (`direct`, `bind_interface: tun-lan-ИМЯ`). Обычный `direct-out`
при `auto_detect_interface` привязан к внешнему интерфейсу и не может пройти
по таблице ЛВС: соединение заканчивается `no route to host`.
Проверка без изменений: `sudo python3 -I /usr/local/lib/remoteagents/server/lan_share.py check ИМЯ ПОДСЕТЬ`.

## Сервер: применение, откаты и сторож

Обычный путь — мастер или `server/server-apply.sh`: plan → apply → **новое SSH**
→ повторный apply с `--confirm-ssh-checked`. Уже открытое established SSH не
доказывает доступность нового соединения. Один запуск подтверждает только
изменение, которое ожидало подтверждения до его начала.

Ручной путь для администратора (значения задаются отдельно, профиль вне Git):

```bash
sudo bash server/lan-vpn.sh add "$LAN_NAME" "$LAN_OVPN" --ip-check-url "$LAN_IP_CHECK_URL"
sudo bash server/lan-vpn.sh test "$LAN_NAME" "$LAN_HOST" "$LAN_PORT"
# После проверки нового SSH, в течение пяти минут:
sudo bash server/lan-vpn.sh confirm "$LAN_NAME" --ssh-checked
sudo bash server/lan-vpn.sh status
```

`add` устанавливает OpenVPN на сервере при отсутствии. Подсеть можно добавить
повторяемым `--subnet`; для логина — `--auth-stdin`/`--ask-auth`.
Без connect/push за 20 секунд — откат. Для split-DNS сервера нужны одновременно
`--dns-domain` и `--dns-server` внутри подсети ЛВС, работающий systemd-resolved:
назначаются DNS только интерфейсу, `~ДОМЕН`, `DefaultRoute=no`; глобальный DNS
не меняется. При выключении выполняется `resolvectl revert`.

```bash
sudo bash server/lan-vpn.sh rollback
sudo bash server/lan-vpn.sh disable "$LAN_NAME"
sudo bash server/lan-vpn.sh enable "$LAN_NAME" --ip-check-url "$LAN_IP_CHECK_URL"
sudo bash server/lan-vpn.sh remove "$LAN_NAME"
```

Перед первым изменением ставится независимый таймер `remoteagents-lan-rollback.timer`
на пять минут. Root-only снимки — `/var/lib/remoteagents/lan/pending`.
Ошибка вызывает немедленный откат; потеря процесса — таймер; reboot — boot recovery
до sing-box. `confirm` требует свежий `test` не старше двух минут и снова проверяет
маршруты, защиту, внешний IP. Другие сетевые изменения поверх pending запрещены.

Откат выключает **все управляемые ЛВС**, восстанавливает свои файлы/защиту и
выключает их автозапуск. Прежние сессии сами не переподключаются.
`disable/remove` тоже используют защитную транзакцию; после локальной проверки
таймер снимается. Последняя удалённая сеть убирает свои routes/DNS/firewall и
выключает общие guard/recovery units; установленный код units остаётся.
`lan_share.py` хранит прежние правила и их владение до нового SSH; ошибка запуска,
пять минут без confirm или reboot до подтверждения возвращают прежние файлы.

Конфиг применения без ключа `lan` (например, только сети «доступ с ПК», которые программа на сервер не передаёт) политику `lanShare` не меняет; снять её можно только конфигом с явным `lan` (в т.ч. `"lan": []`).

### Клиент — обычная служба

`remoteagents-lan@ИМЯ.service`: `Restart=always`, `RestartSec=10`, `StartLimitIntervalSec=0`,
в `client.conf` управляемые строки `persist-tun`, `persist-key`, `keepalive 10 60`,
`resolv-retry infinite`, `connect-retry 5 60` (импортированные такие же строки и `ping*`
вырезаются). Упал или ping-restart — клиент сам поднялся, tun и маршруты таблицы 42000+N
живут, хук при повторном подключении идемпотентен. Ошибка хука пишется в stderr (journald)
и завершает клиента `systemctl kill -s SIGTERM`; поднимет его systemd (не `stop`).
Сторожа и авто-лечения нет (решение владельца 19.11): таймер `remoteagents-lan-watch`
удалён, `install_runtime` при установке сам снимает и удаляет его старые юниты.
Если отвалилась сама клиника, это не наша проблема. Периодический
`remoteagents-reconcile` не применяет и не повторяет транзакцию lan-share (пишет
«lan-share pending ждёт confirm или отката»); применяет её только `apply` владельца,
откатывает только одноразовый таймер. `lan-vpn.sh regen ИМЯ` переписывает управляемые
строки существующего `client.conf` (секреты не выводятся, клиент не перезапускается).
Одноразовые откаты `enable/test/confirm` остаются.

### Статичная защита

Работает без сторожа и переживает рестарт и перезагрузку.

| Защита | Где | Когда действует |
|---|---|---|
| `pull-filter ignore` redirect-gateway/redirect-private/dhcp-option/dns/route-ipv6/ifconfig-ipv6/block-ipv6, `route-noexec` | `/etc/remoteagents/lan/ИМЯ/client.conf` | всегда: клиника не навязывает маршруты и DNS |
| Только наши маршруты: таблица 42000+N (подсети в `tun-lan-ИМЯ` + `unreachable default`), `ip rule pref 1000+N to <подсеть>` | `route_ops` через хук | ставятся при каждом подключении |
| nft `inet remoteagents_lan`: из `tun-lan-*` только established, forward запрещён, в `tun-lan-*` только подсети профиля, к шлюзу клиники только root udp/tcp его порта | `remoteagents-lan-firewall.service` | при загрузке, до клиента |
| `_prestart`: клиент не стартует без nft-таблицы или при её подмене | `ExecStartPre` | каждый запуск |
| Исключение endpoint клиники точным `ip rule pref 2000 /32 uid 0` (не `route_exclude_address` TUN sing-box; причина аварии 15.11) | `endpoint_ops` | всегда |
| inbound-guard: nft `inet remoteagents_inbound` (ct mark 0x5241) + `ip rule pref 8990 fwmark 0x5241 lookup main`; ответы на входящие SSH/443/8444 идут через main | `server_apply.py`, `remoteagents-network-guard.service` | **только при заданном `proxyOut`** |

Интернет через клинику пойти не может: достаточно любой из трёх защит (pull-filter и
route-noexec; правила pref 1000 только для подсетей профиля; nft-egress только в подсети
профиля).

Состояние сети — `/var/lib/remoteagents/lan/ИМЯ.json`, общий публичный снимок —
`/var/lib/remoteagents-status/lan.json`. Журнал событий без секретов —
`/var/log/remoteagents/lan.log`, диагностика OpenVPN root-only —
`/var/log/remoteagents/lan-ИМЯ.openvpn.log`. Публичный статус даёт фиксированную
причину; сырой журнал целиком не публикуется. Сторож выхода, nft-защита ответов
и серверный recovery относятся к [SERVER-APPLY.md](SERVER-APPLY.md).

## Снимок сети и приёмка

`transport/Collect-NetState.ps1` только собирает сведения и сравнивает снимки,
не меняет сеть. В комплекте — маршруты, адаптеры, DNS/NRPT, процессы/службы,
настройки прокси и журналы. Не добавляйте секреты в Label/ProbeUrls.

```powershell
powershell -NoProfile -File transport/Collect-NetState.ps1 -Label до
# Сохраните напечатанный путь первой папки, затем измените состояние:
powershell -NoProfile -File transport/Collect-NetState.ps1 -Label после
powershell -NoProfile -File transport/Collect-NetState.ps1 -Compare 'ПАПКА-ДО','ПАПКА-ПОСЛЕ'
```

Живая приёмка выполняется на Windows 10/11, включая Windows PowerShell 5.1,
и сервере с реальным каналом; Linux-тесты её не заменяют:

1. Установка помощника, отказ UAC и повтор, запуск без повторного UAC, удаление службы.
2. Две ЛВС: доступ по IP и имени, выключенная сеть, недоступный testHost,
   конфликт одной подсети; чужие маршруты и DNS сохраняются.
3. Выключенный общий VPN: локальные сети, мост и Диск работают; включение меняет
   интернет, локальные сети сохраняются. SSH/SOCKS-путь показывает отсутствие UDP.
4. Совместимость по матрице: частичный и полный чужой VPN, собственный split-DNS,
   смена Wi-Fi, сон/возврат, потеря сервера и ядра; статус не остаётся успешным.
   При потере пути/UDP — `on → searching → on`, тот же TUN и PID ядра, без
   выключения и повторного включения. Чужой VPN, запущенный после нашего,
   обнаруживается фоновым снимком: `conflict`, оба процесса остаются живы.
   Падение ядра даёт поиск и перезапуск; зависание самого цикла даёт аварийное закрытие.
5. Выход, kill трея, kill помощника, остановка SCM и зависание сторожа:
   обычный интернет возвращается, наши маршруты/NRPT/WFP убраны. Сравнить снимки.
6. Обновление с выключенным и включённым VPN, неудачная новая сборка и откат;
   восстановление VPN подтверждается новым помощником, без старого процесса.
7. Сервер: add/test/новое SSH/confirm, недоступный шлюз, таймер без confirm,
   reboot во время pending, сбой nft/маршрута, disable/remove; проверить внешний
   IP, запрет публичных назначений через ЛВС и сохранение чужих правил.
8. Прежний конфиг принимается; повторный экспорт содержит только действующие
   настройки. После уборки прежней установки чужие параметры браузера сохраняются.

## Что убрано

Удалены lan-proxy/PAC и TCP-пробросы, старый `--vpn-host`, интеграция Tailscale
(установка, миграция службы и транспортный кандидат) и отдельный RemoteVPN.
OpenVPN устанавливается только на сервере. Остались временные совместимые уборки:
`LegacyPacCleanup` восстанавливает прежний `AutoConfigURL`, только когда есть
`state/lan-pac.json` и текущее значение точно равно записанному нашему loopback URL;
чужое значение сохраняется, учёт затем удаляется. Удаляются старые записи
`Run\RemoteVPN`, а `Vpn.Legacy.ps1`/`LegacyCleanup.cs` убирают наши прежние остатки.
Поле `tailscale` старого конфига принимается, игнорируется и не экспортируется.
