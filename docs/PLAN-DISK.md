# План: аналог Яндекс Диска без сборки

Автор плана: Claude. Исполнитель: Codex `gpt-6.1-sol`, high. Приёмка: Claude проверяет код и результаты сам, затем владелец на Windows. `.exe` только после того, как всё работает.

## Схема

```text
Папка Windows ⇄ Syncthing (127.0.0.1) ⇄ один SSH-туннель ⇄ Syncthing (127.0.0.1) ⇄ ~/Disk/<имя>
```

Старый установщик, снимки, проверка свежести, мост и привязки проектов здесь не используются и не меняются.

## Шаги

| № | Что | Готово, когда |
|---|---|---|
| 1 | Журнал и его отправка на сервер | Первая строка видна на сервере до запуска всего остального |
| 2 | Серверный Syncthing без root | Запуск в изолированном HOME работает, старые Syncthing не затронуты |
| 3 | Syncthing на Windows, SSH из существующего профиля | Подключение и знакомство устройств автоматические |
| 4 | Двусторонние папки, версии, исключения | Обмен с этими настройками проходит на двух настоящих Syncthing |
| 5 | Трей | Значок и меню соответствуют реальному состоянию |
| 6 | Контекстное меню, именованный канал | Папка подключается правым кликом |
| 7 | Проверка владельцем на тестовой папке | Критерии 8–12 из `SPEC-SYNC.md` |
| 8 | Перевод настоящих проектов | По одному, по команде владельца |
| 9 | Упаковка в `.exe` | Только после шагов 7 и 8 |

## Приёмка Claude перед передачей владельцу

1. Прочитать код: никаких адресов и имён в коде, секреты не пишутся в журнал, старые подключения не затронуты.
2. Самостоятельно перезапустить проверки Linux.
3. Проверить коммит сканером секретов.
4. Описать владельцу, что проверено реально и что проверяется только на Windows.

## Ограничения

Без `sudo`, `systemd`, изменений сети, `sing-box`, других проектов и старых подключений. Push делает только Claude после приёмки.

## Уточнение владельца 8 ноября 2026

Папки непосредственно в `~/Disk` автоматически предлагаются всем Windows-устройствам RemoteDisk. Windows принимает их в базу `%USERPROFILE%\Disk\<label>` (как Яндекс Диск; владелец может выбрать другую базу, и тогда папки из прежней базы переезжают с сохранением ID) только в отсутствующий или пустой каталог; занятый путь остаётся pending с записью «папка занята». Ручное подключение сохраняется. Для server discovery разрешён пользовательский systemd timer; прежний запрет systemd в плане этим уточнением заменён. Уже принятые папки перемещаются только отдельной явной командой с сохранением folder ID. См. `disk/README.md`.

## Исчезнувшие серверные папки (16 ноября 2026)

`bootstrap`/`reconcile` и `add-device` снимают регистрацию исчезнувшего проекта через
`DELETE /rest/config/folders/<id>`. Обрабатываются только точные абсолютные пути
`~/Disk/<имя>`: корень Disk, вложенные, внешние, относительные пути и ссылки не затрагиваются.
Файлы на сервере и компьютерах этот механизм не удаляет.

Корень Disk должен быть доступным непустым каталогом. Отсутствие папки наблюдается
не менее 30 с по монотонным часам; timer с интервалом 2 с снимает регистрацию на
первом подходящем запуске после этого порога. Состояние `missing-folders.json`
рядом с `connection-watch.json` записывается атомарно. Недоступный или пустой корень,
смена его устройства/inode, перезагрузка сервера и возвращение папки сбрасывают
соответствующее наблюдение. Перед DELETE повторно проверяются корень, отсутствие
пути и актуальный путь регистрации. Ошибка одной папки не останавливает остальные.

В том же файле сохраняются ID и пути снятых регистраций (`removed`): клиент всё ещё
предлагает сохранённую локальную копию серверу, но `accept_pending` не принимает
такое предложение обратно. Эта память сохраняется и при недоступном Disk. Когда
каталог возвращается на сервер, обычный reconcile снова предлагает его с прежним ID
(для нового местного проекта — имя каталога); отметка снимается только после
успешной регистрации. Поддерживается и возвращение ранее принятой входящей папки
с её собственным ID. В stderr пишется имя папки и факт снятия регистрации без секретов.

На компьютере остаются локальные файлы и локальная регистрация Syncthing. У
`GET /rest/db/completion?folder=<id>&device=<serverID>` поле `remoteState` меняется с
`valid` на `notSharing`, хотя устройство может оставаться подключённым и локальный
`GET /rest/db/status?folder=<id>` показывать `state: idle`, `pullErrors: 0`.
Это означает прекращение обмена этой папкой, а не удаление локальной копии.
`notSharing` бывает и у ещё не принятой сервером новой загрузки: для надписи
«удалена на сервере, локальная копия сохранена» клиенту нужна память о прежнем
подтверждении `remoteState: valid`. Одна ошибка папки не должна объявлять весь Диск
неработающим; клиентская реализация и её тесты ведутся отдельно.

Стенд `disk/test-disk.py` проверяет полный цикл с настоящими Syncthing и реальным
ожиданием 30 с, сохранность клиентской копии, повторное предложение с тем же ID,
защиту от обратного приёма, краткое исчезновение, недоступный/пустой/заменённый
корень, точность путей, независимые таймеры папок и ошибки DELETE (включая потерю
ответа после применённого удаления). Граничные часы остальных сценариев задаются
непосредственно серверной функции; REST и файловые системы остаются настоящими.
