# Конфигурация RemoteAgents, версия 1

Этот документ предназначен владельцу и ИИ-агенту, который готовит настройки. Машиночитаемая схема —
[`config.paste.schema.json`](../app/launcher/config.paste.schema.json), пример без доступов —
[`config.paste.example.json`](../app/launcher/config.paste.example.json). Контракт взаимодействия потоков —
[`CONFIG-CONTRACT.md`](CONFIG-CONTRACT.md).

**Агент не читает `secrets/`, ключи, значения переменных окружения и содержимое Bitwarden. Не просит человека
писать пароль в чат.** Для ввода вызывает `secret set` с понятным объяснением, для переноса — `secret import`.
Статус узнаёт через `secret status`. Для обсуждения использует только экспорт «для ИИ». Не вставляет секреты
в `hint`, название компьютера, адреса, имена секретов, аргументы команд, журналы или сообщения об ошибках.

Доступ передаётся полным конфигом. Получатель файла без мастер-пароля получает доступ сразу; закрытый конфиг
передают отдельно от мастер-пароля. Мастер-пароль не сохраняется. Здесь нет одноразовых приглашений.

## Общие правила

Конфиг — строгий JSON-объект UTF-8, не более 4 МиБ, с `"kind":"remoteagents-config"`, `"schema":1`.
BOM и переводы строк CRLF допустимы. Комментарии, повторные ключи, неизвестные поля, неверные типы и версии
отклоняются. `hint` — необязательная публичная строка-подсказка в структурных объектах; она не выполняется как код.
В словарях `entries`, `hops`, `secrets` ключи имеют специальный смысл, произвольных полей-подсказок там нет.

Отсутствующий раздел оставляет предыдущие настройки. Исключение — мост: без секции `bridge` или её полей действуют `enabled=true` и `allowShell=true`, если для компьютера ранее явно не задано `false`. При первом сохранении существующей установки подхватываются известные настройки сервера, моста, Happier, компонентов,
серверного прокси, а также публичный `RemoteDisk/base.txt` соседней стандартной установки.
Существующие SSH/Happier/proxy-ключи переносит сама программа в vault, агент их не читает.

При сохранении заданные свойства объектов объединяются
с предыдущими, массивы заменяются целиком. Ссылка `{"secret":"имя","hint":"откуда человек берёт секрет"}`
заменяется целиком; значение хранится в `secrets`, не внутри `server`/`happier`/`proxyOut`/маршрутов.
Пустое значение или отсутствие значения означает запрос человеку; уже имеющееся значение vault сохраняется
при вставке публичного конфига. Для явной очистки используют `secret set` с пустым вводом.

Имя секрета: до 64 знаков; первый — строчная латинская буква, цифра или буква Unicode, остальные также могут
содержать `.`, `_`, `-`. Заглавная ASCII-латиница запрещена; кириллица, включая «Офис», допустима. Имена
`protected`, `kdf`, `check`, `hint` зарезервированы. Не помещайте пароль в имя секрета.

Схема в EXE скомпилирована из того же декларативного описания, что опубликованный JSON Schema; тест сравнивает
их. Дополнительные смысловые проверки: имена секретов, соответствие `kind` маршрута, безопасные пути Disk,
метаданные шифрования и формат конвертов. Это позволяет проверять до распаковки бандла без внешнего валидатора.

Кнопка «Открыть Happier» в трее и главном окне сначала проверяет локальный
`/_remoteagents/health` (GET без прокси/редиректов, до 1,5 с, JSON-объект с логическим `ok: true`).
При успехе открывает постоянный локальный origin; при отказе — прежний облачный `webappUrl`.
Проверка выполняется вне UI-потока. Адрес API и `account.WebUrl` остаются облачными.
Без облачного URL левый клик также проверяет включённую локальную страницу; при недоступности открывает окно программы.

## Поля

| Поле | Назначение |
|---|---|
| `deployment.method` | `host` по умолчанию; `docker` распознаётся, но применение пока отклоняется до развёртывания. |
| `deployment.dockerfile`, `.image` | Ссылка на Dockerfile или образ для будущей реализации; [скелет](../server/docker/README.md). |
| `kind` | Всегда `remoteagents-config`. |
| `schema` | Целое `1`. Поле `version` из старого `config.json` не является полем переносимого конфига. |
| `hint` | Публичное пояснение до 2048 знаков. |
| `device.name` | Человеческое имя компьютера, 1–80 знаков без перевода строки; движок передаёт его мосту как `deviceName`. |
| `server.address` | IP или DNS-имя SSH-сервера, без логина, URL, команд и пробелов. |
| `server.port` | SSH-порт 1–65535; при отсутствии применяется 22. |
| `server.login` | Пользователь SSH: до 32 строчных латинских букв, цифр, `_`, `-`; начало — буква или `_`. |
| `server.hostKeys` | До 32 открытых ключей хоста в формате `ssh-ed25519 AAAA…` / другого поддержанного OpenSSH типа, без адреса и переносов строк. Необязательно; проверку доверия выполняет SSH-движок. |
| `server.key` | Ссылка на текст закрытого SSH-ключа. Не путь к файлу. |
| `server.rootPassword` | Ссылка на пароль первоначального входа/администратора; подсказка по умолчанию — пароль из письма хостинга. После успешной установки рабочего ключа восстановительный экспорт должен использовать этот ключ. |
| `server.routes` | До 32 вариантов маршрута; порядок сохраняется, пробует движок. |
| `server.routes[].kind` | `direct`, `proxy` или `hop`. У `proxy` обязателен объект `proxy`, у `hop` — `hop`; чужие для выбранного вида объекты запрещены. |
| `server.routes[].proxy.type` | `socks` или `http`. |
| `server.routes[].proxy.server`, `.port` | Адрес/порт локального или доступного SSH-прокси. |
| `server.routes[].proxy.login`, `.password` | Публичный логин и ссылка на пароль прокси; поддержку аутентификации маршрута обеспечивает транспорт. |
| `server.routes[].proxy.checkUrl` | Необязательный собственный HTTPS URL проверки, без userinfo. |
| `server.routes[].hop.host`, `.port`, `.user` | Адрес, порт (по умолчанию 22), пользователь SSH промежуточного сервера. `host` и `user` обязательны. |
| `server.routes[].hop.hostKey` | Необязательный открытый ключ хоста промежуточного сервера. Проверку доверия выполняет движок. |
| `server.routes[].hop.key`, `.password` | Ссылки на закрытый ключ и/или пароль промежуточного сервера. |
| `connection.enabled` | Желаемое включение связи. Проверенную готовность сообщает движок. |
| `bridge.enabled` | Включить управление компьютером. По умолчанию `true`, в том числе без секции `bridge`; `false` — только по явному решению владельца для конкретного компьютера. |
| `bridge.allowShell` | Разрешить выполнение команд через мост. По умолчанию `true`, в том числе без секции `bridge` или поля (конституция, 6д). В мастере обе галочки включены, отдельно разрешение не спрашивается; `false` — только по явному решению владельца для конкретного компьютера. |
| `happier.mode` | `same` — существующий аккаунт, `new` — новый аккаунт. |
| `happier.account` | Необязательный открытый id аккаунта на сервере (64 hex, из `accounts/server-account.mjs list`) для `same`, когда аккаунтов несколько. Аккаунт обычной установки Happier (`~/.happier`) равноправен с подключённым программой. |
| `happier.label` | Подпись аккаунта, 1–80 знаков. |
| `happier.serverUrl`, `.webappUrl` | Собственные адреса API и веб-интерфейса, только HTTPS без логина/пароля в URL. |
| `serverComponents.happierWeb` | Клиент принимает описанный в [HAPPIER-WEB.md](HAPPIER-WEB.md) блок единого экспорта: `enabled`, `port`, `updateIntervalHours`, `keepReleases`, `keepChats`, `quotas {enabled, claudeProbe, claudeProbeSec}`, необязательный HTTP(S) origin `serverUrl`. Диапазоны совпадают с серверной схемой: интервал 1–168 ч, 2–10 релизов, 1–100 чатов, проба 60–86400 с, порт 1024–65535. Применяет сервер. |
| `happier.localWeb` | Необязательный строгий объект `{enabled: bool, port: 1024–65535, serverPort: 1024–65535}`; все три поля обязательны, `hint` допустим. Без объекта локальная страница выключена; старые конфиги работают как прежде. |
| `happier.localWeb.port` | Постоянный Windows origin `http://127.0.0.1:<port>/` (рекомендуется 47831). Канал резервирует его до остальных портов и никогда автоматически не переносит. |
| `happier.localWeb.serverPort` | Порт службы happier-web на серверном `127.0.0.1`; может отличаться от локального. При занятом локальном порте отключается только вход страницы, диагностика — в статусе/журнале канала. |
| `happier.key` | Ссылка на секретный ключ аккаунта. Для нового аккаунта ключ создаёт слой применения; не придумывать его. |
| `disk.base` | Корень Disk на принимающем компьютере (по умолчанию `%USERPROFILE%\Disk`); на другом компьютере пользователь может выбрать другой. Принятые папки без `path` ложатся в `<корень>\<id>`. |
| `disk.folders` | Папки сервера, которые **принять сразу при установке**: массив `{ "id": "Проект" }` или `{ "id": "Фото", "path": "D:\\Фото" }`, до 256. `id` — имя папки верхнего уровня в `~/Disk` на сервере, одно имя без `/`; `path` — необязательный абсолютный путь на этом компьютере (диск или UNC, без ссылок; не корень Disk и не его родитель; пути не пересекаются). Без поля или с `[]` ничего не принимается. Прежние значения (`"all"`, строки `"Проект"`/`"Проект/docs"`, `{ "path", "direction" }`) читаются, а не отклоняются: направление, `all` и вложенный путь игнорируются с предупреждением в журнале окна. |
| `disk.external` | Устарело: папки вне Disk из конфига не подключаются. Поле читается и игнорируется с предупреждением; папку подключают командой Проводника «Загрузить на сервер» или в Syncthing Tray. |
| `vpn` | Настройки и совместимость — [VPN-LAN.md](VPN-LAN.md). |
| `proxyOut.type`, `.server`, `.port` | Тип (`socks`/`http`), адрес, порт серверного выхода в интернет; обязательны, если раздел задан. |
| `proxyOut.login`, `.password` | Публичный логин и ссылка на пароль серверного прокси. |
| `proxyOut.exitIp` | Ожидаемый внешний IP сервера. Необязателен, по умолчанию `proxyOut.server`; для DNS-имени сервера прокси задайте IP явно. |
| `serverNetwork` | Первоначальное создание системного sing-box: `enabled`, свободный `tunAddress`, `tunName`, `inboundPorts`, ссылка `inbounds` на JSON-массив серверных входов. [Порядок и откат](SERVER-APPLY.md). |
| `proxyOut.ipv6` | `"block"` запрещает исходящий IPv6, сохраняя входящие ответы, loopback и ICMPv6 для соседей/PMTU; `"allow"` явно разрешает прямой IPv6. Если поле не задано, программа и серверный экспорт добавляют `block`. Явный `allow` читается для совместимости. |
| `proxyOut.checkUrl` | Собственный HTTPS URL проверки выхода; подтверждение/откат остаются в сетевом движке. |
| `lan[]` | Настройки и совместимость — [VPN-LAN.md](VPN-LAN.md). |
| `telegramGateway.enabled`, `.port` | Шлюз Telegram от имени `server.login`; сертификат и клиентские ключи создаются установщиком, порт 1–65535. |
| `agent.sudo` | `none`, `apply`, `full`. Экспорт по умолчанию явно выдаёт `full` (NOPASSWD ALL); другой выбор — `--agent-sudo {none,apply,full}`. Без поля сервер применяет прежнее умолчание `apply` (ограниченная root-копия команды), существующие права не удаляются: при их отличии шаг может остаться `agent: blocked`. См. [SERVER-APPLY.md](SERVER-APPLY.md). |
| `components.transport.enabled` | Включение компонента связи. |
| `components.disk.enabled` | Включение компонента RemoteDisk. `false` — не устанавливать Диск, даже если в конфиге есть `server`. |
| `components.control.enabled` | Включение компонента моста. |
| `components.vpn.enabled` | Включение компонента VPN. |
| `secrets.<имя>` | Текст секрета, `enc1:…` при мастер-пароле, либо `""`. Пустые и неиспользуемые именованные записи сохраняются при полном экспорте. |
| `secrets.protected` | Только `master-password`; отсутствие означает открытые значения. |
| `secrets.kdf.name` | Только `pbkdf2-sha256`; используется вместе с `protected`. |
| `secrets.kdf.iterations` | 200000–2000000. Экспорт создаёт 200000 итераций. Верхний предел ограничивает затрату времени на недоверенный ввод. |
| `secrets.kdf.salt` | Base64 случайной соли 16–64 байта; экспорт создаёт 32 байта. |
| `secrets.check` | Зашифрованная строка `remoteagents` для проверки мастер-пароля. |

**Канал первым.** `vpn.enabled=false` вместе с `vpn.bootstrap.channel` (выдаёт `remoteagents config export --vpn channel`):
раздел «Канал до сервера» не включает TUN и не просит UAC, а запускает демон связи (sing-box от имени пользователя); тот сам выбирает
рабочего кандидата — прямой VLESS или через промежуточный сервер из `catalog.relays`. SSH шага «Сервер» и дальше идёт через его
локальный SOCKS-вход `127.0.0.1:<transport.channelSocksPort>` (по умолчанию 2223); в `config.json` ставится `transport.channelFirst=true`.

В `config.json` программы уже есть служебные `schema`, `version`, `transport`, `wizard` и т. п. Их нельзя вставлять
как переносимый конфиг. Переносимое желаемое состояние хранится там в `profile`, без раздела `secrets`.

## Папки — инструкция для ИИ-агента

Диск использует Syncthing. Программа ставит его и Syncthing Tray и знакомит компьютер с сервером всякий раз,
когда в конфиге есть `server` (отключить: `components.disk.enabled: false`). В Проводнике предложения сервера видны как пустые
полупрозрачные папки с облаком. ПКМ «Скачать на компьютер» принимает выбранную папку; её настоящий ID берётся из предложения,
а имя — из label. Направление и дополнительные исключения можно настроить в Syncthing Tray.

`disk.folders` нужен только чтобы принять часть папок сразу. Спроси владельца: **«Какие папки сервера принять сразу? Остальные
вы скачаете через Проводник или Syncthing Tray»**. Имена за него не придумывай; без ответа **не добавляй `disk.folders`**. Без поля или с `[]` ничего не принимается.

```json
{"disk": {"folders": [{"id": "Проект"}, {"id": "Фото", "path": "D:\\Фото"}]}}
```

`id` — имя папки прямо в `~/Disk` на сервере: без `/`, `\`, `..`, точки или пробела в конце, зарезервированных имён Windows; кириллица допустима.
Одинаковые `id`, в том числе отличающиеся регистром, отклоняются. При установке программа ставит Syncthing и Syncthing Tray, добавляет
устройство сервера и принимает перечисленные папки (до ~30 с ждёт предложения сервера; нет предложения — создаёт папку с этим `id`).
Повторное применение принятое не меняет; Syncthing, его `config.xml`, принятые папки и файлы не трогаются. Установка идёт в фоне, окно можно закрыть.

Прежний формат (`"all"`, `["Проект", "Сайт/docs"]`, `{"path": "Фото", "direction": "receive"}`, `disk.external`) читается и не отклоняется:
вложенный путь заменяется папкой верхнего уровня, `all`, направления и `external` игнорируются, предупреждение — в журнале окна. Так же работает
конфиг от `remoteagents config export --folders …`, пока сервер выдаёт прежний формат. Список принятых папок из программы не выгружается:
он живёт в Syncthing, а не в конфиге.

**Файлы никогда не удаляются** — ни установкой, ни повторным применением, ни удалением папки из `disk.folders`.

В меню Проводника у программы три пункта с одним значком — значком программы из трея (зелёный круг). Какой пункт показать,
зависит от самой папки: на заглушке — «Скачать на компьютер», на синхронизируемой папке (в Disk и вне) — «Оставить только на сервере»,
на остальных обычных папках — «Загрузить на сервер». На корне Disk наших пунктов нет. Папка, подключённая только на приём
(receive only), получает и «Загрузить на сервер»: он включает отправку и загружает её локальные изменения. Подпапки синхронизируемой
папки считаются обычными: «Загрузить на сервер» на них отклоняется с пояснением, потому что путь уже входит в подключённую папку.

ПКМ «Загрузить на сервер» подключает любую обычную папку на её текущем месте, включая папки вне Disk. Имя должно быть свободно
на Диске; ссылки, корни дисков и пересекающиеся регистрации Syncthing не принимаются. Наш шаблон исключений подключается через
`#include .stignore-remoteagents`, существующие правила сохраняются. Новая регистрация: `sendreceive`, `fsWatcherDelayS=2`,
`maxConflicts=-1`, staggered versioning. Сервер принимает предложение своим механизмом; локальная программа не меняет сервер по SSH.

ПКМ «Оставить только на сервере» доступна у подключённой папки. Команда требует подтверждённой синхронизации с сервером,
убирает только локальную регистрацию Syncthing и переносит локальную папку в Корзину, затем создаёт пустую заглушку на том же месте.
При отмене или ошибке Корзины регистрация восстанавливается, если исходная папка сохранилась. Для сетевых и съёмных дисков без локальной
Корзины операция отклоняется. Файлы на сервере эта команда не удаляет. Путь внешней заглушки хранится локально в
`%LOCALAPPDATA%\RemoteDisk\explorer-placeholders.json` с привязкой к ID сервера.

Действующее описание сети: [Локальные сети и VPN](VPN-LAN.md).

## Стандартные имена секретов

| Имя | Что вводит человек / импортирует программа |
|---|---|
| `server-key` | Закрытый SSH-ключ доступа этого конфига. |
| `server-root-password` | Первоначальный пароль root из письма хостинга. |
| `hop-key` | Закрытый ключ SSH промежуточного сервера. Для нескольких hop допустимы собственные имена. |
| `hop-password` | Пароль SSH промежуточного сервера. |

## Ввод без раскрытия агенту

```text
RemoteAgents.exe secret set server-root-password --why "Пароль root из письма хостинга"
RemoteAgents.exe secret status
RemoteAgents.exe secret import server-key --from env:RA_SERVER_KEY
RemoteAgents.exe secret import server-key --from bitwarden:идентификатор-объекта/ssh-key
RemoteAgents.exe secret import proxy-out-password --from bitwarden:идентификатор-объекта/password
```

`set` показывает отдельное WinForms-окно со скрытым вводом; многострочный ключ можно вставить или выбрать из файла.
Отмена не меняет значение. В терминальном Linux-варианте ввод скрыт, redirected stdin не принимается. Пустой ввод
сохраняется как «нет». Вывод агенту — только «сохранено»/«отменено» либо общая причина отказа, без значения.
Коды: 0 — успех, 1 — отмена/ошибка источника/хранилища, 2 — неверные аргументы. `status` показывает объединение
имён vault и ссылок в конфиге: `есть`/`нет`, с отметкой `ссылка в конфиге`.

У `import` имя назначения обязательно. Переменную читает сама программа, агент не выполняет `echo`, `printenv`
или аналогичные команды. Bitwarden CLI `bw` (нативный `bw.exe` на Windows) должен быть установлен и уже разблокирован владельцем; программа
запускает `bw get item`, не печатает его stdout/stderr и не выполняет вход/разблокировку за человека. Поддержаны
`password`, `username`, `totp` (содержимое поля seed, не вычисленный код), `notes` и точное имя пользовательского
поля; повторные пользовательские поля с одним именем отклоняются. Таймаут процесса 15 с, размер ответа 4 МиБ.

Команды встроены в EXE: `RemoteAgents.exe secret …` (и `--home <путь>` для другой установки) выполняются до запуска трея, параллельно работающей программе.

## Мастер-пароль и экспорт

`enc1:` — Base64 от `IV[16] || AES-256-CBC(PKCS7, UTF-8(value)) || HMAC-SHA256[32]`.
HMAC покрывает `IV || ciphertext`. PBKDF2-HMAC-SHA256 от мастер-пароля и соли создаёт 64 байта: первые 32 для AES,
следующие 32 для HMAC. Каждый секрет и `check` получают независимый случайный IV. Сначала проверяется HMAC,
затем расшифровывается CBC. Пустые значения остаются пустыми. Другие значения при `protected` обязаны быть `enc1`.
`kdf`/`check` без `protected`, смешение открытых и защищённых значений, повреждение и неверный пароль отклоняются.
Только `secrets.protected` определяет режим: без него даже буквальное значение с префиксом `enc1:` считается открытым текстом. Это проверка содержимого, не сетевой проверенный статус.

`Parse` не пишет на диск. `Unlock` проверяет `check` и **все** непустые секреты, возвращает новый объект;
при ошибке — `InvalidDataException("Неверный мастер-пароль")`, без частичного применения. `Locked`-объект нельзя сохранить.

`Export(home, null)` собирает полный открытый конфиг; с непустым мастер-паролем — защищённый. Включаются значения
vault и пустые записи отсутствующих ссылок. `ExportForAi` заменяет каждое значение секрета на `"<есть, скрыт>"`
или `""`, убирает метаданные мастер-пароля и маскирует известные значения также в публичных строках-подсказках.
Это единственный экспорт, пригодный для чата/буфера агента. При его обратной вставке маркер означает пустое
значение и не перезаписывает уже имеющийся секрет.

## Хранилище и материализация

`secrets/vault.json`: `schema:1`, `protection`, `values` (`имя → строка`), до 256 имён и 4 МиБ файла. На Windows `protection:dpapi-current-user`,
каждое значение защищено Windows DPAPI текущего пользователя, без UI и без machine scope. Файлы/каталоги получают
DACL только текущего пользователя. На Linux `protection:plaintext-linux`: значения открыты, каталоги 0700, файлы 0600.
Файл одного режима не принимается в другом режиме. Перенос выполняют полным экспортом, не копированием vault.

**Агент под тем же пользователем технически способен прочитать Linux-файл и расшифровать DPAPI на Windows.**
Это защита от случайной утечки в чат/логи/контекст и от других пользователей, а не изоляция от кода того же пользователя.
Поэтому правило «не читать секреты и не просить пароль в чат» обязательно даже при DPAPI.

`Store` сохраняет `profile` и vault под тем же коротким mutex, который используют launcher и PowerShell. Отсутствующий
раздел сохраняется; конфликтующие `server`/`happier`/`disk` пропускаются, пока их имена не переданы в `acceptSections`.
Секреты пропущенного раздела тоже не заменяются. `Conflicts` возвращает строки с префиксом раздела и «сейчас / в конфиге»;
не выполняет живых проверок и не объявляет раздел готовым. Проверки выполняет движок.

После сохранения и заполнения недостающих ссылок вызывают `SecretVault.Materialize(home)` отдельно. Метод сначала
проверяет весь план, затем атомарно заменяет каждый файл. Ссылка без значения не даёт файла и пути в манифесте и
перечисляется в `missing`: раздел, которому она нужна, честно не пройдёт с понятной причиной, остальные работают
(серверу нужен ключ **или** пароль root; ключ нового аккаунта Happier создаёт сам шаг). Старый файл вместо пустой ссылки
не используется. Секретные файлы создаются с закрытыми
правами **до** записи текста. Симлинки/Windows reparse points, выход за `home`, коллизии выходных файлов запрещены.
Переводы строк ключей и `.ovpn` приводятся к LF здесь; значения vault и парольные строки сохраняются без изменений.

| Ссылка в profile | Выход относительно `home` | Потребитель / адаптация |
|---|---|---|
| `server.key` | `secrets/server-key`; при совпадении endpoint/логина и отсутствующем или таком же ключе — `keyPath` существующего SSH-профиля внутри `secrets/` или `ssh-profiles/`; для нового ключа действующего профиля — отдельный файл (при необходимости `secrets/server-key-pending`) | `Wizard.Server.ps1` (`Request.keyFile`), SSH-профиль (`keyPath`), `Transport.Common.ps1`, Disk. Генерация/обновление публичного SSH-профиля — C/D. |
| `server.rootPassword` | `secrets/server-root-password` | D читает внутри приложения и передаёт через `PasswordRelay`, не argv/журнал. |
| `happier.key` | `secrets/happier-pending.key` | `Wizard.Common.ps1:Invoke-WizardAccount`; действующий `happier-account.key` заменяет сам шаг с проверкой/откатом. |
| `proxyOut.password` + публичный `login` | `secrets/proxy-out.json`, объект `username`, `password` | `Wizard.Network.ps1:Get-WizardProxySecret`. |

При изменении действующего SSH-ключа прежний файл сохраняется, новый путь берётся из `serverKeyFile` манифеста;
движок проверяет вход и только потом переключает публичный SSH-профиль. Служебный `.json`/скрипт/EXE не может быть целью ключа.

Материализация не меняет работающий transport/config, не запускает сеть и не удаляет прежние файлы: они могут
нуждаться для отката действующего подключения. Движок использует текущий манифест и текущие ссылки, не подбирает
случайно оставшиеся ключи/пароли. Сначала решает конфликты, затем сохраняет/материализует только принятые разделы.
Чистый VPS: после успешного раздела «Сервер», вошедшего по паролю root, окно (`ConfigSession.PromoteServerKey`) берёт ключ,
которым программа теперь входит рабочим пользователем, кладёт его в vault как `server-key`, меняет `profile.server.login`/`key`,
убирает `rootPassword` и очищает значение root-пароля (`SecretVault.Set(home, имя, "")`). Поэтому «Сохранить конфиг в файл»
восстанавливает доступ без пароля хостинга. Успех определяется ответом шага, а не наличием файла.

## Автоматическое серверное развёртывание

`serverNetwork.enabled: true` разрешает первое создание sing-box на чистом VPS.
`proxyOut` задаёт `type: socks|http`, адрес/порт и ссылку на пароль, `exitIp`, HTTPS `checkUrl`,
`ipv6` по умолчанию `block`. `serverNetwork.inbounds` — ссылка на секретный JSON-массив
дополнительных входов sing-box; `inboundPorts` — доступные компьютеру TCP-порты для проверки.
`lan[].testHost/testPort` — предпочтительные имена проверки; `host/port` читаются как алиасы.
`lan[].auth` ссылается на JSON-строку username/password, профиль `ovpn` — отдельный секрет.
EXE передаёт все серверные секреты через in-memory pipe → stdin SSH; enc1 открывается
приложением прежним механизмом. Секреты не попадают в RequestFile, argv или журнал.

[SERVER-APPLY.md](SERVER-APPLY.md) описывает plan/status/apply, новое SSH, автоподтверждение,
ограничения существующего sing-box, sshd и экспорт публичного серверного снимка.


После успешного серверного применения root хранит восстановительный конфиг с нужными
секретами в `/etc/remoteagents/server-apply/recovery.json` (0600, каталог 0700).
Это открытые значения под защитой прав root, не мастер-пароль пользователя.
Первоначальный root-пароль и SSH-ключ клиента туда не копируются. Таймер раз в 30 с
восстанавливает подтверждённую управляемую сеть и выполняет сверку серверных разделов.
Подробные границы: [SERVER-APPLY.md](SERVER-APPLY.md#восстановление-подтверждённой-установки).
Серверные компоненты, агентские авторизации, идентичности и границы описаны в
[SERVER-COMPONENTS.md](SERVER-COMPONENTS.md). Это не снимок произвольной ручной установки или
содержимого папок Disk. Данные проектов восстанавливаются из отдельной резервной копии.

После успешного развёртывания можно собрать конфиг с серверными секретами командой
`remoteagents config export --include-server-secrets --output …` под root; при
`--master-password-stdin` секреты защищаются тем же enc1. Нужны совпадающие публичный
и root-only восстановительный снимки. [Команда и ограничения](SERVER-APPLY.md).
Обычный экспорт без этого флага не читает root-only секреты.

## Автообновление программы

```json
{"update":{"enabled":true,"auto":true,"intervalHours":6,"remoteDir":"~/.local/share/remote-agents/dist"}}
```

Эта секция допустима в переносимом конфиге и в настройках `config export` администратора. При вставке переносимого
конфига она объединяется с локальной секцией update; транспортные `args`, `sshExe`, `viaLocalPort`, `hostKeyAlias`
остаются локальными служебными параметрами, не входят в публичный переносимый формат. При отсутствии `args`
используется активный SSH-профиль; интерактивного пароля и принятия изменившегося host key нет.

Новый EXE проверяет текущий конфиг до установки и принимает прежние схемы через миграции. Сейчас прежний
локальный формат без schema дополняется до schema 1; формат переносимого конфига остаётся schema 1.
Явный неподдерживаемый номер не исправляется догадкой. При отказе рабочая версия и секреты сохраняются;
показывается просьба получить новый конфиг у администратора. Подробный протокол — [LAUNCHER.md](LAUNCHER.md).

У компьютеров старой выдачи `enabled=false` записала сама старая программа, без поля `auto`. Новая программа
считает такую запись прежним умолчанием и включает `enabled=true, auto=true`; явный отказ всегда содержит `auto`.
Старому EXE фоновое обновление не добавить — нужна одна ручная установка новой сборки.
