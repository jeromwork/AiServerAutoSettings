# Чаты на сервере без RDP

В запускном файле выберите сервер, затем **14 — Чаты Codex и Claude в браузере**.
При первой установке выберите Codex, Claude или оба. Программы скачиваются прямо на сервер;
устанавливается стабильный Happier с запуском после перезагрузки. RDP не требуется.
Повторное открытие пункта 14 не устанавливает компоненты заново.

## Первый вход

1. В отдельном окне нажмите **Подключить сервер к аккаунту**.
2. Нажмите **Открыть подтверждение входа**, войдите в Happier в браузере и подтвердите сервер.
   Запрос действует 10 минут; если истёк — нажмите подключение ещё раз.
3. В Happier откройте настройки нужного агента выбранной машины и войдите в Codex/Claude,
   если ещё не входили на сервере. Подписки агентов отдельны от аккаунта Happier.
4. Нажмите **Новый чат**, выберите машину, папку и агента. Для нового проекта можно
   использовать папку `~/work`. Для подключённого проекта выберите серверную папку,
   показанную установщиком при подключении проекта.

Вход в аккаунты подтверждает владелец. Установщик не читает файлы с паролями/токенами,
не сохраняет одноразовую ссылку в журнал и не считает установку успешным входом.

## Несколько устройств и людей

- На своих компьютерах откройте [Happier](https://cloud.happier.dev/) и войдите в один аккаунт.
  Установщик создаёт ярлык **Чаты Codex и Claude** на рабочем столе.
  Скачивать серверные приложения на каждый компьютер не нужно.
- Создавайте отдельные чаты для разных проектов и агентов. В новом чате проверяйте машину и папку.
  Несколько устройств могут работать с общими чатами одного аккаунта.
- Для всех людей используется один порядок: пункт **14**, затем браузер.
  Чтобы работать с общими чатами выбранного сервера, на всех устройствах войдите в один
  аккаунт Happier. Дополнительные имена и профили людей в установщике не нужны.
  Каждый может вести свои проекты и чаты; аккаунты агентов, файлы и лимиты будут общими.
  На другом устройстве достаточно браузера: повторно привязывать сервер не нужно.
- Для исполнения на другом компьютере Happier должен быть установлен и привязан также
  на той машине. Открытая вкладка не делает компьютер исполнителем. Эта установка
  подключает выбранный Linux-сервер. Существующее управление Windows продолжает работать
  отдельно, пока открыты подключение папок и установщик.
- Задачи на сервере продолжаются после закрытия браузера/установщика; сервер должен быть включён.
  Нужны входы в Happier и агента, а также доступные лимиты подписки агента.

## Голос

В Happier включите голос в настройках. Диктовка и голосовой диалог зависят от браузера,
режима и провайдера. Управляемый голос может иметь отдельную оплату/лимиты; установщик
не оформляет подписки и не подставляет API-ключи. Для диктовки текста также подходит
голосовой ввод Windows в поле сообщения.

## Выбор и ограничения

Проверены официальные репозитории, стабильные выпуски и сообщения об ошибках Happier и HAPI.
Выбран Happier: общий интерфейс для машин и агентов, веб-клиент, голос и шифрование.
Используется официальный стабильный установщик с проверкой подписей выпусков.
Уже установленная версия при открытии чатов самовольно не обновляется.
Дополнительные публичные порты управления не открываются: клиент использует HTTPS Happier Cloud,
а фоновые соединения исходящие. Интерфейс отличается от официальных приложений Codex/Claude.
Доставку ответа и восстановление чата после разрыва следует проверять после входа в аккаунты.

## Мост управления Windows

Мост соединяет MCP-инструменты `windows_*` на Linux-сервере с исполнителем PowerShell
на выбранном компьютере. Linux-брокер передаёт запросы через существующий SSH-туннель;
команды выполняются с правами вошедшего пользователя Windows. Мост не связан с одним
чатом: несколько агентов и MCP-сеансов используют один компьютер одновременно.
Выбирайте точные `projectId` и `hostId` из `windows_devices`, а для shell и процессов
передавайте один уникальный `taskId` на всю задачу. Совпадающие `taskId` считаются одной
задачей, поэтому разным агентам с независимыми задачами нужны разные идентификаторы.

Обычные `windows_command` и `windows_process_start` выполняются параллельно.
У `windows_command` ответ остаётся синхронным для вызывающего агента (до 60 секунд),
но ожидание не задерживает запросы других агентов. Для установки, перехода на другую
схему, изменений сети/служб и перезагрузки укажите необязательный `exclusive: true`.
Например, аргументы команды в режиме управления: `{"projectId":"control",
"hostId":"<из windows_devices>","taskId":"maintenance","command":"<разрешённая команда>",
"exclusive":true}`.

Исключительная операция не запускается, пока живы shell-операции других задач;
обычная операция другой задачи не запускается, пока действует исключительная.
Сопутствующие команды той же задачи разрешены. Отказ немедленный, без очереди:
агент получает причину, может согласовать завершение задачи и явно повторить запрос.
Это исключает скрытое многоминутное ожидание и не требует политики очереди.
Ответ содержит только метаданные, например
`Target environment busy: taskId=maintenance operation=process_start started=2026-11-10T12:00:00.0000000Z`.
Команда и её аргументы в сообщение замка не попадают. Статус, чтение/список файлов
и файловые инструменты не участвуют в shell-замке и остаются доступны для диагностики;
эксклюзивность не заменяет согласование одновременной записи в один файл.

Лимиты координируются атомарно через mutex и `%LOCALAPPDATA%\RemoteAgents\environment\operations.json`
для всех исполнителей одного пользователя: 8 живых команд/процессов на `taskId`,
64 суммарно. Запуск тоже резервирует слот, включая проверку синхронизации.
Завершившийся `process_start` автоматически освобождает слот и замок.
Для `windows_process_poll` остаётся до 32768 символов вывода на процесс, не более
64 завершённых результатов на исполнителя; старые вытесняются. Результат хранится
до первого чтения владельцем или 300 секунд после обнаружения завершения.
Повторный poll после этого возвращает «неизвестный процесс / вывод прочитан или истёк».
`poll` и `stop` с чужим `taskId` отклоняются и не потребляют результат, даже если
исполнитель запущен в старом режиме без обязательной привязки цели.
Запись операции с мёртвым PID или с PID, переиспользованным другим процессом,
не держит замок и не занимает слот.

### Совместимость и доставка обновления

Формат запросов и `operations.json` (schema 1) сохранён. Новый исполнитель принимает
старые запросы без `exclusive` как обычные. Старый MCP работает с новым исполнителем;
чтобы запросить исключительность, нужен новый MCP. Новый MCP с прежним исполнителем
продолжает обычные вызовы; `exclusive: true` явно отклоняется **до запуска команды**,
если статус не подтвердил `coordination.exclusive: true`. Старый исполнитель не знает
новых правил и сохраняет прежнюю сериализацию/лимиты. В смешанной группе исполнителей
записи без поля `exclusive` считаются исключительными; полная параллельность требует
обновления всех исполнителей этого пользователя. Heartbeat нового брокера идёт параллельно у нового исполнителя; у старого во время
активного запроса он откладывается, чтобы долгая команда не дала ложное отключение.
В старом режиме без `taskId` запросы
одного исполнителя получают общий legacy-идентификатор: для изоляции нужен явный `taskId`.

Обновление файлов на сервере само по себе не заменяет работающий Windows-процесс.
На каждом компьютере установите актуальный комплект штатным способом:
`05-control.cmd` (обёртка вызывает `Start-WindowsControl.ps1 -Install`) либо штатный
переход/установку через приложение. Установка копирует зависимости моста в локальную
`control/app`; управляемая установка с `-LauncherHome` создаёт каталог версии по хешам.
Она перезапускает мост, поэтому сначала завершите нужные фоновые процессы.
При старте этап `prepare server` передаёт из **этого установленного комплекта**
`codex-windows-bridge.py`, `codex-bridge-session.py` и каталог узлов на сервер, атомарно
обновляет файлы и регистрирует MCP. Это отправка с компьютера на сервер, а не скачивание
свежего Windows-исполнителя с сервера. Старый комплект на другом компьютере при подготовке
может снова заменить общие серверные файлы прежними: обновляйте все компьютеры.
Перезапустите MCP-сеансы агентов, чтобы они загрузили новую схему и код.
В `windows_status` после обновления должны быть `coordination.exclusive=true`,
`per_task_limit=8`, `global_limit=64`, `completed_ttl_seconds=300`.

### Локальная проверка параллельности

`python3 -m unittest -v test-windows-bridge-concurrency test-windows-bridge test-windows-control test-node-execution test-multi-node < /dev/null`
запускает изолированные стенды. На Linux нужен `~/.cache/pwsh-test/pwsh`;
PowerShell запускается с `-NonInteractive`, временными HOME/LOCALAPPDATA и CRLF-входом.
Новый стенд запускает настоящие дочерние pwsh, TCP-исполнитель, Unix-брокер и MCP stdio.
Windows-идентичность и системная метка рождения процесса заменены Linux-эквивалентами
только во временной копии тестового исполнителя. Проверки PS 5.1, Windows mutex,
реального `taskkill /T`, установки/автозапуска и SSH-туннеля требуют отдельного живого
прогона на Windows. Прохождение Linux-стенда их не подтверждает.
